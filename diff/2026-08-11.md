# Legado Python 引擎反馈差异复核

日期：2026-08-11  
反馈书源：`🌸爱丽丝书屋(免翻)`  
基准：Legado `3.23.110211`

## 复现结果

- 实时搜索“美母为妻”返回 10 本。
- 首本详情成功，目录返回 120 章，首章正文返回 3,548 字。
- 发现页“总排行”和“月排行”均返回 0 本。
- 同一排行页面实际包含 50 组 `div.rec_rullist > ul` 书目；当前书源规则只识别 `li:has(span.s2 > a)`，因此列表规则没有命中。

## 实现差异结论

本次没有发现 Python 规则解释器与固定 Legado 在该书源调用路径上的语义差异。故障来自项目内书源数据的回归：2026-08-07 为当时观察到的紧凑排行页面，把发现规则从旧版 `div.rec_rullist / li.two` 完全替换成 `span.s2`；网站随后再次返回旧版排行布局，而不是固定使用单一结构。实际 App 能加载，说明其当前导入规则或缓存规则仍能识别旧布局。

需要修复的项目差异是“保存的书源配置与 App 可用配置/实时页面不一致”，不是引擎擅自回退。按照 Legado 严格执行书源规则的原则，引擎不应在规则无匹配时猜测书卡。

## 修复

- `resource/bookSource.json` 与 `resource/bookSource_passed.json` 的发现规则改为显式兼容两套已观察布局。
- 列表规则：`div.rec_rullist > ul, li:has(span.s2 > a)`。
- 书名、地址、分类分别使用固定规则的 `||` fallback；旧版额外读取作者和最新章节。
- 增加两套 HTML 的离线回归，禁止再次用一种实时布局覆盖另一种布局。

## 验收项

- 实时总排行应恢复非零书目。
- 搜索、详情、120 章目录和正文链路保持通过。
- 1,066 个书源静态审计与全量测试不得回退。

## 规则引擎重新审计（第二轮）

原“差异清零”结论不能成立，本轮已确认并处理以下遗漏：

- `BookSource` 字段虽已声明，但 Python 原实现错误地使用全字段对象相等；Legado 仅以 `bookSourceUrl` 判断实体相等。
- 配置导出曾丢弃 `false`、`0`、空字符串和空规则对象，导致禁用状态等配置无法无损往返。
- 缺少规则对象惰性创建、配置级 `equal`、分组增删与显示辅助语义。
- 缺少历史 `ImportOldData.fromOldBookSource` 整条迁移路径；旧版 URL、规则分隔符、音频类型、UA、搜索/发现/正文规则现在由 Python 迁移。

上述项目已有固定历史源码对应测试。编码检测、规则解析长尾、Rhino/Java/Android 兼容层仍处于重新审计中，在这些项目完成前差异状态保持“未清零”。

### BaseSource 与可空实体语义

- 原 JS 桥缺少 `getTag`、`put/get`、`getLoginJs`、`loginUi()`、`login`、`evalJS` 和 `getShareScope` 的可观察入口。
- `setVariable(null)`、登录信息删除及返回值与固定源码不一致；现已按删除、`Unit/null` 和布尔返回分别处理。

- `getHeaderMap(hasLoginHeader)` 现支持动态 JS header、默认 UA、大小写不敏感 UA 检查及可选登录头覆盖。当前 1,066 个书源中有 40 个动态 header，原实现会将其全部静默丢弃。
- BookSource 的 Kotlin 可空字符串及六个规则对象恢复为 `null`；Gson 风格导出排除 null，同时保留 false、0 与显式空值。

上述差异已补回归。其他兼容层仍继续重新审计，状态未清零。

### 编码、持久状态与 JavaScript 请求复核

- 固定版 `utf8ToGbk` 与显式 GBK 请求使用 Java 的 GBK，而非 Python 先前扩大接受范围的 GB18030；补充字符现在与 Java 一样替换为 `?`。
- JavaScript 请求响应编码只遵循 HTTP 响应声明及固定编码检测，不再错误地用 URL 请求选项中的 `charset` 覆盖响应解码。
- 文件与压缩包的无声明文本改走固定 `EncodingDetect` 路径；普通文件保留历史实现的 8,000 字节补零采样行为。
- 登录信息按固定版设备 ID 派生密钥加密落盘；非法密文与旧明文均按固定异常路径返回 `null`，不再增加 Python 专属明文回退。
- 原 JavaScript 网络桥无论 `enabledCookieJar` 为何都使用共享 Cookie opener。现按固定 `== true` 语义处理：仅显式 true 启用，false/null 均不发送、接收或持久化 Cookie；字段缺省仍采用 `BookSource` 构造默认 true。

### 第十轮 StrResponse、Jsoup 响应与 WebView 交接复核

- 原桥把 StrResponse 和 Jsoup Connection.Response 合成同一个宽松对象，导致 `String(StrResponse)` 错误返回正文、伪造 `header/bodyAsBytes/status` 等不存在的方法，并把非成功响应正文伪装成 `errorBody`。现已按固定类型拆分公开表面；StrResponse 的 `toString/message/headers/isSuccessful/errorBody/raw/url` 恢复历史语义。

### 第十一轮 BackstageWebView 请求头与 Cookie 回写复核

- 固定 BackstageWebView 在每次页面完成时读取最终页面的 Android Cookie，但调用 `CookieStore.setCookie(tag, cookie)`，其中 tag 是 `source.getKey()`；它不是按重定向后的最终域保存，也不是与旧 Cookie 合并。Python 原先按 final URL 合并，跨域验证后会把 Cookie 留在错误域并残留旧键。
- 桌面浏览器回写现先清空 source key 对应的 CookieStore/请求 Cookie，再用浏览器完整 Cookie 字符串替换；空字符串同样清空。即使最终页面跳到另一域，后续书源请求仍从 source key 域取得验证 Cookie。
- JavaScript `webView/webViewGetSource/webViewGetOverrideUrl` 现向浏览器传递调用时求值的 `source.getHeaderMap(true)`，包括动态 header、默认 UA 和登录 header。此前直接 WebView 桥完全没有传请求头。
- JavaScript AnalyzeUrl 的 WebView 分支也携带 source key 作为 Cookie 回写 tag；浏览器返回的 Cookie 与普通阅读入口现在使用同一替换规则。
- 已增加跨域最终 URL、旧 Cookie 替换、空 Cookie 清除、动态/登录请求头与直接 WebView 回写回归；全项目门禁保持 `408 passed, 28 subtests passed`。仍需继续核对浏览器异常/超时及非 2xx 响应细节，状态未清零。

### 第十二轮 HTTP 状态重试与 Session Cookie 生命周期复核

- 固定 OkHttp 对非 2xx 响应按 `0..retry` 重试并最终返回最后一个 Response；网络 IOException 不进入该状态重试循环。Python 主请求与 JavaScript 请求保持这一边界，非 2xx 正文、状态、reason、协议和重复响应头均进入 StrResponse，而不是 `raiseForStatus`。
- 原实现把 urllib/aiohttp 收到的全部 Cookie 持久化，并保留原 Path/Secure；这与固定 CookieManager 将无 Expires/Max-Age 的 Cookie 只放内存 session map、持久 Cookie 放数据库、二者再按 session 优先合并不一致。
- 响应 Cookie 现先按注册域压平名称和值，再区分 session/persistent。Session Cookie 不落盘；若与持久 Cookie 同名，只在本次运行覆盖，重启后底层持久值恢复。持久状态保留 Kotlin MutableMap 的既有键顺序。
- 主阅读响应现同样保存 `headersMulti/message/protocol/responseKind`，让 loginCheckJs 得到与 JavaScript AnalyzeUrl 相同的 StrResponse 元数据。
