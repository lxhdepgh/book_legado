# 2026-08-07 开发日志：Legado 书源引擎兼容性复核

## 运行性能优化

- 书源反序列化直接复用 dataclass 字段映射，避免为每条书源重复创建字段集合。
- 管理页为 URL 与搜索文本增加有界 LRU 缓存，并对搜索输入增加 180ms 防抖。
- 搜索、状态过滤不再重复重建分组下拉选项；只有刷新或批量数据变更时更新。
- QuickJS 脚本清理、JS 规则拆分、XPath 路径和步骤解析增加有界缓存。
- 保留此前完成的检测优化：搜索与分类请求重叠执行、分类规则引擎延迟创建、失败回退复用已下载页面。
- 微基准（当前 1066 条书源）：反序列化约提升 3.97 倍，重复搜索约提升 2.77 倍，重复 JS 规则规范化约提升 111.7 倍。
- 验证：性能与阅读关键链路 68 项测试通过；完整 160 项中 159 项通过，唯一失败为语料数量固定值与当前用户数据不一致。

## 阅读器操作体验优化

- 书架条目显示“上次读到”的章节名称；点击存在阅读记录的书籍时，刷新目录后直接续读。
- 续读优先按章节 URL 定位，URL 不存在时才使用保存的章节索引，降低目录更新后的错位风险。
- 正文顶部增加常驻工具栏，无需滚动到底部即可使用上一章、目录和下一章。
- 工具栏显示当前章节在目录中的位置和章节名称。
- 增加 13–28 范围的正文字号调节，当前已加载的连续阅读内容会同步更新。
- 移出书架增加确认对话框，避免误触删除阅读记录。
- 新增阅读器交互回归测试，覆盖工具栏、续读定位与字号边界。

## 分类分页零值兼容

- 修复内联 URL 模板将合法数值 `0` 转为空字符串的问题。
- 修复范围限制在 `{{…}}` 表达式结果写回 URL 的阶段，不改变独立 JS 请求规则。
- 保留 `None`、布尔 `False`、空字符串和空容器的既有空值行为。
- 覆盖 `{{page - 1}}` 与 `{{(page - 1) * 20}}` 等常见 Legado 分类分页写法。

## 阅读进度与离线缓存

- 阅读状态新增章内滚动偏移、滚动比例、字号和最后阅读时间，采用 500ms 防抖保存，并在阅读页卸载时强制落盘。
- 重新打开应用后，按书源、书籍和章节恢复阅读章节、字号及章内位置。
- 新增独立 `reader-cache`：目录按书籍缓存，正文按章节缓存，图片字节使用 Base64 安全序列化。
- 点击有缓存的书架书籍时不再请求目录；正文命中缓存时直接进入阅读。
- 后续章节预取同时写入磁盘，关闭应用后仍可复用。
- 磁盘正文缓存限制为 256MB，按最旧访问文件淘汰；移出书架时同步删除该书缓存。
- 目录增加搜索、正倒序切换和手动刷新；书架按最近阅读排序并显示本章进度。
- 为保证章内位置可准确恢复，阅读区改为单章滚动模型，不再自动把多章拼接到同一滚动区域；上一章/下一章和预取仍保留。

## 项目目标

本项目用于导入、管理和检测 Legado（阅读）书源，并提供从发现、搜索、详情、目录到正文阅读的完整执行链路。当前实现已从“书源可用性检测工具”扩展为带桌面界面的兼容执行器，核心代码集中在 `app/services`，界面代码集中在 `app/views`。

本次复核的目标是：整理现有开发成果，对照仓库内 1,127 个真实书源检查规则覆盖情况，并明确尚未完成或仍有兼容风险的部分。

   其中一部分字段已在运行引擎中实现，但没有被全量规则语法审计覆盖。因此“24,281 条规则全部通过”只代表当前审计字段集合，不代表 JSON 中每个规则值都已检查。

2. **搜索关键字检查规则未形成执行闭环**

   `ruleSearch.checkKeyWord` 在 301 个书源中出现，但当前搜索流程没有明确执行该规则。需要对照 Legado 的调用时机和返回语义补充实现与测试，否则部分书源可能无法正确过滤或转换关键字。

3. **目录 `formatJs` 未执行**

   当前语料有 5 个书源使用 `ruleToc.formatJs`，代码中未找到对应执行路径。数量虽少，但属于明确的规则字段遗漏。

1. **正文展示语义不完整**

   - `ruleContent.imageStyle` 有 437 个书源使用，目前没有完整应用到阅读界面；

2. **书评规则未实现**

   标准 Legado 生态中还可能出现 `ruleReview`。当前内置语料没有该顶层字段，数据模型、引擎和界面也未实现书评链路。它不影响本语料，但属于与完整 Legado 功能对齐时的缺口。

   当前测试大量使用模拟响应。真实书源还会受站点失效、TLS、Cloudflare、登录状态、动态渲染、地区限制、Cookie 和反爬策略影响。建议增加抽样端到端测试，并把失败区分为“站点失效”“网络限制”“规则不兼容”“交互未完成”。

4. **Java/Android 兼容层是按需模拟，不是完整运行时**

   目前 API 集合覆盖了内置语料扫描到的调用，但新导入书源仍可能使用未实现的 `Packages.*` 类、Java 重载、Rhino 特性或 Android API。审计也主要识别显式方法调用，动态属性访问、反射和 `eval` 生成的调用可能漏检。

## 继续复刻记录

### 规则语义复核与结论修正

本轮通过开源 Legado 兼容实现的 Kotlin 模型和调用链核对字段语义，修正前文的两项判断：

- `ruleSearch.checkKeyWord` 是“校验关键词”，供书源检测时发起一次样例搜索，并不是搜索结果过滤或关键词转换规则。项目原有 `check_service.py` 已按此语义实现，因此它不属于运行引擎遗漏。
- `ruleToc.formatJs` 仍存在于规则模型中，但参照实现没有实际调用点；当前语料虽然有 5 个该字段，值均为空。因此暂不添加臆测的执行行为，避免制造与 Legado 不一致的新语义。

### 本轮完成的实现

1. **扩展全量语料审计**

   - 将 `nextTocUrl`、`downloadUrls`、正文 `title` 等选择器字段纳入规则审计；
   - 将 `preUpdateJs`、`payAction`、`imageDecode`、`webJs`、`loginCheckJs`、`coverDecodeJs` 等独立脚本字段纳入 JavaScript 编译审计；
   - 增加 `replaceRegex`、`sourceRegex`、`bookUrlPattern` 正则字段审计；
   - 增加未知规则字段检测，未来导入包含新字段的书源时不会静默漏掉；
   - 区分选择器、脚本、正则和元数据，避免把 `checkKeyWord`、`imageStyle` 错当成选择器。

2. **补充前向兼容模型**

   `BookSource` 新增 `ruleReview` 字段，导入和导出时不再丢失外部书源携带的书评规则。当前内置语料没有 `ruleReview`，执行链路仍待实际样本驱动实现。

3. **对齐正文标题规则**

   实现 `ruleContent.title`：正文首次加载时执行标题规则，结果同时写入内容文档和当前章节名称。阅读界面优先显示解析后的标题，行为与参照实现一致。

4. **保留图片布局规则**

   `ruleContent.imageStyle` 现在随 `ChapterContent` 保留，不再在引擎层丢失。`FULL` 的含义为图片使用最大可用宽度；后续可继续完善界面层不同取值的视觉映射。

5. **修正正文替换执行顺序**

   原实现对每一页正文分别执行 `replaceRegex`，再合并分页。Legado 的执行顺序是先按顺序获取并合并全部正文分页，再执行一次替换规则。本轮已改为：

   ```text
   分页抓取 → 每页正文规则 → 顺序合并 → replaceRegex/JS → 内容块解析
   ```

   这项修复保证普通正则和 JavaScript 替换都能匹配跨页内容，并避免每页脚本重复修改共享状态。

### 当前兼容边界

经过本轮修正，当前语料的所有规则字段均已被分类，选择器和脚本审计不再存在已知盲区。尚不能宣称“任意 Legado 书源 100% 兼容”，主要边界为：

- `ruleReview` 已可无损保存，但尚无内置样本和书评执行/UI 链路；
- `imageStyle` 已传递到内容文档，界面层仍需完整映射不同历史取值；
- Java/Android/Rhino 桥接仍是按实际语料实现的兼容层，不是 Android JVM；

- 真实网站的失效、登录、风控、WebView 和网络差异仍需要端到端抽样验证。

本轮结论：规则引擎对当前 1,127 个书源的字段覆盖已经闭环，正文执行顺序进一步与 Legado 对齐。后续复刻工作应从“补字段”转向“真实失败样本驱动的行为对齐”，重点是书评、图片布局和未覆盖的动态 Java/Rhino 行为。

## 找书与详情交互优化

### 问题

找书结果原先把整张书籍卡片的点击事件直接绑定到“加入书架”。用户只是想查看一本书时也会立即收藏，不符合“浏览结果 → 查看详情 → 决定是否收藏”的常见操作流程。同时，引擎虽然在加载目录时会解析详情规则，但界面没有独立的书籍详情入口。

### 调整

- 点击搜索或发现结果中的书籍卡片，改为打开书籍详情弹窗，不再自动加入书架；
- 结果卡片右侧继续保留书签按钮，作为明确的快捷收藏操作；
- 详情弹窗展示封面、书名、作者、分类、字数、最新章节和简介；
- 详情弹窗提供明确的“加入书架”按钮；
- 新增 `LegadoReadingEngine.book_info()`，只请求详情页并执行 `ruleBookInfo`，不会为了查看详情而加载整份目录；
- 支持详情页 `init`、重命名、作者、简介、分类、最新章节、字数、封面和下载地址等既有规则；
- 详情加载失败时仍显示搜索结果中已有的信息，并提示完整详情加载失败；

## 大量书源无法解析的原因分析

本节仅记录诊断结论，尚未修改规则引擎。

### 在线复查结果

`bookSource.json` 有 1,127 个书源，历史 `bookSource_passed.json` 有 1,005 个，差集为 122 个。对这 122 个书源重新执行连通和搜索检查后，首次结果为：

| 阶段 | 数量 |
| --- | ---: |
| 服务端可正常访问 | 16 |
| HTTP 客户端错误/风控响应 | 65 |
| 无法连接 | 26 |
| 超时或其他连接异常 | 15 |
| 实际进入搜索解析 | 16 |
| 搜索成功 | 7 |
| 搜索无结果 | 7 |
| 搜索 HTTP 错误 | 2 |

因此历史未通过的 122 个书源中，106 个在本次检查中根本没有进入规则解析。站点失效、域名变化、HTTP 403/404、超时、断开连接和风控页是“不可用书源”的第一大原因，不能全部归因于规则引擎。重复检查时可访问数量会波动，也说明网络和站点状态本身并不稳定。

### 规则引擎中的高影响差异

1. **阅读链路丢失 `##` 正则后处理**

   搜索字段主要通过 `_field_value()` 执行，可以处理 `选择器##正则##替换`；详情、目录和正文主要通过 `_strict_value()` 执行。后者会截掉 `##` 后面的内容再执行选择器，却没有执行被截掉的替换。

   受影响的内置语料规模：

   | 规则区域 | 使用普通 `##` 后处理的书源 | 规则数 |
   | --- | ---: | ---: |
   | `ruleBookInfo` | 575 | 1,160 |
   | `ruleToc` | 185 | 211 |
   | `ruleContent` | 379 | 427 |

   其中正文的独立 `replaceRegex` 已有单独处理，但 `content##...`、`title##...`、`nextContentUrl##...` 仍会受影响。这是“搜索正常，点击后详情为空、目录地址错误、章节名或章节 URL 错误”的最可能代码原因。

2. **Jsoup 索引语义没有完整复刻**

   Legado 支持：

   - `[0,1]` 多索引；
   - `[!0,1]` 排除多索引；
   - `[start:end:step]`；
   - 负数索引；
   - `[-1:0]` 反转列表；
   - 越界截断和区间端点包含。

   当前实现主要支持单索引和简单冒号范围，不支持逗号索引与步长，而且 Python 切片的结束位置不包含端点，与 Legado 的区间语义不同。当前语料至少有 15 个明确的数字逗号索引规则，包含详情分类、下载地址和搜索列表等关键字段。

3. **规则阶段链没有统一实现**

   Legado 的 `splitSourceRule()` 会把普通规则、`{{...}}`、`@get`、`@put`、多个 `<js>`/`@js:`、正则替换拆成连续阶段，每一阶段以上一阶段结果作为输入。当前项目分别在搜索、详情、目录、正文和下一页逻辑中实现了多套近似流程，支持程度不同。

   后果是同一条规则在搜索字段中能工作，在目录或正文中可能失败；多个 JS 阶段、JS 前后都有选择器、JS 返回对象后继续 JSONPath/Jsoup 解析等组合尤其容易出现差异。

4. **`@html` 返回内容不同**

   参照实现的 `html` 会返回匹配元素的外层 HTML，并移除 `script`、`style`；当前解析器返回 `decode_contents()`，即只返回内部 HTML。依赖外层标签、属性或后续正则包含边界标签的规则会得到不同结果。

5. **JSONPath 和 XPath 底层实现不同**

   Legado 使用 Jayway JsonPath 与 JXDocument；项目使用 `jsonpath-ng`、`elementpath` 和兼容转换。过滤表达式、联合索引、递归查找、函数、返回对象类型、缺失值处理，以及 HTML 转 XML 后的容错行为并不完全相同。静态“可编译”不能证明运行结果一致。

6. **真假值判断过窄**

   Legado 的 `isTrue()` 规则是：除空值、`null`、`false`、`no`、`not`、`0` 外，其他非空字符串都视为真。当前目录代码只认可一个固定白名单。`isVolume`、`isVip`、`isPay` 返回任意非空标记时，可能被错误判定为假。

7. **远程脚本没有进入静态审计**

   当前语料有 43 个书源带 `jsLib`，9 个书源通过 `Reload(...)` 动态下载并 `eval` 远程代码。审计器只编译书源 JSON 中的包装脚本，不会下载并分析远程脚本，所以“1,567 段脚本编译通过”不覆盖这些实际执行代码。

   在线复查已捕获一个真实样本：`ZERO搬运网` 在执行动态脚本时出现 `TypeError: not a function at Map`。这类失败可能来自远程库加载失败、加载顺序不同、远程代码更新，或 Rhino 与 QuickJS 的全局对象差异。

8. **Rhino/Java/Android 兼容仍是模拟层**

   QuickJS 与 Rhino 在 Java 对象重载、数组和集合、构造器、原型、隐式字符串转换、异常类型、正则和 `eval` 作用域上存在差异。显式 API 名称扫描为零遗漏，只能证明方法名已登记，不能证明参数重载和对象行为完全一致；动态生成的方法调用也无法被当前扫描发现。

9. **解析异常被宽泛捕获并转成空结果**

   `_list_nodes()`、`_strict_value()` 等位置会捕获广泛异常并返回空列表，随后尝试通用 CSS 猜测。这样界面通常只显示“解析为空”，真正失败的规则、阶段和异常被隐藏；通用猜测还可能把导航链接误当成书籍或章节。当前缺少与 Legado Debugger 类似的逐阶段日志。

10. **“无结果”不等同于“解析器不支持”**

   校验关键词可能过时，网站可能改版、返回登录页、验证码页、地区限制页或空搜索页。若响应是 HTTP 200，现有检查很容易将这些情况统一记录为“规则解析结果为 0”。需要保存最终 URL、状态码、内容类型、响应摘要、实际规则类型和匹配数量才能准确分类。

### 原因优先级判断

按当前证据，建议依次处理：

1. 网络/站点不可用与规则失败分开统计，避免把 106 个未进入解析的源计为解析失败；
2. 统一规则阶段执行器，优先修复 `_strict_value()` 丢失 `##` 后处理；
3. 完整复刻 Jsoup 索引语义与 `@html` 行为；
4. 对齐 Legado 的真假值判断；
5. 为每个规则阶段增加可查看的调试日志；
6. 再用真实失败响应逐项补齐 JSONPath、XPath、Rhino 和远程脚本兼容。

核心结论：当前“大量无法解析”由两类问题叠加造成。数量上主要是站点和网络不可用；在真正进入阅读链路的书源中，`_strict_value()` 与 Legado 阶段模型不一致是最明确、覆盖面最大的规则引擎缺陷。

## Rhino 对象字符串与失败分类修复

继续分析真实抽测中“猫耳听书（优）”的 `cannot read property '1' of null`：其 `bookUrl` 脚本通过 `String(result).match(/id=(\d+)/)` 读取 JSONPath 返回的记录。Legado/Rhino 中该记录是 Java Map，字符串形式为 `{id=123, name=...}`；当前 QuickJS 直接接收普通对象，`String(result)` 为 `[object Object]`，导致正则必然失败。

5. 检测器不再把所有 `JsBridgeError` 都标为“引擎缺少 JS 支持”：未实现 API 才归为 `js_needed`，桥接网络失败归为 `http_error`，书源脚本对响应结构的断言失败归为 `parse_error`。
6. “皮皮漫画”复查表明远程搜索脚本从首页正则提取 `keyword=` 地址时匹配为空；当前已明确归类为书源脚本/站点结构失配，而非规则引擎未实现。

新增 Java Map 字符串、JSON 对象直接传入 JS、Python 桥接异常保真和失败分类测试。验证结果：完整测试集扩展至 103 项，全部通过。
