# 2026-08-11 问题与解决方案

## 用一次实时页面结构覆盖书源原规则

- 现象：爱丽丝书屋搜索和阅读正常，但发现页所有排行返回 0 本；Legado App 中可正常加载。
- 原因：2026-08-07 网站短暂呈现 `span.s2` 紧凑布局后，项目把旧版 `rec_rullist` 规则完全替换。网站当前再次返回旧版结构，严格执行新规则的 Python 引擎自然没有匹配。此前离线测试只覆盖新布局，错误地把书源数据回归当成已解决。
- 方案：书源列表、书名、地址和分类规则显式覆盖两套已经观察到的结构；保留旧版作者、最新章节字段。引擎继续严格执行规则，不进行智能猜测。
- 防复发：对可能按设备、节点或时间切换 DOM 的站点，新增布局时必须保留仍可能出现的旧布局，并在同一测试中同时验证；实时成功不能替代多布局离线夹具。

## 空 Map 和静态 header 掩盖 BaseSource 差异

- 现象：报告把登录和请求头标记为完成，但未登录时 Python 返回空 Map，动态 `header` 在 JS 桥内被当作非法 JSON 丢弃。
- 原因：测试按“避免脚本报错”的宽松目标编写，没有对照 `BaseSource.kt` 的 null、返回类型、Cookie 联动和 `getHeaderMap` 执行路径；模型字段齐全也被误当成实体语义完整。
- 方案：严格移植 BaseSource 的可观察方法；UI 自身对 null 做安全处理，不改变引擎返回值；动态 header 在 source 方法调用时执行并补默认 UA，登录头只在显式参数为 true 时合并。
- 防复发：能力表每个“完成”项必须至少覆盖正常、缺失、非法输入、返回类型和副作用，书源语料中存在的动态字段需统计实际数量，不能只做字段名扫描。

## JavaScript 请求忽略书源 Cookie 开关

- 现象：普通阅读请求会按书源隔离或禁用 Cookie，但规则脚本中的 `java.ajax/request/connect/post/ajaxAll` 始终使用全局 Cookie opener，禁用 Cookie 的书源仍可能发送和接收 Cookie。
- 原因：早期桥接只迁移了请求方法，没有把固定 `getSource()?.enabledCookieJar == true` 的条件带到所有 JavaScript 网络入口；复核时又一度把 Kotlin 可空布尔误写为“不是 false”。
- 方案：所有 JavaScript 网络入口共享同一开关，仅显式 true 安装 Cookie 处理器和持久化响应 Cookie，false/null 使用无 Cookie opener；字段缺省采用 BookSource 默认 true。
- 防复发：可空布尔必须分别覆盖 true、false、null，网络开关需同时断言请求头、响应副作用及持久状态，而不是只检查 opener 是否存在。

## BaseSource 宽松回退掩盖固定异常和作用域

- 现象：动态 header 直接返回对象也能成功、脚本异常被吞掉；旧明文登录状态能绕过 AES；登录函数会残留到后续规则；JSON 数组 jsLib 被拆成脚本执行。
- 原因：实现以“尽量继续运行”为目标扩大了固定源码的接受范围，没有分别对照 toString/Gson、runCatching 边界、SharedJsScope 分支和新 runtime scope 生命周期。
- 方案：按固定调用顺序和异常范围执行；解密失败返回 null；login 使用一次性局部 eval；jsLib 只对 JSON object 执行 URL 映射，其余整体求值。
- 防复发：每个兼容入口同时测试合法值、合法但不接受的类型、语法异常、null/undefined、连续两次调用和持久副作用。

## 静态审计能力表自身产生假清零

- 现象：审计器把不存在的 `source.putVariable` 认作已支持，却遗漏真实 BookSource 公共方法；测试也没有断言正则问题列表和总 successful 状态。
- 原因：能力表来自早期 Python 桥而非固定接口逐方法生成，门禁只检查部分列表。
- 方案：以 BaseSource.kt、BookSource.kt 重建 source 方法集合，删除额外方法；门禁显式检查全部问题列表及总成功状态。
- 防复发：能力表更新必须同时提供固定源码方法证据和运行时可调用测试，禁止仅凭语料未命中宣告支持。

## source 方法正确但真实请求绕过语义

- 现象：`source.getHeaderMap(true)` 单测正确，但 ReaderEngine 仍直接解析 source.header，导致动态 header 使用章节 URL、登录 header 不进入请求；无 source 请求还会错误启用 Cookie。
- 原因：模型桥和 Python aiohttp 传输层各维护了一套 header/Cookie 逻辑，修复只落在桥层。
- 方案：请求入口统一调用 source.getHeaderMap(true)，并严格使用 source key、nullable Cookie 开关和精确小写 proxy；删除 URL option proxy 扩展。
- 防复发：宿主方法测试之外必须验证最终 wire headers、CookieJar、connector 和 option 覆盖顺序。

## 文件与封面接口接受了固定类型之外的结果

- 现象：封面脚本返回 URL/Base64 也被接受；downloadFile/cacheFile/importScript 绕过 source 请求上下文，cacheFile 不写 CacheManager。
- 原因：为了适配桌面 UI，把 InputStream/ByteArray API 改造成宽松字符串接口，并用文件 mtime 近似缓存 TTL。
- 方案：封面只接受 ByteArray；下载通过 AnalyzeUrl 等价请求；CacheManager 保存 md5Encode16 路径与 TTL，importScript 复用 cacheFile。
- 防复发：测试官方单/双参数重载、错误返回类型、空 body、source header/Cookie、缓存可观察条目和只下载一次行为。

## 把三个 JavaScript 宿主类合并成一个万能 java

- 现象：任何规则脚本都能调用 AnalyzeRule、AnalyzeUrl 和 BaseSource 方法的并集；静态能力审计因此显示“都支持”，却没有验证方法在正确上下文中是否存在。
- 原因：早期 QuickJS 桥只有单一 bootstrap，没有保存创建脚本宿主的 Kotlin 类信息；BaseSource.evalJS 也直接使用外层 eval。
- 方案：JsContext 携带 rule/url 宿主类型并按类隐藏专属方法；BaseSource.evalJS 使用 source 自身和固定五个基础绑定的新词法调用。
- 防复发：能力门禁必须同时断言“应存在”和“应不存在”；同名方法还必须分别验证不同宿主的数据回退和副作用，不能只验证函数可调用。

## 用单一全局变量字典近似 RuleDataInterface

- 现象：java.put 总是写引擎全局字典，chapter/book.putVariable 又通过另一组前缀存储；求值结束后实体快照会把新增变量覆盖。AnalyzeUrl 还会错误回退到 source。
- 原因：桥接层只保留了变量名和值，没有保存 AnalyzeRule/AnalyzeUrl 构造时传入的 chapter、book 和 ruleData 对象关系。
- 方案：按固定优先级选择实际变量字典，实体方法与 java 方法共用状态；仅 AnalyzeRule 允许最终 source 回退，并在同步时合并而非覆盖变量表。
- 防复发：同一测试必须覆盖同名键的四级遮蔽、空字符串回退、null 删除、跨作用域持久化以及 AnalyzeUrl 禁止 source 回退。

## 把目录 formatJs 当作普通规则脚本执行

- 现象：formatJs 能访问 java、source、book、result 和 jsLib，远超固定 BookChapterList 只提供的 index/chapter/title/gInt。
- 原因：所有 JavaScript 都被送入同一个 JsContext 默认宿主，没有追踪直接 RhinoScriptEngine.eval 的特殊 SimpleBindings。
- 方案：增加独立 format 宿主，保留跨章节共享 gInt，只暴露固定四项绑定并禁用共享 jsLib。
- 防复发：除 AnalyzeRule/AnalyzeUrl/BaseSource 外，所有直接构造 SimpleBindings 的源码调用点都要单独建作用域契约测试。

## 用 Python truthiness 和通用 HTTP 配置解释 UrlOption

- 现象：webView="false" 被开启、webView=0 被关闭；method=PUT 真正发送 PUT；非法 retry 只忽略 retry 而保留 POST/body；空 type 被视为未设置；JSON body 被 URL charset 错误编码。
- 原因：请求字典直接进入通用 aiohttp/urllib 层，没有先经过 UrlOption 的 Kotlin getter、Gson 整体反序列化和 AnalyzeUrl 字段分析。
- 方案：增加 UrlOption 规范化层和 Java/Gson 字符串转换；传输层区分字段 charset 与结构化 body charset，并按固定顺序执行 POST WebView 和登录检查。
- 防复发：每个 Any?/String?/Int?/Long? 字段必须覆盖 null、空串、false、"false"、0、对象、非法数值和未知方法，且同时断言最终 wire method/body/header 与副作用顺序。

## 把 enabledCookieJar 误当作 Cookie 总开关

- 现象：false/null 书源不发送 CookieStore 已保存 Cookie；存在临时 Cookie header 时又完全丢弃数据库中的其他 Cookie。JavaScript 请求还只继承静态 source.header。
- 原因：Python 把 CookieStore 和 OkHttp CookieJar 合并成同一开关，并用“有 Cookie header 就跳过 jar”的浏览器式逻辑替代 AnalyzeUrl.setCookie。
- 方案：CookieStore 始终按请求域读取并与精确 Cookie header 合并；enabledCookieJar 只选择真实/空 CookieJar。JsExtensions 的 AnalyzeUrl 请求在调用点执行 source.getHeaderMap(true)。
- 防复发：Cookie 测试必须交叉覆盖 true/false/null、数据库/临时同名与异名键、动态/login header、响应 Set-Cookie 和跨子域读取。

## 用浏览器 CookieJar 近似 Legado 的注册域 CookieStore

- 现象：Cookie 只在写入时的完整主机和 Path/Secure 范围内可见，兄弟子域无法读取；一刀切修正后，关闭 CookieJar 的直接 Jsoup 请求又错误携带了 CookieStore。
- 原因：Legado 的 CookieStore 先通过 OkHttp PublicSuffixDatabase 求 effective-TLD-plus-one，再把响应 Cookie 压平为名称/值；AnalyzeUrl 与 JsExtensions 直接 Jsoup 请求是否加载 CookieStore的条件也不同，标准 CookieJar 无法直接代替这组语义。
- 方案：保存固定 OkHttp jar 和其中的公共后缀数据，以 Python 实现同表算法；持久状态按注册域、根路径、非 Secure 归一化，并用内部请求标记区分 AnalyzeUrl 与直接 Jsoup 分支。
- 防复发：同时测试 `com.cn`、私有后缀、通配、例外、IP、兄弟子域、旧状态升级，并交叉覆盖 AnalyzeUrl/Jsoup 与 CookieJar true/false/null。

## 用一个宽松 Response 对象代替 StrResponse 与 Jsoup Response

- 现象：`String(java.connect(...))` 返回正文，connect 响应具有固定类中不存在的 `header/bodyAsBytes/status`；HTTP 状态文字和重复 Location 丢失，JavaScript AnalyzeUrl 的 webView/ZIP/XML 路径未执行。
- 原因：桥接层只保存 body、单值 headers、status 和 URL，并让所有请求入口共用同一对象；测试依据早期 Python 表面编写，反而固定了非官方行为。
- 方案：响应数据携带类型、reason、protocol 和多值头；JavaScript 按类型构造公开方法，内部字节读取使用独立私有桥；AnalyzeUrl 字符串与 WebView 流程按固定源码顺序执行。
- 防复发：预言测试必须分别覆盖 StrResponse、Jsoup Connection.Response、OkHttp Response，验证应存在与不应存在的方法，并测试重复头、非 2xx、ZIP/XML、GET/POST WebView 和最终 URL。

## 按 WebView 最终域合并 Cookie，而不是按 source tag 替换

- 现象：跨域验证页面返回 Cookie 后，Python 把它保存到验证站域；回到原书源仍没有 Cookie，且验证前的旧 Cookie 键继续残留。直接 `java.webView` 还没有传 source/login header。
- 原因：桌面适配按普通浏览器 CookieJar 设计，忽略了 BackstageWebView 的 `CookieStore.setCookie(tag, CookieManager.getCookie(finalUrl))`；同时 WebView 桥没有迁移 `getSource()?.getHeaderMap(true)` 参数。
- 方案：浏览器结果以 source key 为 tag 整体替换 CookieStore，空值清除；同步清理并重建请求 CookieJar。所有直接 WebView 调用在调用点解析动态、默认和登录请求头。
- 防复发：用 source 域与最终验证域不同的测试，同时断言旧键消失、source 域得到新键、最终域不被污染，并覆盖空 Cookie 与动态登录头。

## 把响应 Session Cookie 当成持久 Cookie

- 现象：无 Expires/Max-Age 的登录会话在 Python 重启后仍存在；响应 Cookie 还受原 Path/Secure 限制。同名 session 覆盖持久 Cookie 后，底层值永久丢失。
- 原因：urllib/aiohttp CookieJar 同时承担 CookieStore 数据库和 CookieManager 内存 session map，持久化时无条件序列化整个 jar；没有迁移固定 `saveCookiesFromHeaders` 的 persistent 分类与两层合并。
- 方案：响应入口解析 Expires/Max-Age，session 仅留内存并标记；持久化排除 session，同时为同名覆盖保存持久 shadow。所有响应 Cookie 先压平到 effective-TLD-plus-one 根路径和非 Secure 表面。
- 防复发：同一名称先写持久值、再写 session 值，必须断言运行期 session 胜出、磁盘仍是持久值、重启恢复持久值；另测不同名 Cookie、Path/Secure 和兄弟子域。

## 把 setCookie 与 replaceCookie 做成同一种合并操作

- 现象：脚本调用 `cookie.setCookie(url,"only=1")` 后旧持久键仍存在；调用 replaceCookie 却会删掉旧键。写操作还错误返回 Boolean，并把文本中的 Path 当属性吞掉。
- 原因：桥接层直接复用了浏览器 SimpleCookie/CookieJar，没有迁移 CookieStore 存储整段字符串、cookieToMap 合并以及 Kotlin Unit 返回的公开契约。
- 方案：setCookie 清空并重建持久域字符串，replaceCookie 仅合并持久 map；session 层独立保留。使用 CookieStore 自身的分号/等号解析规则，并对 JavaScript 隐藏 Python Boolean。
- 防复发：同一测试依次执行 set、replace、再次 set，断言键顺序和旧键去留；覆盖空值、字面量 null、无等号字段、Path 普通键、返回类型和 4096 字符裁剪。

## 能力审计遗漏 CookieStore 公开方法

- 现象：固定源码公开 `cookieToMap` 与 `clear()`，但静态能力表漏报，Python 注入对象也没有 `clear()`；此前问题列表为 0 仍可能在真实调用时失败。
- 原因：能力表由早期桥接实现手工反推，没有从固定 `CookieStore.kt` 的完整公开表面逐项建立双向契约。
- 方案：补齐 `cookieToMap/clear` 能力登记；按 Rhino 重载选择恢复精确参数数量和 Kotlin null 检查；`clear()` 仅删除持久 OkHttp Cookie，保留内存 session。
- 防复发：能力审计必须与固定源码公开方法集合对照，并为每个新增方法同时验证正常返回、少传/多传、null、持久化副作用和重启状态。

## 以 Python 能力表反推固定公开方法造成遗漏

- 现象：`JsExtensions.toURL/logType` 在桥中存在，但能力审计未登记；`toURL(null)` 被改为空地址，`logType` 返回参数而非 Unit。
- 原因：能力表和桥接代码互相作为依据，没有以固定 Kotlin 声明、重载与返回类型作为独立真值源。
- 方案：按固定源码逐项登记方法签名、nullable、返回类型和副作用；本轮先恢复 toURL/logType 契约。
- 防复发：每个公开方法必须同时具备源码定位、能力登记、正常路径、少传/多传、null、返回类型及可观察副作用断言。

## 用通用文件工具近似 ArchiveUtils 生命周期

- 现象：文件方法把 null/少传当空路径；同名压缩包每次解压都会删除旧目录；`getTxtInFolder` 对普通文件不执行官方的消费删除。
- 原因：桥接层按 Python 文件工具的直觉语义实现，没有迁移 Rhino 重载选择、Kotlin 非空检查和 `ArchiveUtils.TEMP_PATH` 的 lazy 生命周期。
- 方案：公开方法逐个恢复签名；首次解压重建 ArchiveTemp，后续复用 MD5-16 子目录；目录消费严格保留成功、普通文件和空目录分支副作用。
- 防复发：文件 API 测试必须验证返回值之外的首次/再次调用、同名覆盖、旧文件残留、删除后 exists、缺失项和异常后目录状态。

## 网络压缩读取绕过 AnalyzeUrl

- 现象：普通规则请求带动态/登录 header 和 Cookie，但 `getZip/Rar/7z*Content(URL)` 只发送默认 UA；proxy、retry 和 URL option 也不进入请求链，并可能错误启动 WebView。
- 原因：Python 压缩工具自己用 opener 下载字节，没有复用已迁移的 AnalyzeUrl 请求流程。
- 方案：所有网络压缩输入通过 `_request_json` 获取 bodyBytes，并传递调用时 source header、baseUrl、CookieJar 开关和 source key；ByteArray 路径显式禁用 WebView。
- 防复发：网络压缩回归必须同时断言动态 header、登录 header、proxy、Cookie 开关/tag、嵌套 URL option 原文和 webView 禁用，不能只验证成功解压。

## 非 2xx 压缩响应遗漏 Cookie 且异常原因丢失

- 现象：HTTPError 分支能返回正文，却只持久化旧 Cookie 状态，不接收本次 Set-Cookie；传输失败到 JavaScript 后只显示 Python call failed。
- 原因：错误响应与正常响应维护两套 Cookie 收尾；压缩回调未经过统一 `_bridge_call` 错误记录。
- 方案：非 2xx 与普通响应共用 `save_response_cookies`；压缩回调统一记录底层异常，同时继续向规则抛出。
- 防复发：使用真实非 2xx 压缩字节交叉验证正文解析、CookieJar true/false、session/持久重启状态，并用 URLError 断言错误原因可见且不回退为空内容。

## 语料未调用导致 WebView 公开方法漏登记

- 现象：固定 JsExtensions 有两个嗅探方法，但能力表没有；null URL 又被桥接层自动替换为 baseUrl，改变 WebView 加载模式。
- 原因：静态审计只比较“语料已调用方法”和“已登记方法”，无法发现语料未调用的固定公开 API；通用浏览器适配又抹平 nullable 参数。
- 方案：从固定源码提取完整公开方法集合并强制为能力表子集；三个方法逐个恢复重载、null 和 options 传递。
- 防复发：公开表面测试不依赖书源语料覆盖率；WebView 回归必须断言传给浏览器的原始 html/url/js 是否仍为 null。

## AnalyzeRule 状态方法被当作字符串工具

- 现象：setContent/setBaseUrl 返回字符串而非 this，null baseUrl 变成文本；redirectUrl 整个从 rule 宿主消失。
- 原因：桥接早期只服务规则求值结果，没有迁移 AnalyzeRule 本身的可观察对象状态与链式 API。
- 方案：为 rule java 对象保留 content/baseUrl/redirectUrl 状态，严格实现重载、null、返回身份和宿主隔离；URL 解析留在 JS 内避免跨语言异常崩溃。
- 防复发：状态方法必须断言 `return === java`、调用前后公开属性、无效输入保留旧值、null/arity 与另一宿主不可见性。

## 专属方法缺失且规则缓存污染共享 jsLib

- 现象：规则脚本无法调用 splitSourceRule/evalJS，URL 脚本无法读取 isPost/getUserAgent；初次补缓存后共享 jsLib 第二次求值出现重复声明错误。
- 原因：桥接只覆盖语料常用选择器方法，没有迁移 AnalyzeRule 实例缓存与 AnalyzeUrl 构造后状态；QuickJS 持久全局又不同于每次新建的 Kotlin AnalyzeRule 实例。
- 方案：显式迁移宿主方法和模式状态；缓存使用每次 bootstrap 重置、可重复声明的 var，同时保持单次求值内对象身份。
- 防复发：交叉验证 rule/url 方法存在与不存在，并把所有新增宿主状态放入共享 jsLib 连续多次求值回归。
## AnalyzeRule/AnalyzeUrl 同步对象边界

- 原 `reGetBook` 会在精确作者未命中时错误采用搜索首项，现改为书名与作者同时相等，否则传播与固定源码一致的失败。
- 原三个同步字节/Response 方法仍可能误走 WebView，且 `getStrResponse` 忽略三个公开参数；现已分离请求路径并传递 WebView JS/源码正则。
- 原字节接口遗漏 AnalyzeUrl 的 data URI 快速路径，非 2xx 响应也缺失 reason、多值头和响应类型元数据；现已补齐。
- 原 `initUrl()` 错误返回 URL 字符串且不校验参数；现恢复 Unit、零参数及初始公开 URL 状态。
- 后续若扩展到任意 Android/OkHttp/Glide 第三方对象的全部反射表面，应另立版本范围；本轮门禁针对固定 Legado 两个核心宿主的全部同步公开方法。
## AnalyzeUrl nullable source

- 问题：Python 上下文提取直接对 null source 调用 `vars()`，同时把“没有 source”与“BookSource 缺省 enabledCookieJar=true”混为一谈。
- 修复：单独记录 nullable source；内部空宿主只服务桥初始化，执行用户规则时以局部参数绑定 `source=null`，并强制关闭 CookieJar。
- 防回归：校验 JS 可见 null、同步请求 Cookie 开关和空 source key；同时从固定 BaseSource/BookSource 自动提取公开方法检查注册集合。

## 未挂载 Flet 控件读取 page 导致错误处理再次异常

- 现象：启停书源保存失败后本应回滚，但在单元测试或控件尚未挂载时读取 `self.page` 会抛出 `RuntimeError`，覆盖原始保存错误。
- 原因：Flet 的 `Control.page` 不是可空普通属性；控件不在页面树中时访问就会抛异常，不能使用 `if self.page` 判断。
- 方案：先捕获未挂载时的 `RuntimeError`，只在确实取得 Page 后显示 SnackBar；无论页面是否存在都先完成状态回滚。
- 防复发：状态修改测试同时覆盖已挂载交互与未挂载逻辑调用；错误提示不得成为数据恢复的前置条件。

## ISO-8859-1 二进制字符串在 NUL 处被桥接截断

- 现象：CBC 密文在网页中长度正确，进入书源脚本后却变为空数组，报 `Data must be padded to 16 byte boundary`；解密后生成的带 JSON 请求头图片标签也可能被当作普通正文。
- 原因：Python callable 向 QuickJS 返回包含 `0x00` 的字符串时在 NUL 处截断。书源通过 `bytesToStr(..., ISO-8859-1)`、`substring`、`strToBytes` 分离 IV 和密文，因此截断破坏了块边界；图片解析又使用了不支持 `src="url,{...}"` 内部引号的简单正则。
- 方案：Latin-1 转换完全留在 QuickJS 内逐字符执行，不让二进制字符串跨 Python 边界；内容块解析复用已有的嵌套请求选项图片模式。
- 防复发：必须覆盖 0—255 全字节往返、NUL 位于首部和中部、CBC IV/密文切片，以及内嵌 headers 的图片标签；实时书源成功不能替代这些离线边界测试。

## 固定手机窗口与书架来源绑定限制桌面阅读

- 现象：所有平台都被设置为 430×820，桌面无法利用横向空间；书架条目只能依赖加入时的书源，原书源失效后无法像 Legado 一样更换来源。
- 原因：窗口几何没有区分桌面和移动平台；书架服务缺少保留用户状态并替换来源身份的原子操作，阅读页也没有跨书源搜索入口。
- 方案：仅对桌面平台设置宽窗口和最小尺寸；增加切换来源服务与 UI，搜索候选后同步更新 snake_case/Legado 字段，并让旧章节 URL 失效、按保留的章节索引恢复。
- 防复发：窗口测试分别覆盖桌面与移动；来源切换测试必须覆盖分组、排序、字号、章节序号、旧 URL 清除、持久化重开及重复书架键拒绝。

## 外观配置损坏可能阻止应用启动

- 风险：用户手工编辑、旧版本残留或写入中断可能使 `appearance.json` 无法解析；若主题在页面构建前直接加载，异常会阻止整个 UI 启动。
- 方案：主题服务集中校验配置，未知模式与皮肤回退默认；非法 JSON 改名为带时间戳的 `appearance.invalid-*.json` 后继续使用默认主题。
- 防复发：持久化使用同目录临时文件原子替换；自动测试必须覆盖合法往返、未知值和损坏 JSON 三条路径。

## 旧目录地址指向首章导致 chapter list is empty

- 现象：书架中的《我的功法无限提升》目录地址为 `/changgui/9977/1.html`，该页面是正文页，不含目录选择器，最终抛出 `chapter list is empty`。
- 原因：书源的 `ruleBookInfo.tocUrl` 与章节列表选择器相同，标量解析将首章链接保存为目录地址；其 `chapterUrl: "href"` 又依赖当前节点直接读取属性，原引擎把 `href` 当作后代选择器。
- 方案：错误目录页无结果时回退书籍详情页一次；对 HTML 当前节点存在的裸属性规则直接读取并继续执行 URL 解析和正则后处理。
- 防复发：离线测试同时覆盖错误目录页、详情页完整章节、裸属性链接和只回退一次；实时验证必须使用不读取本地 Cookie 的临时会话。

## Flet 0.86 移除 Page.show_snack_bar

- 现象：保存外观或执行其他提示操作时报 `'Page' object has no attribute 'show_snack_bar'`。
- 原因：项目依赖 Flet 0.86，该版本将 SnackBar 纳入 DialogControl 生命周期，应通过 `Page.show_dialog()` 展示；部分旧版调用未随依赖升级迁移。
- 方案：所有提示统一经过 `app.ui_feedback.show_snack_bar()`，内部调用当前版本的 `page.show_dialog(snack_bar)`。
- 防复发：禁止业务视图直接调用版本相关的旧提示方法；测试验证辅助方法只依赖 `show_dialog`，并通过全项目文本检查清除遗留调用。

## 书架状态正确但新增行重复显示

- 现象：加入一本新书后标题显示“书架中有 3 本书”，列表却渲染 4 行，最后一本出现两次；持久化文件没有重复数据。
- 原因：每次刷新都创建全新的无 key `ListTile`/`Card`，连续页面更新时 Flet 客户端无法稳定识别同一书籍控件，可能保留旧行并追加新行。
- 方案：基于书源地址与书籍地址生成确定性 SHA-256 摘要，分别作为列表和网格控件的稳定 key。
- 防复发：回归测试必须同时校验列表、网格 key 唯一，并在连续两次渲染后保持完全一致；数据层去重测试继续保留。

## 搜索型书源被误提示为分类解析失败

- 现象：“二三小说”等书源显示“没有可解析的分类标签”，用户容易理解为书源异常。
- 原因：这些书源原始配置只有 `searchUrl`、没有 `exploreUrl`，属于 Legado 的仅搜索书源；界面此前把无分类能力与分类解析为空合并成同一提示。
- 方案：按原始配置区分能力；无 `exploreUrl` 时标注“仅搜索”并直接引导关键词搜索，只有存在分类配置但结果为空时才提示分类入口不可用。
- 防复发：测试覆盖下拉能力标记、状态提示和分类容器为空，不得通过猜测站点地址为仅搜索书源伪造分类。

## 打包后书源修改可能写入只读资源目录

- 风险：默认加载 `resource/bookSource.json` 后将其记录为当前保存路径，导入或管理书源时会尝试回写安装目录；单文件打包还可能写到会被删除的临时解包目录。
- 原因：只区分了书架数据目录，没有区分“只读内置资源”“用户持久数据”和“可清理缓存”。
- 方案：内置书源只作为首次种子，运行时书源固定保存到 OS 标准用户数据目录；正文缓存和浏览器配置进入标准缓存目录，全部采用明确目录和原子替换。
- 防复发：路径测试必须覆盖 Windows、macOS、Linux，不得依赖 cwd、`__file__` 或 EXE 位置；资源种子测试需确认保存后原文件字节不变且用户副本可重开。

## 书架子项 key 无法完全阻止 Flet 尾行残留

- 现象：加入第四本书后统计和持久数据均为 4，本地复合键无重复，但 Flet 客户端仍显示 5 行，新增项重复一次。
- 原因：稳定子项 key 只能帮助同一集合内对账；连续导航和刷新补丁到达时，Flet 0.86 仍可能在原 ListView 根上保留旧尾项。
- 方案：每轮书架渲染创建带递增代次 key 的新 ListView/GridView，并原位替换宿主容器最后一个子树，强制客户端卸载旧集合后挂载唯一新集合。
- 防复发：不能只断言持久化数量或子项 key；测试还需验证根 key 每轮变化、宿主指向最新根，且连续新增后两种布局的控件数始终等于书架数据数。

## 普通预取缓存不能作为整书离线缓存

- 风险：原阅读缓存只保存打开或预取的少量章节，并受 256MB 淘汰限制；图片块通常仍是远程 URL，断网后漫画不可读。
- 方案：新增用户主动触发的整书任务，缓存完整目录和所有正文；下载图片字节并保留请求头，使用离线标记保护整书不被普通淘汰。
- 并发约束：书源规则变量会在章节间传递，整书缓存按书内顺序执行；失败章重试 3 次，同书任务用书源/书籍复合键防止重复。
- 防复发：测试必须覆盖已有文件跳过、卷标题过滤、失败重试、再次运行零请求、图片离线字节及 `.offline` 标记。
