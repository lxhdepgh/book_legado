## 2. 各服务落点

### 2.1 SourceCheckService（§3.1 / §3.4）
- 外壳化 `app/services/check_service.py`（M2 冻结副本）：本壳只调 `check_service.check_sources(sources, concurrency, timeout, on_result, auto_disable)`，**四段流水线/九态/自动停用零改动**。
- 入口：`async check_source(source_json)`（单源，dict/BookSource 皆可）、`async check_all(groups=None)`（批量）、`cancel()`（同步取消在跑任务）。
- `on_result(result, done, total)` 回调里：写 `status.progress = done/total` → 发 `CheckFinishedEvent(source_id=raw_url, state_class=check_state, summary=…)` → 触发点③ fire-and-forget 复跑 `CompatAuditService.audit_source`（失败仅 warning，不阻断检测）。
- `block_pages.block_reason` 作为共享依赖 import（九态 blocked 结论归属，判定逻辑零改动）。
- on_start 经 `_resolve()` 注入/懒解析 SettingsService、SourceService、CompatAuditService（dotted path，并行未就绪时降级 None，不阻断导入）。

### 2.2 RuleRepairService（§3.2 / §3.4）
- 外壳化 `app/services/rule_repair.py`：`repair(source, chapter, *, extra_chapters=(), book=None, engine=None, timeout=15)` 直调底层 `diagnose_content_rule`，**ProbeEngine 焊死的本地 HTML 回放语义原样保留**（测试经 `engine._request_transport` 注入假传输，不出网）。
- 报告缓存：`report_id = uuid4().hex` 存入 `self._reports`，发 `RepairReportReadyEvent(report_id, source_id)`；`get_report(report_id)` 供视图取回。
- **红线保留**：诊断阶段绝不写回；仅 `apply_fix(report_id, fix_id)` 在用户确认后，经 `SourceService.update_source_rule(url, field, value)` 才写回。未知 report_id 直接拒绝。
- **第六十七轮起这一页能自己起手**：`chapter_candidates(source_url, *, max_scan_ms=200,
  per_book=100, max_rows=300, clock=…)`（`:196`）
  从**书架已缓存目录**里取样本章，全程零联网（读目录走 `asyncio.to_thread`，卷标题与空地址滤掉）。
  第七十轮把"本数上限"拆成两个预算，第七十一轮按实测成本把**翻目录那一档改成时间**：
  单本价格随章数差 60 倍（100 章 0.4 ms ↔ 5000 章 25.7 ms），按本数封顶等于
  "8 本小书 3 ms"与"8 本大书 206 ms"算同一件事；而并发买不回来（8 本只省 4.5%，
  16 本起为负，GIL）。现在 **`max_scan_ms`** 管翻目录（检查在每本开读之前，
  且第一本永不被切）、**`max_rows`** 管下拉下发（约 0.024 ms/行），每本摊到
  `max_rows ÷ 实际本数`（再受 `per_book` 上限），抽样步长**向上取整**（`len // allowance` 会超额）。
  开读前先做一次**只 stat 的普查**（8 本 0.11 ms）——没缓存过的书不占名额。
  返回值不再是裸 list，而是 `CandidateFace(groups, shelf_books, cached_books, shown_books, rows)`：
  被预算切掉的书必须报得出来（`skipped_books`），界面上念成"在架 N 本、本地读过 M 本、
  还有 K 本没摊到"，第七十轮那种"静默丢掉第 4 本之后"不再存在。
  等间隔抽样、保持原顺序，五千章一本不会退化成"取前 100 章"。
  实测成本表与取舍见 `docs/dev-logs/2026-10-03.md` 第七十一轮 §1-§2。
  配合检测快照新留的 `sample_chapter_urls`
  （`source_check_service.py:535`，`CheckFinishedEvent` 不加键）与视图上的手填地址出口，
  自愈页不再是一页"等待自愈报告…"。契约、护栏与浏览器取证见 `docs/dev-logs/2026-10-03.md`。
- **第七十轮：写回开始发事件**。`app/services/sources/source_service.py:399` 覆写
  `update_source_rule`——冻结基类那份只落盘不发事件，于是列表页/找书页/书架在自愈写回后
  仍显示旧规则；现在 `super()` 干完活补一条 `SourceChangedEvent(change_type="updated", source_id=…)`，
  冻结件零改动，源不存在时基类抛 `KeyError` 则不发事件。
- **第七十一轮：这一页的读屏面补齐**（浏览器语义树实测，PORT 8713-8715 三支探针）。
  `RuleRepairView` 里裸 `TextField` 与 `Text(selectable=True)` 在语义树中都是
  **role/aria-label/textContent 三样全空**的节点，而 `Semantics` 包 `selectable` 文本
  连标签自己都不进树——所以：手填正文页地址那只框改套 `ft.Semantics`，标签跟着
  `on_change` 念出"正文页地址：<用户填的那串>"（套上之后键盘照打，30 拍 `on_change`
  全收到）；`set_manual_visible` 连外壳一起收（只藏里面那只，读屏会念出一条不存在的路）；
  报告卡的原/新规则与"没有候选"那句**去掉 `selectable`**、整段包进 `ft.SelectionArea`
  （那两串是点「应用并重试」之前唯一能读到"要写回什么"的地方）。复制面改由
  `SelectionArea` 提供，但**浏览器里没量到拖选**（连线上就在用的 `selectable=True`
  那一格也拖不出选区，判为探针手势没打进去），故这条只有结构护栏，没有实测读数。
  全库另有 22 处 `selectable=True`（13 个视图）同患此疾，记入 004 待修清单。
- CheckFinishedEvent 自动触发入口按任务要求做成可选（最小实现仅 UI 触发，未在本壳串联检测事件）。

### 2.3 CompatAuditService（§3.7）
- 外壳化 `app/services/compat_audit.py`：`audit_source(source)` 复用其内部纯函数（scan_missing_java_packages、_rule_strings、_rule_entries、_validate_rule_syntax、_validate_regex_field 等）做单源审计，**静态审计函数本身零改动**；执行经 `asyncio.to_thread` 避免阻塞事件循环。
  **第六十三轮换过执行位置**：走的是 `audit_off_loop` → `ProcessPoolExecutor(spawn)`
  （`_audit_one` 一行未改，只是不再在本进程跑），池建不出来/被打穿才退回
  `asyncio.to_thread`，并给得出"这条没审"（`AuditReport.not_audited`）。
  取舍、实测数与护栏见 `docs/dev-logs/2026-09-30.md` 第六十三轮。
- 返回 `AuditReport`（dataclass）：source_id + missing_java_apis/missing_object_apis/unknown_fields/unsupported_pseudos/js_syntax_errors/regex_errors + rule_syntax_errors/suggestions + not_audited + `clean` property。字段命名与并行 OnlineImportService 读取口径一致。
- 三触发点：①导入即审 ②保存即审 ③检测流水线复跑（由 SourceCheckService 调用）。
  **①的归属后来钉死在落库层**（`current-system-design.md` §5.6）：
  `SourceService.import_sources_json(..., audit=True)` 逐条审（扫码导入 / WebDAV 恢复
  这些不经门面的入口全靠它），`OnlineImportService` 为了出 `ImportResult.warnings`
  自己先审一遍、再传 `audit=False`。此前两条链同时开火，一个源审两遍、`audit_log`
  落两行。②在 `save_source`，③在检测流水线每源复跑（**故意再审**：源可能已被手改）。
- **audit_log 落库为本服务新增职责**：每次审计（含干净源）写一行 audit_log，missing_apis 存 JSON 文本；`list_logs(source_id)` 只读查询。

## 4. 与契约的偏差（均为最小实现/并行协调所需，已留中文注释）

1. **取消方法命名**：契约字面为 `stop()`，但 `Service` 基类已有 async 生命周期 `stop()`（状态机 STOPPING→DISPOSED）。为不破坏生命周期，在跑检测的取消同步方法命名为 `cancel()`，生命周期停止走基类 async `stop()`（`on_stop()` 内调 `self.cancel()`）。
2. **repair 签名**：契约字面 `repair(book_url)`，本壳按底层 `diagnose_content_rule` 真实签名取 `repair(source, chapter, *, extra_chapters, book, engine, timeout)`——底层是 M2 冻结副本，签名不可改。
3. **events.py 三事件**：D 项本应由本线追加，实际并行子代理已在 `app/core/events.py` 按契约同字段定义（CheckFinishedEvent/RepairReportReadyEvent/ImportFinishedEvent + SourceChangedEvent），本线直接 import，未重复定义。
4. **BookSource 对象审计入口**：`BookSource.from_dict().to_dict()` 会滤掉未知 ruleContent 字段，故对 BookSource 对象不再断言 unknown_fields（dict 原始 JSON 入口仍能检出）。
5. **CheckFinishedEvent→RuleRepairService 自动串联**：按任务「可选、最小实现仅 UI 触发」要求，未做自动串联。
