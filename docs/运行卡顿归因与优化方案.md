## 1. 结论一句话

「偶尔会卡」不是引擎算得慢，也不是数据库排队，而是**一条事件触发的整表重取被连发很多次**，
加上**界面 isolate 上同步的逐字节搬运**。前者是可数的风暴（1371 条批量禁用 = 1371 次整表重取），
后者是有固定单价的钱（≈34 ms/MB，其中 ≈2/3 在 Dart 侧的读写循环里）。

落地之后（§5）：整表重取的单价 7.447 → **3.735 ms**（读法那一改，6.82×），
一窗 60 条事件的重取次数 60 → **1**，全选 1371 条批量禁用从**环里 1371 帧 / 界面 1371 次重取**
变成**1 帧 / 1 次重取**，那一发调用自己的墙钟 **879.6 → 33.3 ms**（逐条 autocommit 合成一条事务）。
剩下的最大一块是 `jsonDecode`：`source_list` 那发 1.824 ms、`source_export` 那发 **137.477 ms**——
它不在本轮射程里（要动的是载荷形状，不是搬运形状）。

| 一个 250 ms 窗口里的事件数 | 一发 poll 载荷 | 该发总耗时 | 每条事件 |

### 2.6 三个 `source_list` 读数口径不同，不许混用

安静上下文单发 **1.769 ms**（B3 空闲臂）→ 夹在一次 11.3 MB 导出与 1371 行模型构建旁边 **7.235 ms**（C1 底价臂）→ 阶梯里 390 ms 那一发后面 **8.12 ms**（A 臂）。
差量全是**同一 isolate 上的堆压力**（记忆 `bench-replay-must-drop-previous-graph`）。这条本身就是「大载荷会把身边一切都变贵」的证据，也是 §4-M4 的立足点。

## 3. 一根需要点名的仪器分歧

B2 那条微环（2000×3 次「每次 open+lookupFunction」）读到 **111.18 µs/对**（缓存复用臂 6.26 µs/对）。
生产分段表（§2.1 的「查表」列）在同一发调用里读到的是 **0.02–0.04 ms/发**。
后者放不下前者：一发 `engine_poll` 总账才 0.15 ms，装不下 2 对 × 111 µs。**判定 B2 的绝对值是微环自造的**
（环里没有别的活，`DynamicLibrary.open` 产生的句柄/闭包回收全挤在计数窗口里）；本轮**不据此立任何目标**，
缓存句柄那一改按 §2.1 的 0.02–0.04 ms/发 记功，量级为「小而确定」，不是卡顿主因。

## 4. 优化设计（四条，按性价比排序）

### M1 事件合流（治风暴，客户端一处）✅ 已落地

现状（改前）：[`events()`](../legodo_dart/lib/core/rpc/ffi_engine_adapter.dart) 的轮询把一批事件逐条 `add`
→ [`ref.listen` 每条回调一次](../legodo_dart/lib/core/events/event_listener.dart#L24)
→ 每屏每件事各发一整次 §2.4 的活。窗口里 60 条 = 60 次重取 = 457 ms。

改法：在 `listenToEngineEvents` 这一处（它就是为「只有一份写法」而存在的）加**同名合流**：
一个回调周期内同名的多条只跑一次，名字之外的过滤语义不动。
落点选这一处而不是各屏，是因为 [event_listener.dart 的头注释](../legodo_dart/lib/core/events/event_listener.dart#L1)
已经把「每屏自己写会飘成三种形状」写成了这一层的立身理由；各屏 debounce 等于把这条规矩再拆一次。

**落地时的落点修正（D2=B 定下来的窗口形状决定的）**：合流放在
[`coalesceBatch`](../legodo_dart/lib/core/rpc/ffi_engine_adapter.dart#L124)，
调用点在 `events()` 把一批轮询结果往 `controller` 灌之前那一步（[:283](../legodo_dart/lib/core/rpc/ffi_engine_adapter.dart#L283)），
不在 `listenToEngineEvents`。理由：D2 选的窗口就是"一个轮询批"，而批在 `events()` 里已经是一份现成的
`List<EngineEvent>`——放到 `event_listener` 那一层要么再自己攒一个缓冲（等于新计时器，D2 明确不要），
要么只能看到已经被拆开的单条事件，合不了。`event_listener` 那层的立身理由（只有一份写法）没被破坏：
它依旧不认识任何具体屏幕。白名单是一条 `const Set`（[:120](../legodo_dart/lib/core/rpc/ffi_engine_adapter.dart#L120)），
进来的判据只有一条：**界面读不读它的 payload**。

### M2 FFI 读写路径（有固定单价的钱）✅ 已落地

- 读：`_readCString` 的逐字节循环 → 先扫终止符（窗口含 0）再 `asTypedList(n).utf8.decode(view)`。§2.2 实测省 2.9 ms/MB。
- 写：`_toNativeUtf8` 的逐字节写入 → `asTypedList(len)..setRange` 一把拷。
- 分配：改前 [`_Mem`](../legodo_dart/lib/core/ffi/engine_ffi.dart#L63) 每次分配都重开 kernel32 再 `lookupFunction` → 句柄与两个函数指针各存一份静态。§2.1 记功 0.02–0.04 ms/发。
三处都在同一文件，互不依赖，可单测（读臂可离屏拿一段真字节验证两臂解出同一串）。

落地后另两笔**当场测出来但没改**的账，记在这里免得下轮重问：

- **要不要给 `Call` 加长度出参**：不要。读臂的底价现读了——`source_list` 那一发「只扫终止符」0.094 ms、
  「已知尺寸原生扫」0.078 ms；`source_export`（12 MB）4.526 / 3.824 ms。加出参最多省 0.016 / 0.70 ms，
  而那要把 ABI 从 `char*` 改成 `(char**, size_t*)`，两侧四份绑定跟着动。**不动。**
- **分配器去掉 `HEAP_ZERO_MEMORY`（0x00000008）**：试过、撤了。12 MB 那一臂两趟 21.98（带清零）/ 21.71 ms（不带），
  270 KB 那一臂 0.608 / 0.648 ms——**差量都在噪声里**。那 1.7 ms/MB 的底价其实是 `utf8.encode` 自己，不是清零。
  既然实测无收益，就留着那遍免费兜底（万一漏写终止符，清零让越界读读到的是 0 而不是堆里的旧字节）。
  这一条已钉进 [`_Mem.malloc`:91](../legodo_dart/lib/core/ffi/engine_ffi.dart#L91) 的注释。

### M3 大载荷不整包过 RPC（11.5 MB 那一发）— 未动，见 §6-D5

`source_export` 单发 **390 ms**（§2.1）——一次同步阻塞 23 帧，用户体感就是「点了导出，整个界面死了一下」。
`import_text` 同理（一次 1371 条源全量进 Dart）。
可选：改成**落盘/读盘路径**（导出写文件、界面只拿统计与文件名），或把这类大动作挂到一次性后台 isolate 上跑。

### M4 逐源发布合成（治源头）✅ 已落地

- 批量启用/删除（改前）：`doSourceBatchEnable` / `doSourceBatchDelete` 逐 url 调 `svc.Enable` / `svc.Delete`，
  而那三条单条口各发一条 `SourceChangedEvent`
  → 全选 1371 条批量禁用 = **1371 条事件** = M1 之前 1371 次整表重取
  （按 §2.4 单价 7.447 ms 折算是 ≈10.2 s 的界面 isolate 占用——这是折算，不是实测墙钟；
  实测口径见 §5 J4），摊在 4 发/秒的轮询里永远排不完。
- 检测自动禁用同一条路（[check_service.go:812](../legodo_dart/backend_go/internal/services/check_service.go#L812) 每条不可用源 `Save` 一次）。
- 对照：导入已经是对的形状——[`ImportSourcesJSON`:289](../legodo_dart/backend_go/internal/services/source_service.go#L289) 事务提交后只发一条 `imported`。

改法：批量动作与一轮检测各自**收尾发一条汇总事件**（payload 带 `count`/`urls` 供界面用），与导入同形。

落地形状：三条静默口 [`SaveSilent`:112](../legodo_dart/backend_go/internal/services/source_service.go#L112) /
[`DeleteSilent`:149](../legodo_dart/backend_go/internal/services/source_service.go#L149) /
[`EnableSilent`:168](../legodo_dart/backend_go/internal/services/source_service.go#L168)
+ 单一发布口 [`publishChanged`:133](../legodo_dart/backend_go/internal/services/source_service.go#L133)
+ [`EnableBatch`:184](../legodo_dart/backend_go/internal/services/source_service.go#L184) / [`DeleteBatch`:217](../legodo_dart/backend_go/internal/services/source_service.go#L217)，
handler 侧 [`doSourceBatchEnable`:657 / `doSourceBatchDelete`:665](../legodo_dart/backend_go/pkg/ffi/engine.go#L657) 不再逐 url 调单条口。

**「与导入同形」含事务那一半**：逐条 `Execute` 时每发一次 autocommit，实测 0.64 ms/行，
1371 行 = **879.6 ms** 同步压在界面 isolate 上（FFI 没有出口，调用方只能干等 53 帧）。
改成一条事务 + 一条 prepared 语句后同一发 **33.3 ms**（§5 J4 追加那一行）。
缓存和广播的次序沿用导入那套：**只在提交成功后**改缓存，`publishChanged` 在事务之外——
「库里真的变了」之后才发声。

**检测那一路没改成一条**（与 §4-M4 原稿的偏离）：一轮检测里逐条发是有意留的，
界面检测屏画的就是"哪一源被自动停了"这一条条；M1 的合流把它兜到**每 250 ms 一拍最多重取一次**
（§5 J4 的 E 臂实测：1371 条逐条发布 → 界面 5 次重取 / 21.8 ms）。

### J4 读数（`.probe/t115d_batch_enable.dart`，环与界面两个**独立**的口，各自一条游标）

- **A 批臂**（`source_batch_enable`，1371 条一次）：环那一头**发了 1 帧**（单轮最多 1 帧，poll 4 次，`lost=false`）；
  界面那一头**收到 1 条 → 重取 1 次**，isolate 被占 **3.5 ms**（0.2 帧）。落库核对：1371 条 `enabled` 全=false、没落地 0 条。
- **B 逐条臂**（M4 之前的形状：逐 url `source_enable` × 1371，同一趟里跑）：环那一头**发了 1371 帧**（单轮最多 1371 帧）。
  这一臂只用来给"环里多少条"定数，界面侧那格**不算数**——主 isolate 正忙着连发 1371 次调用，腾不出手 poll，
  所以它读到"收到 1 条"是仪器自己的形状，不是合流的功劳。M1 的上限由下面 E 臂量。
- **E 后台发布臂**（M1 的账）：另一条 isolate 连发 1371 条 `source_enable`（失败 0 条），界面 isolate 空得下来按 250 ms 一拍。
  发布窗口 **1040.4 ms / 4 拍 → 收到 5 条 → 重取 5 次 = 21.8 ms isolate（1.3 帧）**。
  这就是"发布口没合成"时的上限：**每拍最多重取一次**，与环里躺着 1371 条无关。
- **C 小批正控**（6 条）：1 帧 / 1 次重取（3.7 ms）；**D 空批正控**（`urls=[]`）：`{"updated":0}` 且环里新增 **0** 条。
  这两根是防"整批一条"退化成"什么都不发"和"空批也发声"。
- **归因分记**（判据不许合并）：
  **M4** = 环里帧数 **1371 → 1**（同一批数据、同一次调用）；
  **M1** = 发布口若仍逐条（B/E 那一类），界面重取从「环里几条就重取几次」变成「每 250 ms 一拍最多一次」，
  实测 1371 条 → **5 次 = 21.8 ms**；改前形状按 §2.4 单价折算是 1371 次 ≈ 10.2 s（**折算，不是墙钟**）。
- **追加那一刀（M4 范围内的事务）**：A 臂那一发的**墙钟**在两趟之间 **879.6 → 33.3 ms（26×）**。
  同一趟里逐条臂 B = **987.0 ms**（它逐条 autocommit，没被这一刀碰到）→ 两臂差量就是事务的账。
  这一发是同步压在界面 isolate 上的（FFI 无出口），879.6 ms ≈ **53 帧**——比风暴本身还贵，
  所以它属于本轮要治的卡顿，不是"顺手快了一点"。
- **收尾核对**：探针结束时库里 1371 条、`enabled` 1371 条（各场动作复原后都验过形状，防探针把现场留成脏的）。

## 6. 决策清单与拍板结果（2026-10-16 拍定：D1=A+M4、D2=B、D3=C、D4=B、D5=B、D6=B）

| # | 决策点 | 选项 | 推荐 |
|---|---|---|---|
| D1 | 事件合流落点 | A. 客户端 `listenToEngineEvents` 一处（所有屏同享，语义收口）　B. 各屏自己 debounce　C. 只做后端合成（M4），客户端不动 | **A + M4 一起做**。B 会把「只有一份写法」拆回四份；C 单独用则 RSS/换源那两类逐条进度事件仍裸奔 |
| D2 | 合流窗口取多大 | A. 一个帧周期（16.7 ms，同名合并后跑一次）　B. 一个轮询周期（250 ms，等于"一批一次"）　C. 可配常量并钉死在事件名白名单上 | **B**。事件本来就按 250 ms 一批到，窗口对齐批界最省且不引入新计时器；A 多一条 vsync 依赖，C 是第三条实现 |
| D3 | 哪些事件许合流 | A. `SourceChangedEvent` 一类"只表示库里变了、payload 界面不读"的　B. 所有同名事件都合　C. 逐事件名单（进度类不合，必须逐条画） | **C，一期名单只放 `SourceChangedEvent`**。进度类合流会把"跑到第 37 源"变成跳号，界面那些行靠的就是逐条 |
| D4 | M2 范围 | A. 只改读（§2.2 的钱在读侧）　B. 读 + 写 + 缓存 kernel32 三处全改　C. 不动 | **B**。三处同一文件、都能离屏单测，读臂省 2.9 ms/MB 是实测，写与查表是顺手且量小 |
| D5 | 11.5 MB 导出这一发 | A. 保持现状（用户显式动作，卡 390 ms 一次）　B. 改成落盘，RPC 只回统计与路径　C. 挂一次性后台 isolate（`Isolate.run`），协议面不动 | **B**。C 只把「谁被冻住」换掉，界面侧 await 之后仍要 `jsonDecode` 11.5 MB；B 才是把这钱从界面上拿走。A 是本轮唯一"实测很贵但改动最省"的对照项，若不愿动协议就选 A |
| D6 | 找书 partial 快照（累积推流 O(n²)） | A. 现在就改成增量（动协议面）　B. 先测出这条再定　C. 不管，靠 D1 合流吃掉重取 | **B**。本轮**没测到它**（离线复现需要回环假源跑真 `search.start`），形状可推但代价未知；按「测不出的数字不写、不改」，先立一条测量任务再谈改协议 |

**落地情况**：D1/D2/D3/D4/D6 按推荐落地（读数以 §5 为准）。三处与拍板时的字面不同，都在上面各节写明了理由：
M1 的落点从 `event_listener` 挪到 `events()` 的批边界（D2=B 的窗口形状决定，§4-M1）、
M4 的"与导入同形"补上了事务那一半（§4-M4、§5 J4 追加）、
检测那一路**没**改成一条（保留逐条，由 M1 兜住，§4-M4 末段）。

**D5=B 未落地，因为落点没有消费方**：`exportSources` 在 `lib/` 里只有三处——
接口默认实现 [`engine_repository.dart:220`](../legodo_dart/lib/core/rpc/engine_repository.dart#L220)、

369.636 压到 **244.461 ms**（§5 J3）。等"导出"真做到界面上时，落盘那一改跟它一起做。

## 7. 明确不做 / 已知降级

- 不拆 `StorageService` 的 `s.mu`，不做读写锁（§2.3：打到 1890 发/秒也只贵 0.2–0.3 ms；§5 J5 复跑同量级）。
- 不动 250 ms 轮询本身，不加推送通道（FFI 无出口；底价 0.15–0.22 ms、占空比 0.061%，它不是卡顿源）。
- 不缩 `srcToMap` 投影（[engine.go:1187](../legodo_dart/backend_go/pkg/ffi/engine.go#L1187) 已是 8 个短字段，238 KB / 1371 条 = 每条 174 B，没有可删的胖字段）。
- 不引入 isolate 常驻 RPC 线程（D5 若选 C 也只覆盖大载荷；把每发小调用都挂上消息往返，是把 §2.4 的 7 ms 换成 7 ms + 往返）。
- 找书协议语义一期不动（D6 选 B）。
- **不给 `Call` 加长度出参**（§4-M2：底价现读后省 0.016 / 0.70 ms，不值 ABI 的账）。
- **不动分配器的 `HEAP_ZERO_MEMORY`**（§4-M2：撤了实测无收益，差量在噪声里，留着那遍免费兜底）。
- **不把一轮检测的自动停用合成成一条**（§4-M4 末段：界面画的是逐条；M1 已兜到每拍最多重取一次）。
