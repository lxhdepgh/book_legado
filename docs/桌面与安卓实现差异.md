## 0. 双端全景速览



| 维度       | Legado Android 版                                                                 | 桌面端（本项目）                                                                 |
| -------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 语言 / 运行时 | Kotlin + JVM + Android Framework（minSdk 21 / targetSdk 36，JDK 17）                | Python 3 + Flet（Windows/Linux/macOS，亦可跑 Android）                         |
| UI 组织    | XML + viewBinding，46 Activity + 17 Fragment，系统 Activity 栈                        | Flet 控件树，3 目的地、8 个视图文件，单窗口                                               |
| 异步模型     | Kotlin 协程（Dispatchers.IO/Main + Flow + mapParallelSafe）                          | asyncio + EngineHub 独立守护线程事件循环 + QuickJS 单线程优先级队列                        |
| JS 引擎    | Rhino 1.8.1（真 JVM 互操作，ClassShutter 白名单沙箱）                                        | QuickJS（Python 侧手写 Java API shim，能力面由 `implemented_java_api_paths()` 枚举） |
| HTTP 栈   | OkHttp 5.3.2（单例连接池，可选 Cronet 后端）                                                 | aiohttp（cookie 罐 + 代理复用会话）+ Playwright 浏览器层                              |
| 持久化      | Room 单库 legado.db（v89，22 实体，45 条迁移）                                              | JSON（书源 / 书架）+ SQLite（搜索结果）+ 文件缓存（正文）等共 7 种介质                            |
| 功能面      | 书源管理 / 检测 / 找书 / 换源 / 阅读 + TTS 朗读、RSS、下载、漫画、视频、WebDAV 备份、书源编辑器、词典、本地书、内置浏览器、二维码等 | 书源管理 / 四段检测 / 规则修复 / 找书 / 换源 / 阅读器 / 整书缓存；无 TTS、RSS、下载、漫画、备份、编辑器等（见 §1）  |
| 系统集成     | 11 个 Service + 4 个 Receiver + 通知渠道 + Firebase 统计                                 | 单窗口进程内一切活动，无后台服务、无通知、无媒体按键                                               |
| 分发       | Gradle 出 APK（minify + ProGuard）                                                  | PyInstaller 单文件 EXE + Playwright 分发 + `--smoke-test` 冒烟自检                |

### 1.4 视频书（video 类型书籍）播放模式：面板已接出，形态仍与 Legado 不同

* 状态：~~已确认差异（完全无界面）~~ → **部分消除**（09-27 第二十一轮：播放会话接进阅读器，
  缺的是"独立视频书页"那一层，不再是"整条没有界面"）

* Legado 侧证据：`ui/video/VideoPlayerActivity.kt:96`（视频书播放界面）、`service/VideoPlayService.kt:65`（播放服务，基于 help/exoplayer、help/gsyVideo）、`ui/video/ChapterAdapter.kt`（章节播放列表）；书籍类型 `constant/BookType.kt:14` `video = 0b100`。

* 桌面侧位置（现状）：服务面 `app/services/content/media_play.py`（`MediaPlayService` 播放列表 + 状态机 + 位置落库；`FletVideoBackend` 只在视图层装配，换源的播放意图随 `autoplay` 一条消息下发、叫停在控件上落 `pause()`）；界面面 `app/views/reading/video_play_bar.py`（`VideoPlayBar`：一个播放面 + 播控 + 播放列表弹层，9 个回调槽；播放器事件先过"伪 completed / 伪报错"甄别）+ `app/views/reading/reader_view.py:638`（正文视频块渲染成「在本页播放」条目，**不再内嵌播放器**）；接线 `app/controllers/reader_controller.py:1121-1330`（起播/暂停/上下条/停止/收起/换书叫停 + `MediaPlayStateEvent` 镜像）；进度列 `books.play_chapter_index` / `play_position`（schema v7）。

* 差异说明（还剩什么）：
  1. **形态**：Legado 把"章节即视频 URL"的书整体当成视频书，打开的是独立播放页；
     桌面端是**阅读器正文里的一块面板**——正文视频块与视频书共用同一条链路（连读几章
     就攒几条），没有全屏播放页；
  2. ~~**不自动接下一条**~~ —— 第二十二轮已接、**第二十四轮已端到端取证**：
     `flet_video` 的 `on_complete`（只认 `data` 为真的那一发）→ `VideoPlayBar.on_ended` →
     `ReaderController.video_ended` → 服务 `mark_ended()` → 按列表顺序点下一条
     （只认"正在放"、等落库期间换条/切页就放弃、报错**不**连播）。离线浏览器探针
     `probe_auto_next.py` 8/8：6 秒假片位置自己走到 4→6，**+6.06s 客户端报片尾**后面板自己
     换到第 2 集、回环假源新增一次 `/clip/ep2.webm` 请求；停止后补发的完成事件不连播；
     最后一条停在 `ended` 不绕回。Legado 侧那半截是服务层连播，不依赖控件；
  3. **书架那行仍显示阅读进度**：视频书没有正文，`chapter_index` 不随播放推进，
     "读到第几章"和实际看到第几集是两码事（v7 把两者分列正是为此）；
  4. **无后台播放**：没有通知栏 / 锁屏 / 媒体按键，切走页面即停（面板随阅读器 detach 停播）。
  5. **web 面（把界面开在浏览器里）看第三方视频书会黑屏**：flet_web 给页面带了
     `Cross-Origin-Embedder-Policy: require-corp`，书源的视频地址在别的主机/端口上，
     源站不回 `Cross-Origin-Resource-Policy: cross-origin` 就被浏览器拦成"没有可用源"。
     这一条不是桌面端代码能补的（要给源站发头），原生窗口面不受影响。
     备注：正文内嵌 `<audio>` 块同理走 `flet_audio`（`reader_view._audio_control`），
     Legado 的 `AudioPlayService` 是后台音频书播放，不属同一功能。

#### 2.A 规则求值与解析语义（条目 2.1–2.12）

### 2.1 XPath 用 elementpath 重写而非 JsoupXpath，扩展函数靠正则改写补齐



* 状态：已确认差异

* Legado 侧证据：`model/analyzeRule/AnalyzeByXPath.kt` `AnalyzeByXPath`/`strToJXDocument`（L27-41），引擎为 `org.seimicrawler.xpath.JXDocument`（jsoup DOM 上的 XPath 实现）；`getStringList` L92-131。

* 桌面侧位置：`services/legado_rule_parser.py` `xpath_values`（L1050-1214），实际引擎是 Python `elementpath`（L1124-1174，注释自承 "without a native extension"），并在求值前用正则把 JsoupXpath 方言改写：`following-sibling-one::`→`following-sibling::*[1]`（L1140-1143）、`first()`→`1`（L1144）、属性比较 `^=$=*=~=`→`starts-with/ends-with/contains/jx-matches`（L1152-1161）、尾部 `html()/outerHtml()/allText()/num()`（L1128-1135）、自定义函数 `substring-ex/substring-after-last/substring-before-last/format-date/sum`（L1064-1123）。

* 差异说明：两端不是同一个 XPath 引擎。Legado 走 JsoupXpath（基于 jsoup 节点树，节点轴与 `asString()` 取值语义固定）；桌面走 W3C elementpath，再用正则把书源里常见的 JsoupXpath 扩展翻译成等价表达式。覆盖到的常见扩展已补齐，但任何未被正则覆盖的 JsoupXpath 私有轴 / 函数（或依赖 jsoup 节点树身份的写法）在桌面会解析失败或取错值。

* 备注：桌面同时复刻了 `</td>`→包 `<tr>`、`</tr>/</tbody>`→包 `<table>` 的片段包裹（`legado_rule_parser.py` L489-492，对应 `AnalyzeByXPath.kt` L29-34），这一处是对齐的。

### 2.3 正则是 Python `re` 转译层，Java 原子组与所有格量词未翻译



* 状态：已确认差异

* 桌面侧位置：`services/java_regex.py` `translate_pattern`（L136-178）把 Java 语法翻成 Python re：命名组→`(?P<n>)`（L158-159）、`\p{}`→按 `unicodedata.category` 扫全码点生成字符区间（L26-58）、内联标志（L160-173）、`\Q..\E`（L146）、`\R\z\G\h\v` 等（L147-155）。对 `(?>` 与 `*+/++/?+` 做全文件检索无任何翻译分支。

* 差异说明：常用特性（命名组、Unicode 属性、懒惰匹配、内联标志、替换串 `$1/${n}`）桌面都已转译；但 Python `re` 本身不支持 Java 原子组 `(?>...)` 与所有格量词 `X*+/X++`，桌面也未做改写。书源正则一旦用到这两种写法语义（用于阻断回溯），Legado 能编译执行，桌面会 `re.error` 或行为退化为贪婪回溯，可能取到不同匹配。

* 备注：影响面取决于真实书源是否使用；这是兼容件 `java_regex.py` 的已知能力上限，建议在 `tests/test_legado_compat.py` 补原子组 / 所有格用例确认。

### 2.13 超时模型：四段 connect/write/read/call  vs 两段 total/connect，且默认总时长大幅缩短



* 状态：已确认差异

## 4. 架构与技术栈差异

### 4.1 语言与运行时完全不同：Kotlin/JVM/Android 平台 vs Python 3 + Flet 跨平台运行时



* 状态：已确认差异

* Legado 侧证据：`libs.versions.toml` `kotlin = "2.3.10"`（L3）、`kotlinx-coroutines-android/core = "1.10.2"`（L21）；`app/build.gradle` `jvmToolchain JavaLanguageVersion.of(17)`（L30-32）、`minSdk 21 / targetSdk 36`（L51-52）；整个应用跑在 Android Framework（`android.app.Application`）之上。

* 差异说明：Legado 是原生 Android 应用，语言 / 标准库 / 线程模型全部建立在 JVM 与 Android Framework 之上；桌面端是 Python 进程内由 Flet 托管 UI 的跨平台应用，同一套代码可跑 Windows/Linux/macOS 与 Android（`platform_support.py` 按 `ft.PagePlatform` 分支）。这决定了后续所有条目（生命周期、线程、存储、系统集成）的差异方向。

* 状态：已确认差异

### 4.15 加密 / 安全面不同：hutool-crypto + Rhino 类白名单沙箱 vs pycryptodome 的 Java 加密 API shim



* 状态：已确认差异

* Legado 侧证据：`libs.versions.toml` `hutool = "5.8.22"`（L43，`hutool-crypto`，L111）；`help/crypto/`：`SymmetricCryptoAndroid.kt`、`AsymmetricCrypto.kt`、`Sign.kt`，供书源 JS 经 Rhino 桥调用；JS 侧沙箱为 `RhinoClassShutter`（`RhinoScriptEngine.kt` L325）限制脚本能反射到的 Java 类。

* 桌面侧位置：`requirements.txt` `pycryptodome>=3.20`（L16）；`app/services/legado_js.py` L5976 起在 Python 侧实现 `AES/ARC2/ARC4/Blowfish/DES/DES3/ChaCha20-Poly1305/RSA(PKCS1_v1_5/OAEP)/ECC` 全套 Java 加密 API 的等价 shim，L316-327 另用 AES-ECB 加密本机登录态。

* 差异说明：两端加密库选型不同（hutool vs pycryptodome），但定位一致 —— 都是给书源 JS 提供 `java.encrypt` 类能力。真正的架构差异在沙箱：Legado 脚本能触达多少 Java 类由 ClassShutter 白名单决定，桌面端脚本可触达的能力面完全由 Python 侧手写注册了哪些 API 决定（`implemented_java_api_paths()`），天然更窄。

* 差异说明：Legado 有完整的崩溃落盘、远程统计和多语言 / 夜间资源体系；桌面端是单人桌面工具取向，没有日志框架、没有崩溃上报、界面不做国际化。这对 "线上问题排查" 的运维能力差距很大。
