# 找书与换源逻辑：Legado 参考实现与本项目对齐情况

本文整理 Legado Android 版（`other_history/legado-main`，只读参考）的**全书源找书**与**书籍换源**逻辑，
以及两处功能依赖的配套逻辑，并逐条标注本项目（Flet 桌面端）的对齐方式与落地位置。

- 参考源码根：`other_history/legado-main/app/src/main/java/io/legado/app`
- 本项目实现：`app/services/search_model.py`、`app/services/engine/rule_engine.py`、
  `app/services/reading/reading_service.py`（编排）、
  `app/controllers/find_books_controller.py` / `bookshelf_controller.py` /
  `reader_controller.py`（界面装配）、
  `app/views/reading/find_books_view.py` / `source_switch_dialog.py` / `reader_view.py`（纯控件）
- 回归测试：`tests/test_legado_compat.py`（`SearchModelTests`、merge 语义）、
  `tests/test_reading_services.py`（搜索编排 + 换源扫描）、

  `tests/test_offline_source_chain.py`（本地假源端到端链路）

## 1. 找书（全书源搜索）

### 1.1 一轮搜索的生命周期

`model/webBook/SearchModel.kt`

| 行为 | 参考实现 | 说明 |
| --- | --- | --- |
| 新搜索 | `search()` L52-73：`searchId != mSearchId` 且 key 非空 → 关掉上一轮、清空结果、按范围重取书源、`searchPage = 1` | 用 searchId 判断"新一轮"还是"翻页" |
| 翻页 | 同 id 再次调用 → `searchPage++` | 分页状态跟着模型走，界面不用自己记页号 |
| 书源为空 | `callBack.onSearchCancel(...)` 直接返回 | 空范围是取消，不是失败 |
| 逐源搜索 | `startSearch()` L76-113：`mapParallelSafe(threadCount)` + 每源 `withTimeout(30000L)` | 慢源 30 秒出局，不拖整轮 |
| 并发上限 | `threadCount` 默认 32；OkHttp 侧另有 `min(threadCount, MAX_THREAD=9)` 的派发池 | 32 是在飞请求数，9 只是派发线程数 |
| 命中续页 | `hasMore = hasMore || items.isNotEmpty()` | 只要有一个源返回过结果就允许继续翻页 |
| 停止 | `close()` L212 取消 job 并关闭池；`pause()/resume()` 用 `workingState` 门在源之间挂起 | 暂停粒度是"源与源之间"，不吃掉在飞请求 |

本项目：`app/services/search_model.py` 的 `SearchModel.search()` 是上述生命周期的移植（searchId/页码/`_generation`/`asyncio.Queue` 工作池）；
上层编排在 `reading/reading_service.py::search_books()`（同 `search_id` 再调即翻页，换 id 取消上一轮），
界面侧 `FindBooksController.search() / load_more() / stop_search()` 只负责带 generation 回写 UI。
`MAX_THREAD` 从参考实现的 9 提到 32，理由写在 `search_model.py` 的 `MAX_THREAD` 附近（我们的 worker 直接持有请求，上限应落在 flow 这一层）。

### 1.2 搜索范围

`ui/book/search/SearchScope.kt`

- 取值：`""` = 全部启用书源；`名称::url` = 单书源；`a,b` = 分组列表（L15-25）。
- `getBookSourceParts()` L108：分组会被修剪（不存在的分组丢掉），全空时回退到"全部启用"。
- 结果按书源 `customOrder` 排序（`BookSourceDao` 查询里 order by）。
- 持久化：分组范围写入 `AppConfig.searchScope`（L148-149）；**单书源范围故意不保存**，避免下次打开还在单源模式。

本项目：`FindBooksController.open_scope()` 出范围对话框，取值常量 `_SCOPE_ALL / _SCOPE_UNGROUPED`
（`app/controllers/find_books_controller.py:32-33`）+ 书源分组去重列表；
范围解析与排序在 `ReadingService.searchable_sources()`：只取启用且带 `searchUrl` 的书源，
按 `(customOrder, bookSourceName)` 排队。
**差异**：选项是「全部书源 / 未分组 / 分组：X」，**没有单书源范围**（Legado 的 `名称::url`）。
参考实现故意不保存单源范围，本项目则尚未提供该入口——单源搜索目前只能靠浏览页选定书源。

### 1.3 结果合并（mergeItems 的四桶语义）

`model/webBook/SearchModel.kt` L116-198。每次收到一个源的结果，就把结果分到四个桶：

| 桶 | 判定 | 排序 |
| --- | --- | --- |
| equal | `name == key` 或 `author == key` | 按 `origins.size` 降序 |
| tags | `kind` 包含 key | 按 `origins.size` 降序 |
| contains | `name` 或 `author` 包含 key | 按 `origins.size` 降序 |
| other | 其余 | 不排序，`precision` 开启时整桶丢弃 |

输出顺序固定为 `equal + tags + contains + other`。去重键是 `(name, author)`，重复时只做 `pBook.addOrigin(nBook.origin)`；
`origins` 是 `@Transient` 的内存集合，**不落库**（`data/entities/SearchBook.kt`）。

本项目：`app/services/engine/rule_engine.py::merge_search_items()` 完整移植四桶与排序（本项目一次调用合并一条新结果，
语义与参考实现逐条合并等价）；`BookItem.origin_set()/add_origin()` 对应 `origins`。
测试：`tests/test_legado_compat.py::test_search_model_merge_origin_precision_and_rank_order`。

### 1.4 结果落库与结果流

`model/webBook/SearchModel.kt` L96-107：每个源返回后依次做四件事
「`releaseHtmlData()` → `searchBookDao.insert(...)` → `mergeItems()` → `callBack.onSearchSuccess()`」。

- 落库：`data/dao/SearchBookDao.kt` L59 `@Insert(onConflict = REPLACE)`，主键是 `bookUrl`，所以同一本书重复搜索是覆盖。
  目的是让**换源列表不用联网就有内容**（见 2.1）。
- 结果流：`ui/book/search/SearchViewModel.kt` L28 `ConflateLiveData(1000)`，
  `postValue` 会把连续刷新合并成"最新的那份"，上限约每秒一次；界面因此不会被上千个源刷爆。

本项目：`SearchModel.worker` 做同样顺序，落库失败只吞掉自己的异常、不影响已合并的结果；
结果流是 `ReadingService._publish_search_partial()`（每合并一个源发一条 `finished=False` 事件）
→ `FindBooksController` 用 `self.throttle(self._on_search_finished, 0.5)` 订阅，
即 0.5s 节流 + 只认最新 `search_id`（迟到快照丢弃）。差异：本项目每次刷新都重建结果列表，
没有"命中数没变就不重绘"的短路——书源量级下开销可接受，真出现卡顿再加回那层判断。
存储实现是 `search_model.py::SearchBookStore`（SQLite，表 `search_books`，主键 `book_url`）。

### 1.5 试读不加入书架（notShelf）

参考实现在详情页点「阅读」时，若书不在书架就写一条**打了 `BookType.notShelf` 标记的 `books` 记录**
（`ui/book/info/BookInfoActivity.kt` L1068-1081，标记定义见 `constant/BookType.kt` L52-54），
书架查询再把它过滤掉（`data/dao/BookDao.kt` L32-34）。要点是：**进度、目录、变量照常写这条记录**，
它只是不在书架列表里出现；退出阅读器时弹「是否将《x》放入书架？」（`ui/book/read/ReadBookActivity.kt` L1691-1716），
选「否」就删掉这条临时记录；`AppConfig.showAddToShelfAlert` 控制是否弹窗；
启动时 `MainViewModel.init` 再清一次残留（`BookDao.deleteNotShelfBook`）。

本项目：`ReadingService.open_book(source, book, shelve=False)` 写一条 `in_bookshelf=False` 的记录
（`is_shelved` / `shelved_books` 判定与过滤，均继承旧 `SourceService`），书架渲染、「继续阅读」卡、
批量刷新都只认 `shelved_books()`；启动清理由 `SourceService.on_start()` 调
`discard_unshelved_books()` 并连带清掉该书的目录/正文缓存。
「加入书架」按钮走 `shelve_book()`：同键已有暂存行时**原地转正**（`promote_to_bookshelf()`，进度保留），
不是当重复拒绝。

退出阅读器的询问已复原（2026-09-25）：阅读器工具栏最左「退出阅读」（`ReaderView.on_exit_reader`）
→ `ReaderController.exit_reader()` 经 `ReadingService.staged_record()` 回拿当前暂存记录 →
弹「是否将《x》放入书架？」→「放入书架」`promote_staged_book()`（进度/缓存不动，原地转正）、
「不放入」`discard_staged_book()`（书架记录 + `books` 表进度行 + 目录/正文缓存一起删），
两条分支都**落回找书页**，非试读的书直接回书架。旧实现见
`old_code/app/views/reading_view.py:2560-2630`。

**当前差异**：
- 只在点「退出阅读」时询问；用左侧导航直接切走不拦（导航层拦切页会波及所有页面）。
- 没做 `showAddToShelfAlert` 开关：Legado 允许关掉这个弹窗，本项目恒定询问。

## 2. 换源

### 2.1 打开对话框：先读本地，再问网络

`ui/book/changesource/ChangeBookSourceViewModel.kt`

- `searchDataFlow` L118-127：先用 `getDbSearchBooks()` 把库里已有的结果灌进列表并 `trySend`（界面立刻有内容），
  **只有列表为空时才 `startSearch()`** 自动联网。
- `getDbSearchBooks()` L399-421：`SearchBookDao.changeSourceByGroup(name, author, sourceGroup)`，
  即"书名相同 + 作者 like + 书源启用 + 书源分组匹配 + 按 customOrder 排序"，
  inner join `book_sources` 让**已删除的书源自动消失**。
- `changeSourceCheckAuthor` 默认 false：默认不按作者过滤，作者只是加分项。
- `refresh()` L163-171 也走同一条读库路径。

本项目：`BookshelfController.open_source_switch()` 打开 `SourceSwitchDialog` 后调用
`ReadingService.switch_seeds(item)`，用 `SearchBookStore.list_by_name_author()` 取本地结果，
过滤掉已删除/已禁用/无搜索规则的书源，直接渲染成候选列表，
状态行显示「本地已有 N 个结果，点"搜索其他书源"可联网核对」；网络扫描仍由用户点击触发。
测试：`tests/test_offline_source_chain.py`（本地种子不联网）、
`tests/test_views_reading_m2.py::SourceSwitchDialogTests`。

### 2.2 一轮扫描

`ChangeBookSourceViewModel.search()` L204-260

- 书源集合：分组为空取全部启用；分组不存在时**回退到全部启用**并清空该偏好（L190-202）。
- 并发：`mapParallel(threadCount=32)`，每源 `withTimeout(60000L)`；失败只吞掉并继续。
- 逐源进度：`onEachIndexed { index, source -> _changeSourceProgress.update { index + 1 to source.bookSourceName } }`。
- 命中过滤：`filter = { fName, fAuthor, _ -> fName == name && (!checkAuthor || fAuthor.contains(author)) }`
  —— **书名精确相等**，作者按需包含。
- 默认不加载详情/目录/字数（`changeSourceLoadInfo/LoadToc/LoadWordCount` 默认 false），
  即"一轮换源 = 每个源一次搜索请求"。

本项目：`ReadingService.switch_source()` 为上述流程：`SWITCH_CONCURRENCY = 32` 的 worker 池
（`asyncio.Queue` + 上限个 worker）、每源 `asyncio.wait_for(..., SWITCH_TIMEOUT = 10s)`、
逐源进度经 `on_progress(completed, total, failures)` 回调（`SWITCH_PUBLISH_INTERVAL = 0.5s` 节流）
刷对话框的进度条与「正在扫描 x/y 个书源，n 个失败」，
失败按原因分类计数（`_switch_failure_reason`：超时 / 网络错误 / 被拦截 / 规则不支持 / 接口未模拟）、
结果同样落库（扫描命中即 `self._search_store.insert(books)`）。
差异：连接阶段超时不在这里设——引擎是池化共享的（`RuleEngineService`，总超时默认 15s），
所以本项目用 `wait_for` 在调用点兜 10s，而不是给一轮扫描新建短命引擎。
旧的「已用 X，预计还需 Y」速度外推文案未保留（只有计数），需要时补在 `on_progress` 的消费侧。
命中判定用书名**包含**关键词而不是精确相等，理由是搜索框允许用户改关键词、站点书名常带卷/后缀；
排序与作者加分见 2.3。
测试：`tests/test_reading_services.py::test_switch_source_scans_concurrently_with_timeout`、
`tests/test_views_reading_m2.py::SourceSwitchProgressTests`（进度回调接到对话框进度条与状态行）。

### 2.3 排序与评分

`ChangeBookSourceViewModel.kt`

- 默认比较器 L90-98：`bookScore 降序 → sourceScore 降序 → originOrder 升序`；
  打开 `changeSourceLoadWordCount` 时换成"有字数优先 → 章节数降序 → 字数降序 → originOrder"。
- 评分存储：`help/config/SourceConfig.kt` L9-30（`setBookScore/getBookScore/getSourceScore`），
  用户对某本书某来源的评分会分给书源总分。
- 读库路径的排序由 SQL 负责：`order by t2.customOrder`（书源顺序）。
- 附加操作：`topSource/bottomSource` 直接改书源 `customOrder`，让这个来源长期排前/排后。

本项目：`ReadingService.rank_switch_matches()` 用
「书名精确相等 → 作者包含（有作者时）→ 书源优先级 → 书源名」排序。
候选优先级来自 `BookshelfController._switch_candidates()`：先排除当前源自身与
未启用/无搜索规则的源，再按「同站点（`_site_token` 主机首段相同）优先，其次书源 URL」排队；
它承担了参考实现里 `originOrder`（书源顺序）+ 同站推断的角色。
本项目没有用户评分体系，故 `bookScore/sourceScore` 两级权重未实现。

### 2.4 提交换源

`ui/book/changesource/ChangeBookSourceDialog.kt`

- `changeTo()` L330-345：先比对书籍类型，类型不同先弹确认。
- `changeSource()` L382-410：`bookMap[primaryStr()] ?: searchBook.toBook()`（复用已加载的详情），
  取目录走 `tocMap` 缓存或 `getChapterListAwait`；文件类书源不解析目录。
- 换源后由 `ReadBookViewModel.changeTo` 落到阅读器：`Book.migrateTo(book, toc)` 决定读到哪一章
  （`help/book/BookHelp.kt` L499-545：标题相似度 `nameSim > 0.96` 或章节号差 < 1），
  然后删旧书行、插新书 + 目录、`resetData()`、`loadContent()`、发 `SOURCE_CHANGED` 事件。
- 源被删除且正好是当前书源时，走 `autoChangeSource()` 兜底（L555-575）：按书籍类型找一个能取到目录的源。

本项目：`BookshelfController._confirm_switch()`（二次确认）→ `_do_switch()` →
`ReadingService.apply_source_switch()` → `SourceService.switch_bookshelf_source()`，
走 `ReadingCache` 清旧源缓存并保留阅读进度（对应 `migrateTo` 的阅读位置续接）。
差异：不做 `bookMap/tocMap` 预取，目录在用户点开书时按需加载；没有换源时加载目录/字数的开关。

## 3. 配套逻辑

### 3.1 HTTP 栈（为什么参考实现"换源很快"）

`help/http/HttpHelper.kt`

- 单例 OkHttpClient：连接池复用、`connectTimeout 15s`、`readTimeout/callTimeout 60s`、`retryOnConnectionFailure(true)`（L59-65）。
- Cookie 按域记忆（`${domain}_cookieJar` 内存缓存，L29-45），代理客户端按代理串缓存。
- 域名连接阶段失败很快就抛，不会占满线程池。

本项目：`LegadoReadingEngine` 的 aiohttp 会话按 `(cookie 罐, 代理)` 复用（见 `docs/` 与
`tests` 中的会话复用回归），换源/找书用的每个短命引擎再单独限连接与总时长。

### 3.2 持久化与过期清理

- `App.kt` L104：启动时 `searchBookDao.clearExpired(now - 1 天)`，搜索结果只保留一天。
- `data/dao/SearchBookDao.kt` L66 `clearExpired(time)`。

本项目：`SEARCH_STORE_TTL_MS = 24h`，`ReadingService.on_start()` 调
`SearchBookStore.clear_expired(now - TTL)`；库落在主库 SQLite 的 `search_books` 表（M6 起不再单文件）。
测试：`tests/test_reading_services.py::test_search_store_seeds_expire_on_start`。

### 3.3 删除书源时的连带清理

`help/source/SourceHelp.deleteBookSource()`：删书源的同时清书源变量、`SourceConfig` 里的评分/变量、缓存。
换源列表因为走 inner join，书源一删条目自然消失。

本项目：换源候选与本地种子都以 `service.sources` 实时解析，书源被删/禁用后自动从列表消失
（`ReadingService.switch_seeds` 的候选过滤与 `BookshelfController._source_by_url` 返回 None 即跳过）。

## 4. 对齐清单

| 参考实现能力 | 本项目 | 落地位置 |
| --- | --- | --- |
| searchId 区分新搜索/翻页、模型内维护页码 | 已对齐 | `search_model.py::SearchModel.search` |
| 每源独立超时、源间并行 | 已对齐（每源 `wait_for` 10s、并发上限 32） | `reading_service.py` `SWITCH_TIMEOUT` / `switch_source` |
| mergeItems 四桶 + origins 聚合 + precision | 已对齐 | `engine/rule_engine.py::merge_search_items` |
| 列表规则空命中时按详情页解析；解析失败退化为空结果 | 已对齐（失败即 0 本书，不再抛错） | `engine/rule_engine.py::search` / `explore_document` |
| 搜索结果落库（bookUrl 主键、REPLACE） | 已对齐 | `search_model.py::SearchBookStore` |
| 搜索结果直接开读（不绕书架页） | 已对齐（结果行与详情框都有「阅读」入口） | `find_books_controller.py::read_book` → `reading_service.py::open_book` |
| 搜索开读不加入书架（`BookType.notShelf`） | 已对齐：暂存记录 + 书架过滤 +「加入书架」原地转正 + 退出时"是否放入书架"询问（放在导航栏切走不拦，见 §1.5 差异） | `source_service.py::is_shelved` / `sources/source_service.py::shelve_book` / `reader_controller.py::exit_reader` → `reading_service.py::staged_record` `promote_staged_book` `discard_staged_book` |
| 退出阅读器询问「放入书架」（`ReadBookActivity` + `showAddToShelfAlert`） | 已采纳（询问复原；开关未做，恒定询问） | `views/reading/reader_view.py` 工具栏「退出阅读」+ `reader_controller.py::_ask_about_staged_book` |
| 启动清理 notShelf 残留（`BookDao.deleteNotShelfBook`） | 已对齐（连带清目录/正文缓存） | `sources/source_service.py::on_start` / `discard_unshelved_books` |

## 6. 速度：单核串行与"规则复用"（2026-09-28 实测）

> 全部数字都是本轮当场测得，基准脚本收工已删除（过程与数字见
> `docs/dev-logs/2026-09-28.md` 第三十～三十三轮）。方法：`aiohttp` 本地回环假源
> （零网络延迟）+ 真引擎，32 个源各搜一次；页面 132KB / 400 条书目；
> 阶段计时靠包住 `ReaderEngine._request_transport / _list_rule_pipeline /
> _books_from_nodes` 与 `parse_markup` 取得，事件循环停顿用心跳协程量。
> 回归护栏见 `tests/test_check_performance.py`（`RuleCompileCacheTests`、
> `SharedConnectorPoolTests`）。**不许拿这些数字去解释真实站点耗时**——回环把网络压成了 0。

### 6.1 慢的不是网络，是单核 CPU 串行

| 阶段（单次搜索，改前 → 改后） | 改前 | 改后 |
| --- | --- | --- |
| 网络 + 解码 | 10.1–10.5ms | 10.2–10.8ms |
| `parse_markup`（html5lib） | 77.7–79.9ms | 76.0–84.3ms |
| 列表规则管线 | 82.7–85.2ms | 81.0–92.6ms |
| **字段规则（400 节点 × 6 字段）** | **210.2–214.5ms** | **109.7–111.1ms** |
| 单次搜索墙钟 | 315.7–317.4ms | 210.1–223.2ms |

"改前"这一列不是翻旧提交，是**同一脚本运行时把本轮加的三处缓存关掉**测的
（旧提交里 `select_jsoup` 还没有计划这一层，直接对比会混进结构差异）。

32 源扫描：1 个 worker 11313.9ms（改前）→ 7440.2ms（改后），
32 个 worker 10816.7/10644.4ms → 7105.0/7075.5ms，**加速比改前改后都是 1.05×**；
心跳协程本该每 10ms 醒一次，改前停顿合计 10150ms / 墙钟 10644ms（**95%**，最长 1083ms），
改后 6631ms / 7076ms（**94%**，最长 909ms）——
**墙钟的九成是循环被一段 Python 计算占住**，不是等待。
收益全部来自"少做事"，一条线程也没多开：并发不提速这一点改动前后一样。

参考实现快在这里：Legado 的 32 是"在飞请求数"，请求跑在 OkHttp 自己的派发线程上，
解析在 `min(32, MAX_THREAD=9)` 条**真操作系统线程**上并行；本项目的并发写死在代码里
（`reading_service.py:52 SWITCH_CONCURRENCY = 32`、`check_service.py` 的
`CHECK_CONCURRENCY = 8 / CHECK_MAX_CONCURRENCY = 16`），且经 `EngineProxy` 派发到
**EngineHub 的一条循环线程**（`app/core/engine_worker.py`），32 是 32 个协程，
CPU 密集段完全不并行。
GIL 侧实测印证：4 段 html5lib 解析，顺序 339ms vs 4 线程 345ms（0.98×）——
纯 Python 解析开线程不会变快，只有换 C 扩展（lxml 22.9ms / html.parser 33.5ms /
html5lib 74.9ms，同页面对同一文档）或上进程池才有效。换 builder 会改树形与
空白语义，与 §1–§3 已经钉死的 Jsoup 对齐结论冲突，本轮**不动**。

### 6.2 已经落地的两条

1. **规则文本级复用**（`app/services/engine/legado_rule_parser.py`）：
   字段规则要对 400 个节点各跑一遍，而选择器文本只有一个，重写结果却按节点重算。
   新增 `_JsoupPlan` + `@lru_cache(512) _cached_jsoup_plan`（把选择器重写、
   `##`/`@` 拆分、伪类剥离这些**只跟文本有关**的活挪出 DOM 循环），
   `_split_rule_expression`、`_jsoup_part` 同样上缓存；
   `*|` 那条要从当前节点标签名展开通配，结果随 context 变，**留在不缓存的路径**。
   XPath 侧早有 `_path_steps` / `_step_parts` 两条缓存，这次补的是 Jsoup 那半边。
   效果：字段规则 210–214ms → 110–111ms（−48%），32 源扫描 10644–10817ms → 7076–7105ms（−34%）。
2. **连接池按事件循环共享 + 引擎池上限 8→32**（`rule_engine_service.py`、
   `rule_engine._session_for`）：池小于并发数时扫描会把引擎连同它的会话一起淘汰；
   引擎本身实测构造 0.55ms、`aclose()` 0.09ms，省下的只是对象，丢掉的是热连接。
   现在 `TCPConnector(limit_per_host=5, resolver=dns_ip_resolver())` 按循环建一条、
   会话以 `connector_owner=False`
   挂上去（对齐 OkHttp 单例 client 的 ConnectionPool；代理会话仍自建 connector）。
   **resolver 必须与引擎自建那条同值**：dnsIp 钉表（[M1-2.14]）挂在 resolver 上，
   共享池少带它 = 走池的引擎悄悄不再按钉表解析，而回环假源是 IP 字面量、根本不走解析，
   基准与套件双双全绿也照不出来（护栏 `test_shared_connector_keeps_the_dns_ip_resolver`
   钉住两侧类型）。
   **回环基准量不出收益**（pool32 6637/6716ms、pool8 6669/6579ms、
   私有 connector 6602/6653ms——同进程对照，差异在噪声内），因为假源全站同主机、
   零延迟；它的价值在真实多主机 TLS 场景少重握手，本轮不给它编数字。

### 6.3 "为什么现在没有解析复用"——三层答案

| 层次 | 现状 | 能否复用 |
| --- | --- | --- |
| 规则**编译** | `compile_rule_program` 早就 `@lru_cache(4096)`、XPath 的 `_path_steps/_step_parts` 也有，缺的是 Jsoup 那半边 | ✅ 本轮已补（§6.2-1） |
| 规则**求值**（同一选择器 × N 节点） | soupsieve 自己缓存编译后的 pattern（`css_parser._cached_css_compile`），慢在**匹配**不在解析 | ⚠️ 只能换更快的匹配器，语义会变，不动 |
| **已解析文档** | 每个响应只解析一次（`parse_markup` 调用数=1）；跨阶段（详情→目录→正文）拿的是三份不同文档 | ❌ 没有第二次解析可省；Legado 的 `AnalyzeRule` memo 也是按文档记的 |

所以"少解析一遍"这条真正的漏点不是文档解析了两遍，而是**规则被重算了 N 遍**——已修。

### 6.4 JS 那条我原来的判断是错的（记下来免得再提）

曾建议"没有 jsLib 的源也共享 JS scope"。拆开销实测：单次求值 9.08ms，其中
`ctx.eval` 原生段 7.78ms（一次求值提交 3 段、合计 16461 字符），
`quickjs.Context()` + `set_memory_limit` 只 0.14ms，109 次 `add_callable` 与其余
Python 侧合计 1.29ms。**9.08ms 里约 86% 是那段 ~16 万字符 bootstrap 每次重新编译**，
而共享 context 并不省它——现有 jsLib 路径同样每次重_eval bootstrap
（`bootstrap + library_program + rule_program`，只有 `library_program` 免了）。
再核对参考实现：`SharedJsScope.getScope()` 对 `jsLib.isNullOrBlank()` **直接返回 null**，
并对共享 scope 调 `scope.preventExtensions()` 挡住隐式全局——
Legado 对无 jsLib 的源本来就是不共享作用域，而且它的 `java/source/cookie/cache`
是 `bindings["java"] = this` 放进的**宿主对象**，不是一段重编译的 JS。
所以：①按原方案做只有 ~0.2ms/eval 的收益；②还会把隐式全局泄漏进共享作用域
（反而偏离参考实现）。**本轮不做**。真要快，路径是把 bootstrap 拆成
"每 context 一次"的静态段与"每次求值"的动态前缀（21 个插值孔全在 L931–L990
与两处运行时常量上），那是一次需要逐值审计 2700 行 JS 的改造，风险与收益不匹配，
留作后续并单独评审。
