## 2. 架构与关键决策

### 2.1 ReadAloudService（§1.1 / §9.2 TtsBackend）

- **`TtsBackend` 抽象基类**：`speak(text, opts)` / `stop()` / `is_speaking()` / `state`，
  外加 `available`（后端是否可用）与 `last_error`（降级原因）。
- **SystemTtsBackend**：pyttsx3 桥。`pyttsx3.init()` 包在 try/except 内——缺驱动/无
  音频设备时**不抛崩**，置 `available=False / state=error`，由服务自动回退。
  `runAndWait` 阻塞，经 `asyncio.to_thread` 挪到工作线程，不卡事件循环。
- **EdgeTtsBackend**：edge-tts 在线神经语音。`import edge_tts` 失败即降级。
  M4 完成"合成取流"链路；真实出声播放接 flet_audio 属 M5（服务零 flet，不直连控件）。
- **HttpTtsBackend**：书源规则 HTTP-TTS。按 `opts["url"]` 模板（`{text}` 占位，URL 编码）
  拼地址，经可注入 `fetcher(url, headers) -> bytes` 拉音频流。默认 fetcher 经
  `_default_http_fetcher` 接到 RuleEngineService 池化引擎的 `fetch_media`（会话复用 /
  Range 续传 / UA / cookie 一致，§2.22）。测试注入 stub fetcher，不发真实请求。
- **自动回退**：`_resolve_active(engine_type)`——请求后端不可用时按
  edge→http→system 回退，验收不绑定单一引擎（§8.4 风险清单）。
- **tts_profiles CRUD**：`list_profiles / add_profile / remove_profile`，headers 存 JSON。

### 2.2 MediaPlayService（§1.4 / §9.2 VideoBackend）

- **`VideoBackend` 抽象基类**：`open(media_url, headers)` / `play` / `pause` / `seek` /
  `stop` / `state`。
- **FletVideoBackend**：flet_video 控件后端（三端主路径）。原设计「只在视图层实例化并注入控件」；
  **2026-09-27 复核：这条从未成立**——视图层没有任何地方实例化 FletVideoBackend（实测仅测试代码构造），
  MediaPlayService 在 app/ 下零调用方；阅读器正文内嵌视频由 `app/views/reading/reader_view.py:531-537`
  直接 `import flet_video as ftv` 自建 `ftv.Video`，**完全绕过本服务**（无播放列表/seek/进度落库）。
  服务层零 flet import、经鸭子类型调控件的约定本身不变，但没有视图把控件接到服务上。
  > **2026-09-27 第二十一轮更新：上面这条复核结论已不成立。** 视图侧接出了
  > `views/reading/video_play_bar.py`（`FletVideoBackend` 现在由 `ReaderController` 在起播时
  > 实例化并注入控件，reader_controller.py:1195），`reader_view` 不再自建播放器；
  > 播放位置也已从 `chapter_index` 分出（schema v7 `books.play_chapter_index`，见下条与
  > `current-system-design.md` §5.12/§6）。
- **SystemPlayerBackend**：降级后端。平台分支收敛在后端内——Windows `os.startfile` /
  macOS `open` / Linux `xdg-open`（subprocess），无图形环境/无关联播放器时置 error。
  不进主路径（§1.4）。
- **open_book**：章节列表即播放列表；**play_chapter / pause / resume_playback / seek**；
  播放位置落 books 表（v7 起为 `play_chapter_index` + `play_position`，
  **不再借用阅读进度的 `chapter_index`**）。
- **视频扩展名集合**：`from app.services.engine.reading_engine import _MEDIA_EXTENSIONS`
  复用（`{"mp4","m3u8","webm","mkv","mov","flv","ts","m4v"}`），未改该文件；
  导出 `VIDEO_EXTENSIONS` 与 `is_video_url()`。

## 3. schema v4（契约 §8）

`_migrate_v4(conn)` 做两件本线交付：

1. `CREATE TABLE IF NOT EXISTS tts_profiles`（id/name/url/headers(JSON)/engine_type）
   + `idx_tts_profiles_engine`；
2. `ALTER TABLE books ADD COLUMN play_position REAL NOT NULL DEFAULT 0`（幂等：先查
   `PRAGMA table_info`，列已存在则跳过）。

**与 RSS 线的合并约定**：v4 是 M4 四线共享迁移点。本线只写 tts_profiles +
books.play_position；**RSS 线应在 `_migrate_v4` 函数体内追加 `rss_sources`/
`rss_articles` 等表 DDL（追加，不要整体替换本函数）**。books 表播放章节索引**复用
v2 已有 `chapter_index`**（契约 §8"以 v2 实际列名为准"），仅补秒级 `play_position`。

## 5. 与契约偏差

- **无功能性偏差**。两点实现取舍（不改变契约语义）：
  1. **HttpTts 出声播放**：M4 按契约"可实现基础请求"，只完成取流（fetch_media 复用 +
     stub 可测）；真正把音频流传给播放器播放留待 M5 接 flet_audio。契约 §5 原文即
     "M4 可实现基础请求，音频流缓存经 BookCacheService"。
  2. **BookCacheService 音频流缓存**：M4 未实际接盘（HttpTts 取到字节即记录
     `last_request`），缓存落 reader-cache 的串联留待与播放后端接通时补；接口已留
     （ReadAloudService 构造参数 `cache`）。
- **SystemTtsBackend 测试策略**：按契约"pyttsx3 无音频设备环境不可用属预期，测试用
  stub 后端"，单测中除降级路径外**不真实实例化 SystemTtsBackend**（避免 SAPI 拉起
  污染共享 engine 线程）。

## 6. 跨平台冒烟清单（§1.1 / §1.4 跨平台策略）

- 纯 Python 路径（三端一致，无平台分支）：TtsBackend 抽象 / ReadAloudService 状态机 /
  tts_profiles CRUD / MediaPlayService 播放列表与落库 / 事件发布。
- 平台分支（已收敛在后端内）：
  - SystemTtsBackend：pyttsx3 内部按平台选 SAPI(Win)/NSSpeech(mac)/espeak(Linux)；
    加载失败即降级回退 edge-tts，不绑定单一引擎。
  - SystemPlayerBackend：Win `os.startfile` / macOS `open` / Linux `xdg-open`，经
    `sys.platform` 分支；仅降级路径，非主路径。
- 主路径 flet_video / flet_audio：契约设想由视图层在桌面三端装配，服务层零 flet 依赖。
  （2026-09-27 复核：朗读已按设想接致——`ReadAloudBar` 在视图层装配；flet_video 主路径**未兑现**，
  视图层唯一 flet_video 使用点是 reader_view.py:531-537 内嵌视频，直建控件不经 MediaPlayService。）
