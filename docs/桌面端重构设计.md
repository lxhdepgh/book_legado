### 0.2 复用资产清单（决策 4 的落点）

核心资产**只加壳、不改行为**，外壳化后进入新架构：

- **规则兼容层**（`app/services/` 下原文件）：`legado_rule_parser.py`、`rule_engine.py`、`reading_engine.py`、`legado_js.py` + `java_regex.py` / `icu_charset.py` / `custom_url.py` / `public_suffix.py` / `query_ttf.py` → 收编进 `RuleEngineService`；修复项（差异 §2 网络/规则组）在壳内原位增强，行为对齐由差分工具与 `test_legado_compat.py` 守门。
- **检测/修复/审计**：`check_service.py` → `SourceCheckService`；`rule_repair.py` → `RuleRepairService`；`compat_audit.py` → `CompatAuditService`。
- **浏览器层**：`headless_browser.py` / `interactive_browser.py` / `web_page_renderer.py` / `block_pages.py` → `BrowserService`（+拦截识别作为共享工具随检测/修复使用）。
- **缓存与进度**：`book_cache_service.py` → `BookCacheService`；`reading_progress.py` → `ReadingService`；`search_model.py` 的 `SearchModel`/`SearchBookStore` → 阅读域（搜索模型随 `SourceService` 换源链路 + `StorageService` 落库）。
- **业务服务**：`source_service.py` → `SourceService`；`engine_worker.py` → `EngineHub`（升级为全服务执行域）；`theme_service.py` → `ThemeService`。

明确**新写**（Legado 有、桌面无对应资产）：TTS/朗读、RSS、本地书解析、导出、WebDAV、下载中心、媒体播放、书签、内容搜索、全局替换、词典、字体、二维码、自动更新、Web 桥、在线导入、书源编辑视图、漫画数据服务。

### 0.3 全局约束（升级自 `docs/architecture-rules.md`）

1. 不引入新的 JS 引擎：`@js:` 规则只走 QuickJS（`legado_js.py`）。
2. 规则行为必须与 Legado 原版对齐：新能力先对照参考实现再进实现；行为差异记录到差异文档并对齐（本文 §2 为修复清单）。
3. 不修改只读参考目录 `base_history/`、`other_history/`。
4. 智能体不擅自提交（git-workflow）。
5. 密钥不入库（secrets-policy）。
6. **任何服务不得跑在 Flet 事件循环上、不得持有 Flet 控件**（由"引擎红线"升级为全服务约束）；服务触 UI 仅允许经 `BrowserService` 的交互回调解耦。
7. 搜索/换源的并发与取消语义不得破坏（SearchModel searchId/页码/generation、换源本地种子+联网扫描+候选排序）。
8. 存储收敛：新功能一律走 `StorageService`；"书"的记录不允许出现第三份重复库（目标见 §6）。
9. 测试护栏：核心资产外壳化不得改变行为——差分工具 + `test_legado_compat.py` 作为外壳化守门；新增逻辑附 `tests/test_*.py`。
10. 服务间通信只经 `EventBus` 或显式接口方法，禁止服务 A 直改服务 B 内部状态。
11. 跨平台约束：任何新外部依赖必须 Windows/macOS/Linux 三平台可用；平台专属 API 一律后端抽象（见 §1 各条目跨平台策略）。

### 0.4 冻结服务词汇表

基础设施（core/）：`ServiceHub`、`EventBus`、`EngineHub`、`StorageService`、`SettingsService`。

业务服务（services/，按域）：书源域 `SourceService`、`SourceCheckService`、`RuleRepairService`、`CompatAuditService`、`OnlineImportService`；阅读域 `RuleEngineService`、`ReadingService`、`BookmarkService`、`ContentSearchService`、`BookCacheService`、`DownloadService`、`ImageBookService`；内容形态域 `ReadAloudService`、`MediaPlayService`、`RssService`、`LocalBookService`；工具域 `ReplaceRuleService`、`DictService`、`FontService`、`QrCodeService`、`BookExportService`、`WebDavService`、`UpdateService`、`WebBridgeService`、`BrowserService`、`ThemeService`。

各服务职责见 §4.2 表；书源代码编辑器不设独立服务（校验归 `SourceService`+`CompatAuditService`，编辑器 UI 属视图层，见 §7）；改封面归 `SourceService`（封面字段维护 + Pillow 图片处理）。

## 1. 功能复刻归属（差异 §1 的 19 项 → 新架构服务）

> 本分节覆盖差异文档 §1 全部 19 项（1.1–1.19）；1.1/1.2/1.5 由整合方种子条目并入，其余 16 项（1.3/1.4/1.6–1.19）按基线第三节冻结服务清单归属。

### 1.1 未实现 TTS 语音朗读（后台朗读服务）

- 承接服务：`ReadAloudService`（新建，services/content/）
- 关键依赖：`RuleEngineService`（HTTP-TTS 与朗读文本规则求值、cookie/代理/超时语义复用）、`ReadingService`（朗读进度与续读位置）、`BookCacheService`（音频书流缓存）；外部库 `pyttsx3`（系统 TTS 桥：Windows SAPI / macOS NSSpeech / Linux espeak）
- 跨平台策略：抽象 `TtsBackend` 接口（系统 TTS / edge-tts 在线 / HTTP-TTS 书源三种后端）；桌面无通知栏与媒体会话，播放控制由 Flet 迷你播放条 + 全局快捷键承担；无后台保活需求（窗口即进程）
- 与核心资产关系：HTTP-TTS 请求语义复用 `RuleEngineService` 网络栈（差异 §2 网络项修复后与 Legado HttpHelper 一致）；`speak_text/speak_speed` 变量已存在于 legado_js 规则上下文（差异 §1.1），规则层无需改动
- 迁移阶段：M4（先系统 TTS 最小可用，HTTP-TTS 随网络栈修复后接）

### 1.2 未实现 RSS 订阅

- 承接服务：`RssService`（新建，services/content/）
- 关键依赖：`RuleEngineService`（feed 抓取与规则订阅求值复用）、`StorageService`（表 `rss_sources` / `rss_articles` / `rss_read_records` / `rss_stars`，对标 Legado 4 实体）；外部库 `feedparser`（标准 feed 解析）+ 规则引擎兜底
- 跨平台策略：纯 Python，无平台 API 依赖
- 与核心资产关系：feed 抓取走 `RuleEngineService` 网络栈（会话复用、UA 可配、超时语义一致）；文章正文/列表解析用 `legado_rule_parser` 规则体系
- 迁移阶段：M4

### 1.3 未实现漫画（image 类型书籍）专用阅读器
- 承接服务：`ImageBookService`（新建，`services/reading/`）；协作 `ReadingService`（章节/正文取数）、`BookCacheService`（图片缓存）。
- 关键依赖：`RuleEngineService`（image 类型书仍走现有章节规则管线解析出图片 URL 列表）；`BookCacheService` 图片内联与预取；`StorageService` 主库 `books` 表的 `bookType=image` 标记；文件目录 `image-cache/`（漫画页图）。
- 跨平台策略：纯 Python + Flet。纵向无限滚动用 Flet 可滚动容器实现，三端一致；漫画色彩滤镜（灰度/电子墨水变换）由 Pillow 预渲染图片完成，不依赖平台图像 API；大图分块懒加载、磁盘缓存命中率三端对齐，无平台分支。
- 与核心资产关系：新写。阅读视图侧把现有 `views/reading_view.py:3490` 把图片块当 `ft.Image` 线性内嵌排列的经验抽出来，重构为独立的漫画渲染通道；章节解析直接复用 `reading_engine.py` 的 `chapters`/`content` 管线，不另写解析；`book_cache_service.py` 的图片内联能力复用。
- 迁移阶段：M2

### 1.4 未实现视频书（video 类型书籍）播放模式
- 承接服务：`MediaPlayService`（新建，`services/content/`）；协作 `ReadingService`（章节列表即播放列表、播放位置落 `books` 进度）。
- 关键依赖：`flet-video` 播放控件（已在 requirements.txt）；`RuleEngineService` 复用 `reading_engine.py:156` 的视频扩展名集合 `{"mp4","m3u8",...}`；`StorageService.books` 表播放进度字段；`EventBus` 推送播放进度事件。
- 跨平台策略：播放后端抽象接口 `VideoBackend`，桌面三端默认统一走 `flet-video`；m3u8/HLS 与 DRM 能力受该后端限制，不承诺超集。仅当 `flet-video` 在某平台不可用时降级为"用系统默认播放器打开 URL"（Windows `os.startfile` / macOS `open` / Linux `xdg-open`），降级分支做成可选后端，不进主路径。
- 与核心资产关系：新写。现有 `views/reading_view.py:3505-3511` 的正文内嵌单 `<video>` 块是"正文流里嵌一个控件"形态，本条目把播放会话/播放列表/记忆位置抽成独立服务；`reading_engine.py` 的视频扩展名集合复用。
- 迁移阶段：M4

### 1.5 未实现 WebDAV 云备份/恢复与远程书籍

- 承接服务：`WebDavService`（新建，services/tools/）
- 关键依赖：`SourceService`/`ReadingService`/`RssService`/`ReplaceRuleService` 等（备份对象导出为 JSON/文件流）、`BookExportService`（导出产物上传）、`StorageService`（备份包落盘与导入）；外部库 `webdavclient3`（纯 Python）或基于 aiohttp 自实现（复用网络栈语义）
- 跨平台策略：纯 Python；桌面无 Android 系统备份框架，备份编排为"导出 zip → 上传"，恢复为"拉取 → 校验 → StorageService 导入"
- 与核心资产关系：无规则层依赖；备份 JSON 结构与 Legado 备份格式对齐（跨平台互操作）
- 迁移阶段：M5

### 1.6 未实现书源代码编辑器（带语法高亮的规则编辑器）
- 承接服务：不设独立服务。主承接 `SourceService`（复用重构，`services/sources/`，书源 JSON 校验/保存/CRUD）；协作者 `CompatAuditService`（保存即触发 JS/Java API 支持面静态审计）；编辑器 UI 属视图层（新增 `CodeEditorView`）。
- 关键依赖：`SourceService`（落 `StorageService.book_sources` 表）；`CompatAuditService` 复用 `compat_audit.py`；可选"单条规则试跑调试"复用 `RuleEngineService` 的 `extract_values`/单字段求值；语法高亮词表来自 `legado_rule_parser.py` 的规则关键字。
- 跨平台策略：纯 Flet 自绘编辑器（输入框 + 分词高亮层），三端一致；不引入 Web 系 code editor 以免拖入第二套 Chromium 渲染依赖（红线 1：不引入新 JS 引擎同理控制膨胀）。
- 与核心资产关系：`SourceService`、`CompatAuditService` 复用重构；编辑器视图新写（差异文档确认 `app/` 全目录 0 命中）。

### 1.9 未实现阅读字体文件选择与字体管理

### 1.10 未实现二维码扫描与生成

- 与核心资产关系：新写（差异文档确认 `app/` 现 0 命中）。

### 1.11 未实现本地书导入与本地文件解析（epub/mobi/pdf/umd/txt）

## 4. 服务架构设计

### 4.1 设计原则

- **进程内多服务**：全部服务跑在主进程内（决策 2），无独立进程、无跨进程 IPC；并发与隔离由 `EngineHub` 事件循环与协程保证。
- **仿 Legado service/ 职责划分**：以差异文档对 Legado `service/` 包的读码证据为参照（TTSReadAloud/HttpReadAloud/AudioPlay → 桌面 `ReadAloudService` 三合一；CacheBook → `BookCacheService`；CheckSource → `SourceCheckService`；Download → `DownloadService`；ExportBook → `BookExportService`；Web/WebTile → `WebBridgeService`；VideoPlay → `MediaPlayService`），并把 Legado 在 `ui/` 层的功能（RSS、词典、字体、二维码、书签、替换、本地书、编辑器、搜索等）也提升为服务模块，让业务逻辑统一出 UI。
- **服务无 UI**：服务只暴露数据与方法，不感知 Flet；所有界面状态流转经事件发布。
- **只加壳不改行为**：复用资产（§0.2）先以适配外壳进入服务层，行为由差分工具守门，修复项（§2）在壳内原位增强。

### 4.3 服务间通信

- **请求-响应**：服务 A 调用服务 B 的方法——经 `ServiceHub.get(B)` 定位实例；协程方法一律经 `EngineHub`/`EngineProxy` 派发（`run_coroutine_threadsafe`），保证被调方跑在自己的事件循环上，调用方（UI 或服务）不阻塞。
- **通知（解耦）**：`EventBus` 发布 `AppEvent` 子类事件，异步投递给订阅者（订阅即回调注册，线程安全）。核心事件清单（设计期冻结，命名即约定）：

| 事件 | 载荷要点 | 发布方 → 订阅方 |
| --- | --- | --- |
| `ServiceStateChangedEvent` | service_id, state, error | ServiceHub → Dashboard/任意视图 |
| `SourceChangedEvent` | change_type, source_id | SourceService → 检测/书源视图/书架 |
| `CheckFinishedEvent` | source_id, state_class, summary | SourceCheckService → CheckView |
| `RepairReportReadyEvent` | report_id, source_id | RuleRepairService → RuleRepairUi |
| `SearchFinishedEvent` | search_id, items | 阅读域 → 找书/换源视图 |
| `DownloadProgressEvent` | task_id, kind, progress, speed | DownloadService → 下载中心/整书缓存视图 |
| `ReadAloudStateEvent` | state, book_url, chapter, position | ReadAloudService → 迷你播放条 |
| `MediaPlayStateEvent` | state, book_url, chapter | MediaPlayService → 视频视图 |
| `ProgressSavedEvent` | book_url, chapter_index, position | ReadingService → 书架/进度卡 |
| `BookmarkChangedEvent` | book_url, op | BookmarkService → 阅读器 |
| `ImportFinishedEvent` | kind, count, errors | OnlineImportService/LocalBookService → 导入视图 |
| `BackupFinishedEvent` | kind, ok, detail | WebDavService → 备份设置页 |
| `UpdateAvailableEvent` | version, notes, url | UpdateService → 关于/设置页 |
| `RssRefreshedEvent` | source_id, new_count | RssService → RSS 视图 |
| `SettingsChangedEvent` | keys | SettingsService → 全体订阅视图 |

- **规则**：事件只承载不可变数据快照（dataclass），禁止事件里塞对象引用让接收方改发送方状态（约束 10）。

### 4.4 生命周期与启停

- 服务状态机：`REGISTERED → INIT → STARTING → RUNNING ⇄ SUSPENDED → STOPPING → DISPOSED`。
- 服务声明 `dependencies`（如 `SourceCheckService` 依赖 `SourceService`、`RuleEngineService`、`BrowserService`(可选)；`DownloadService` 依赖 `RuleEngineService`、`StorageService`）；`ServiceHub` 启动时按拓扑序（先依赖后消费者）`start_all()`，退出时逆序 `stop_all()`，超时未停则记录并强制 DISPOSED（桌面单进程，退出即进程回收，停止只保证落盘与事件收尾）。
- 懒启动：轻量服务（QrCode/Font/Theme）注册即 RUNNING（无资源）；重服务（BrowserService 拉起 Chromium、WebBridgeService 监听端口、ReadAloudService 加载 TTS 引擎）由首次使用触发，`SUSPENDED` 用于资源释放（如投屏窗口关闭后 BrowserService 挂起内核会话）。
- 异常策略：服务 `start()` 失败不阻断其他服务（hub 记录 error 并继续），失败服务进入 `SUSPENDED` + 状态可见，UI 提示"某服务未就绪，相关功能降级"（与现有无头内核缺失降级同哲学）。

### 4.5 状态可见性

- 每个服务暴露 `status: ServiceStatus`：`state` / `last_error` / `started_at` / `updated_at` / `progress`（0-1 可选）。
- `ServiceHub.status_report()` 汇聚全量；每次状态迁移发布 `ServiceStateChangedEvent`。
- UI 侧 `ServiceDashboardView`（设置页/工具栏入口）实时展示：服务名、状态、错误、资源占用摘要（如引擎队列长度、下载任务数、浏览器会话数），满足决策 2"状态可见"要求。

### 4.6 服务与视图边界

- 服务层零 Flet 依赖（import 层禁止 `import flet`）。
- 唯一例外通道：`BrowserService` 的交互回调（登录/验证码/投屏输入）经 `interaction_loop` 注入到视图层——保留现有 engine_worker 的灰色地带设计并收编为显式接口（`BrowserInteractionCallback`），不扩散。

### 5.2 模块边界与依赖方向

- **方向规则**（升级自 architecture-rules §1）：
  - `views/ → Controller → services → core → storage`；`models/` 仅被 services 与 storage 依赖。
  - 服务域间允许调用但**单向**：`content/` 可依赖 `reading/` 与 `sources/`；`reading/` 可依赖 `sources/`（书源数据）与 `tools/` 中的 `BrowserService`；`tools/` 只依赖 `reading/` 的 `RuleEngineService` 与 `core/`，**不反向**依赖 content；任何域不得依赖 `views/`。
  - `BrowserService` 例外：其交互回调接口定义在 core（`BrowserInteractionCallback`），视图实现该接口注入，不违反依赖方向（沿用 interaction_loop 既有模式）。
- **边界检查**：目录包边界即依赖边界，禁止跨域 import（如 `services/tools/` import `services/content/` 视为违规）；CI/测试中加 import-lint 用例守门。
- **共享工具模块**（不构成服务，仅函数/类库，归各域内 `_lib/` 或 core）：`block_pages`（拦截识别，被 SourceCheckService/RuleRepairService 使用）、`java_regex/icu_charset/custom_url/public_suffix/query_ttf`（随 RuleEngineService）、`engine_worker`（升为 core EngineHub）。

### 5.3 红线清单 v2（替换 architecture-rules §3）

1. 不引入新的 JS 引擎：`@js:` 规则只走 QuickJS（legado_js.py）。
2. 规则行为必须与 Legado 原版对齐；差异修复执行本文 §2 清单；行为差异必须记录到差异文档。
3. 不修改只读参考目录 `base_history/`、`other_history/`。
4. 智能体不擅自提交；提交前需开发者明确指示。
5. 密钥不入库（令牌/密码/私钥/Cookie/已填充 .env 值）。
6. **任何服务不得跑在 Flet 事件循环、不得持有 Flet 控件**；服务触 UI 仅经 `BrowserService` 交互回调（`BrowserInteractionCallback`）。
7. 搜索/换源的并发与取消语义不得破坏（SearchModel searchId/页码/generation、换源本地种子+联网扫描+候选排序）。
8. 存储收敛：结构化数据一律进 `StorageService` 主库；"书"的记录不允许出现第三份重复库；新功能禁止新增散落介质（目标 §6）。
9. 测试护栏：核心资产外壳化由差分工具 + `test_legado_compat.py` 守门（行为不变）；新增逻辑附测试。
10. 服务间通信只经 `EventBus` 或显式接口方法；事件载荷为不可变数据快照。
11. 跨平台：新依赖必须三平台可用；平台专属能力必须后端抽象（§1 各条目的跨平台策略为设计约束）。
12. 高风险操作（删除/覆盖/发布/批量修改）走预览-确认（承接现有"谨慎行事"要求）。

## 6. 数据模型与存储设计

### 6.1 现状与问题（差异文档 §4.7 的落点）

现状 7 种介质（`docs/current-system-design.md` §4.6）：`bookSource.json`、`bookshelf.json`、`appearance.json`、规则状态 JSON、cookie 文件、`search-books.sqlite3`、`reader-cache/` 文件目录 + `chromium-profile*/`。问题：无统一 schema 约束与迁移体系；"书"的记录分散在 bookshelf.json / SearchBookStore / reader-cache 三处（红线 8）；新功能（RSS/书签/替换规则/下载任务等）若沿用散落 JSON 会继续恶化。

### 6.2 目标存储层（三类介质）

1. **SQLite 主库**（对标 Legado `legado.db`，文件名沿用 `legado.db`，目录 `data_dir/`）：全部结构化数据；由 `StorageService` 独占访问，schema 版本化 + 迁移脚本（`storage/migrations/`）。
2. **文件目录**：正文/大对象/缓存——`reader-cache/`（章节正文）、`downloads/`（下载与导出产物）、`image-cache/`（封面/漫画/缩略图）、`chromium-profile*/`（浏览器登录态，维持现状）；路径统一经 `StorageService` 分配，容量淘汰策略收敛为"逐目录策略 + 全局配额"。
3. **互操作/备份格式（JSON/zip）**：书源导入导出、WebDAV 备份包、配置迁移载体——运行时不再读写，仅在导入导出/备份恢复时生成与消费。

### 6.3 主库表草案（设计期约定，不写完整 DDL）

### 6.4 迁移与兼容

- **v1 迁移**：启动时 `StorageService.migrate()` 从旧介质一次性导入——`bookSource.json → book_sources`、`bookshelf.json → bookshelf`（reading 块原样保留）、`search-books.sqlite3 → search_books`、appearance 等 → `settings`；导入完成后旧文件改名备份（`.legacy-bak`）而非删除，保留人工回退。
- **兼容保证**：书源/书架 JSON 导入导出能力保留（`SourceService` 互操作接口），WebDAV 备份包格式与 Legado 对齐（差异 §1.5）。
- **TTL 与清理**：`search_books` 沿用 24h TTL（差异文档/找书换源文档）；reader-cache 容量淘汰保留；整书缓存钉住不淘汰（差异 §3.5）在 `StorageService` 中登记钉住集合。
- **不迁移**：`chromium-profile*/`（浏览器登录态，目录即格式，不动）；`reader-cache/` 正文文件（内容复用，仅索引迁入主库）。

## 7. UI 层架构（Flet 多视图组织）

### 7.1 现状问题

`views/` 平铺 8 个文件；`ReadingView`（172KB / 209 方法）聚合找书/书架/阅读器/换源/登录/整书缓存六大职责、30+ 状态字段（architecture-rules §2.3 已知结构性问题）。全量功能复刻（19 项）后视图数量将翻倍，若沿用单体必然失控。

### 7.2 目标组织：视图按域分包 + 控制器

```
views/
├── source/     BookSourceListView, SourceImportView, SourceEditView(代码编辑器), CheckView, RuleRepairUi
├── reading/    FindBooksView, BookshelfView, ReaderView, SourceSwitchDialog, LoginDialog, BookmarkPanel, ContentSearchBar
├── rss/        RssSourceManageView, RssArticleListView, RssReadView, RssFavoritesView
├── library/    LocalBookImportView, MangaReaderView, VideoBookView, DownloadCenterView, WholeBookCacheView
├── tools/      WebDavBackupView, ExportView, QrCodeView, DictDialog, ReplaceRuleManageView, FontSelectView, WebBridgeConsole, BrowserView(投屏)
└── settings/   SettingsView, AppearanceView, ServiceDashboardView, AboutView(更新入口)
```

- 每视图 = 轻壳（Flet 控件布局）+ `Controller`：Controller 订阅 `EventBus` 事件、调用服务方法、把数据快照渲染进控件；视图不含业务逻辑。
- 视图间零 import：跨视图协作（如 FindBooks 开读交给 Reader）经服务事件与 `ViewRegistry` 路由回调（沿用现有 `on_read_book` 模式，明确为注册表而非互引）。
- `ReadingView` 按 architecture-rules §2.3 拆分方向落为 `FindBooksView/BookshelfView/ReaderView`，共享状态收敛到 `ReadingService`（阅读上下文）+ 会话级 controller。

### 7.3 导航

- 顶部目的地从 3 个扩展为分组式 `NavigationRail`（宽窗）与底部导航（窄窗，沿用现状自适应）：**阅读**（找书/书架/阅读器）、**书源**（列表/检测/修复/编辑器）、**RSS**、**下载**（下载中心/整书缓存）、**工具**（备份/导出/Web 桥/二维码/替换/词典/字体）、**设置**（外观/服务状态/关于）。
- 声明式路由表 `ViewRegistry`：目的地 → 视图类 + 所需服务；阅读器沉浸模式（隐藏导航）保留；新视图一律注册进路由表，禁止散落 if/elif 装配。
- 特殊形态（非目的地，模态/覆盖层）：投屏浏览器窗口（`BrowserView` + `BrowserService` 交互回调）、朗读迷你播放条（全局覆盖层，订阅 `ReadAloudStateEvent`）、换源/登录对话框。

### 7.4 控制器模式

- `Controller` 生命周期与视图绑定（attach/detach）：attach 时订阅事件，detach 时退订（防止跨页泄漏）；协程调用经 `EngineProxy`，UI 线程只 await future。
- 节流与合并：高频事件（下载进度、搜索结果流）沿用现状节流策略（对齐文档 §1.4 的 0.5s 节流、命中数变化才重绘），在 Controller 层实现，不进服务层。
- 状态可见：`ServiceDashboardView` 订阅 `ServiceStateChangedEvent` 渲染全服务状态（§4.5）。

### 7.5 视图与服务的对应检查（防越界）

- 视图只能 import 自己的 Controller、`ViewRegistry`、`models/` 数据类；不得 import 服务实现类以外的接口面（经 `ServiceHub.get()` 按类型取）。
- import-lint 守门：`views/` 不得 import `services/*` 具体模块文件（只能经 core 的接口层），保证边界可机器检查。

## 8. 迁移路径

### 8.1 迁移策略

- **核心资产只加壳不改行为**：规则兼容层/检测/浏览器/缓存以适配外壳进入服务层，内部实现冻结（行为由差分工具与 `test_legado_compat.py` 守门）；修复项（§2）在壳内原位增强，每项修复独立提交、独立测试。
- **旧代码共存到 M7**：新服务与旧 `views/services` 单体并行运行（双轨），每里程碑以"服务外壳 + 新视图最小可用"交付；M7 才删除旧结构。
- **一切经 ServiceHub**：从 M1 起，新代码一律通过 `ServiceHub` 取服务，禁止直接 import 服务实现类做业务调用（测试除外）。
- **可回滚**：数据迁移只读旧文件并留 `.legacy-bak`；核心资产无行为变化 ⇒ 回滚=切回旧入口 + 恢复旧数据文件，成本低。

| QuickJS 单线程串行化 @js 求值（差异 §2.10） | 中 | 不修复（引擎约束），文档化；死循环 JS 超时隔离加入 legado_js 调度器（§2.10 条目） |
| 摄像头扫码（QrCodeService）在无摄像头/虚拟机上不可用 | 低 | OpenCV 后端缺失时降级为"仅生成 + 手动输入"；扫码功能不阻塞其他交付 |
| PyInstaller 包体增大（新增依赖：pyttsx3/ebooklib/webdavclient3/opencv/fontTools/feedparser） | 中 | 依赖按服务懒加载（服务未使用不 import）；打包冒烟测试覆盖动态依赖（现有 --smoke-test 扩展） |
| WebBridgeService 监听端口的安全面（本机可访问性） | 中 | 默认仅绑定 127.0.0.1 + 令牌校验；开关默认关闭 |

### 8.5 回滚策略

- 每个里程碑独立分支/标签；出口条件未过不进入下一阶段。
- 数据层：旧 JSON 文件保留到 M7 之后（`.legacy-bak`），迁移可逆——回滚 = 停新架构入口 + 恢复旧数据文件 + 启动旧主入口。
- 代码层：核心资产无行为变化 ⇒ 服务外壳可在数小时内拆除（外壳只做路由/事件包装）；UI 拆分与旧视图并存期，回滚只需切回旧视图注册表。
- 组织层：M1–M3 全部出口条件含"旧功能可用"双轨，任何阶段失败不影响旧版本发布。

### 9.2 关键抽象命名与职责（面向实现，不含完整代码）

| --- | --- | --- |

### 9.3 外壳化样板（以 RuleEngineService 为例，说明性描述）

原核心资产（`services/engine/` 下六个模块）保持文件级原样；`RuleEngineService` 外壳提供：`async chapters/book_info/content/search/explore(...)`（转发原类方法）、`put/get`（变量作用域经外壳统一入口，修复 §2.9 的落点）、网络栈配置（UA/超时/代理，读取 SettingsService，§2.13/2.20 落点）、`engine` 实例池（短命引擎语义保留）。行为守门：`test_legado_compat.py` 对外壳实例跑原有用例集，零漂移为通过。其余复用资产外壳同构（检测/修复/审计/浏览器/缓存/主题）。
