### 一、为什么必须先把两个症状分开

桌面端是 `FLET_APP`：**Python 进程是服务端，窗口是独立的客户端进程**，客户端靠一条
连接收补丁。于是"窗口停在 loading"有两种完全不同的成因，修法也相反：

- **A 界面循环被压住**：服务端还活着，但事件循环长时间顾不上 socket → 客户端超时断开、
  不再渲染。要修的是循环上的占用。
- **B 服务端进程被打断**：最后那行 `Assertion failed: ... module.c:99` 是 C 运行时
  `assert` 的**原生 abort**，Python 侧不可捕获，进程当场没了 → 窗口只剩最后一帧。
  要修的是崩溃本身。

本轮把 A 量到**否证**，把 B 的五个候选形状也全部否证，所以两条都还挂着——这是本轮的
诚实结论，不是"查完了"。

### 三、取证六：`module.c:83` 与 `:99` 是同**一对** enter/leave

先把断言本身读清楚，别再猜机制。本机 `_quickjs.cp312-win_amd64.pyd` 里全库只有一处
`module.c`（偏移 671234），两条断言串**紧挨着**：

```
... | module.c | !runtime_data->thread_state | runtime_data->thread_state | d |
    malloc_size | malloc_limit | memory_used_size | ... | atom_count | atom_size | ...
```

后面那一串是 quickjs 运行时统计字段，说明这两条在同一对相邻函数里：

| 断言 | 语义 | 什么时候响 |
| --- | --- | --- |
| `:83` `assert !thread_state` | 进原生段时"里面不许已有人" | 上一轮（2026-09-29 第四十一轮）钉住的**两条线程同时进同一个 Context** |
| `:99` `assert thread_state` | ~~出原生段时"里面必须有人"~~ **第五十四轮更正：这句错**，`:99` 是 `prepare_call_python`，即 **JS 回头调 Python 桥函数那一刻槽位必须非空**（"出原生段"是 `:92`/`:106`） | ~~**进出配对失衡**：leave 时 thread_state 已经空了~~ |

所以 `:99` 不是 `:83` 的另一种写法，要的形状也不同——本轮五族候选全部围绕"谁能把配对搞失衡"。

### 五、取证八：那 6 行 10054 到底是谁家的 socket（未定）

要判的是"远端书源主动 RST（引擎循环上的 aiohttp 客户端连接）"还是"Flet 客户端到
服务端被掐（界面循环上的 socket）"。做法：本地起一条**裸 TCP 假源**（不走 aiohttp.web，
免得它先把异常吞成 `Error handling request`），收到 `/rst` 就写半个响应头，然后
`SO_LINGER=(1,0)` + `close()`；客户端用生产同构形状——**专属线程上的 asyncio 循环 +
aiohttp ClientSession**（即 `check_service` 的 probe/search 那条路），并给那条循环挂
`set_exception_handler` 把记录原样收回来。

`.probe/connection_reset_who_attr.py` → `.probe/out_rst_who.txt`：

```
GET /rst 调用方拿到 正常返回（1 ms）      ×2
GET /ok  调用方拿到 正常返回（0 ms）
捕获到 0 条循环级异常记录
```

**本机这个形状没复现**（aiohttp 把被截断的响应当读完就返回了，`_call_connection_lost`
一次都没进异常处理器）。所以：

- 不能断言"10054 是扫描噪声"，也不能断言"Flet 客户端掉过线"；
- 需要现场证据才判得了：下一次复现时，把每条 `Exception in callback ...` 的
  **线程名/loop id** 打出来（在两条循环上都装 `set_exception_handler`，只加标识、
  不改行为），一眼就知道是谁家的 socket。

**每条 `_quickjs.Context` 一份**（`RuntimeData` 就是 Context 对象本体，`:27`，注释
"Used when releasing the GIL"）。

于是"`:99` 为什么会空"收窄成三条路，全指向**同一个 Context 在 eval 期间被别的东西碰过**：

1. 另一条线程在同一条 Context 上走完 `end_call_js`（`:90`）——它会读走槽位并置 `NULL`；
   原生入口一共四个（`runtime_eval :507`、`runtime_module :533`、`object_call :257`、
   `runtime_execute_pending_job :536`），日志只覆盖了第一个；
2. `js_python_function_finalizer`（`:382`，体 `:385-408`）——上游自己写着
   `NOTE: This may be called from e.g. runtime_dealloc, but also from e.g. JS_Eval …
   TODO: integrate better with (prepare|end)_call_(python|js)`（`:388`），它在
   `Py_XDECREF(node->obj)` 前后直接翻 `thread_state`；触发者是 `runtime_clear`（`:371`，
   循环 GC）或 eval 里重绑旧绑定的释放；
3. Python 侧从别处调 JS 函数对象再回到 Python（`object_call` 那一族）。

另外确认一条**生产早已绕开的坑**：`js_python_function_call` 开头有一句
`has_time_limit` 就抛 `Can not call into Python with a time limit set.`——这正是
`legado_js.py:936-943` 那段注释说"只设内存上限、不设 time limit"的原因，
本轮从源码侧再钉一次。

### 四、照现场造的两个新形状，还是 0 崩

现场说"一条 Context 被进了 5112 次、每次重绑 109 个桥函数"，那这两个就得单独否证：

| 形状 | 臂 | 样本 | 结果 |
| --- | --- | --- | --- |
| 一条共享 Context 上反复重绑 | `accumulate`(重绑+eval，生产形状) / `bindonce`(只绑一次) / `rebindonly`(只重绑不 eval) | 8000 轮 × 109 = **872 000 次重绑**，`.probe/qjs_shared_context_rebind_attr.py 8000 109` | 三臂 rc=0 全活（1.2 s / 0.7 s / 0.5 s） |
| 循环 GC 在**别的线程**上收"捕获了 Context 所有者的桥闭包" | `gcaway`(B 线程纯 Python churn 逼 GC 落在 B) / `gconA`(无 B) / `plain`(绑不捕获所有者的 lambda) / `nogc`(禁用 GC) | 40 轮 × 109 个环闭包 + 每轮一次 40 万次循环的 eval，`.probe/qjs_gc_cross_thread_attr.py 40` | 四臂 rc=0 全活 |

四臂的分工是关键：`plain` 抽掉"环"、`nogc` 抽掉"GC"，如果只有 `gcaway` 崩才归得到
"跨线程循环 GC"。这条假设**没被证实也没被推翻**（0 崩），但它把"跨线程 GC"从
"最可能的形状"降成了"要现场才能判的形状"。

至此 004 表格里离线否证的候选累计 **8 个形状**。剩下活着的只有一个：
**某条 journal 当时看不见的线程，在这条 eval 结束前碰了这条 Context。**

### 五、日志升级：四种记录 + 在飞表 + 读回器

`app/services/engine/legado_js.py`：

| 记录 | 写点 | 字段 |
| --- | --- | --- |
| `ev=E` | `_journal_eval`，紧贴 `ctx.eval` 之前（位置由源码行号护栏钉住） | `ts pid th` **`thid`** `depth runtime fresh jslib bytes rule url` |
| `ev=X` | `_journal_leave`，`_evaluate_locked` 的 `finally` **第一句** | `thid runtime` **`ref=`**`<自己那条 E 的序号>` `took=<ms>` `out=ok 或 err` |
| `ev=!` | `_journal_eval` 发现这条 `runtime` 已在飞、而在飞的**线程 id 不是自己** | `thid runtime` **`other_thid other_seq`** |
| `ev=C` | `close()` 第一句 `_journal_close` | `thid` **`inst=0x…`** `shared=<共享 Context 条数>` |

- 为什么加**数字** `thid` 而不只看线程名：线程名会重名（两条 `Thread-N`），而 `:99` 判的
  恰恰是"是不是同一条线程"，`get_ident()` 才是可比量。
- `write()` 现在**返回序号**（失败仍只是置"日志不可用"，绝不抛），配对靠这个序号做 `ref=`。
- 在飞表 `_JOURNAL_INFLIGHT: dict[ctx 序号, (线程 id, 进记录序号, 上一层同款)]` 是进程级的：
  进时压上一层、出时还回上一层（嵌套 `depth>1` 也能配对），`_journal_leave` 弹干净。
  `ev=!` 正常**永远不该出现**（求值都排在 dispatcher 唯一线程上）——出现就是现场证据，
  而且它**落在进之前**，崩了也还在盘上。
- 读回器 `crash_journal_inflight(path=None, limit=8)`：把整环读完、收齐所有 `ref=`，
  回"有 `E` 没 `X`"的那几条。判"没回来"只能靠成对，**不能看尾巴**——尾巴可能只是被
  环形容量挤掉的顺序假象。`_journal_kind()` 把**没有 `ev=` 的老记录按 `E` 处理**，
  所以在 `crash-20260930-131140.journal` 上它会回"最后 8 条都没出来"：那是**格式换代**，
  不是第八条线索。
- 容量 4 MiB → **8 MiB**（`_JOURNAL_SIZE`，32768 条 = 16384 对）：现场 15.49 分钟写 13010 条，
  成对后同样时长要写 ~26000 条，4 MiB 大约 8 分钟就开始吃掉开头。

### 二、改法：`audit_off_loop` 送进程池，线程池留作退路

| 落点 | 形状 |
| --- | --- |
| `compat_audit_service.audit_off_loop` | 走 `loop.run_in_executor(pool, _audit_one, data)`；池 `None` 才退回 `asyncio.to_thread` |
| `_new_pool()` | `ProcessPoolExecutor(max_workers=4, mp_context=spawn)`，**建池的唯一出口**（测试把它换成同接口线程池就能不 spawn 地验编排） |
| 懒建 + 常驻 | 第一条审计来时建一次，整轮共用（建池+首条实测 177~205 ms，每条建一次会把省下的全赔回去） |
| 建不出来 | `disabled=True` + 记原因，**不再一条条重试**（没权限 / 冻结包缺 `freeze_support` / 杀软拦 spawn 都是这一档） |
| 子进程被打穿 | `BrokenProcessPool` → 摘池、**这一条不重跑**、回一份 `not_audited` 报告；重建满 3 次就永久退回线程池 |
| `AuditReport.not_audited` | 新字段。它必须存在：子进程被打穿时返回的是**空清单**，只靠七个清单判 `clean` 就等于把"没审"显示成"这条源干净" |
| `source_check_service` | 扇出上限改成**两档**：走子进程 8 条、退回线程池 2 条（`_audit_fanout_bound()` 每轮读一次） |

为什么不重跑毒源：换进新池会再带走一个 worker，退回线程池跑等于把原生 abort 请回主进程

（`_AUDIT_WARNING_FIELDS`）、编辑器审计栏和 `audit_log` 的 payload。

### 五、Windows spawn 上踩到/挡掉的五条

1. **子进程会重新执行 `__main__`**：`main.py` 顶层一句 `from … import build_app_shell`

3. **`ProcessPoolExecutor` 一旦被打穿就永久报废**，不能靠"再塞一条试试"，只能摘池重建；
   重建有次数上限。
4. **`asyncio.to_thread` 起线程之后取消不掉**——所以退回线程池那一档的取消只是

## 第六十四轮：自动分级检测——浅遍先扫，进队列的源再补验正文（任务 #26~#30）

### 二、判据①实现里有一个真 bug，被快照照出来了

第一版按"主机那一段里有个点"判主机，于是 `search.php?key={{key}}`、

阅读链。现在只认两种形状——IP 字面量、或最后一段查得到公共后缀表里的已知顶级域

`{}()=$<>;,"` 这类模板/执行字符的按"无从判定"走判据②。跨站桶 111 → **35**。

交叉核验用**另一套独立实现**（`.probe/tiered_queue_census.py` 故意改用"最后一段是 2~6
个字母"这种不同规则），两套路子给出 713/169/35 vs 704/169/44，9 条分歧逐条看全是
`search.html`、`s.php,{...}`、`index.xml`、`index.php?s=…` 这种真相对路径——分歧方向

Q4（同家退回裸 netloc）。

### 三、编排：一轮两遍，进度与结论都只有一份

`SourceCheckService._run_tiered()`（外壳，`check_service` 那份 M2 冻结件一行未改）：
静态判据先收 → 队列里携带的接着收 → 浅遍（`CHECK_DEPTH_LIST`）→ 浅遍结论再过判据③
入队 → 深遍（`full`，`fresh_round=False`）→ 合并 → 队列结算 → **一次**关审计进程池。

为跨两遍准备的四个口子（都在 `_run_checks`）：

* **分母是本轮计划源数，分子是"已定论"的源数**（`counts=` 钩子）：被浅遍收进队列的那条
  还没定论，浅遍里不推进度、深遍里才推。换成"派发条数"当分子，控制器按 source_id 去重
  数进度会提前到 100%（变异 S3 就是把它改回派发数，`test_the_bar_counts_settled_sources_not_dispatches` 红）。
* `settled_before` 让第二遍接着数，不回头（变异 S4）。
* `fresh_round=False`：审计扇出计数与信号量**不**在第二遍重置，否则关池那道闸门数错账（变异 S5）。
* `_merge_by_url` 按 `raw_url` **FIFO 配对**而不是 dict 覆盖：库里两条源填同一地址时，
  覆盖会把其中一条的结论吞掉（同一 dict 对象出现两次，`idx` 互相覆写）。变异 S6 就红在这儿。

顺带修掉一处白付的钱：静态审计原来跟每条结果跑，浅遍排进深检队列的那条源被审了两次
（浅遍那份马上被深遍顶掉）。现在闸门放在 `on_result` 里，只审会被留下的那行——
`_audit_one` 中位 3.2 ms、p95 189 ms（第六十三轮单价），一个深检源省一次是一次（变异 S2）。

### 四、队列是**跨轮**的账，不是这一轮的预算

`DeepQueue` 只存 `raw_url → {reason, attempts, ts}`：取的时候按 `raw_url` 回当前源列表捞，
捞不到就淘汰，不留幽灵条目。`DEEP_MAX_ATTEMPTS=3`、TTL 7 天、试满后 cooldown 24 小时。
两个反直觉处已钉死：试满但**还没歇够** cooldown 的条目要留着（删了等于配额没有，
`prune` 的注释）；同一个原因反复排进来**不许**把次数洗白，只有判据换了才算新信息
（变异 Q7）。

(B) **结论等价**：同一批形状，两遍跑完的九态与一遍全完整档逐条比 ——
浅遍 34 / 深遍 18（`{list_usable:16, cross_host:1, undecidable_host:1}`），
两边都是 `search_only 19 / fully_usable 17`，**不一致 0 条**。分档只改了"为哪些源花钱"。

(C) **花费**（三臂都过同一个服务外壳，外壳并发 8；按 `ab-bench-must-interleave` 交替）：
参照单价 36 条同形状源——浅遍 **12.1 ms/源、2.00 次 HTTP（正文段 0.00）**，
完整档 **23.7 ms/源、4.92 次 HTTP（正文段 2.92）**，单价比 0.508。
按深遍占比扫档（每档交替 3 轮取中位，"省>0 = 两遍更便宜"）：

```
  深遍占比 |  full墙钟  tiered墙钟       省 |  full请求  tiered请求 |  full正文段  tiered正文段 | 链派发
     5.6% |      480       557  -16.1% |    75.0      75.0 |       3.0        3.0 |   36→2   ← 这里开始亏
    16.7% |      498       573  -15.2% |    87.0      95.0 |      15.0       15.0 |   36→6

**两臂的正文段请求数每一档都相等**，而两遍臂的总请求逐档更高（最高档 230 vs 168）。
线性模型给的打平点是"深遍占比 52.0% 才开始亏"，实测**最低那一档（5.6%）就已经亏 16.1%**——
因为模型漏了判据自身的形状：手里有书（= 阅读链会真跑、真花钱）的源，浅遍结论必然是
`list_usable`，于是全部进队列；不进队列的那批（搜索空手 / blocked / unusable）本来就不发
正文请求。链派发数从 36 掉到 2 只说明那些派发立刻以 `no_candidates` 返回、一次 HTTP 都不花
——**派发减了，钱没减**。

⇒ **同一轮里"先浅后深"买不到便宜。**便宜只在时间维度：首轮只付浅遍单价（12.1 vs 23.7 ms/源
= 2.0×），贵的那一半摊到后续轮次里。这与开发者说的"推到缓存组里，**等待**和后续检测"是同一件事。

(D) **候选门（判据③的"手里有书"）值多少钱**：同一批源、同一条流水线，只把
`has_prose_candidates` 打成恒真（= 变异 Q1 在真流水线上的价钱）：

```

候选门省 17.0% 墙钟、36 次请求，而正文段一次都没多花（那 18 条立刻 `no_candidates` 返回）；
不补它时两遍相对一遍全完整档**反而贵 65.1%**——分档就白做了。

### 八、待开发者定的一件事（证据已给全）

既然 (C) 实测"同一轮里紧接着跑第二遍"是**净亏**（−15.2% ~ −47.8%），轮内深遍这一半要往哪走，
是本轮唯一没定的产品决策：

1. **照现状留着**（轮内浅+深）：一轮就给出完整结论，代价是这一轮比一遍全完整档慢
   15%~48%，收益只在"结果里那条源分得清验没验过正文"。
2. **把深遍挪出这一轮**：`check_all` 只跑浅遍 + 入队，深遍由"每轮吃一小片 / 空闲时 /
   显式补验按钮"消化——这是 (C) 结论直接指向的做法，首轮只付 12.1 ms/源（2.0×便宜），
   代价是"这一轮跑完"并不等于"结论跑完"。
3. **撤掉轮内第二遍**，`DeepQueue` 只当跨轮机制（回到第 2 种的最简形态）。

判据、队列、合并、进度、护栏四种做法下都复用，不需要重写。
