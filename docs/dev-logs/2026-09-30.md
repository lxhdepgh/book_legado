### 一、为什么必须先把两个症状分开

桌面端是 `FLET_APP`：**Python 进程是服务端，窗口是独立的客户端进程**，客户端靠一条
连接收补丁。于是"窗口停在 loading"有两种完全不同的成因，修法也相反：

- **A 界面循环被压住**：服务端还活着，但事件循环长时间顾不上 socket → 客户端超时断开、
  不再渲染。要修的是循环上的占用。
- **B 服务端进程被打断**：最后那行 `Assertion failed: ... module.c:99` 是 C 运行时
  `assert` 的**原生 abort**，Python 侧不可捕获，进程当场没了 → 窗口只剩最后一帧。
  要修的是崩溃本身。

本轮把 A 量到**否证**，把 B 的五个候选形状也全部否证，所以两条都还挂着——这是本轮的
诚实结论，不是"查完了"。

### 三、取证六：`module.c:83` 与 `:99` 是同**一对** enter/leave

先把断言本身读清楚，别再猜机制。本机 `_quickjs.cp312-win_amd64.pyd` 里全库只有一处
`module.c`（偏移 671234），两条断言串**紧挨着**：

```
... | module.c | !runtime_data->thread_state | runtime_data->thread_state | d |
    malloc_size | malloc_limit | memory_used_size | ... | atom_count | atom_size | ...
```

后面那一串是 quickjs 运行时统计字段，说明这两条在同一对相邻函数里：

| 断言 | 语义 | 什么时候响 |
| --- | --- | --- |
| `:83` `assert !thread_state` | 进原生段时"里面不许已有人" | 上一轮（2026-09-29 第四十一轮）钉住的**两条线程同时进同一个 Context** |
| `:99` `assert thread_state` | ~~出原生段时"里面必须有人"~~ **第五十四轮更正：这句错**，`:99` 是 `prepare_call_python`，即 **JS 回头调 Python 桥函数那一刻槽位必须非空**（"出原生段"是 `:92`/`:106`） | ~~**进出配对失衡**：leave 时 thread_state 已经空了~~ |

所以 `:99` 不是 `:83` 的另一种写法，要的形状也不同——本轮五族候选全部围绕"谁能把配对搞失衡"。

### 四、取证七：五个候选形状族，全部 0 崩（本轮否证）

每族都是**子进程隔离**（崩了不影响其余形状），判定一律区分三档：
`崩`（rc≠0 或 stderr 有 `Assertion failed`）/ `干净` / `探针报错`（rc=1 且 stderr 是
Python 异常 = 探针自己没跑起来，**不许**混进"崩"）。

| # | 候选形状 | 样本 | 探针 / 输出 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | Context 在**非归属线程**销毁（含同线程、异线程、未用过就丢、逃逸的值、循环引用靠 GC） | 5 形状 × 子进程 | `.probe/qjs_free_thread_attr.py` → `out_qjs_free_thread.txt` | 全活 |
| 2 | Python 异常**跨 QuickJS 的 C 边界**（回调里 raise ValueError/BaseException/RecursionError、嵌套求值里 raise、raise 后丢弃帧与 Context、值活得比 Context 久、撞内存上限、JS 栈溢出、200 轮 raise 风暴） | 11 形状 | `.probe/qjs_raise_across_bridge.py` → `out_qjs_raise.txt` | 全活 |
| 3 | 每源一条 runtime + jsLib 求值**累积** 400 轮 | 400 轮 | `.probe/qjs_context_leak_attr.py` → `out_qjs_leak.txt` | Context 存活恒 **1**、Runtime 恒 1、RSS 37.8 → 48.4 MB 后在 48–50 MB 平台波动（**不涨**） |
| 4 | **求值进行中**释放 runtime（派发器正待在这个 Context 里时 `del`） | after/during 各 5 次子进程 × 4 轮 | `.probe/qjs_free_during_eval_attr.py` → `out_qjs_free_during.txt` | 两臂各 **5 次里崩 0 次** |
| 5 | **同一个 Context 在 JS→Python 回调里重入**（生产里 `legado_js.py:548` 的内联重入分支用的还是同一个 `self`，于是 `_evaluate_locked` 会从 `_shared_js_contexts[js_lib_key]` 取到**同一个缓存 Context** 再 eval 一层） | 重入 1/2/4/8/16 层，各 5 子进程 × 300 轮；另加"最里层抛异常穿出去"两形 + 新建 Context 对照组 | `.probe/qjs_same_context_reentry_attr.py` → `out_qjs_reentry.txt` | `same_inline_d1..d16` 各 **5/5 存活**、`same_inline_raise` 5/5、对照组 `fresh_d4/d16/fresh_raise` 各 5/5 |
| 6 | **解释器收尾**时守护 JS 线程还在原生 eval 里（`threading._shutdown()` 只等非守护线程，而 `legado-quickjs` 和看门狗都是 daemon，`legado_js.py:149-152`） | 3 形状 × 10 子进程，单次求值标定到 400 ms | `.probe/qjs_shutdown_race_attr.py` → `out_qjs_shutdown.txt` | `崩=0 干净=10 未接上=0`（三形状都是） |

两个"差点被骗"的地方，按仓库规矩写下来：

- **形状 6 的第一版是空的**：worker 每次 eval 只有几毫秒，主线程 `STOP.set()` 后 worker
  立刻出来，重叠窗口根本没接上——"8/8 干净"量的是**没发生的事**。第二版先把单次求值
  标定到 400 ms（`calibrate()` 真跑真调），worker 在**进原生 eval 前**置 `inside=1`，
  主线程 return 前读它，只有读到 1 的样本才算数，并让 worker 回报"主线程返回后多少毫秒
  才出来"。重跑 10/10 样本确实在原生码里跨过了收尾，仍然 0 崩。
- **形状 5 的对照组一开始也是假的**：新 Context 上没注册 `__cb`，JS 直接
  `ReferenceError`，被分类成"探针报错"（0/5 存活）。给每层 inner Context 补上
  `add_callable` 后对照组 5/5 活，这才算和 `same_inline` 可比。

另外，上一轮（第四十一轮）已经量过的两条继续成立，本轮没有推翻：**quickjs 求值期间
放 GIL**（`.probe/qjs_gil_held.py`，198 ms 求值期间旁路心跳最大间隔 2.0 ms），
所以"一条长 eval 把界面循环饿死"这条也**不成立**。

### 五、取证八：那 6 行 10054 到底是谁家的 socket（未定）

要判的是"远端书源主动 RST（引擎循环上的 aiohttp 客户端连接）"还是"Flet 客户端到

免得它先把异常吞成 `Error handling request`），收到 `/rst` 就写半个响应头，然后
`SO_LINGER=(1,0)` + `close()`；客户端用生产同构形状——**专属线程上的 asyncio 循环 +
aiohttp ClientSession**（即 `check_service` 的 probe/search 那条路），并给那条循环挂
`set_exception_handler` 把记录原样收回来。

`.probe/connection_reset_who_attr.py` → `.probe/out_rst_who.txt`：

```
GET /rst 调用方拿到 正常返回（1 ms）      ×2
GET /ok  调用方拿到 正常返回（0 ms）
捕获到 0 条循环级异常记录
```

**本机这个形状没复现**（aiohttp 把被截断的响应当读完就返回了，`_call_connection_lost`
一次都没进异常处理器）。所以：

- 不能断言"10054 是扫描噪声"，也不能断言"Flet 客户端掉过线"；
- 需要现场证据才判得了：下一次复现时，把每条 `Exception in callback ...` 的
  **线程名/loop id** 打出来（在两条循环上都装 `set_exception_handler`，只加标识、
  不改行为），一眼就知道是谁家的 socket。

`LegadoJsRuntime._journal_eval()`，调用点贴着 `ctx.eval` 那一行（所有准备工作之后、
`try:` 之前）。形状：4 MiB 定长环形文件（16384 条 × 256 B），字段
`ts pid th depth runtime fresh jslib bytes rule url`；默认落
`%LOCALAPPDATA%\LegadoBookSourceCheck\diagnostics\quickjs-eval.journal`，新建时把
上一份改名 `*.prev`（刚崩那份不能被下一轮扫描覆盖）；`LEGADO_JS_JOURNAL`
给 `0|off|no` 关掉、给路径就写到那里。

为什么必须落在**进原生码之前**、为什么是 mmap 环而不是"每行一刷"——都是当场测的。
`.probe/js_crash_journal_probe.py`（死亡姿势：`ctypes.CDLL("ucrtbase.dll")._invoke_watson`，
实测退出码与现场逐位相同 = 3221226505 = 0xC0000409；`ntdll` 根本不导出
`RtlFailFast`，第一版探针就是踩这个栽的，见 §六）每形状 3 个子进程：

| 形状 | rc | 盘上遗言 | faulthandler 栈 | atexit/SIGABRT |
| --- | --- | --- | --- | --- |
| `ring_nosync`（生产形状：不 close、不 msync） | 3221226505 ×3 | **100/100 条** | — | 0/3 |
| `ring_sync` | 3221226505 ×3 | 100/100 条 | — | 0/3 |
| `plain_flushed`（追加 + flush） | 3221226505 ×3 | 2/100 条 | — | 0/3 |
| `plain_buffered`（只 write 不 flush） | 3221226505 ×3 | **0/100 条** | — | 0/3 |
| `faulthandler`（enable 到文件） | 3221226505 ×3 | 100/100 条 | **0/3，文件 0 字节** | 0/3 |
| `fh_control`（同一接线，0xC0000005 访问违例） | 1 ×3 | 0 | **3/3，309 字节** | 3/3 |
| `no_journal` | 3221226505 ×3 | 0 | 0/3 | 0/3 |

两个结论：① `__fastfail` 绕过 Python 异常、信号处理器与 atexit，只有**已经写进盘**的
内容还算数；② 想靠 `faulthandler` 拿 traceback 拿不到（0/3、0 字节），而同一支接线在
可捕获的致命错误下落 3/3——那个 0/3 不是探针假阴性。所以"每行一刷"这条原计划
（待修清单 1 的字面写法）被换成 mmap 环：脏页写回由内核在进程结束时做，热路径上
不需要我们 msync。

成本（`.probe/js_journal_cost_attr.py` → `out_journal_cost.txt`，7 轮交替 × 20000 次）：

| 项 | 中位 | 占一段真规则 |
| --- | --- | --- |
| 拼字段 | 0.07 µs | 0.14% |
| 环形写（不 sync） | **0.38 µs** | 0.77% |
| 环形写 + 每行 msync | 23.47 µs | 47.16% |
| 追加 + flush | 1.74 µs | 3.50% |
| 一段真规则求值 | 49.78 µs | 100% |

字段压平（换行/制表会毁掉按行取证的形状）三臂对照，`.probe/js_journal_field_cost_attr.py`
→ `out_journal_field_ab.txt`，四臂按轮轮换起点、7 轮 × 30000 次：现编译正则 0.932 µs、

### 三、`:99` 的语义更正（照上游源码，不再照 .pyd 里的字符串猜）

`reference/` 目录**并不存在**（早前文档记的路径是过期的），本轮从 PyPI 拉
python-quickjs **1.19.4 sdist** 实读（`D:/tmp/qjs1194/quickjs-1.19.4/module.c`）。
四个记账函数与断言：

| 行 | 断言 | 真语义 |
| --- | --- | --- |
| `:81 prepare_call_js` / `:83` | `assert(!thread_state)` | 进原生段前槽位必须空 |
| `:90 end_call_js` / `:92` | `assert(thread_state)` | 出原生段时槽位必须是自己刚存的那位 |
| **`:98 prepare_call_python` / `:99`** | **`assert(thread_state)`** | **JS 回头调 Python 桥函数那一刻，槽位必须非空** |
| `:105 end_call_python` / `:106` | `assert(!thread_state)` | 回调期间槽位必须已让空 |

**所以第五十二轮写在 004 里的那句"`:99` = 出原生段时 thread_state 已空（进出配对失衡）"
是错的**——那句描述的是 `:92`/`:106`。`:99` 站在 **JS→Python 回调**这一层，全库唯一调用点是
`js_python_function_call`（`:411`，`prepare_call_python` 在 `:419`），也就是
`ctx.add_callable` 绑进去的那 109 个桥函数被 JS 调用的一刻。`thread_state` 是
**每条 `_quickjs.Context` 一份**（`RuntimeData` 就是 Context 对象本体，`:27`，注释
"Used when releasing the GIL"）。

于是"`:99` 为什么会空"收窄成三条路，全指向**同一个 Context 在 eval 期间被别的东西碰过**：

1. 另一条线程在同一条 Context 上走完 `end_call_js`（`:90`）——它会读走槽位并置 `NULL`；
   原生入口一共四个（`runtime_eval :507`、`runtime_module :533`、`object_call :257`、
   `runtime_execute_pending_job :536`），日志只覆盖了第一个；
2. `js_python_function_finalizer`（`:382`，体 `:385-408`）——上游自己写着
   `NOTE: This may be called from e.g. runtime_dealloc, but also from e.g. JS_Eval …
   TODO: integrate better with (prepare|end)_call_(python|js)`（`:388`），它在
   `Py_XDECREF(node->obj)` 前后直接翻 `thread_state`；触发者是 `runtime_clear`（`:371`，
   循环 GC）或 eval 里重绑旧绑定的释放；
3. Python 侧从别处调 JS 函数对象再回到 Python（`object_call` 那一族）。

另外确认一条**生产早已绕开的坑**：`js_python_function_call` 开头有一句
`has_time_limit` 就抛 `Can not call into Python with a time limit set.`——这正是
`legado_js.py:936-943` 那段注释说"只设内存上限、不设 time limit"的原因，
本轮从源码侧再钉一次。

### 四、照现场造的两个新形状，还是 0 崩

现场说"一条 Context 被进了 5112 次、每次重绑 109 个桥函数"，那这两个就得单独否证：

| 形状 | 臂 | 样本 | 结果 |
| --- | --- | --- | --- |
| 一条共享 Context 上反复重绑 | `accumulate`(重绑+eval，生产形状) / `bindonce`(只绑一次) / `rebindonly`(只重绑不 eval) | 8000 轮 × 109 = **872 000 次重绑**，`.probe/qjs_shared_context_rebind_attr.py 8000 109` | 三臂 rc=0 全活（1.2 s / 0.7 s / 0.5 s） |
| 循环 GC 在**别的线程**上收"捕获了 Context 所有者的桥闭包" | `gcaway`(B 线程纯 Python churn 逼 GC 落在 B) / `gconA`(无 B) / `plain`(绑不捕获所有者的 lambda) / `nogc`(禁用 GC) | 40 轮 × 109 个环闭包 + 每轮一次 40 万次循环的 eval，`.probe/qjs_gc_cross_thread_attr.py 40` | 四臂 rc=0 全活 |

四臂的分工是关键：`plain` 抽掉"环"、`nogc` 抽掉"GC"，如果只有 `gcaway` 崩才归得到
"跨线程循环 GC"。这条假设**没被证实也没被推翻**（0 崩），但它把"跨线程 GC"从
"最可能的形状"降成了"要现场才能判的形状"。

至此 004 表格里离线否证的候选累计 **8 个形状**。剩下活着的只有一个：
**某条 journal 当时看不见的线程，在这条 eval 结束前碰了这条 Context。**

### 五、日志升级：四种记录 + 在飞表 + 读回器

`app/services/engine/legado_js.py`：

| 记录 | 写点 | 字段 |
| --- | --- | --- |
| `ev=E` | `_journal_eval`，紧贴 `ctx.eval` 之前（位置由源码行号护栏钉住） | `ts pid th` **`thid`** `depth runtime fresh jslib bytes rule url` |
| `ev=X` | `_journal_leave`，`_evaluate_locked` 的 `finally` **第一句** | `thid runtime` **`ref=`**`<自己那条 E 的序号>` `took=<ms>` `out=ok 或 err` |
| `ev=!` | `_journal_eval` 发现这条 `runtime` 已在飞、而在飞的**线程 id 不是自己** | `thid runtime` **`other_thid other_seq`** |
| `ev=C` | `close()` 第一句 `_journal_close` | `thid` **`inst=0x…`** `shared=<共享 Context 条数>` |

- 为什么加**数字** `thid` 而不只看线程名：线程名会重名（两条 `Thread-N`），而 `:99` 判的
  恰恰是"是不是同一条线程"，`get_ident()` 才是可比量。
- `write()` 现在**返回序号**（失败仍只是置"日志不可用"，绝不抛），配对靠这个序号做 `ref=`。
- 在飞表 `_JOURNAL_INFLIGHT: dict[ctx 序号, (线程 id, 进记录序号, 上一层同款)]` 是进程级的：
  进时压上一层、出时还回上一层（嵌套 `depth>1` 也能配对），`_journal_leave` 弹干净。
  `ev=!` 正常**永远不该出现**（求值都排在 dispatcher 唯一线程上）——出现就是现场证据，
  而且它**落在进之前**，崩了也还在盘上。
- 读回器 `crash_journal_inflight(path=None, limit=8)`：把整环读完、收齐所有 `ref=`，
  回"有 `E` 没 `X`"的那几条。判"没回来"只能靠成对，**不能看尾巴**——尾巴可能只是被
  环形容量挤掉的顺序假象。`_journal_kind()` 把**没有 `ev=` 的老记录按 `E` 处理**，
  所以在 `crash-20260930-131140.journal` 上它会回"最后 8 条都没出来"：那是**格式换代**，
  不是第八条线索。
- 容量 4 MiB → **8 MiB**（`_JOURNAL_SIZE`，32768 条 = 16384 对）：现场 15.49 分钟写 13010 条，
  成对后同样时长要写 ~26000 条，4 MiB 大约 8 分钟就开始吃掉开头。

一次真实求值的三条记录（本轮 smoke，`LEGADO_JS_JOURNAL` 指到临时路径）：

```
#1 ev=E ts=1790747753.042 pid=68680 th=legado-quickjs thid=52736 depth=1 runtime=1 fresh=1 jslib=5af957c7 bytes=16 rule=ruleSearch.bookUrl url=https://journal-demo.test
#2 ev=X ts=1790747753.050 pid=68680 th=legado-quickjs thid=52736 runtime=1 ref=1 took=0.0 out=ok
#3 ev=C ts=1790747753.051 pid=68680 th=MainThread thid=70804 inst=0x2061146a030 shared=1
```

`#3` 的 `thid=70804` 与求值线程 `52736` **不同**——这条 smoke 顺手证实了
"实例是在主线程 close 的，而它手上那条共享 Context 的最后一任引用就在主线程掉下去"
这个形状**在生产里真的存在**（`close()` 不清 `_shared_js_contexts`，字典随实例一起没）。
这正是第三节的嫌疑 #2 的入口，而它以前一条记录都没有。
