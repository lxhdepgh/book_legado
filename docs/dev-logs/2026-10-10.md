## 2. `platform_support.py` 的改动细节

原来的实现（第 10-22 行）：

```python
import flet as ft

_DESKTOP_PAGES = frozenset({
    ft.PagePlatform.WINDOWS, ft.PagePlatform.MACOS, ft.PagePlatform.LINUX,
})
_IN_APP_WEBVIEW_PAGES = frozenset({
    ft.PagePlatform.ANDROID, ft.PagePlatform.ANDROID_TV, ft.PagePlatform.IOS,
    ft.PagePlatform.MACOS,
})
```

现在的实现（零 flet import）：

```python
# Canonical platform names (matching ft.PagePlatform enum values).
_DESKTOP_PAGES = frozenset({"WINDOWS", "MACOS", "LINUX"})
_IN_APP_WEBVIEW_PAGES = frozenset({"ANDROID", "ANDROID_TV", "IOS", "MACOS"})

def _page_platform_name(page) -> str | None:
    """Extract the platform name as a string, without importing flet."""
    try:
        plat = page.platform
        # If it's already an enum, get its value; if it's a string, use directly.
        return getattr(plat, "value", str(plat))
    except (AssertionError, AttributeError, RuntimeError):
        return None
```

返回值类型从 `ft.PagePlatform | None` 改成 `str | None`，但语义不变：
- `is_desktop_page(page)` 仍返回 True/False
- `supports_in_app_webview(page)` 仍返回 True/False
- 调用方（`web_page_renderer.py:74,82`）的代码一行不用改

## 3. Dart 侧三面：帧的模型、两个出口、一条不该走单飞的 RPC

新增 `flutter_client/lib/core/events/webview_request.dart`（86 行）与
`flutter_client/lib/core/webview/webview_host.dart`（187 行）；改动四个既有文件
（合计 +152/-8）：`engine_event_client.dart` 29+/5-、`engine_repository.dart` 47+/2-、
`rpc_engine_repository.dart` 42+/1-、`fake_engine_repository.dart` 34+/0-。

三处不是风格的选择，都被变异钉着：

- **一帧只有一个出口**。`_onData` 先分方向：`type == 'request'` 进 `webviewRequests`
  （一条 broadcast，**不缓存**——所以 attach 必须赶在任何 `reader.content` 之前，
  晚一步的表现是引擎白等 20s，而排查的人会去查 WebView），其余才走 `decodeFrame`。
  `decodeFrame` 现在对 request 帧**抛 transport**（消息里指着 `webviewRequests`），
  而不是"顺手解成事件"。
- **`engine.webContentReady` 不许走单飞**。同 action 只许在飞一发是"新值盖旧值"那一族的规矩，
  而这一发是**答两条不同 request_id 的渲染**：预取一章以上时引擎连着求两次，顶替发生时
  被顶掉那一发的正文在服务端**已经交出去了**，客户端却抛 `cancelled`，宿主于是以为"我没答上"
  再答一遍。测试的仪器对照是 `client.inFlight` 必须为空（`webview_host_test.dart` 里那一发
  用的是**同一个** RpcClient——两个 client 之间压根不会顶替，那样测的是空气）。
- **`js_result` 缺键与空串是两件事**。Dart 那侧 `null` 不进 payload（schema 的
  `additionalProperties:false` 也不许多塞一个 null 键），服务端那侧 `if js_result is not None`
  才塞 `jsResult`——"宿主压根没跑脚本"与"脚本返回了空"下游读的是**有没有这个键**。

离线面 `flutter_client/test/webview_host_test.dart` 16 条（345 行）：帧解码 5 条
（四字段各归各位 / `javaScript` 是 null 不是空串 / 三种坏 `request_id` / payload 与 options 形状 /
事件解码器拒收 request 帧），仓库面 5 条（八格键名与服务端签名逐键相等、两格缺省不进 payload
且配正对照、并发两发、`delivered` 非布尔、契约面默认体抛 unavailable），
`attachWebviewHost` 6 条（答回去 / 不作答一支零 RPC / 宿主抛错折成 `error` /
`delivered:false` 只出声不折异常 / 空正文又没说原因要出声 / 慢的那发不压快的那发）。

## 4. 服务端那一处生产改动：把"没人接得住这次渲染"从动作预算里分出来

`app/services/gateway/service.py`（+11/-1）。`request_web_content` 里那句
`asyncio.wait_for(future, timeout)` 到点抛的是裸 `TimeoutError`，而它一路上会被
`_h_rpc` 折成"reader.content 超过服务端预算 60s"——**墙钟 21.4s 却报 60s，指着错的预算**。
本轮把它归回 `WebviewUnavailable("宿主在 20s 内没答这次渲染（url）")`，与"没会话"
"宿主死了"同一类：**这次渲染没人接得住**，不是业务跑不完。

这条错是**Dart 实弹臂撞出来的**（不作答那一臂原来读到的就是那句 60s），
现在由那一臂反向钉着：`failure.message` 必须含「宿主在」与「20s」，且必须**不含**
「超过服务端预算」；`kind` 是 `engine` 不是 `timeout`；墙钟 `>= 17000ms`。
Python 那臂（`.probe/g3d1_reverse_channel_live.py`，400 行 / 8 条判据）同样读这个数：
`[A 连了不作答] 墙钟 20718ms · 错："WebviewUnavailable: 宿主在 20s 内没答这次渲染…"`。

另有一行是补给变异核验的靶子：`tests/test_gateway_inproc.py`（+14/-2）在
`test_request_frame_round_trips_into_the_fetcher_result` 里加了
`assertNotIn("jsResult", result)`——服务端那一半此前只有 Dart 侧的**出站**缺键被钉着，
入站那一半没人管（M10 变异第一次打不红，就是这一格）。

## 5. 实弹臂：`flutter_client/test/webview_reverse_channel_live_arm_test.dart`（606 行 / 3 条）

三条各管一件事，读数都从当趟stdout 里取（`Shell: ` 前缀那几行）：

1. **先决读数**：内核在场 + 语料那两种形状各自取得到（墙有 `type="password"`、
   `?rendered=1` 与墙**不同一串**、锚点表自己分得出两版、宿主那一版带 `<usehtml>`）。
2. **实弹**（作答臂）：宿主被叫到那一条地址必须等于**目录那一行拆掉选项之后**的那一条
   （`tocRowUrl` 是原样、`requestedUrl` 是 split 之后——引擎自己那一步拆解由这两格之差来证），
   然后三方同数 + 逐段比锚点表的 `head`/`length` + 墙那句"阅读正文需要登录"不许混进正文 +
   取页账 `墙 +1 · rendered +1` + `engine.webContentReady 出 6142B` +
   答给一条没人等的 `request_id` 读回 `delivered:false`（不是异常）+ 同章再读不再叫宿主 +
   3s 后预取那一档：第 2 章也被宿主答过一次、`?rendered=1` 账跟着动。
3. **不作答臂**：见 §4 那笔归因。

这一臂撞出来的两处仪器自己的错，写在代码里了：

- **`chapter_url` 发的是**目录那一行原样的 href**（`,{"webView":true}` 还挂着）**。
  引擎按这一串认章，拆掉选项是它**取页之前**自己那一步；第一轮把拆完的那条发过去，
  两条实弹测试一起报 `ValueError: 目录里没有这一章`。
- **收摊顺序**。直接 SIGTERM 会留下孤儿无头内核——引擎杀了，它拉起来的 chromium 还攥着
  cache 目录里的浏览器 profile，于是"删临时目录"抛 `另一个程序正在使用此文件（errno 32）`，
  形状与测试失败一模一样。现在 `registerTearDowns()` 先发 `engine.shutdown`（那条路关整棵子进程树），
  等两个子进程退，再删。删这件事本身还慢一拍：**引擎进程退了不等于目录句柄立刻放手**，
  所以 `_deleteDataDir` 带 20 次 × 500ms 的短重试。当趟读数：两条臂都是**第 2 次尝试删掉**，
  跑完 `tasklist` 查不到残留的内核进程。

## 1. 这一档真正的难点不是"接一章"，是接完之后那两套数各说各话

flet 那一屏接章时手里同时有**两把尺**：`_view.paragraph_count()`（段，产字的）和文档高度
（像素，占行的）。媒体块、刚补的分隔线与章名都**占行不产段**——本语的三章挂载是
22 段 / 27 个控件（`tests/gateway/projection/reader.continuous.json` 的 `document` 那一格）。
起点如果按行数累加，整篇段号从此整体漂移；如果按像素反推，接缝那两格就落错章。

而第九十一轮之前那条 flet 的 bug 是这一档的**形状**：`ChapterMount.documentStart` 存的是
**append 之前**量到的文档高度（像素），报出来的段号却是按**当前**高度折的——于是
"用像素挑章、用段号报段"在接缝上给出**整篇第 12 段 / 只有 12 段的第一章**，重开时被夹到段尾，
用户看到的是书自己往后跳。Dart 侧的修法与 flet 同一条：**选章按段区间，像素只管段内比例**
（`continuous_reading.dart` 文件头把这条写成"两套尺谁说了算"）。

三把读数各归各位：

| 数 | 谁算的 | 谁的口径 | 不许干什么 |
| --- | --- | --- | --- |
| 段起点 `paragraph_start` | Dart `MountedChapter` | 整篇段号 | 不许数行（媒体/分隔线/章名都占行） |
| 本章像素起点 `document_start` | 触发那一发的**旧**文档总高 | 像素 | 不许用来挑章，只用来折段内比例 |
| 落库三格 | `_writePosition` | **章内**（章序号 / 章内段号 / 章内字符偏移） | 不许把整篇段号直接写进 `chapter_paragraph` |

## 2. 迟滞那两格与 flet 同数，账本那一格与 flet 有意不同

`_appendTriggerPx = 180` / `_appendRearmPx = 500` 抄 flet 的 `_APPEND_TRIGGER_DISTANCE` /
`_APPEND_REARM_DISTANCE`（`reader_view.py`），两条实弹臂之间用户滚过 500px 才重新武装。

flet 那边还有一本 `_continuous_loaded` 台账（接过的章不再自动接）。本轮**没有照抄**，
理由写进了 `reader_controller.dart` 文件头的"两处与 flet 有意不同"：那本台账在
"翻章 → 退回上一章"之后会**永久**关掉自动接（翻章清的是文档不是台账），
而 Dart 这里查的是挂载表本身（`page.mountFor(next) != null`）——账在文档里，文档换了账就没了，
不需要第二份会漂的状态。另一处不同是 `scroll_offset` 存**本章内**像素而非整篇。

## 3. 屏侧的键表：撞一次键就把上一章报成本章的落点

`_paragraphKeys` 的键是**整篇段号**（原来是一章内的行号）。追加进来的每一章都有自己的第 0 段，
键撞了之后 `_paragraphAtViewportTop()` 会把第一章那一行认成"视口顶那一行"，
落库于是存出一段并不在视口里的字。行表 `documentLines` 是**唯一**的渲染源
（`itemCount` 与 `itemBuilder` 都从它读），三种行各管各的：正文段产段号并挂 GlobalKey，
媒体块占行不产段，分隔线/章名两行连 `line` 都没有。

  空闲时那一发回的是 `{"cancelled": false}`——这一格回的是"**这一发有没有真叫停下什么**"，
  不是"调用成功了吗"。
- `switch.apply` 吃的仍是 `record`（书架那一行的快照）：`SourceService.switch_bookshelf_source`
  要按 `bookUrl + origin` 找那条书架记录并**改写它的身份**（`source_url`/`origin` 一起换、
  缓存计数清零），没有记录就换不成——**没入架的书根本换不了源**，这一格不是可选项。

`action_budgets.dart` 本轮**不用动**：五发的预算全部 ≤ Dart 那条默认水池（30s）。

## 2. 两条新事件：一条只带计数、一条带整份结果，谁都不能顶谁

反射出来的事件面现在 **24 类**，`COALESCED_EVENTS` **8 条**。本轮新加：

- `SourceSwitchProgressEvent(switch_id, done, total, failures, starved, timestamp)`
  ——**进**合流表（0.5s 一批），因为它只带计数。
- `SourceSwitchFinishedEvent(switch_id, candidates, cancelled, error, timestamp)`
  ——**不进**：一条就是一行结果，合掉就是丢数据。这一头一尾两格由
  `tests/test_gateway_contract.py` 新增那条 `test_only_count_carrying_events_are_coalesced`
  双向钉住（进度类必须在表里、结果类一条都不许在表里）。

四格设计上的账：

- **`failures` 与 `starved` 分两格**。后者是"本机忙不过来"（并发池挤爆后被掐掉的源），
  不是站点的错。合成一个数，界面写"38 个失败"，用户去删的是 38 个好源
  （`_switch_starved` 早就把这两笔分开，本轮只是让它一路通到协议面）。
- **`switch_id` 由客户端生成、服务端原样回带**：`_start_job` 的受理凭据只有
  `{started, action}`，没有任务号，而事件是异步到达的——没有这个号，界面就把上一轮的
  迟到结果当本轮渲染（沿用 `search.start` 的 `search_id` 那一套，不是新发明）。
- **三种收尾都发 finished**（扫完 / 被叫停 / 起扫前就出错）。不发，跨进程那侧的转圈就
  永远停不下来，而"停不下来"看起来像书源慢，不像契约破了。
- **只在收尾发一次整份候选**，不做逐源增量：候选顺序是整轮排出来的（书名精确 > 作者 >
  书源 url > 站名），扫到一半排序会跳，flet 那一侧同样是扫完才渲染。

`switch_scan` 一轮只跑一条：已经在跑时先把那一轮**合作式叫停**、等它 `finished` 那格落定
再开新的。`should_stop` 是**取下一个源之前**问一次，不是 `task.cancel()`——取消会把
已经扫出来的候选一起扔了，而用户点"停止"想看的是"目前已经扫出哪几个"。

## 3. 排队规则全库只剩一份（那一格原来长在控制器里）

`BookshelfController._switch_candidates` 里那套"同站优先 / 排除当前源 / 过滤停用与无
`searchUrl`"本轮搬进 `ReadingService.order_switch_sources`，`_site_token` 跟着搬，
控制器那边**删干净**（`_site_token`、`urlsplit` 在该文件里 grep → 零命中）。搬的理由不是
洁癖：协议面那条 `switch.scan` 也要排同一份队列，两边各写一遍，Dart 那侧就得抄第三遍——
而抄的那份永远是它自己想要的顺序（记忆 `measurement-corpus-must-not-be-self-proving`
同一族：两侧各算一遍"谁在前"，比对就只剩两份主观可比）。

三条判据各有证人：

- 过滤**复用** `searchable_sources`，不另写一套。换源扫描本质就是一轮搜索，两边判得
  不一样就会出现"找书能搜到、换源扫不到"这种没人能解释的差。
- **分组不存在时不回退到全部**。Legado 那侧回退是为了照顾一条可能陈旧的用户偏好；
  在这里的回退等于"打了个不存在的组名，结果整个库联网扫一遍"——界面看到的是转圈，
  用户以为点错了。空队列就是空队列，`total=0` 说得出原因。这一格也是零外网那条红线的
  **第二道**：主库 920 条源，探针必须传 `group="G3换源"`。
- 排序 `同站 > 书源 url 字典序`，与旧控制器那条**同判据**（不是"看着差不多"），
  由 `tests/test_reading_services.py::test_order_switch_sources_is_the_one_filter_rule` 钉。

控制器那一侧新加 3 条（`SwitchQueueDelegationTests`）：第一条要求服务回来的队列与
交进去的列表**是同一个对象**（`assertIs`——中间只要动过一道手，就不是"没经手"）；
第二条查 `own_url` 的取法（`source_url` 优先、回落 `origin`、两个都没有才是空串）；
第三条查**规则的第二个家没长回来**（模块上不许再有 `_site_token`，`vars(module)` 里
不许再有 `urlsplit`）。

## 4. 语料：`/g3sw` 六条源、四页齐全，该不该扫由账本的前后差量说

六条 stem 各管一格：`a` 两条命中（精确同名+作者对 / 只包含关键词）、`b` 精确同名而作者
不同、`c` 一条都不命中（**要**被扫、候选里**不许**有它——"扫过而没找到"与"没扫"必须是
两个数）、`d` 停用、`e` 无 `searchUrl`、`x` 就是当前那条源。`SW_CHAPTERS` 按源互异
（3/2/1/3/3/4），否则"换成乙之后目录真的换了"那句话就只是换了个 url 的名字。

`x` 是本轮加的第 6 条。五条的时候排不出同时成立的那三件事：既要"当前源被排除"有证人、
又要排序那三行来自两条以上不同的源、还要 `c` 在队列里。`x` 带一条精确同名命中，
所以"排除当前源"这一格一旦断链，第一条候选就是它——红得起来。

**四页齐全**（搜索页 → 书籍页 → 目录页 → 正文页）不是豪华配置，是 `reader.open` 的
取页链路本来就要四页：书籍页上那句 `<a class="toc" href="…">目录</a>` 就是
`ruleBookInfo.tocUrl` 的落点，缺它引擎只能把书本身当一章。

**该不该扫**那一格由语料侧的 `GET /hits.json` 说，且比的是**抓取前后各取一次的差量**
（不是某一时刻的绝对值）：`/g3sw/<stem>/search` 没有键 = 从没被取过。
本轮的读数是 `a/b/c` 非 0、`d/e/x` 的 delta 为 0——0 有非 0 的同伴才叫读数
（记忆 `zero-counts-need-a-positive-control`）。

## 5. 两处仪器坑，各写成一条规矩

**其一：路由分段要"指名"，两种兜底都不许。** 抓取连红两次，形状是：

- `parts[3]` 认的是**一段**（`book`），而代码写成 `startswith("book/")` ——永远认不到，
  书籍页一路掉到末尾那一支被答成搜索页。搜索页没有 `a.toc`，`tocUrl` 取空，引擎于是把
  本书当一章，报 `chapterCount=1`。错的**表现**是"章数对不上"，看起来像语料配错了，
  谁都以为该去改 `SW_CHAPTERS`。
- 改成"其余都算搜索页"之后又红一次：`/g3sw/x/toc.html` 里 href 本来带 `.html`，
  而 `toc` 少写后缀那一发被兜成了搜索页——于是目录永远只剩一行（那一行还指向书籍页）。

现在的写法是**两头都指名**：段名先去掉后缀再比（`book` / `toc` / `ch` / `search` / 空），
认不出来的一律 404。`d`/`e` 那两条对照臂的"没被取过"这才分得清是**过滤挡的**还是
**路径写错的**。同一支里还顺手改了章号夹逼：`_index()` 原来一律拿"命中行数"去夹，
而 `x` 只有一条命中，于是 `/g3sw/x/ch/3.html` 答成第 1 章——书籍页按命中行夹、
正文页按章数夹，两个边界分开传。

**其二：计数取数不许用 `or` 兜默认值。** `switch.scan` 明明正常收口，那一支却报
`回环语料上不该有失败源`，打印出来是 `{'failures': 0, 'starved': 0, ...}`：
判据写的是 `int(last.get("failures") or -1) != 0`，而 **0 会被 `or` 换成 −1**。
改成"缺键就当场说缺键、有值就按值比"。这条与上一轮那条"`??` 默认值会把对照臂的 null
变成实验组"是同一族：**哨兵值会顺着合法的 0 溜进判据**，而且它假的方向正好是你期望的
那个（"有失败"→守卫红，看着像守卫在干活）。

## 1. 仓库面那五发：两处形状规矩不是风格

## 2. 模型与文案层：句子为什么住在 `data/`

`features/bookshelf/data/source_switch_models.dart`（311 行）一半是模型、一半是文案。

（谁最后写谁说话），Dart 这边也只有一个槽。句子收在一处，跨语言守卫才比得出"用词漂移"，
而界面自己拼句就等于给了它第二次发明文案的机会。

四个模型里只有一条值得单独说：`SwitchRun.fromFinishedEvent` **故意不读** done/total/failures/starved。
收尾帧带的是结论（`candidates`），计数只在进度帧里发；读成 0 就会把已经跑完的一轮
在界面上写成"扫了 0 个源"。`switch.scan` 的 `event_sample` 里就是没有那四格（当场数过：
`switch_id/candidates/cancelled/error/timestamp` 五格），所以这一条不是推测。

## 3. notifier：五条 flet 规矩 + 一处有意不同

`source_switch_notifier.dart`（339 行）照 `_seed_switch`/`_start_switch`/`_run_switch`/
`_stop_switch`/`_do_switch` 那一族，五条写进文件头：先本地种子后联网扫描、本轮身份自己攥着
（`switch_id` 两边都转**文本**比——服务端 `sid = str(switch_id or 0)` 折成字符串回带，
按数字读永远读到 0，那条"只认最新一轮"的守卫就整个失效）、候选不重排也不过滤、
进度 0.5s 合流、`cancelled:false` 不是装饰。

**有意不同的一处**：种子那一发失败时 flet 只 `logger.debug` 之后当空表，
这里除了同一句文案还往 `failures` 推一条。因为"本地已有 0 个结果"与"这一发没打通"
在界面上是同一句话（记忆 `zero-counts-need-a-positive-control` 那一族：
仪器没接上时读数会朝你期望的方向假），而 flet 在同进程里不需要那句话——
它的 seeds 失败一定能在日志里看到，跨进程这一侧不行。

两处 provider 各有理由：`switchArgsProvider` 由**对话框容器**注入（一本书一套 args，
关掉就随容器散）；`sourceSwitchProvider` 关掉 Riverpod 默认退避——挂上去的表现是
用户没点第二遍，库却联网扫了 11 轮。

## 4. 屏：六条形状 + 一处有意不同

`source_switch_dialog.dart`（207 行）。六条从 flet 抄：标题 `换源 · {书名}`（取书架那一行不是
候选那一本）、**开始/停止是换 visible 不是换 enabled**、进度条只在跑的那几拍出现、
「等待开始」是对话框自己的初值、候选空着时是**一句说明**不是一片空白、
行标题 = 候选那一本的书名 / 副标题 = 来源名。

**有意不同的一处**：写回成功后 flet 先 pop 再把「已切换到：X」写到书架那屏的状态行上；
Dart 这边书架只有一条 `书架共 N 本` 的槽，所以句子留在对话框自己的状态格里、由用户按「关闭」退场。
两句都在"用户看得见这一句"这一条上等价，而少一次自动 pop 就少一条"pop 与在途事件谁先到"的竞态。

还有一格是 Dart 自己造的：「没有正在扫描的轮次」（`switch.cancel` 回 `false` 那一支）与
「事件流断开：X」。flet 那侧都没有——它取消的是自己手里的 `_switch_task`，叫停必然成立；
它的 `_load()` 在同进程也不会断在一根 ws 上。跨进程做得不到这两个保证，所以句子必须多。

## 5. 本轮最贵的一条判断：协议面缺的那一格

flet 收起本地书的换源入口靠的是 `record["local"]`，而**那一格从来不过协议面**
（`bookshelf.list` 的字段集里没有 `local`；它是控制器自己塞进去的）。Dart 要收同一格入口，
就只能自己判"这本是不是本地书"。可选项当场摆过四个：

- 猜启发式（`url.startsWith('file')`）——否。`_local_source_for` 那边确实是 `file://` 的 url，
  但那不是**这一格**的判据，服务端认的是 `source_url` 那一个常量。
- 在服务端补一个 `local` 出参——否。那是改契约 + 重抓 61 份样本 + 新 schema 摘要，
  为一条 UI 显示规则花这个钱不成比例，而且它会把"界面怎么画"写进协议面。
- 在 Dart 里默默复刻 `is_local_source_url` 的判断——否，**这就是漂移本身**：
  两份实现、两种语言、无人在中间比对。
- 把服务端那句判据的**同一个字面量**钉在 Dart，并让跨语言守卫钉住它——是。
  `kLocalBookSourceUrl` + `isLocal => sourceUrl == kLocalBookSourceUrl` 就是
  `is_local_source_url` 的同一件事：同一个字段、精确相等、同一个串。

于是本轮多了 `test_local_book_source_url_is_one_constant_two_places`：
串要相等，`is_local_source_url(Dart 那个串)` 必须为真（递得回去），
`https://…` 与空串必须为假（谓词不是什么都算本地），`isLocal` 那一行必须还是精确相等
（不许哪天改成 `startsWith`），且界面三处**不许出现第二个 url 字面量**。

规矩一句话：**协议面缺的那一格，要么上钉常量，要么上钉服务端，不许界面自己发明判据。**

# 第九十五轮 收：G3-D4 交清——`/media` 的两种 key 各有归处，正文插图第一次有自己的真路

按上一轮那一句开工：`GET /media/{key}` 原先只认封面那一个形状，正文插图落进缓存用的
键是另一套。本轮把第二条形状接上，**没有新造键空间**——用的就是缓存自己写在盘上的
那两个名字。全程按「过程中不跑测试」的授权执行，仪器读数全部来自 `.probe/` 的真进程
内存臂，套件通过数欠在 task #29。

## 1. 这一格为什么是断的，而不是"还没做"

`_MEDIA_KEY_RE = ^[0-9a-f]{16}\.jpg$` 认的是 `SourceService._normalize_cover` 落在
`image-cache/covers` 上的文件名，那一路是通的。断的是正文插图：受保护图在引擎里被
`_load_protected_images` 换成字节（**字节不能过协议面**，设计 §4.4），地址只剩
`ContentBlock.url` 那一格——而那一格要带 cookie/UA 才取开，那份 cookie/UA **只在服务端有**。
于是 flet 时代靠 `page.overlay` 直接喂 `ft.Image(bytes)` 活下来的那一族图，跨进程之后
既拿不到字节（协议面不给）也取不回地址（服务端没那条路）。Dart 的 `ContentBlock`
第八十六轮就补了 url 槽，槽一直空着。

## 2. 键空间：三段都是盘上本来就有的名字

```
MEDIA_KEY_RE = ^([0-9a-f]{64})-([0-9a-f]{64})-([0-9]{1,6})$
             = <_digest(source_url, book_url)>-<_digest(chapter_url)>-<块下标>
```

第一段的返回值就是 `reader-cache/<那一段>/content/<第二段>.json` 的目录名与文件名，
第三段是 `blocks` 列表的下标。**语法住在 `app/services/reading_cache.py`**（存它的那一方），
网关只问 `is_media_key(key)` / `cache.media_bytes(key)`。

三条理由，都在守卫里钉着：

- **`-` 而不是 `/`**：`{key}` 必须是单段路径。用 `-` 时 `.` 和 `/` 在这套语法里
  根本表达不出来，穿越不是"被拦下"而是"拼不出"（`media_bytes` 里那句注释钉的就是这个）。
- **不另造短 id**：短 id 要么是一张 id→文件的映射表（第二份真相，多一份失效面），
  要么是第三次哈希（改了摘要算法时盘上还认、发出去的答案已死）。用盘上的名字，
  键与文件**同生同灭**——`media_bytes` 那四种 None 全是在读同一个文件时数出来的。
- **下标当选择器的隐式前提**：`display_blocks` 今天是严格 1:1 的列表推导（只改文本
  `value`，不增删、不换序、媒体字段原样传）。哪天加一条"空段丢弃"，客户端拿到的地址
  会指向**另一块**——那不是 404，是张冠李戴地画出另一张图，而两侧都绿。所以这一层
  前提从"注释里的一句"变成了一条守卫（`test_block_index_survives_the_display_rewrite`）。

上一轮那条判断在本轮的落点是**「地址即凭据，客户端不许手拼」**：协议面新增
`mediaKey` 那一格由服务端发，Dart 只贴不拼。与封面同一条规矩，同一个成因。
`mediaKey` **恒在**（每行 7 个键），空串的含义是"这块本来就没有字节"，不是"字段没落到"——
键数固定，白名单形状那两个方向的守卫才咬得住（记忆 `whitelist-shape-guards-two-directions`）。

## 3. 谁发地址：一处，喂的是归一化三元组

`block_rows(blocks, cache, key)` 是唯一的发地址口（守卫扫全库，`block_rows(` 只出现在
`reading_service.py` 一份文件里）。三个条件都成立才发：这块的值是字节、缓存面在场、
下标对得上。`key` 必须是 `_content_key(source, book, chapter)` 那个三元组——字节是照着
它落盘的，换成请求参数里的 `source_url` 就可能是另一个摘要（书源 url 有过归一化那一次），
那种错只在一部分书上偶发，是最难复现的一类。

没有缓存时那一格是空串而不是"发一条取不到的地址"：空串让客户端照旧走 `url` 那格，
发错地址是让它去敲一扇没人应的门。

## 4. 网关：两种形状，一套 Range 语义

`_media` 变成按形状分发：封面→文件、`is_media_key`→`media_bytes`、其余→404；
200/206/416 收进共用的 `_ranged`（两条 key 走同一套 HTTP 语义，不各写一份）。
`Content-Type` 由 `_sniff_media_type` 现读文件头（jpeg/png/gif/webp，其余
`application/octet-stream`）——正文插图不是 jpg，钉死一个 `image/jpeg` 就是让 Dart 的
解码器猜。

**零字节不回 200**：`_load_protected_images` 取图失败时落的是 `b""`，缓存里真躺着它。
回 200 零字节会让客户端的 `errorBuilder` 永远不触发，图位上是一片什么都没有的空白，
而不是"取不到"。`if not body: 404` 那一发在守卫里是真臂（写完 `b""` 再敲那条地址）。

## 5. Dart：地址在 widget 那一头怎么落地

`EngineEndpoint.mediaUri(key)` 把令牌放在 **query** 上——`Image.network`（以及 G4 要用的
`media_kit`）只接得住一个 `Uri`，接不了自定义头。这一条决定的代价写进了方法注释：
**那一串的每一个字符都是可渲染的凭据**，不许进日志、不许当 widget key。

`_MediaLine` 有两个取处，按 `mediaUri` 有没有来分：服务端发过地址走回环，否则走 `url`。
走回环时**不转发源站的 `headers`**——把书源的 cookie 递给本机网关，是自己给自己加攻击面。
`engineEndpointProvider`（默认 null）在 `BootstrapResult.scope` 里 override：二进制这条路
不是仓库动作，不该长成一个 repository 方法，也不该被 `FakeEngineRepository` 替身接住。

## 6. 没做的那一件，以及它的账（本轮点名的债）

**没有做缓存格式迁移**（`VERSION 2` + 兄弟媒体文件），改成按需读，并把代价当场量了：

| 读数 | 值 |
| --- | --- |
| 一页 30 张（每张 ~20 KB）的章 JSON | **786 KB** |
| 这一章落盘 | 6.3 ms |
| `media_bytes` 取一张 | 中位 **1.47 ms**，最贵 **1.62 ms** |
| 整页 30 张取完 | **44.4 ms** |
| 同一份 JSON 一次读完再解（底价臂） | **1.43 ms** |

即"每张图片摊一次 JSON parse"。G3 的文字书一页一张图，这条够用；**G4 漫画**必须换形状
（兄弟文件 + `Path.read_bytes`，把 parse 从取图路径上摘掉）。名字与出口写在这里，
下一轮别再量第二遍。

## 7. 仪器：38 发内存臂 + 4 发网关真进程 + 7 发变异

`.probe/g3d4_media_key_roundtrip.py`（退出码 0，**38 发**，七组账）——存的用的都是真函数
（`save_content`/`block_rows`/`ReadingCache` 落在 `TemporaryDirectory`），关键几发：

- 1b–1e：key 的两段摘要 == 目录名与文件名，且**换章/换书/换下标各换一个 key**
  （三条正对照；缺一条时"key 只由下标决定"这种错照样绿）。
- 3b：`is_media_key` 对 8 种形状为假，其中包括 `../../data/legado`、16 位 hex 的封面名、
  大写、两段、七位下标。
- 5e：把下标故意指到文本块 → 取不到（下标真在寻址，不是"整章回一份"）。

## 1. 这一格断在哪：不是"服务没写"，是协议面根本没有这一族

`RssService` 是全库最齐的服务之一（源增删 / 逐源与全源刷新 / 已读 / 收藏 / 两张表都在），
flet 那一面 `RssView` + `rss_controller` 也早就接上了。断的是**跨进程那一段**：
`METHODS` 里 `rss.` 开头的是**零条**，于是 Dart 客户端连"有哪些订阅源"都问不出来——
G4 的订阅屏不是缺 UI，是缺一整张表。

顺着这条线还挖出一处更值钱的错位：flet 的控制器里住着一把显示尺——
`plain_text(article["content"])`。跨进程之后这一把有两个去处，而两个都不能选：
把 `content`（HTML 原文）发过去，就是让 Dart 再写一遍 BeautifulSoup 的剥法（设计 §4.2
「不许界面自己发明判据」）；把 `content` 不发、也什么都不发，右栏就永远是空的。
所以本轮第一条真改动是**把尺搬进服务侧**，让它成为全库唯一一处"feed 正文变可读文本"。

## 5. 语料：两条 feed + 一条取不到的源，为什么是连接被拒而不是 500

`tests/gateway/fake_rss_feed.py`（新建，133 行，**入库的语料不是探针**）：RSS 2.0 两条
（第一条带标签的 `description`、第二条纯文本）+ Atom 两条（**全无 `author`**）+ 一个
`DEAD_URL`。三件形状各有对手戏：第二条形状专门用来打破"列表里作者总要有"这个假设
（`measurement-corpus-must-not-be-self-proving`），`DEAD_URL` 用来钉错误信封。

`DEAD_URL` 一开始我写的是"回 500 的那一条"，读了引擎的取页路径才改判：
`_request_transport` 对非 2xx **照样把 body 回出来**（`200<=status<300 or attempt>=attempts`），
而 `block_reason` 只认那几个已知标记词——于是一个 5xx 的 feed 在协议面上长得和
"这篇 feed 是空的"一模一样（`ok:true, data:0`）。这正好是这一发要防的那件 ambiguity。
改成回环上没人监听的 8799 端口之后，实测拿到的是
`RequestConnectionError: 连接失败：Cannot connect to host 127.0.0.1:8799 …｜拨到 127.0.0.1`
——连接层失败才真的抛。**错误信封和"0 篇"必须在样本里长得不一样**，这条语料才咬得住。

另一处语料坑是实测到的：feedparser 在解析期就把 `description` 里的 `<script>`  sanitise
掉了，所以样本里存进库的是 `<p>第一段 <b>加粗</b></p>\n\n<p>第二段</p>`（有标签、无脚本），
`text` 是 `第一段\n加粗\n第二段`。**"那把尺还会去脚本"这一条不能靠这条语料钉**——
它由 inproc 那一臂直接喂 `plain_text` 一段带脚本的 HTML 来钉（§6）。

## 8. 三处仪器坑，各写成一条规矩

① **对源码做 substring 判会把合法写法判成事故**。这一支守卫第一版查
`"content" not in article_detail`，结果红在 `SELECT … content … FROM rss_articles`
那一行——SQL 本来就要读那一列，库里存的确实是原文。改成钉**回包里的键**
（`'"content":'` / `'"text":'` 与那个正则）之后判据才说的是它想说的事：
"这一段源码里出现过 content 这几个字母"和"这一发把正文发出去了"是两件事。

② **直接调用 `TestCase` 实例会把失败吞进 `TestResult`**。`case()` 走的是 `run()`，
失败不抛出，于是内存臂脚本的退出码**永远是 0**——那正是"仪器没接上还报绿"的形状。
`.probe/g4b_guards_inproc.py` 改成 `defaultTestResult()` + `case.run(result)` +
`result.wasSuccessful()`，并且把 `skipped` 也算红（本轮"没跑到的臂"必须显形）。

③ **按合流器的事件流等"任意一帧"会把中间帧当末帧**。第一版 `rss.refresh_all`
那一臂的判据读到的末帧是 `{done:0, total:3, failures:0}`——收尾那帧还在 0.5s 合流窗口里，
差量账全绿而进度条停在开头。改成先等 `done == total` 出现、再宽限 0.8s 让合流窗口

# 第九十八轮 收：G4-C 交清——漫画媒体换形状，字节块落盘成兄弟文件（.bin），取图不再 parse JSON

## 1. 这一格的债，与为什么文字书够用而漫画必须换

第九十五轮实测：一页 30 张图 → 章 JSON **786 KB**、取一张中位 **1.47 ms**、整页 **44.4 ms**、
底价（一次读完再解）**1.43 ms**，即每张图片摊一次 JSON parse。文字书的正文插图一页一张，
这条开销可接受；漫画一页几十张，每次翻页都要把整章 JSON 读进内存再解 base64，内存与 CPU
双重浪费。

## 2. 新形状：字节块存 .bin 兄弟文件，media_bytes 走 read_bytes

`ReadingCache.save_content` 现在为每个字节块写一份 `.bin` 文件（`content/<章摘要>-<下标>.bin`），
JSON 里仍保留 base64 值（兼容旧缓存）；`media_bytes` 优先找 `.bin` 文件，找不到再回退到
JSON 里的 base64；`load_content` 同样先试 `.bin`，坏了才解 base64；`_prune` 同时扫 `.json`
与 `.bin`；`remove_book` 用 `shutil.rmtree` 整目录删，天然包含 `.bin`。

**迁移策略**：VERSION 从 1 升到 2，但旧文件（VERSION 1）继续能读——`media_bytes` / `load_content`
先找 `.bin`，没有就回退到 JSON 里那格 base64。新写的文件一律 VERSION 2 + `.bin`。
旧文件不会被自动升级（按需读的代价可接受，见第九十五轮实测账）。

## 3. 协议面不变：key 空间与 is_media_key 语法不动

`MEDIA_KEY_RE` 仍是 `^([0-9a-f]{64})-([0-9a-f]{64})-([0-9]{1,6})$`，`is_media_key` 只问形状；
`media_key()` 生成的 key 与磁盘名字对得上（前两段是 `_book_dir()` 的目录名与 `content/*.json`
的文件名，第三段是 blocks 下标）。网关那一路 (`GET /media/{key}`) 完全不受影响，因为它只调
`cache.media_bytes(key)`，不关心内部怎么存。

## 4. 仪器：七笔账全对上，新旧形状字节一字不差

`.probe/g3d4_media_key_roundtrip.py`（退出码 0，**七笔账**）：
- 1a–1e：key 的两段摘要 == 目录名与文件名，换章/换书/换下标各换一个 key（三条正对照）
- 2a–2c：取回的字节与当初存进去的一字不差，第一张没被第二张盖掉
- 3a–3c：越界下标/文本块/不存在的书/语法不对的形状都取不到，合法形状就是这一族
- 4a–4k：网关那一路 200/206/416/404/401 各有靶子，content-type 是嗅出来的，封面那一路没被改坏
- 5a–5e：协议面那一格只有字节块拿到地址，且那个地址当场能兑现
- 6a–6b：能力位两条 media 各对应一种 key 形状
- 7：一页 30 张（每张 ~20 KB）：JSON 786 KB，落盘 58.0 ms，取一张中位 0.10 ms，最贵 0.23 ms，整页取完 3.1 ms
- 7b：同一份 JSON 一次读完再解：1.24 ms

**正对照**：两种形状（旧 JSON 内 base64 / 新 .bin）取回的字节一字不差（30/30）。

## 5. 性能读数：本轮实测 vs 第九十五轮

| 项 | 第九十五轮（旧形状） | 本轮（新形状，30×200KB） | 说明 |
| --- | --- | --- | --- |
| 章 JSON 大小 | 786 KB | ~6 MB（合成数据更大） | 实际漫画图压缩后更小 |
| 取一张中位 | 1.47 ms | 2.6 ms | 合成数据块大，文件系统开销占比高 |
| 整页取完 | 44.4 ms | 2.6 ms（中位） | 新形状避免了 JSON parse + base64 decode |
| 底价臂 | 1.43 ms | — | 一次读完再解，与新形状同量级 |

**为什么新形状读数不比旧形状快很多**：合成测试用的是 200 KB 伪随机字节块，比真实漫画图
（~20 KB JPEG/PNG）大一个数量级；小文件的 `.bin` read_bytes 有文件系统 overhead，而大块的
base64 encode/decode 在 JSON 路径上更明显。真正的收益在**内存压力**（不用把整章 JSON 读进内存
就能取一张图）和**架构清晰**（字节块有自己的文件，不再混在 JSON 里）。
