## 1. 这一档为什么是"最后一 rung"：内核不在，整条反向通道不会响

`main.py:86-96 _engine_browser_fetchers` 在 `browser.available_fetcher() is None` 时返回
`(None, None)`，于是 `url,{"webView":true}` 那一族**直接退回纯 HTTP**，反向通道压根不会响。
这时候"宿主没被叫到"与"通道断了"是**同一个形状**——所以两条实弹臂都把内核在场当**先决读数**
（当场取到 `chromium_installed=True @ C:\Users\73517\AppData\Local\ms-playwright`），
缺了它出声跳过而不是绿着过。Python 侧那一臂把这条写进了 `.probe/g3d1_live.out` 的第一行，
Dart 侧写进三条测试的开头（`markTestSkipped('这台机器没有无头内核：反向通道不会响')`）。

选择链是四段，本轮第一次每一段都有读数：

```
LegadoReadingEngine._request（url 带 webView 选项 且 webview_fetcher 不是 None）
  → BrowserService.render_webview → _silent_render（真无头内核渲染）
  → block_pages.looks_like_gate(那一版正文)  ← 认下"这页还要人"才不交内核那一版
  → _remote_webview = GatewayService.request_web_content → /ws 的 request 帧
  → 客户端 /rpc engine.webContentReady 把正文递回来
```

`looks_like_gate` 认的是**空正文**、共享的拦截页指纹、以及 `type="password"` 那个登录框
（`app/services/block_pages.py:72-85`）。语料那堵墙用的就是第三条。

## 3. Dart 侧三面：帧的模型、两个出口、一条不该走单飞的 RPC

新增 `flutter_client/lib/core/events/webview_request.dart`（86 行）与
`flutter_client/lib/core/webview/webview_host.dart`（187 行）；改动四个既有文件
（合计 +152/-8）：`engine_event_client.dart` 29+/5-、`engine_repository.dart` 47+/2-、
`rpc_engine_repository.dart` 42+/1-、`fake_engine_repository.dart` 34+/0-。

三处不是风格的选择，都被变异钉着：

- **一帧只有一个出口**。`_onData` 先分方向：`type == 'request'` 进 `webviewRequests`
  （一条 broadcast，**不缓存**——所以 attach 必须赶在任何 `reader.content` 之前，
  晚一步的表现是引擎白等 20s，而排查的人会去查 WebView），其余才走 `decodeFrame`。
  `decodeFrame` 现在对 request 帧**抛 transport**（消息里指着 `webviewRequests`），
  而不是"顺手解成事件"。
- **`engine.webContentReady` 不许走单飞**。同 action 只许在飞一发是"新值盖旧值"那一族的规矩，
  而这一发是**答两条不同 request_id 的渲染**：预取一章以上时引擎连着求两次，顶替发生时
  被顶掉那一发的正文在服务端**已经交出去了**，客户端却抛 `cancelled`，宿主于是以为"我没答上"
  再答一遍。测试的仪器对照是 `client.inFlight` 必须为空（`webview_host_test.dart` 里那一发
  用的是**同一个** RpcClient——两个 client 之间压根不会顶替，那样测的是空气）。
- **`js_result` 缺键与空串是两件事**。Dart 那侧 `null` 不进 payload（schema 的
  `additionalProperties:false` 也不许多塞一个 null 键），服务端那侧 `if js_result is not None`
  才塞 `jsResult`——"宿主压根没跑脚本"与"脚本返回了空"下游读的是**有没有这个键**。

离线面 `flutter_client/test/webview_host_test.dart` 16 条（345 行）：帧解码 5 条
（四字段各归各位 / `javaScript` 是 null 不是空串 / 三种坏 `request_id` / payload 与 options 形状 /
事件解码器拒收 request 帧），仓库面 5 条（八格键名与服务端签名逐键相等、两格缺省不进 payload
且配正对照、并发两发、`delivered` 非布尔、契约面默认体抛 unavailable），
`attachWebviewHost` 6 条（答回去 / 不作答一支零 RPC / 宿主抛错折成 `error` /
`delivered:false` 只出声不折异常 / 空正文又没说原因要出声 / 慢的那发不压快的那发）。

## 4. 服务端那一处生产改动：把"没人接得住这次渲染"从动作预算里分出来

`app/services/gateway/service.py`（+11/-1）。`request_web_content` 里那句
`asyncio.wait_for(future, timeout)` 到点抛的是裸 `TimeoutError`，而它一路上会被
`_h_rpc` 折成"reader.content 超过服务端预算 60s"——**墙钟 21.4s 却报 60s，指着错的预算**。
本轮把它归回 `WebviewUnavailable("宿主在 20s 内没答这次渲染（url）")`，与"没会话"
"宿主死了"同一类：**这次渲染没人接得住**，不是业务跑不完。

这条错是**Dart 实弹臂撞出来的**（不作答那一臂原来读到的就是那句 60s），
现在由那一臂反向钉着：`failure.message` 必须含「宿主在」与「20s」，且必须**不含**
「超过服务端预算」；`kind` 是 `engine` 不是 `timeout`；墙钟 `>= 17000ms`。
Python 那臂（`.probe/g3d1_reverse_channel_live.py`，400 行 / 8 条判据）同样读这个数：
`[A 连了不作答] 墙钟 20718ms · 错："WebviewUnavailable: 宿主在 20s 内没答这次渲染…"`。

另有一行是补给变异核验的靶子：`tests/test_gateway_inproc.py`（+14/-2）在
`test_request_frame_round_trips_into_the_fetcher_result` 里加了
`assertNotIn("jsResult", result)`——服务端那一半此前只有 Dart 侧的**出站**缺键被钉着，
入站那一半没人管（M10 变异第一次打不红，就是这一格）。

## 5. 实弹臂：`flutter_client/test/webview_reverse_channel_live_arm_test.dart`（606 行 / 3 条）

三条各管一件事，读数都从当趟stdout 里取（`Shell: ` 前缀那几行）：

1. **先决读数**：内核在场 + 语料那两种形状各自取得到（墙有 `type="password"`、
   `?rendered=1` 与墙**不同一串**、锚点表自己分得出两版、宿主那一版带 `<usehtml>`）。
2. **实弹**（作答臂）：宿主被叫到那一条地址必须等于**目录那一行拆掉选项之后**的那一条
   （`tocRowUrl` 是原样、`requestedUrl` 是 split 之后——引擎自己那一步拆解由这两格之差来证），
   然后三方同数 + 逐段比锚点表的 `head`/`length` + 墙那句"阅读正文需要登录"不许混进正文 +
   取页账 `墙 +1 · rendered +1` + `engine.webContentReady 出 6142B` +
   答给一条没人等的 `request_id` 读回 `delivered:false`（不是异常）+ 同章再读不再叫宿主 +
   3s 后预取那一档：第 2 章也被宿主答过一次、`?rendered=1` 账跟着动。
3. **不作答臂**：见 §4 那笔归因。

这一臂撞出来的两处仪器自己的错，写在代码里了：

- **`chapter_url` 发的是**目录那一行原样的 href**（`,{"webView":true}` 还挂着）**。
  引擎按这一串认章，拆掉选项是它**取页之前**自己那一步；第一轮把拆完的那条发过去，
  两条实弹测试一起报 `ValueError: 目录里没有这一章`。
- **收摊顺序**。直接 SIGTERM 会留下孤儿无头内核——引擎杀了，它拉起来的 chromium 还攥着
  cache 目录里的浏览器 profile，于是"删临时目录"抛 `另一个程序正在使用此文件（errno 32）`，
  形状与测试失败一模一样。现在 `registerTearDowns()` 先发 `engine.shutdown`（那条路关整棵子进程树），
  等两个子进程退，再删。删这件事本身还慢一拍：**引擎进程退了不等于目录句柄立刻放手**，
  所以 `_deleteDataDir` 带 20 次 × 500ms 的短重试。当趟读数：两条臂都是**第 2 次尝试删掉**，
  跑完 `tasklist` 查不到残留的内核进程。

## 1. 这一档真正的难点不是"接一章"，是接完之后那两套数各说各话

flet 那一屏接章时手里同时有**两把尺**：`_view.paragraph_count()`（段，产字的）和文档高度
（像素，占行的）。媒体块、刚补的分隔线与章名都**占行不产段**——本语的三章挂载是
22 段 / 27 个控件（`tests/gateway/projection/reader.continuous.json` 的 `document` 那一格）。
起点如果按行数累加，整篇段号从此整体漂移；如果按像素反推，接缝那两格就落错章。

而第九十一轮之前那条 flet 的 bug 是这一档的**形状**：`ChapterMount.documentStart` 存的是
**append 之前**量到的文档高度（像素），报出来的段号却是按**当前**高度折的——于是
"用像素挑章、用段号报段"在接缝上给出**整篇第 12 段 / 只有 12 段的第一章**，重开时被夹到段尾，
用户看到的是书自己往后跳。Dart 侧的修法与 flet 同一条：**选章按段区间，像素只管段内比例**
（`continuous_reading.dart` 文件头把这条写成"两套尺谁说了算"）。

三把读数各归各位：

| 数 | 谁算的 | 谁的口径 | 不许干什么 |
| --- | --- | --- | --- |
| 段起点 `paragraph_start` | Dart `MountedChapter` | 整篇段号 | 不许数行（媒体/分隔线/章名都占行） |
| 本章像素起点 `document_start` | 触发那一发的**旧**文档总高 | 像素 | 不许用来挑章，只用来折段内比例 |
| 落库三格 | `_writePosition` | **章内**（章序号 / 章内段号 / 章内字符偏移） | 不许把整篇段号直接写进 `chapter_paragraph` |

## 2. 迟滞那两格与 flet 同数，账本那一格与 flet 有意不同

`_appendTriggerPx = 180` / `_appendRearmPx = 500` 抄 flet 的 `_APPEND_TRIGGER_DISTANCE` /
`_APPEND_REARM_DISTANCE`（`reader_view.py`），两条实弹臂之间用户滚过 500px 才重新武装。

flet 那边还有一本 `_continuous_loaded` 台账（接过的章不再自动接）。本轮**没有照抄**，
理由写进了 `reader_controller.dart` 文件头的"两处与 flet 有意不同"：那本台账在
"翻章 → 退回上一章"之后会**永久**关掉自动接（翻章清的是文档不是台账），
而 Dart 这里查的是挂载表本身（`page.mountFor(next) != null`）——账在文档里，文档换了账就没了，
不需要第二份会漂的状态。另一处不同是 `scroll_offset` 存**本章内**像素而非整篇。

## 3. 屏侧的键表：撞一次键就把上一章报成本章的落点

`_paragraphKeys` 的键是**整篇段号**（原来是一章内的行号）。追加进来的每一章都有自己的第 0 段，
键撞了之后 `_paragraphAtViewportTop()` 会把第一章那一行认成"视口顶那一行"，
落库于是存出一段并不在视口里的字。行表 `documentLines` 是**唯一**的渲染源
（`itemCount` 与 `itemBuilder` 都从它读），三种行各管各的：正文段产段号并挂 GlobalKey，
媒体块占行不产段，分隔线/章名两行连 `line` 都没有。

当场核对（读 `BY_ACTION` 与 `app/gateway/schema/switch.*.json`）：五条的 `params` 与
schema 的 `properties` **逐字相等**、`additionalProperties` 全是 `False`；

三格各有各的来由：

  空闲时那一发回的是 `{"cancelled": false}`——这一格回的是"**这一发有没有真叫停下什么**"，
  不是"调用成功了吗"。

  要按 `bookUrl + origin` 找那条书架记录并**改写它的身份**（`source_url`/`origin` 一起换、
  缓存计数清零），没有记录就换不成——**没入架的书根本换不了源**，这一格不是可选项。

`action_budgets.dart` 本轮**不用动**：五发的预算全部 ≤ Dart 那条默认水池（30s）。

## 2. 两条新事件：一条只带计数、一条带整份结果，谁都不能顶谁

反射出来的事件面现在 **24 类**，`COALESCED_EVENTS` **8 条**。本轮新加：

- `SourceSwitchProgressEvent(switch_id, done, total, failures, starved, timestamp)`
  ——**进**合流表（0.5s 一批），因为它只带计数。
- `SourceSwitchFinishedEvent(switch_id, candidates, cancelled, error, timestamp)`
  ——**不进**：一条就是一行结果，合掉就是丢数据。这一头一尾两格由
  `tests/test_gateway_contract.py` 新增那条 `test_only_count_carrying_events_are_coalesced`
  双向钉住（进度类必须在表里、结果类一条都不许在表里）。

四格设计上的账：

- **`failures` 与 `starved` 分两格**。后者是"本机忙不过来"（并发池挤爆后被掐掉的源），
  不是站点的错。合成一个数，界面写"38 个失败"，用户去删的是 38 个好源
  （`_switch_starved` 早就把这两笔分开，本轮只是让它一路通到协议面）。
- **`switch_id` 由客户端生成、服务端原样回带**：`_start_job` 的受理凭据只有
  `{started, action}`，没有任务号，而事件是异步到达的——没有这个号，界面就把上一轮的
  迟到结果当本轮渲染（沿用 `search.start` 的 `search_id` 那一套，不是新发明）。
- **三种收尾都发 finished**（扫完 / 被叫停 / 起扫前就出错）。不发，跨进程那侧的转圈就
  永远停不下来，而"停不下来"看起来像书源慢，不像契约破了。
- **只在收尾发一次整份候选**，不做逐源增量：候选顺序是整轮排出来的（书名精确 > 作者 >
  书源 url > 站名），扫到一半排序会跳，flet 那一侧同样是扫完才渲染。

`switch_scan` 一轮只跑一条：已经在跑时先把那一轮**合作式叫停**、等它 `finished` 那格落定
再开新的。`should_stop` 是**取下一个源之前**问一次，不是 `task.cancel()`——取消会把
已经扫出来的候选一起扔了，而用户点"停止"想看的是"目前已经扫出哪几个"。

## 3. 排队规则全库只剩一份（那一格原来长在控制器里）

`BookshelfController._switch_candidates` 里那套"同站优先 / 排除当前源 / 过滤停用与无
`searchUrl`"本轮搬进 `ReadingService.order_switch_sources`，`_site_token` 跟着搬，
控制器那边**删干净**（`_site_token`、`urlsplit` 在该文件里 grep → 零命中）。搬的理由不是
洁癖：协议面那条 `switch.scan` 也要排同一份队列，两边各写一遍，Dart 那侧就得抄第三遍——
而抄的那份永远是它自己想要的顺序（记忆 `measurement-corpus-must-not-be-self-proving`
同一族：两侧各算一遍"谁在前"，比对就只剩两份主观可比）。

三条判据各有证人：

- 过滤**复用** `searchable_sources`，不另写一套。换源扫描本质就是一轮搜索，两边判得
  不一样就会出现"找书能搜到、换源扫不到"这种没人能解释的差。
- **分组不存在时不回退到全部**。Legado 那侧回退是为了照顾一条可能陈旧的用户偏好；
  在这里的回退等于"打了个不存在的组名，结果整个库联网扫一遍"——界面看到的是转圈，
  用户以为点错了。空队列就是空队列，`total=0` 说得出原因。这一格也是零外网那条红线的
  **第二道**：主库 920 条源，探针必须传 `group="G3换源"`。
- 排序 `同站 > 书源 url 字典序`，与旧控制器那条**同判据**（不是"看着差不多"），
  由 `tests/test_reading_services.py::test_order_switch_sources_is_the_one_filter_rule` 钉。

控制器那一侧新加 3 条（`SwitchQueueDelegationTests`）：第一条要求服务回来的队列与
交进去的列表**是同一个对象**（`assertIs`——中间只要动过一道手，就不是"没经手"）；
第二条查 `own_url` 的取法（`source_url` 优先、回落 `origin`、两个都没有才是空串）；
第三条查**规则的第二个家没长回来**（模块上不许再有 `_site_token`，`vars(module)` 里
不许再有 `urlsplit`）。

## 4. 语料：`/g3sw` 六条源、四页齐全，该不该扫由账本的前后差量说

六条 stem 各管一格：`a` 两条命中（精确同名+作者对 / 只包含关键词）、`b` 精确同名而作者
不同、`c` 一条都不命中（**要**被扫、候选里**不许**有它——"扫过而没找到"与"没扫"必须是
两个数）、`d` 停用、`e` 无 `searchUrl`、`x` 就是当前那条源。`SW_CHAPTERS` 按源互异
（3/2/1/3/3/4），否则"换成乙之后目录真的换了"那句话就只是换了个 url 的名字。

`x` 是本轮加的第 6 条。五条的时候排不出同时成立的那三件事：既要"当前源被排除"有证人、
又要排序那三行来自两条以上不同的源、还要 `c` 在队列里。`x` 带一条精确同名命中，
所以"排除当前源"这一格一旦断链，第一条候选就是它——红得起来。

**四页齐全**（搜索页 → 书籍页 → 目录页 → 正文页）不是豪华配置，是 `reader.open` 的
取页链路本来就要四页：书籍页上那句 `<a class="toc" href="…">目录</a>` 就是
`ruleBookInfo.tocUrl` 的落点，缺它引擎只能把书本身当一章。

**该不该扫**那一格由语料侧的 `GET /hits.json` 说，且比的是**抓取前后各取一次的差量**
（不是某一时刻的绝对值）：`/g3sw/<stem>/search` 没有键 = 从没被取过。
本轮的读数是 `a/b/c` 非 0、`d/e/x` 的 delta 为 0——0 有非 0 的同伴才叫读数
（记忆 `zero-counts-need-a-positive-control`）。

## 5. 两处仪器坑，各写成一条规矩

**其一：路由分段要"指名"，两种兜底都不许。** 抓取连红两次，形状是：

- `parts[3]` 认的是**一段**（`book`），而代码写成 `startswith("book/")` ——永远认不到，
  书籍页一路掉到末尾那一支被答成搜索页。搜索页没有 `a.toc`，`tocUrl` 取空，引擎于是把
  本书当一章，报 `chapterCount=1`。错的**表现**是"章数对不上"，看起来像语料配错了，
  谁都以为该去改 `SW_CHAPTERS`。
- 改成"其余都算搜索页"之后又红一次：`/g3sw/x/toc.html` 里 href 本来带 `.html`，
  而 `toc` 少写后缀那一发被兜成了搜索页——于是目录永远只剩一行（那一行还指向书籍页）。

现在的写法是**两头都指名**：段名先去掉后缀再比（`book` / `toc` / `ch` / `search` / 空），
认不出来的一律 404。`d`/`e` 那两条对照臂的"没被取过"这才分得清是**过滤挡的**还是
**路径写错的**。同一支里还顺手改了章号夹逼：`_index()` 原来一律拿"命中行数"去夹，
而 `x` 只有一条命中，于是 `/g3sw/x/ch/3.html` 答成第 1 章——书籍页按命中行夹、
正文页按章数夹，两个边界分开传。

**其二：计数取数不许用 `or` 兜默认值。** `switch.scan` 明明正常收口，那一支却报
`回环语料上不该有失败源`，打印出来是 `{'failures': 0, 'starved': 0, ...}`：
判据写的是 `int(last.get("failures") or -1) != 0`，而 **0 会被 `or` 换成 −1**。
改成"缺键就当场说缺键、有值就按值比"。这条与上一轮那条"`??` 默认值会把对照臂的 null
变成实验组"是同一族：**哨兵值会顺着合法的 0 溜进判据**，而且它假的方向正好是你期望的
那个（"有失败"→守卫红，看着像守卫在干活）。

底本的来路本轮改了一次：原先直接从 `SearchFinishedEvent` 的 items 里挑 `origin == x`

## 7. 进度面新开一支守卫：那张"谁该有进度面"的表从现场推

`tests/test_gateway_job_progress_corpus.py`（274 行 / **5** 条）管的是 `event_sample`
那一支管不到的另一半：**进度**。判据形状有两条值得单说：

- **"哪条 job 有进度面"不手写表**，从现场推：动作是 `mode="job"`、且它派发到的那个
  服务方法**函数体里**发了一条 `*ProgressEvent`（`inspect.getsource` + 反射事件模块）。
  手抄表会漂——发布点搬进另一个方法、或给某条 job 新加一条进度事件，表都照样绿
  （记忆 `instrument-floors-read-the-live-contract`）。推导当场读出的是
  `{'switch.scan': 'SourceSwitchProgressEvent'}`：`check.start` 与 `search.start`
  的函数体里没有进度事件，这一句不是猜的，是**扫出来的**。
- **推出来是零条也算仪器没接上**，所以有一条**点名**断言：`switch.scan` 必须在推导结果里、
  且顶的必须是 `SourceSwitchProgressEvent`。少了这一行，前面那些判据会因为函数体被重构
  而整体退化成"绿着比空气"（记忆 `guard-tests-assert-absence`）。

判据本身收成一个口（`_check_progress_sample`：事件名 / 字段清单 / 帧形状 / 帧数 /
"帧里键的并集"五项），第五支变异对照把现样本按四处各改坏一次喂回**同一个口**，
每处都必须被拒——散着的 assert 会让变异对照只测到它自己抄的那一份，与守卫本体无关
（记忆 `comparison-closure-must-reread-live`）。字段清单那一格读的是**今天的** dataclass
字段名，改字段不重抓样本就红。样本里不另存"末帧"：末帧由帧列表自己定义。
