# 第七十八轮 收：窗口拖不动是两笔钱，订阅页窄窗重画

用户这轮说了三件事：「动一下；重新设计下 ui 看看；另外现在应用无法顺畅拖动」。
拖动那一件先量，因为"重设计"要不要动外壳、动哪一层，取决于拖动慢不慢是谁的钱。

## 1. 拖动：先排掉两个嫌疑，再钉住两笔真钱

仪器：`.probe/probe_drag78*.py`。用 `ctypes.windll.user32.SetWindowPos`（**不带**
`SWP_ASYNCWINDOWPOS`，所以它是同步的）每一拍改一次窗口尺寸并等窗口线程处理完，
它的墙钟就是操作系统眼里"这一拍顺不顺"；同时挂一条 10ms 心跳量界面循环被压住多久。
真数据 = 离线导入 `resource/14201_*.json` 的 **917 条书源**，停在书源列表页，全程零外网。

| 臂 | 每拍 SetWindowPos p50 | 处理器合计 | 心跳落后 max |
| --- | --- | --- | --- |
| A 现状处理器 | 197ms | 557ms | 545ms |
| C 什么都不做（处理器摘掉） | 212ms | 0ms | 112ms |
| B 背景图开 + 现状处理器 | 213ms | 1497ms | 530ms |
| A2 现状处理器（背景图已撤） | 222ms | 2061ms | 531ms |
| C2 什么都不做 | 216ms | 0ms | 178ms |
| M 只平移不改尺寸 | 1ms | 558ms | 548ms |
| B2 背景图开 + 只平移 | 0ms | 0ms | 25ms |

三条读数把方向改掉了：

1. **A ≡ C**（197 对 212）：Python 侧那个 resize 处理器**不在每拍的路径上**。
   拖 30 拍 Python 只收到 **1–4 次** `on_resize`（客户端自己合掉了），所以"每拍重建
   整棵根树"这个上一轮的判 suspect 根本不成立——它是那 1–4 次的钱，不是 30 拍的钱。
2. **B ≡ A、B2 ≡ M**：背景图那一层无罪，上一轮计划的"背景层实例复用"就此撤掉
   （没有实测需要，不预留代码）。
3. **M/B2 只平移 0–1ms，改尺寸 200ms**：钱在**客户端重排**，不在网络、不在 Python。

那 1–4 次事件也不是免费的：一次 `on_resize` 处理器要 557–2061ms 把整棵根树重下发，
同期心跳落后 545ms——这就是"偶尔卡一下"。于是两笔真钱分开算：

- **每拍 200ms**：客户端重排长列表。
- **每次事件 0.5–2.1s**：Python 重发整棵根树。

## 2. 对照：贵的是"滚动 Column 里的行"，不是行数

`.probe/probe_drag78c.py`（不带服务、不带外壳，只挂一棵控件树，同一窗口逐臂交替）：

| 那一页里挂的东西 | 控件数 | 每拍 p50 |
| --- | --- | --- |
| 空页 | 2 | 11ms |
| 50 条真实书源行（ListView） | 530 | 12ms |
| 917 条裸 `Text`（ListView） | 918 | 11ms |
| 917 条裸 `Text`（`Column(scroll=AUTO)`） | 919 | 13ms |
| **917 条真实书源行（`Column(scroll=AUTO)`）** | 9200 | **238ms**（回跑 237ms） |
| **同样 917 条真实行（ListView）** | 9172 | **12ms**（回跑 11ms） |

行数不是判据（917 条裸文本装进滚动 Column 也只 13ms），**"行 × 每行控件数 × 容器会不会
虚拟化"才是**：客户端只对 `ListView` 按可见区建行，`Column(scroll=AUTO)` 把 9200 个控件
全实化。同一批行、同一个窗口，238 → 12 只差那一个容器类。

## 3. 改：两处

1. `app/views/source/book_source_list_view.py`：`self._cards` 从 `Column(spacing=6,
   scroll=AUTO)` 换成 `ft.ListView(spacing=6, expand=True)`；顺手删掉重构后没人调用的
   孤儿常量 `BATCH_SIZE`（客户端虚拟化之后更不需要分批）。护栏里那张表另外钉住 8 个
   页的行容器（检测结果 / 书架 / 找书两栏 / 订阅两栏 / 阅读器目录）都必须是 `ListView`。
2. `app/views/navigation.py`：`page.on_resize` 加**档位闸门**——只在跨过
   `NARROW_WIDTH_THRESHOLD` 那一拍才 `rebuild() + _repaint_root()`，同档位内直接返回。

改完同一支探针重跑（`.probe/out_drag78b_fixed.txt`）：五臂每拍 p50 **12–13ms**、
处理器合计 **0ms**、整拖期间**根树没换**、心跳落后 max **134ms**。只平移那两臂照旧
0–1ms（说明不是"整台机器变快了"，是这两笔钱没了）。

## 4. 档位由外壳推给视图：`on_band_change`

闸门把重发次数从 30 压到 0–4，但视图需要的是"**跨过档位**"这个时机，不是"某个时刻的
宽度"——自己读 `page.width` 就会和外壳的档位错开。所以外壳新增
:meth:`NavigationHost._notify_band`，在**重发、`show()`、切页签**三处把
`_is_narrow()` 推给当前视图（只推实现了 `on_band_change` 的，没实现的 getattr 兜空、
一次调用都不许多花；某个页的降级抛了不许拖垮外壳重建）。

## 5. 订阅页重设计：窄窗一次只摊开一栏

上一轮把 RSS 三栏从定宽收进 `expand=3/4/5`，只解决了"被裁"，解决不了"读不了"：
344 那一档每栏只剩 ~90–120px。所以这一轮不再挤宽度，改成两副形状：

- **宽窗**：三栏并排（flex 3:4:5），选源/选文章只换右边两栏。
- **窄窗**：**一次只摊开一栏**，顶部一条「订阅源 › 文章 › 正文」级切换跟着走；选中源
  自动跳到文章、选中文章自动跳到正文；到不了的级（还没选源时的"文章"）置灰；那一级的
  凭据没了（源删光、正文清空）就自动往前退一级。

换形状只动 `visible`，**不换父节点**：这一页两个 `ListView` 在刷新期间正逐条落文章，
中途被摘走就是白丢一截渲染。

像素面（`.probe/probe_rss_shape80.py`，宽 1200 / 窄 360 交替跑两遍，四臂读数一致）：

| 读数 | 宽窗 1184×741 | 窄窗 344×741 |
| --- | --- | --- |
| Python 侧档位回读 | `host._is_narrow=False`、可见栏 `[0,1,2]`、切换条 hidden | `True`、可见栏 `[0]`、切换条 visible |
| 内容区竖向实线列 | **3 条 @ 266 / 493 / 796** | **0 条** |
| 首条源行最右落墨 | 第 1084 列 | 第 **320** 列（距右边缘 23px） |

实线列 266→493→796→1184 就是三栏的右边界：宽窗三栏 **227 / 303 / 388 px**（≈3:4:5）。
窄窗那 0 条 + 首行墨到 320 才是本轮要的判据——**`visible=False` 真的把位置让出来了**，
剩下那一栏自己占满整宽（344 里 23px 是内边距 + 按钮热区），不是"隐藏但留坑"。

## 6. 探针顺手抓到的一条老 bug：源行标题整行不见

第一版像素里，**两副形状都**只剩图标和「⋮」，源名与副标题整个消失。原因是源行的
`trailing=Row([Text("N 未读"), IconButton])`：客户端把这一坨按不收缩的宽度排在最右，
标题/副标题被挤成 0 宽。文章那一栏的 `trailing` 是单个 `IconButton`，同档宽度下标题正常。
改法照它学——未读计数挪进副标题（`12 篇 · 6 未读 · 刷新于 …`），`trailing` 只留按钮。
护栏钉住"源行 trailing 不许是 Row"且未读数还在。

## 10. 第七十九轮：系统朗读从不返回（pyttsx3 线程亲和）

起因是那条 `循环[ui]…收尾竞态[socket 已复位仍被收尾]` + 退出码 -1 的追问：
-1 不由应用任何退出路径产生（mini/full/killclient/wmclose 四臂 rc 全是 0），
形状是外部 `TerminateProcess(handle, -1)`；顺带把**系统朗读**这条真 bug 挖了出来。
另有一条**顺带修掉的**：关窗到进程消失之间那段延迟。上一轮量到的是每次固定多
**5.4 / 5.5 / 5.07 s** 才消失，嫌疑收窄在 `on_stop` 里那条 `tts-teardown`
（它在自己的线程上同步等 COM 对象收尾）。本轮把 COM 引用改成由后端自己的专属线程丢
（`close()` 只排活不 join）之后，同一支探针（`.probe/exit_code_attr78.py --wmclose 22 main.py`）
三次读数 **0.5 / 0.4 / 0.4 s**，退出码仍是 0、收尾竞态行 0 条、traceback 0 条。
Python 侧一切（含 atexit）本来就在关窗后 0.3s 内跑完，quickjs 派发线程、hub 循环、
`pyttsx3.init`、裸 flet 四臂各量过都不背那个数——所以那 5s 就是这条线程，现已归零。

**症状**：点朗读后永远停在"播放中"，不报错、不返回。

**根因**：`SystemTtsBackend.__init__` 在 hub 那条线程上 `pyttsx3.init()` 建 SAPI
COM 对象，`speak` 却 `asyncio.to_thread` 换一条线程去 `say + runAndWait`。
SAPI 的出声事件要回**建对象那条线程**的消息队列，跨线程等它就是静默死锁
（`pyttsx3/engine.py:209` `runAndWait` → `driver.py:184` `startLoop` →
`drivers/sapi5.py:178` 在调用线程 `PumpWaitingMessages()`）。

**A/B 交替实测**（`.probe/tts_affinity_fix.py`，真实 pyttsx3 + 本机 SAPI，两臂各起
子进程、3 轮交替）：

| 臂 | 3 轮 × 2 次读数 |
| --- | --- |
| 修复前（init 在主线程，say/runAndWait 在 `to_thread`） | 6/6 **KILLED>60s**，一条输出都没落进管道 |
| 修复后 | 6/6 **返回**，2.01 / 2.01 / 2.03 / 2.03 / 2.03 / 2.04 s；改完结构再跑一遍仍是 6/6、2.02–2.03 s |

**改法**（`app/services/content/read_aloud.py`）：
1. 一条专属线程 `tts-system`，`init`/`setProperty`/`say`/泵送/`stop`/丢引用
   全部排进它的命令队列；`available` 仍在构造期同步定下来（把 init 排进队列后
   等它的 future，上限 `INIT_TIMEOUT`，超时按不可用降级）。
2. 不用 `runAndWait`，改 `startLoop(useDriverLoop=False)` + `iterate()` 外部循环，
   于是 `stop()` 的停音请求能在这条线程上被取出执行（空闲时才排 `_stop_owned`）。
3. `PUMP_TIMEOUT` 给一条语音封顶：驱动不回 `finished-utterance` 就
   `TimeoutError`，不再是无限等。
4. 新增 `TtsBackend.close()`；`SystemTtsBackend.close()` 只把"停音 + disconnect +
   丢 COM 引用"排进专属线程后立刻返回，**不 join**。`_release` 逐个调 `close()`，
   所以最后一个 COM 引用不再由 `tts-teardown`（或任何别的线程）丢掉。

**护栏与变异核验**（`tests/test_read_aloud_m4.py` 新增 4 条 + `_RecordingEngine`
替身，它照真实外部循环语义工作并记下**每次调用落在哪条线程**）：

| 用例 | 钉住的事 |
| --- | --- |
| `test_system_backend_calls_stay_on_one_owner_thread` | 所有调用（含 init）ident 只有一个且等于专属线程；**没有** `runAndWait`；`startLoop/iterate/endLoop` 齐 |
| `test_system_backend_stop_preempts_long_utterance` | 替身永不回读完事件（长语音），`stop()` 后 speak 必须返回（<5s），且 `stop` 落在 `say` 之后、同一条线程 |
| `test_system_backend_close_releases_on_owner_thread` | `close()` 不等 COM（<0.5s 返回）、专属线程收摊、`disconnect` 在那条线程上、关闭后 speak 立即上抛 |
| `test_service_on_stop_closes_backend_on_owner_thread` | 接线：`ReadAloudService.on_stop` 真把后端关掉 |

变异核验（`.probe/tts_affinity_mutation.py`，用同一份替身与同一组断言）：
M1 只把 speak 挪回 `to_thread` → 抓到 ident 变两条；M2 整段退回旧
`_run_blocking` → 抓到两条 ident + `用了 runAndWait` + `缺 [startLoop, iterate, endLoop]`；
不变异的对照臂 `[]` 全通过。降级那条老用例（`monkeypatch pyttsx3.init` 抛错）照旧绿，
并补了"降级不留专属线程"。
