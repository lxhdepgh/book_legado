设置四个域的协议面、Dart 面、以及 §8 R4 那三项在 **Dart 侧**的复量。

## 1. 协议面：31 条动作，其中 30 条有真进程靶子

`app/gateway/methods.py` 从 G0 那 9 条长到 **31 条**：`call` 23 / `sync` 6 / `job` 2
（`check.start`、`search.start`），命名空间 9 个（`engine` 4、`source` 10、`check` 4、
`search` 3、`bookshelf` 2、`browse` 2、`import` 2、`settings` 2、`theme` 2）。
`app/gateway/schema/*.json` 同步到 31 份——`tests/test_gateway_contract.py` 里
`SchemaAlignmentTests` 钉的是"schema 目录与 action 表同集合"，多一条少一条都红。

模型对象过不了 RPC，所以**没有**把 `BookSource` 直接端上桌，而是在 owning 服务上补了
5 条 JSON 门面（网关仍然只调服务，不反射模型）：

| 门面 | 落在 | 为什么必须是服务侧 |
| --- | --- | --- |
| `SourceService.shelve_by_url` | `source_service.py` | flet 那边"搜到→入架"走的是 `book` dict + 源 url，控制器里那段不能抄进网关 |
| `ReadingService.browse_categories` / `browse_books` | `reading_service.py` | 两条都要**先按 url 取到那条源**再走原路（`_source_by_url`），取不到就诚实报错 |
| `ReadingService.search_in_scope` | `reading_service.py` | `job` 那条：受理回包只有 `{started, action}`，真结果从 `/ws` 的 `SearchFinishedEvent` 走 |
| `SettingsService.read_keys` | `core/settings.py` | 只读**调用方点名的那几格**。**这条是安全边界**：绝不能开成"列全部 setting"，那本库里躺着 `webbridge.token` |

G2-D 又补一条 `search.scopes`（连同 `ReadingService.scope_table`）：**"哪些源能动"只留一份算法**，
flet 那个范围对话框与 Dart 那个读同一张表，两处迟早会给出不同答案的那件事就是这么防的
（记忆 `refactor-regression-orphan-methods` 那一族：接线断在两侧各算一遍的地方）。

## 2. 语料库：31 份黄金样本从此被现契约钉住

`.probe/g2_golden_capture.py` 起一趟真 `main.py --serve` 子进程（同一份 920 行副本），
把 30 条动作各跑一发真往返落成 `tests/gateway/golden/*.json`，`bookshelf.list` 另有一份
带 `include_staged` 的变体。这一趟 /ws 上收到 **69** 条事件，7 类事件名
（`CheckFinishedEvent`、`ImportFinishedEvent`、`ImportProgressEvent`、`SearchFinishedEvent`、
`ServiceStateChangedEvent`、`SettingsChangedEvent`、`SourceChangedEvent`）进了样本。

新立的规矩是**每份样本盖着抓取那趟握手的 `schema_digest`**（本轮现值 `ffef64386bec`），
守卫拿现场算出来的摘要比对：改表或改任一 schema 而不重抓，全库立刻红——而不是让 Dart
拿一份旧字段表比出一个漂亮的绿。`tests/test_gateway_golden_corpus.py` 五笔账（覆盖 /
时效 / 合法性 / 自证 / 形态）里最要紧的两条：

- 覆盖写成"**缺的集合恰好等于例外表**"，不是"⊆"：例外表现在只有一格
  `engine.webContentReady`（反向 WebView 那一发要先有一次在途的 `webview.content` 请求），
  加一行是显式决定，漏抓是事故。
- `mode=job` 的样本必须带 `event_sample`，非 job 的不许带——少了这一段，Dart 只比回包就能
  绿着把"结果从哪来"整条契约漏掉（记忆 `ui-progress-must-travel-as-events`）。

这五笔账的变异证据**长在守卫里**：`test_mutation_controls_show_the_guards_are_not_deaf`
自己把一份样本改坏三处（多一个键 / 改一个值 / 删一个必填），要求重算与校验当场炸。

## 4. G2-F：R4 那三项在 Dart 侧的读数（靶子当天在同一副本上重测）

驱动是 `.probe/g2f_dart_baseline.py`：它 `seed_dir()` 造一次副本，先在同一副本上把 Python
那臂**当天重测**，再把数据目录交给 Dart 拉起第二个引擎（记忆 `docs-numbers-must-be-measured`
——隔两天拿 Dart 的数去比第八十二轮的数，差的可能是缓存或杀软，不是两套客户端）。
完整输出 `.probe/g2f_dart_baseline_run8.log`。

| 项 | flet / Python 靶（第八十二轮） | 今天同副本重测 | Dart 臂 | 底价臂（只差被测那一个变量） |
| --- | --- | --- | --- | --- |
| `source.list` 跨进程 | S p50 **80.6 ms** / 6,969,038 B | S p50 **20.5 ms** / 360,700 B，解析另计 1.7 ms | B 只到线 **22.6**、A 全程 **30.9** | `engine.status` 全程 2.4（载荷 5,530 B） |
| 首屏行落满 | **561 ms** | —— | D2 920 行首屏 **110.5** | 空列表首屏 **35.0**（Δ75.5；一帧只挂 7/920 行） |
| 滚动每拍 | 下发 **390 ms**（空列表 3 ms） | —— | D3 每拍真滚 **62.7** | 每拍落点不动 **1.3**（Δ61.4；24/24 拍一格没换） |

判语三条，都不许越界：

1. **跨进程那项**：同载荷、同一天、同一副本，客户端为那一发付 30.9 ms，Python 侧整发
   （S+解析）22.2 ms ⇒ **1.39 倍**；同跨度（B ÷ S）只有 1.1 倍，差的那 5.9 ms 是 Dart 一发
   之内的解码 + 建模（Python 同载荷解析 1.7 ms）。对着 §9 那格 80.6 ms 的靶，Dart 30.9 ms
   是**过**的——但载荷口径变了（360,700 B vs 6,969,038 B），这句话必须连着 §5 一起读。
2. **界面那两项与 flet 的数不可直读**：Dart 这两臂跑在 `flutter_test` 里，没有 GPU 光栅化，
   列表还是虚拟化的（一帧 7 行）。所以它们**只与各臂自己的底价比**，日志末尾明写了这一条。
   真正可比的是"行数那笔钱"的形状：Δ75.5 ms（920 行 vs 空）、Δ61.4 ms（真滚 vs 不动）。
3. **A−B 用逐轮差**，不用两个中位相减：后者在第一版里读出 92.9 ms，而同一段字符串离线解
   一遍 115 ms，看着像算术矛盾，其实是口径错（某一发 socket 特别慢就把差量摊薄了）。

顺带一条自己踩的：同一份 UI 臂在**整套 `flutter test` 里**跑出来是 76.9 ms（专用驱动那趟
62.7 ms），因为同 isolate 里别的测试还压着分配。记账一律拿专用驱动那一趟。

## 5. 那 1.7 倍不是 Dart 的错：载荷解剖 → 出口投影

第一版复量（`.probe/g2f_dart_baseline_run5.log`）读到的总账是 **1.7 倍**：Dart A 全程
172.5 ms 对 Python S+解析 101.2 ms。Dart 那 172.5 里，`utf8.decode` 13.4 + `jsonDecode`
64.4 都花在解**界面根本不显示的字段**上。于是加了一支当场数字节的仪器
`.probe/g2f_payload_anatomy.py`（口径与线上那一发一致：真走 `BookSource.from_dict` →
`to_dict`，语料同一份 920 行）：

| 键 | 字节 | 占那一发 | 列表那一屏显示吗 |
| --- | --- | --- | --- |
| `exploreUrl` | 2,770,070 B | 40.1 % | 不 |
| `jsLib` | 1,624,820 B | 23.5 % | 不 |
| `ruleBookInfo` / `ruleContent` / `ruleSearch` / `ruleToc` / `ruleExplore` | 合计 1,657,077 B | 24.0 % | 不 |
| 留下的六格（`bookSourceUrl` `bookSourceName` `bookSourceGroup` `bookSourceComment` `enabled` `loginUrl`） | 354,236 B | 5.1 % | **正是界面在读的**（`book_source_list_view.py:208-211` + 搜索框的备注） |

改法不是"让服务返回一个瘦对象"（那会把编辑器的回填一起饿死），而是 §4.2 那张显式表里
新增一格 `Method.fields`：`app/gateway/serialize.py` 的 `project()` 在 `to_json` **之后**、
发信封之前逐行收口，只在网关边界生效。三个决定写在这里：

- **`fields` 算进 `schema_digest`**。改了白名单就是改了契约，老客户端在握手阶段被拒，
  不会悄悄拿到一份字段变薄的载荷。护栏是
  `tests/test_gateway_contract.py::test_schema_digest_moves_when_only_the_projection_changes`
  ——只动投影、不动别的，摘要必须跟着动。
- **`source.get` 故意不投影**。编辑器以它为底本；把列表那六格存回去等于把
  `exploreUrl`/`jsLib` 写成空。这条钉了两处：Python 侧一条单测 + 一条**现场派发**
  （`tests/test_gateway_inproc.py`，用种进去的那条护栏源真打一发，它的底本里真有
  `ruleSearch`/`searchUrl`）。
- **投影遇到错形状必须抛**，不许静默放行：载荷不是行列表、行不是 dict 都当场
  `TypeError`——否则"裁了"与"没裁"长得一模一样。

投影后同一趟复量（run8）：data 351,554 B（**5.1 %**），Python S 从 72.3 掉到 20.5 ms、
解析从 28.9 掉到 1.7 ms，Dart A 从 172.5 掉到 30.9 ms，总账 **1.7 倍 → 1.39 倍**。
另外重生成 flet 投影表并逐行比对：那 920 行渲染出来的 `title`/`subtitle` **一字节都没变**
——这就是"投影没裁掉界面显示的东西"的证据，不是注释里的一句承诺。

## 7. 这一轮的仪器坑（都进记忆了）

1. **"每行键数固定"是不成立的假设**。第一版形状守卫写成"每行的键集必须等于那六格"，
   今天 920 行里只有 **168 行**齐六格——`BookSource.to_dict` 是 Gson 语义，**null 键不落**
   （507 行五格、245 行四格：没设备注或没有登录页的源本来就少那几格）。合法数据被自己的
   守卫判死。改法是拆成两个方向：**多键逐行查**（野键=投影没生效），
   **缺键在全库并集上查**（声明的键一条都没出现=语料不是靶子那份）。
2. **探针里的字节底价会被一次合法的契约改动打断**。驱动原来钉 `MIN_BYTES = 6_000_000`，
   投影上去之后当场报"语料没接上：920 行 / 360,700 B"——那不是回归，那是仪器钉着旧形状。
   现在键集**现读 `BY_ACTION["source.list"].fields`**，字节只报不判（记忆
   `docs-numbers-must-be-measured` 的另一面：口径的来源必须是单一真相）。
3. **恒真的比较口**。D3 那条"底价那一拍一格都没换"原来是
   `_sameRows(baseline, baseline)` 也能绿。现在整个测试只有**一个**比较口，第二边
   **必须现读树**，另有一发正控走同一个函数、要求它判"换了"。这是本轮早先那批仪器核验里
   第 10 发（"比较口改成自我比对"）打不红之后补的洞——补完重跑，那一发红了才算数。
4. `flutter test` 的 `-r expanded` 会给子进程每行加 `Shell: ` 前缀，`G2F-` 不在行首——
   于是 rc=0、读数明明贴在输出里却报"一条都没打"。驱动的 `reading()` 那一层专管剥前缀，
   并配了一条静态自检（`static_self_check`）：这类"仪器自己坏了"不该等下一次 3 分钟的整套驱动。

# 第八十六轮 收：G3-A + G3-B 交清——一把尺量到章内偏移，reader 面 13 条动作各有真进程靶子

这一轮按 §9 进 **G3**，交的是阅读器的**底座那一半**：

- **G3-A 位置契约**：翻页落点这把尺先立起来（否则 G3-B 的出参与 G3-C 的落点各量各的）；
- **G3-B `reader.*` 协议面**：13 条动作 + 13 份入参 schema + 出参序列化
  （`ChapterItem` / `ChapterContent` / `ReadingPosition` → dict），每条一根真进程靶子。

G3 判据里"同一本书翻页落点与 flet 版可比（按字符偏移断言）"那一半要等 G3-C 的 Dart 屏，

（`127.0.0.1:8797`，四页齐全 + 一张受保护插图），一行都不出本机。

## 1. 一把尺：章内字符偏移由段号导出

`app/core/text_layout.py` 是这把尺的唯一定义处：

```
偏移 = 段0 的长度 + PARAGRAPH_JOINER_LEN(=1) + … + 到第 k 段为止
段   = chapter_paragraphs(display_blocks(document))
```

三条都要钉住，缺一条就是两侧各量各的：

1. **数的是段文本，不是块数**。一章有插图时块数 > 段数（第一版就栽在这里：块首偏移
   ≈ 章首偏移，落点永远差一段）。
2. **段间那个 `"\n"` 要算钱**（`PARAGRAPH_JOINER_LEN`）。少算它，一章越深偏移漂得越多，
   而且漂得**单调**——看着像"进度存对了但翻页差半屏"。
3. **必须是 `display_blocks(...)` 之后**的形态。`<usehtml>` 渲染会改字数，用原文切段
   数出来的偏移，客户端在渲染后的文本上根本落不回去。

接进这一把尺的三个读数口（此前各自数了一遍）：`ReadingPosition`（存/读）、
`ContentSearchService` 的 FTS 索引（`paragraph_offsets`）、flet 阅读器的命中跳转。
守卫 `tests/test_reader_position_contract.py` **17 条**，变异核验
`.probe/g3a_mutation_check.py` **13 发全红**（"第三把尺"那一族每一把都单独打过）。

## 4. 三处产品缺陷 + 一处仪器缺陷，都是现场撞的

1. **RPC 存的位置被 `reader.close(save_progress=true)` 盖回默认值**。
   `save_position` 落库了、没写回 `self._session.position`，而退出那一发落的是**会话上**
   那份——于是跨进程客户端存完再退，读回来永远是 chapter 0 / 偏移 0。flet 那条路躲过这一枪
   只因为它的落点本来就在会话上。修法：落库那份同时写回会话，正对照
   `test_position_save_then_close_keeps_the_saved_position`（存 137 → 退出 → 读回 137）。
2. **受保护插图过协议面就永久失去可渲染的地址**。`_load_protected_images` 把块的 `value`
   从 url 换成字节给 flet 画，而 §4.4 那条 `GET /media/{key}` **还没建**——跨进程那侧连
   地址都没了。修法：`ContentBlock` 新增 `url` 一格，`display_blocks`、`ReadingCache`
   （加性 JSON 键，旧文件读回退化成 `""`）、`_block_row` 三处一路带到协议面；字节仍然不过
   协议面（设计 §4.4）。顺带把缓存文档那份**逐字段手抄的复制**换成 `dataclasses.replace`
   ——手抄就是下一个静默丢字段的坑。
3. **`to_json` 不按类型泄漏，所以"泄漏守卫"打它等于自证**。第一版
   `find_leak(to_json(value))` **结构上恒为 None**（它展 dataclass 靠
   `__dataclass_fields__`/`vars()`/`str()`，实例永远变成 dict）。变异核验打不红之后改判据：
   打在**门面裸返回值**上，信封那一步由 `test_every_reader_facade_return_is_json_native`
   单独钉。
4. **仪器自己造了它要读的信号**（本轮最贵的一条）。扫 Dart 调用点那个解析器排掉了
   `import 'x.dart'` 与 `Key('a.b')`，却没排 `'reader.open': 60`——预算表里的**表键**长得
   和调用点一样。后果是 `action_budgets.dart` 一填 reader 那四发，"登记过的每一发都有客户端
   在调"这半边就把**没接界面的动作读成接了**。修法不是把预算表整个跳过（那会把真调用点也
   藏了），是窄到"字面量后跟冒号的不算"，并给这条加了第三种形状的正对照：同一发动作在下一
   行真的被调用，必须照样扫出来。

# 第八十七轮 收：G3-C1 交清——flet 阅读面的落点参照表落地，10 条守卫 16 发变异全红

上一轮交了阅读器的底座（一把尺 + 13 条 `reader.*` 动作）。这一轮交的是 **G3 判据里
"flet 那一半的读数"**：把"这一章切成几段、第 k 段的首字符在哪、屏上第 n 行对应哪个落点"
落成 `tests/gateway/projection/reader.content*.json` 三张表。

为什么要有这张表，而不是把偏移公式抄给 Dart 各算一遍：**两边都跑同一个公式，绿只说明
公式抄得对，不说明屏上第 k 段就是索引里第 k 段**（记忆
`measurement-corpus-must-not-be-self-proving`）。所以表里的答案必须**从真 flet 屏上读回来**
——探针 `.probe/g3c_flet_projection.py` 构造真 `ChapterContent`，调 flet 在用的那两个函数
（`ReaderView.content_plan` 与 `app.core.text_layout` 的坐标族），一个数字都不手写。
G3-C2/C3 的 Dart 屏只许对上这三张表。

## 1. 三张表的形状：尺、屏、落点探针各一份

| 表 | 来源 | 段 | 字符 | 屏上行 | 落点探针 | 存↔读往返 |
| --- | --- | --- | --- | --- | --- | --- |
| `reader.content.json` | 黄金载荷（真子进程那一发） | 8 | 5,802 | 9 | 26 | 8 |
| `reader.content--media_only.json` | **合成输入**：整章只有一张图 | 0 | 0 | 1 | 3 | 0 |
| `reader.content--with_heading.json` | **合成输入**：章首一行是小标题 | 4 | 43 | 4 | 15 | 4 |

黄金那一发 8 段挂在**两个正文块 + 一张受保护插图**上，段首偏移
`[0, 168, 1578, 1884, 4053, 4175, 5286, 5799]`——这一串就是两侧唯一的比对基准。
合成那两发不是"补两条数据"，是**补两种会让行号与段号分裂的形状**：

- 媒体占一行**不产段**（表里那一行 `paragraph_index: null`）。只有黄金这种形状时，
  "把行号当段号"的实现可以蒙过去；插图那一格一插，行号与段号当场差 1。
- 标题行**既认得出是标题、又确实占第 0 段**（显示不缩进、尺上照数）。这一发防的是
  反过来那族错：把标题当"显示层的东西"从尺上剔掉，整章偏移少一段。

**60,169 字节**；而正文在表里本来就已经有两份（`ruler` 与 `display`），第三份是纯重复。

**41,699 字节**，合成那两发体积小、仍原样钉在表里（1,366 / 4,535 字节）。

**输入为什么必须进表**：`.probe/` 是不入库的（`.gitignore:42`），生成脚本不在仓库里。

## 2. 守卫十条（`tests/test_reader_position_projection.py`），四条判据各管一件事

1. **表还对不对当前的 flet**：现算一遍与文件逐格比。改了 `content_plan` 或坐标族
   却没重跑探针，这里红——这是这张表的**保鲜**。
2. **表与协议面那一份是不是同一个数**：表里的 `paragraph_count`/`total_chars` 必须等于
   真 `--serve` 子进程序列化出来的 `paragraphCount`/`totalChars`。跨进程比落点之前，
   先要证明两侧数的是同一章。
3. **这把尺不是那三把错尺**：表里的偏移必须**不等于**①按块数、②不带段间格、
   ③按显示形态（含段首缩进）算出来的那一串。只断言"表 = 正确尺"而不断言
   "表 ≠ 这三种"，等于相信将来没人会重新引进它们。
4. **行与段、存与读**：媒体行不产段 / 标题行产段 / 整章只有媒体时段数为 0 而屏上仍有
   1 行 / 每个段号"存 → 读"回来还是那一段 / 段间那一格算**前一段的段尾** / 越界夹回两端。

第 4 组里那发"段数为 0"必须配**明知非 0 的对照**（记忆 `zero-counts-need-a-positive-control`）：
同一支判据打在黄金表上不许也报 0，否则"仪器没接上"和"这本书真的没正文"长得一模一样。

## 3. 变异核验：16 发全红，两条守卫各配一发"打不红"的错靶子

`.probe/g3c1_mutation_check.py` 分两批发错：**S 批**改生产代码（尺动了，表必须显出陈旧），

两发**我一开始归错了对象**，记下来是因为错得有意思：

- 想让"段间格漏算"打红判据 3。改完照样绿——判据 3 比的是**表 vs 现场算的错尺**，
  而漏算段间格改的是**正确尺**那一侧，表里那串（黄金）反而更"像"错尺了。真正归它管的
  是判据 1（表与现场分家）。这一发最后打在**表本身**上（把偏移列抄成漏算段间格那串）才红。

## 4. 一处仪器缺陷（本轮唯一一次写脏仓库）

变异跑批用 `Path.write_text` 还原文件——它在 Windows 上把 `\n` 翻成 `\r\n`，于是一趟跑批
把三份 LF 产物**整文件换了行尾**：黄金样本 19,372→19,294 字节、`text_layout.py`
6,285→6,153、`reader_view.py` 67,963→66,748（差值正好等于行数）。最阴的是
`git diff` **看不出来**：`core.autocrlf=true` 的 clean 过滤在比较时把 CRLF 归一回 LF，
只有 `git status` 报 M。已按字节恢复（`.probe/g3c1_restore_newlines.py`，只对
"只差换行"的文件动手，其余交人判断），跑批改成 `read_bytes`/`write_bytes` 留底还原，
并在每次跑完后用 `md5sum -c` 逐一核——**判据是字节相等，不是 diff 为空**。
探针落表那一步也一并改成按字节写。这一条已进长期记忆（`windows-inplace-rewrite-crlf`）。
