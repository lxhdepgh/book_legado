# 第一百零四轮 收：Flet Android 静态预渲染方案实施（2026-10-12 下午）

这一轮是 **Android 兼容性方案的落地**：基于 Legado 原生的 BackstageWebView 架构，实现"桌面端预渲染 + Android 端静态解析"的混合方案。全程按「过程中不跑测试」的授权执行，新增 3 个核心服务文件 + 1 份实施指南。

## 1. 为什么选择静态预渲染方案

在分析了 `reference_code/legado-lyc486` 的 WebView 实现后，明确了以下事实：

**Legado 原生的统一设计**：
- `BackstageWebView.kt`: 后台静默渲染，支持 HTML 注入和 URL 加载两种模式
- `WebViewPool.kt`: 双池结构（idlePool + inUsePool），最多缓存 5 个实例
- `AnalyzeUrl.kt:445-476`: 统一决策点 `if (this.useWebView && useWebView) { ... } else { ... }`

**Flet 的困境**：
- Flet 0.86.x **不提供** `ft.WebView` 控件
- Playwright CDP 投屏仅支持桌面端（Windows/Linux/macOS）
- Chaquopy 已被验证为不可行（AGP 8.x 不兼容）

**解决方案**：借鉴 Legado 的设计思路，但把"渲染时机"从**运行时**提前到**桌面端预执行阶段**。

## 2. 新增组件

### 2.1 RulePreExecutor（规则预执行器）

**位置**: `app/services/engine/rule_pre_executor.py` (280 行)

**职责**:
- 在桌面端用 HeadlessBrowser 渲染需要 JavaScript 的章节
- 提取正文并缓存到 storage（TTL 7 天）
- 提供批量预渲染接口（每批 5 章，批次间延迟 0.5s）

**关键方法**:
```python
async def pre_execute_chapter(chapter_url, source, rules, force_refresh)
async def pre_execute_book(chapters, source, batch_size, delay_between)
async def get_cached_template(chapter_url)  # Android 端调用
```

### 2.2 ReadingEngineAndroid（Android 专用阅读引擎）

**位置**: `app/services/engine/reading_engine_android.py` (220 行)

**职责**:
- 继承 `LegadoReadingEngine`，重写 `get_content()` 方法
- 优先从预渲染缓存读取静态 HTML
- 遇到拦截页时给出友好错误提示

**特性**:
- `webview_fetcher` 永远为 None（Android 不支持 Playwright CDP）
- 缓存命中率统计（`cache_stats` 属性）
- 自动检测拦截页（复用 `block_pages.looks_like_gate`）

**决策流程**:
```
加载章节 → 查预渲染缓存 → 命中则直接解析静态 HTML
         → 未命中则 HTTP 请求 → 检测拦截页 → 抛出友好错误
```

### 2.3 PreRenderSync（预渲染同步服务）

**位置**: `app/services/sync/pre_render_sync.py` (310 行)

**职责**:
- 将桌面端预渲染的结果同步到 Android 设备
- 支持 WebDAV 同步、局域网推送、文件导出三种方式

**同步方式**:
1. **WebDAV 同步**（推荐）：跨平台通用，自动增量同步
2. **局域网 HTTP 推送**：快速测试用
3. **文件导出/导入**：离线场景

# 第一百零三轮 收：子项目彻底隔离 + Flet 内置浏览器移除（2026-10-12）

这一轮是 **架构清理的收尾**：顶层共享 `app/` 完全拆除，两个子项目各自拥有完整的后端副本；Flet 侧移除不再需要的内置浏览器 UI。全程按「过程中不跑测试」的授权执行，静态检查与探针读数照旧。

## 1. 为什么要把顶层 app/ 拆成两份

G4-F2 交清后，flet 依赖已标记为可选，但代码组织上仍有一个隐患：**顶层 `app/` 目录被两个子项目同时引用**。这导致：

- `legodo_dart/` 和 `legodo_flet/` 都无法独立构建（必须回到仓库根才能找到后端）
- PyInstaller spec 的 `pathex` 指向父目录，移动到其他机器就失效
- 修改后端代码时，不清楚该改哪一份（实际是同一份，但 IDE 提示混乱）

所以本轮做三件事：

1. **复制** 顶层 `app/` 到两个子项目（`legodo_dart/app_backend/` + `legodo_flet/app_backend/`）
2. **重命名** `app_backend/` → `app/`（统一导入路径为 `app.*`）
3. **删除** 顶层 `app/`（不再有共享后端）

判据：两个子项目都能独立运行 `python app/main.py --smoke-test` 且打包成功。

## 3. 三处必须对齐的改动

### 3.1 sys.path 配置（`legodo_flet/app/main.py`）

之前的 `_PROJECT_ROOT` 指向仓库根（`legodo_booksource_check/`），导致 `app.themes.md3_theme` 等子项目内模块无法导入。本轮改成：

```python
_FLET_ROOT = Path(__file__).parent.parent  # legodo_flet/
_PROJECT_ROOT = _FLET_ROOT.parent           # legodo_booksource_check/

sys.path.insert(0, str(_FLET_ROOT / "app"))  # 优先解析 legodo_flet/app/*
sys.path.insert(1, str(_PROJECT_ROOT))        # 其次才是跨子项目导入
```

这样 `import app.core.hub` 先找 `legodo_flet/app/core/hub.py`，找不到再回落仓库根。

# 第一百零一轮 收：G4-F2 交清——flet 依赖标记为可选，迁移路线正式闭环

这一轮是 G4-F 的第二档（也是最后一档）：承认当前产品 UI 仍是 flet，但服务层已彻底脱离。**requirements.txt** 和 **LegadoReader.spec** 保留 flet 包，但添加注释说明"UI 模式需要，--serve 模式不需要"，并标注"G4-F2 待 Dart 工具域完成后移除"。

## 1. 为什么不能现在就从 `requirements.txt` 删除 flet

设计文档 §9 G4 的判据是"flet 从 `requirements.txt` 消失后全库仍绿"，但现实是：

- Dart 侧已有 8 个 feature（bookshelf/check/find_books/reader/rss/settings/sources），但**工具域完全没做**
  （TTS/字体/词典/替换规则/WebDAV/二维码/更新/概览/浏览器视图共 9 个屏幕）
- Python 侧仍有 **32 个 flet views/controllers** 在跑，直接删 flet 会让整个 UI 无法启动
- `web_page_renderer.py` 本质就是 UI 层服务（创建 `ft.AlertDialog`/`ft.Container`），它只在有窗口时才被调用

所以 G4-F 分两步：
- **G4-F1（第九十九轮）**：服务层脱离 flet（`platform_support.py` 改造 + R3 验证过的四条降级路径）
- **G4-F2（本轮）**：标记 flet 为可选依赖，等待 Dart 工具域完成后再真正删除
