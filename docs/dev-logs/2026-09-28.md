## 第三十轮：换源为什么慢——网络占 3%，剩下是一条循环线程（任务 #60 前置）

### 现场
用户诉求："other_history 里的手机软件换源时查询相当快，我们在 PC 端反而非常慢，
分析一下两者的差别。" 上一轮已经定性过（GIL、单事件循环），本轮换成**测**：
`.probe/bench_perf.py`——aiohttp 起一个回环假源，一页 132KB / 400 条书目，
32 个源各搜一次，用猴子补丁给引擎的五个阶段分别计时，另开一条心跳协程量事件循环卡顿。

### 测出来的四件事

1. **一次搜索的相位拆分（改前）**：400 本书的一次搜索墙钟 316ms，其中
   网络+解码 10.4ms（**3.3%**）、`parse_markup` 79.9ms、列表管线 85.2ms、
   **字段规则 210.2ms**。也就是说"慢"跟网络基本无关，全在 CPU 上。
2. **32 个源的扫描**：单 worker 11314ms / 32 workers 10817ms → **1.05×**。
   给了 32 路并发，几乎一点没快，因为它们在抢同一颗核。
3. **循环占用率**：心跳协程本该每 10ms 醒一次，实测 32 路扫描期间
   迟到总和 10150ms / 墙钟 10644ms = **95%**，最长一次连续 **1083ms** 没醒。
   这一条比第 2 条更有说服力：不是"没起够 worker"，而是**那条循环线程从没空过**。
4. **参考实现快在哪**：`reading_service.py:52 SWITCH_CONCURRENCY = 32`、
   `check_service.py:20-21 CHECK_CONCURRENCY = 8 / CHECK_MAX_CONCURRENCY = 16`——
   看着和 Legado 的 `threadCount=32` 一样，但我们的并发要经 `app/core/hub.py get()`
   返回的 `EngineProxy` 派发到 **EngineHub 的一条循环线程**（`app/core/engine_worker.py`），
   所以 32 是 **32 个协程**；Legado 的 32 是在飞请求数，解析跑在
   `min(32, MAX_THREAD=9)` 条**真操作系统线程**上。网络段我们能让出来，CPU 段不能让。

### 顺带测出并**当场否决**的两个候选
- `bodyBytes: list(raw)`：把字节串转成 JS 侧的整数数组，一次搜索里 0.2ms。**不是热点，不改**。
  第一版设计文档里把它写成过"要换 Uint8Array"，那是不成立的推断，删了。
- `_html_declared_encoding`（扫一遍 HTML 头找 `<meta charset>`）：34.7ms，看着很大，
  但**只在响应头没给 charset 时才走**；回环假源是 `text/html` 直接带 charset，一次也没进。
  真实站点里它按书源分布，本轮没法离线定量 ⇒ 记为"待有真实样本再评"，不动。

### 换解析器的口子为什么**主动不开**
同一个 `parse_markup` 位置换三种实现各测一遍（132KB / 400 条，各 3 次）：
html5lib **74.9ms**、html.parser **33.5ms**、lxml **22.9ms**。换 lxml 看着白捡 3 倍。
不换的理由不是"怕麻烦"：本项目对 Legado 的对齐契约是 **Jsoup 语义**，
Jsoup 自己就是 html5 解析器（畸形标签补全、`<b><p></b>` 这类嵌套修复都和 html5lib 同源），
换 lxml 等于把整条 `test_legado_compat.py` 的解析层保证换成一份没人验过的差异表。
要动它得先有一台能跑 Jsoup 的差分面，那是另一个量级的工程，登记进遗留。

## 第三十一轮：规则复用落地——选择器计划与表达式拆分组装（任务 #60）

### 设计
拆完相位发现真正重复的是**字段规则那 210ms**：一条 `bookList` 有 400 个节点，
每个节点都要把同一段规则文本重新拆一遍、同一个选择器字符串重新解析一遍。
规则文本一轮搜索里只有 6 种，节点有 400 个 ⇒ 重复 400 倍的是"怎么解释这条规则"，
不是"解释出来的结果"。于是只缓存**与节点无关的那一层**：

- `legado_rule_parser.py:1348` `_jsoup_part` 上 `@lru_cache(maxsize=2048)`——
  单个选择器片段的分类（伪类/属性/正则）；
- `legado_rule_parser.py:645/661` `split_rule_expression` 改成**缓存外壳 + 
  `_split_rule_expression` 缓存内核**：分组结果只取决于规则文本，内核返回**元组**，
  外壳每次 `list(...)` 复制出来交还——因为调用方会 `pop` 掉拿到的部件，
  直接交还缓存对象会把缓存改花（这条是本轮唯一一处"缓存反而更危险"的形状，
  所以给了单独一条护栏）；
- `legado_rule_parser.py:1106/1111` `select_jsoup` 走 `_cached_jsoup_plan(selector)`，
  把选择器**重写成计划**（一步一次 `lru_cache`）；带 `*|` 的那条路要从**当前节点**的
  标签名展开通配、结果随 context 变，**留在不缓存的原路径**。

### 效果（同一脚本、同一假源，A/B 只关掉这三处缓存）
| 指标 | 关掉缓存（=改前形状） | 现状 | 变化 |
| --- | --- | --- | --- |
| 一次搜索墙钟 | 316.1 / 315.7 / 317.4 ms | 223.2 / 210.1 / 212.6 ms | −33% |
| 其中字段规则 | 210.2 / 213.1 / 214.5 ms | 110.6 / 109.7 / 111.1 ms | **−48%** |
| 网络+解码 | 10.5 / 10.1 / 10.1 ms | 10.8 / 10.2 / 10.7 ms | 不动（本就不该动） |
| `parse_markup` | 79.9 / 77.7 / 77.9 ms | 84.3 / 76.1 / 76.0 ms | 不动（噪声内） |
| 32 源扫描墙钟 | 10816.7 / 10644.4 ms | 7105.0 / 7075.5 ms | **−34%** |
| 单 worker 扫描 | 11313.9 ms | 7440.2 ms | −34% |
| 32 workers 加速比 | 1.05× | 1.05× | **没变**——并发这条路仍然堵在单核上 |
| 循环迟到占比 | 95%（max 1083ms） | 94%（max 909ms） | 没变 |

两件事要说清楚：
1. 加速**全部来自少做事**，不来自多开线程。加速比改前改后都是 1.05×，
   循环占用率还是 94%——第三十轮定性的瓶颈**一点没被这一改动解掉**，
   它只是让同一个瓶颈要跑的活少了三分之一。
2. "改前"这一列是**把本轮加的三处缓存运行时关掉**测的，不是翻旧提交：
   旧提交里 `select_jsoup` 还不存在计划这一层，直接拿它对比会混进结构差异。

### 剩下那 94% 怎么继续降
唯一能真正并行的形状是**把解析挪出循环线程**（多进程 / 每条 worker 一条循环）。
本轮没做，因为它和已有的两条硬契约打架：引擎的 `interaction_loop` 编组
（记忆 `engine-hub-loop-split`：碰控件的回调必须回界面循环）与
"循环线程上绝不释放 COM/原生对象"。拆成多循环要先把这两条重新验一遍，
不是换个 `ThreadPoolExecutor` 就完事。登记遗留。

## 第三十二轮：连接池与引擎池对齐——**明确不回改性能数字**（任务 #61）

### 设计
`RuleEngineService` 原来 `DEFAULT_POOL_SIZE = 8`，比 `SWITCH_CONCURRENCY = 32` 小，
于是扫描时引擎按 LRU 被反复逐出，每次逐出连带关掉它那份 `ClientSession` 和
`TCPConnector`——**保活连接被丢掉**，下一源重连。两处改动：

- `rule_engine_service.py:95 DEFAULT_POOL_SIZE = 32`（与换源并发对齐，Legado 的
  `threadCount` 也是 32）。先量了引擎构造本身：**0.55ms** 一个，
  所以池子值钱的地方从来不是省了建对象，是**保住了 cookie 罐和 JS 侧状态**；
  `_get_engine` 的说明按这个事实重写。
- `rule_engine_service.py:115/203-214/224` 新增**按事件循环**共享的
  `TCPConnector` 字典 + `_shared_connector()` 工厂，建引擎时注入
  （`rule_engine.py:817/830/875`、`reading_engine.py` 同步转发参数）。
  为什么按循环 keyed：aiohttp 的对象绑循环，而 `hub.require()` 拿的是**裸服务**，
  存在从别的循环上直接调它的路径（EngineHub 只有 `get()` 的代理才派发过去）。
  `on_stop()` 只关**当前运行循环**那份，别循环上的留给它自己的主人关。
- 引擎侧 `_session_for` 现在明确区分 `connector_owner`：
  用共享 connector 时 `connector_owner=False`，这样 `aclose()` 一个引擎
  不会把别的引擎的保活连接一起掐掉（对齐 OkHttp 一个 client 一个 ConnectionPool）；
  socks 代理仍走**私有** `ProxyConnector`，因为它本身就是一条通道，共享没有意义。

### 效果：**回环量不出收益，所以不报数**
`.probe/bench_pool.py` 同一进程内 A/B：pool32 6637/6716ms、pool8 6669/6579ms、
私有 connector 6602/6653ms、单 worker 7012/6983 与 6921/7054ms——
**四档全在噪声里**。原因很直白：回环假源没有握手、没有 TLS、没有往返，
这一改动省的全是那些东西。
中途我还把 pool 提到 32 之后的两次扫描读数（7633 / 8335ms）当成过"变慢了"，
是同进程 A/B 才把它证伪成噪声。结论写成：**这一条是正确性与状态保活的对齐，
不是性能优化**，谁要是拿它引用加速数字，就是失真。

### 提交前抓到的自伤：共享池把 dnsIp 钉表丢了
建共享 connector 时只写了 `TCPConnector(ssl=False, limit_per_host=5)`——
少了私有路径那条 `resolver=self._dns_resolver()`。dnsIp 钉表（[M1-2.14]，
`rule_engine.py:766` 起的 `_DnsIpResolver` 读全局 `_DNS_IP_TABLE`）挂在 resolver 上，
于是**凡走池的引擎都不再按钉表解析**，等于把"书源指定 IP"这个设置整条废掉，
而且没有任何报错。

回环基准对它**完全无感**：假源 URL 是 `127.0.0.1` 字面量，压根不走解析器。
这就是"基准绿 + 全量套件绿 ⇒ 功能照样退化"的标准形状，和
`refactor-regression-orphan-methods` 是同一类，只是这次加害者是我自己本轮的改动。

三处收口：
1. `rule_engine.py` 导出 `dns_ip_resolver()` 工厂（resolver 无状态，只读全局钉表，
   所以可以跨引擎共用一个构造点），`ReaderEngine._dns_resolver()` 改调它；
2. `rule_engine_service._shared_connector()` 建池时 `resolver=dns_ip_resolver()`；
3. 护栏 `test_shared_connector_keeps_the_dns_ip_resolver` 断言**两条路的
   `_resolver` 都是 `_DnsIpResolver`**。它故意**不调 `resolve()`**：
   少了 resolver 时 `resolve("book.example")` 会去查真 DNS，护栏自己就变成联网用例了
   （与"验证一律离线"冲突），所以钉成类型而不是行为——这一条的取舍记在这里，
   免得后人以为"为什么不直接断解析结果"。
   变异核验：把 `resolver=dns_ip_resolver()` 删掉 ⇒ `1 failed`（脚本第一次跑因为
   `subprocess` 按 GBK 解码子进程输出直接崩了，还原没走到，加
   `encoding="utf-8"` + 子进程 `PYTHONIOENCODING` 后重跑；见
   `windows-bash-chinese-output`）。

### 另一处**不属于本轮**的改动，已从工作树退回
提交前逐行过 diff 时发现 `_jsoup_plan` 里多了一条与性能无关的重写：

```python
selector = re.sub(r"(^|[\s>,+~(])@([\w-]+)(?=$|[\s>,+~)])", r"\2", selector)
```

它不在 HEAD 里，也不在本轮的任何设计里，而**行为与它自己的注释相反**：注释说
`@class` 简写"等价于 `[class]`"，替换却写成 `\2`（连边界字符 `\1` 一起吞掉），
实测 `select_jsoup(soup, "@class")` 从 HEAD 的 `SelectorSyntaxError`
变成静默 `[]`（把 `class` 当成了标签名），`li@class` 仍抛错。
全库没有任何用例覆盖 `@属性` 这种选择器。
一条"把显式报错换成静默空结果"的改动**不该混在性能提交里**，所以本轮把它退回，
`docs/找书与换源逻辑对齐.md` 的对齐结论不受影响。真要支持 `@attr` 简写，
得先确认 Legado 的 `AnalyzeByJSoup` 到底怎么处理前导 `@`，再按 `[attr]` 形状重做
并补护栏——登记进遗留。


## 第三十三轮：共享 JS scope——**测完自己把自己否决了**（任务 #62）

原推荐第 5 条是"没有 `jsLib` 的书源也共享 QuickJS context，省掉重复求值"。
读参考实现 + 实测两边都指向反方向，所以**没实现**，只留下证据。

### 实测
`.probe/bench_js3.py`（给 `quickjs.Context` 套一层计数代理，因为
`_quickjs.Context.eval` 是原生不可写属性，且 `legado_js._evaluate_locked` 里是
**函数内 local import**，patch 模块名没用，得重新绑类本身）：

| 项 | 实测 |
| --- | --- |
| 一次 `@js:` 求值总耗时 | 9.08 ms |
| 其中原生 `eval` | **7.78 ms**（85%） |
| `quickjs.Context()` 新建 | **0.14 ms** |
| Python 侧建上下文（含 109 次 `add_callable`） | 1.29 ms |
| 每次 eval 传给 QuickJS 的程序长度 | 16461 字符（bootstrap 拼接后） |

`legado_js.py:929..3711` 的 JS bootstrap 是一整段 f-string，字面量 **163568 字符**、
**21 处插值**（L931–944、L982–990、L1357、L3555）。也就是说 7.78ms 里 QuickJS 在
**重新编译整条 bootstrap**。共享 context 只省下那 0.14ms 的 `Context()`，
编译一次也不会少——现状的 jsLib 路径已经在共享 context，它照样每次 eval 这段。
**省不了 85% 的那一块，就不值得为 1.5% 去换风险。**

### 参考实现同样不共享
`SharedJsScope.kt getScope()` 对 **空白 jsLib 直接返回 null**（即各源各一份），
并且 `scope.preventExtensions()` 挡住隐式全局；`BaseSource.evalJS()` 把
`java` / `source` / `baseUrl` / `cookie` / `cache` 作为**宿主对象**注入，
不是每次重新 eval 一段 JS 垫片。两条都说明：Legado 宁可重复建 scope，
也不要"A 源的脚本写出来的全局被 B 源看见"。我们共享空 jsLib 的 context
等于主动制造这条泄漏。

### 真要降这 7.78ms 的话
只有一条路：把 bootstrap 拆成**静态段**（`ctx.compile()` 一次拿 `Function` 复用）
与**每次求值的 preamble**（那 21 个插值里真正逐次变化的部分）。
本轮没做：21 处插值要先逐个判"是源级常量还是逐次值"，铺开的是一整条
`legado_js.py` 的值捕获审计（2700 行量级），收益上限是每次 `@js:` 少 ~7ms。
登记遗留，等真实书源里 `@js:` 的占比数据支撑要不要做。

| `test_socks_proxy_keeps_its_own_connector` | 走 socks 代理的请求**不共用**共享 connector（用真 `ProxyConnector`，构造期不产生 I/O，所以离线可跑） | 让 socks 分支也走共享路径 | 红 |

第四、五条各返工过一次：前者第一版把"该留下的那个引擎"当成被逐出的那个来断言

### #4 超时预算：这不是调参，是**把本机排队算成了书源坏了**

32 路扫描，同一条零延迟回环源：

| 并发 | 单源墙钟中位 | 单源最长 | 孤立跑一次 | 排队占比 |
| --- | --- | --- | --- | --- |
| 8 workers | 1737ms | 1888ms | 236ms | **86.4%** |
| 32 workers | 4117ms | **8532ms** | 236ms | **94.3%** |

而 `reading_service.py:871` 是
`asyncio.wait_for(self._engine.search(source, key, 1), SWITCH_TIMEOUT)`——
10s 读的是**墙钟**，把"等本机那条循环线程"一起计进去；
`_switch_failure_reason`（`reading_service.py:91-92`）又把
`asyncio.TimeoutError` 归成 `"超时"`，**与真慢源在用户面前完全同形**。
零延迟假源的最长单源已经到 8532ms；叠上真实网络（哪怕只 1–2s）就会开始
把健康源报成超时。这正是"PC 端换源很慢、还全都失败"的机制：
不是慢，是**排队被记成了故障**。

三个选项，按代价从小到大：
1. **把 worker 数收到实测拐点**（见 #6 的曲线，4–8 就到底了）：32 路并发不但不快，
   还制造 94% 的排队。改一个常数。
2. **超时只包网络段**：引擎内 per-request 已有超时；外层不再包整条 `search`，
   解析/取值不计入"源坏了"。语义最干净，但要把 `search` 的内部计时暴露出来。
3. **用 `time.thread_time()` 分离"自耗时 vs 墙钟"**（本机 3.12 可用，本轮确认）：
   排队不计失败，失败原因里把"本机繁忙"和"源超时"分开显示。
   对用户最诚实——但他等的书还是没出来，所以它必须和 1 或 2 搭配。

**推荐 1+3**（1 单独就能消掉绝大部分假超时；3 把剩下的诚实标出来）。2 留作后续。

### #7：取值段快路径（`app/services/engine/legado_rule_parser.py`）

`_JsoupPlan` 多带一份 `fast` 步骤表；只有"纯后代链 + tag/.class"这一族走 `find_all`，
属性选择器、`#id`、伪类、组合符、通配、正则后缀一律留在 SoupSieve 原路。
写第二道"进了快路径但带后置过滤"的闸门时发现自己写不出来——**那是不可达分支**：
那几种写法没有一个字符能进 `_FAST_CHUNK_RE` 的 chunk。于是把上一版那条
`if fast and (attribute_filters or …): fast = ()` 当死代码删掉，闸门收成一处形状判定。
两条语义不是按常识定的，是照生产代码复刻的：class 大小写沿用 `(?<![\w\\])\.` 那条重写
（每个 class 自带 `foldable` 标记），标签名大小写按 builder 分——`parse_markup` 的两条 XML
路都建在 html.parser 上所以不区分，而**真 `xml` builder 区分**，所以快路径带
`_tag_case_insensitive` 闸门让位（`test_xml_builder_keeps_tag_names_case_sensitive` 用真
XML builder 造了一份生产里不存在的文档，专门钉这一格）。

实测（同进程 A/B，`.probe/bench_fast.py`、`.probe/bench_switch.py`）：

| 面 | 关快路径 | 开快路径 | |
| --- | --- | --- | --- |
| 5 条规则 × 2004 节点的选择器匹配 | 31.7ms | 6.9ms | **4.59×** |
| 32 源扫描 · 并发 1 | 7999.7ms | 5757.8ms | −28.0% |
| 32 源扫描 · 并发 8 | 7366.4ms | 5927.0ms | −19.5% |
| 32 源扫描 · 并发 32 | 7579.5ms | 6523.1ms | −13.9% |

护栏 `JsoupFastPathTests` 4 条，按**节点身份**（`id(node)`）逐条差分而不是比文本——
快路径的语义偏移不会报错，只会取值错书。变异 8 条全数变红，其中 4 条第一轮活了下来，
两种原因各有其代表性：语料缺形状（补 `item`、`li.Item` 两条），以及**去变异一条不可达
检查**（那条快路径闸门本身）——后者不是补测试能救的，是把被证明不可达的代码删掉。

**一次自伤，值得单记**：第一版闸门写成 `getattr(node, "builder", None)`。bs4 的
`Tag.__getattr__` 就是 `tag.find(...)`，于是"取一个属性"变成整棵子树搜索：单源搜索
223ms → **5.2s**（`_find_all` 被叫了 8000 次，profile 里 21.1s 有 20.6s 是它）。
测试全绿、基准只是"变慢了"，没有任何一条报错。改成沿 `node.parent` 走到根、
只读写 `node.__dict__` 并缓存结论。**规则**：在 `Tag` 上永远不要用 `getattr(x, name, default)`
探测属性，那是一次搜索而不是读取。

### #4：超时预算与"本机繁忙"（`reading_service.py` + `bookshelf_controller.py`）

`SWITCH_CONCURRENCY` 32 → 8。本轮实测曲线（32 源回环扫描）：
1 路 5757.8 / 2 路 5446.5 / **4 路 5302.3** / 8 路 5927.0 / 16 路 5899.3 / 32 路 6523.1 ms。
最低点在 4，之后只涨不降；**没按最低点取 4**——回环没有网络段，而网络等待才是并发唯一
能白拿的收益，这张表给的是下限（和 #6 那条"别拿回环表去主张降到 4"同一个道理）。

"超时"不再是一个数：`_switch_starved` 按超时窗口内**本线程 CPU÷墙钟**（`time.thread_time()`）
判这次等待是排队还是在等对端，阈值 `SWITCH_BUSY_RATIO = 0.5`；进度回调扩成
`on_progress(completed, total, failures, starved)`，界面写「n 个失败，m 个本机忙不过来」。
理由不是措辞洁癖：混成一个数时界面写"38 个失败"，用户去删的是 38 个好源。

预算实测（并发 32、单源孤立 155.5ms 的一批源）：10s/5s 都是墙钟 5.4s、0 故障 0 繁忙；
压到 2s 时 19 个源被掐断却**没有一个**是真故障；0.5s 时 24 繁忙 + 6 源故障。
护栏 3 条（服务面 2：三路差分的归因 + worker 上限；界面面 1：两个数分开渲染），
变异 9 条全数变红。worker 上限那条断言写成 `== 3` 而不是 `<= 3`：只钉"没超过"的话，
把并发写成 1 也能绿，而那时候整轮扫描慢十倍。

### #68：换源真正的大头是逐行 fsync（`app/services/search_model.py`）

为了读上面那张预算表，先做了一次单源归因（`.probe/bench_insert.py`）：

| 量 | 值 |
| --- | --- |
| ① 引擎孤立搜索（解析+请求） | 154.0ms |
| ② 同一条源走 `switch_source`（含落库） | **1311.8ms** |
| ③ 同 ②，把 `_search_store` 摘掉 | 163.8ms |
| ④ 只做 `store.insert(400 行)` | 1141.2ms |
| ⑤ 同 ④，外面手工包一条事务 | 11.6ms |

`SearchBookStore` 借的是主库那条 `isolation_level=None` 连接（M6 垫片），
`executemany` 在 autocommit 下就是**每行一次 journal + fsync**：98×。新增 `_batch()`——
一批行只 BEGIN/COMMIT 一次、外部已开事务时只加入、失败 ROLLBACK 不留半批。
修完 ② 从 1311.8ms 回到 177.1ms，32 源扫描（并发 1）从 42528ms 回到 5757.8ms。

这条顺带**修正了第三十一轮的一句结论**：当时写"墙钟的九成是循环被一段 Python 计算占住，
不是等待"。心跳停顿测的是"循环没在跑事件"，而逐行提交正好也长这样。九成里有一大半
其实是提交，不是解析。

同型缺陷还剩一处未修：`StorageService.migrate()` 的三个 `_migrate_*` 同样在 autocommit 上
`executemany`（只在首次启动导旧介质时跑一次），登记进遗留。
