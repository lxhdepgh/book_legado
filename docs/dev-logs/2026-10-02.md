## 一、这一句为什么会让人怀疑引擎

`ClientConnectorError.__str__`（aiohttp 3.14 `client_exceptions.py:203`）方括号里填的是
`os_error.strerror`。TLS 握手期被复位时，抛上来的是一条**不带任何参数**的
`ConnectionResetError`（`args=()`、`strerror=None`，末帧 `sslproto.py:581
_on_handshake_complete`），于是用户与开发者看到的整句就是

```
连接失败：Cannot connect to host www.qbmfxs.com:443 ssl:False [None]
```

三个信息全丢了：不知道拨到了哪个地址、不知道是谁抛的、更不知道那句 `ssl:False` 其实
照样走了 TLS（`rule_engine.py:1424` 请求级与 `:1017-1019` 连接器级都是 `ssl=False`，
aiohttp 对它返回 `_SSL_CONTEXT_UNVERIFIED`）。第六十五轮排查时先量出本机把
`www.qbmfxs.com` 吸到 `198.18.8.94`（RFC 2544 的 `198.18.0.0/15`，安全产品做 DNS 吸洞
爱用的段）才定案——但那一步靠的是额外探针，句子里一个字都没写。

顺带把"是不是改坏了引擎"这条查实：第六十三~六十五轮未提交的改动里 `app/services/engine/`
只动了 `public_suffix.py`，最近一笔碰 `rule_engine.py` 的是已提交 `0d7a76e` 的 cookie
落库脏闸门，都在连接建立之后。

## 二、改法：只在抛出点后面追加一段

`rule_engine.py:1491-1502` 的 `except aiohttp.ClientConnectorError` 里，重拨预算用尽之后
先算一次"这次拨的是哪些地址"，再把补充段接在原句后面。**原句一字不动**，重拨次数、超时、
连接池策略一律没碰（这三样是本轮明确划出的禁区）。

新增三样东西（`rule_engine.py:826-888`）：

- `in_sinkhole_range()`：只认 `198.18.0.0/15`，IPv6 先剥 `%ZoneId`，
  双栈写法 `::ffff:a.b.c.d` 也认（`ipv4_mapped`）。
- `_dialed_addresses(host, port)`：dnsIp 钉表命中就以钉表为准并**不再解析**（解析出来的
  可能不是当时拨的那个），否则重新解析一次去重取前几个；任何异常都吞成空列表——
  报错的路上不许再制造一次失败。
- `_connect_failure_tail(exc, addresses)`：纯函数，最多写三件事——
  `底层 <类名>(code=…) 未给出错误文本`（只在 `strerror` 真空时）、`拨到 <地址>`、
  吸洞段提示。走代理（HTTP 或 SOCKS）时整段地址不查：那时拨的是代理的地址。

真句子的变化（`.probe/connect_failure_detail.py` 走真 `_request_transport`，同一台引擎、
同一 URL 各跑改前/改后一遍，输出存 `.probe/out_connect_detail_66.txt`）：

```
【B 回环拒连】http://127.0.0.1:63889/
    改前: 连接失败：Cannot connect to host 127.0.0.1:63889 ssl:False [远程计算机拒绝网络连接。]
    改后: 连接失败：Cannot connect to host 127.0.0.1:63889 ssl:False [远程计算机拒绝网络连接。]｜拨到 127.0.0.1
【C 健康假源】http://127.0.0.1:63890/
    改前: OK 正文 28 字 / text/plain / 查地址 0 次
    改后: OK 正文 28 字 / text/plain / 查地址 0 次
```

## 三、当场被实测推翻的两个假设

1. **"离线也能造出 `[None]`"**：造不出来。今天这台机器的三种连接失败都带 `strerror`
   （拒连 `1225`、明文端口按 https 握手 `10053`），吸洞今天**没开着**——
   `www.qbmfxs.com → 38.47.117.159`（上一轮量到的是 `198.18.8.94`），
   注定不存在的名字直接 `gaierror 11001`。所以护栏改成**合成异常本体**：
   不带参数的 `ConnectionResetError` 交给真 `ClientConnectorError`，`ConnectionKey`
   按生产请求的 `is_ssl=True, ssl=False` 造，先断替身确实长回 `"ssl:False [None]"`，
   再断补充段。吸洞提示那条靠 dnsIp 钉表把域名钉到 `198.18.8.94`，全程零联网。
2. **"`[None]` 那一格大概是解析失败"**：不是。解析失败走的是 `ClientConnectorDNSError`，
   `strerror` 有值（`[getaddrinfo failed]`），而且今天在引擎这头露出来的是
   `连接超时：Connection timeout to host <原 URL>`——超时不是 `ClientConnectorError`，
   本轮没动它，那句里带 URL，仍可归因。

这两个推翻都是**同一条探针**做出来的，不是推理：`.probe/connector_error_shapes.py`
今天重跑一遍（三形状的底层类别、`args`、末几帧都打出来）才把 `[None]` 钉在握手段。

## 四、护栏与变异核验

`tests/test_connect_error_detail.py` 12 条、0.35 秒。两条"不许发生"各配了"该发生的仍然发生"：

- 拒连不许出现"未给出错误文本"（`strerror` 已经说清了）＋原句照旧完整；
- 走代理不许解析目标域名（断解析器调用记录为空）＋底层那句照旧要写出来；
- 健康请求一次都不查地址＋正文 28 字照旧拿到。

`.probe/mutate_connect_detail_guards.py` 七种打断全部当场红：
M1 补全段整体失效 3 红 / M2 摘掉吸洞提示 1 红 / M3 摘掉"底层 …"那段 2 红 /
M4 摘掉钉表优先 3 红 / M5 摘掉代理闸门 1 红 / M6 把地址查询挪到请求之前 5 红（连健康那条
也红，这正是"正常请求一分钱不付"要的落点）/ M7 丢掉 aiohttp 原文只留补充段 3 红；
收尾 sha256 与起手一致（`ebe3e837c8123eee…`）。

写这个脚本时自己踩了一次记忆 `guard-tests-assert-absence` 里那条"还原只能是整文件备份写回"：
`finally` 里 `TARGET.write_bytes(backup)` 传的是 **str**，`memoryview` 当场抛
`TypeError` ⇒ 还原整段没执行，源文件被留在变异态。更糟的是**这条崩溃把核验报告盖掉了**：
第一轮的 `[抓到]` 一行都没打出来就被 traceback 带走，我改完脚本再跑第二次，脚本把
"已经带着一行 `return ""` 的文件"当成备份，在其上又叠了一行（函数里出现两行 `return ""`），
输出的字节数从 122874 变成 122889——**发现脏状态的唯一线索就是这个读数**，
不是任何一条断言。现在脚本起手先按"每种变异的新文本是否已在文件里"证明起点干净，
起手/收尾各核一次 sha256，崩在半路会直接报 `[脏]` 而不是继续核验。
