## 一、这一页原来缺的不是控件，是"能自己起手"

自愈的整条流水线早就在了（`rule_repair.diagnose_content_rule` 真抓 1-3 页样本 →
挖候选 → ProbeEngine 本地回放 → 复核 → 出报告 → 用户点确认才写回），缺的是入口：

- `RuleRepairController` 只订阅 `RepairReportReadyEvent`，报告是别人（阅读器）发起的；
- 视图上连"选哪个源、拿哪一章做样本"的控件都没有，而 `repair(source, chapter)`
  必须要一条**正文页地址**。

章节地址这一格是本轮真正的难点：自愈页不许联网列目录（那是"点开列表页就开始抓站"，
第六十五轮的杀软拦截记忆就写在这条边上），所以只能拿**本地已经有**的东西。三条来源，
全部零联网：

| 顺序 | 来源 | 覆盖面 | 落点 |
|------|------|--------|------|
| ① | 书架那本书的**已缓存目录** | 读过的源 | `rule_repair_service.py:141 chapter_candidates()` |
| ② | 上一轮**检测抽到的样本章** | 检过、没读过的源 | `source_check_service.py:535`（快照多带一栏）+ `rule_repair_controller.py:264 _check_sample_group()` |
| ③ | 用户**手填一个正文页地址** | 前两条都空的源 | `rule_repair_view.py:208 set_manual_visible()` |

②是把已经付过的钱再收一次：检测轮里 `_sample` 已经抓过几章，那几条地址原本只活在
结果字典里、跑完就丢，现在随快照留下（`CheckFinishedEvent` **不加键**——它只有五个
字段，多一个就是 TypeError，护栏里专门钉了这条）。

## 三、浏览器探针抓出来的真 bug：整族下拉都在读一个不存在的字段

第一版探针（`.probe/probe_repair_picker_ui.py`，WEB_BROWSER + Playwright 点语义树）
在真浏览器里点书源下拉、点候选，Python 侧回的是：

```
[py] on_source_picked(None) → 章节 0 条、粘贴框 visible=True
```

用户明明点中了"备份源 二"，程序收到 `None`。根因不在本轮新写的控制器，在视图那一行：

```python
on_select=lambda e: self._fire(self.on_source_picked, getattr(e, "value", None))
```

flet 0.86.5 的事件对象是 `flet.controls.control_event.Event`，字段只有
`name` / `data` / `control`（外加两个 property），**没有 `value`**；`getattr(..., None)`
于是静默回退成 `None`。全仓 `app/views/` 扫下来这种读法有 **6 处 / 4 个文件**：
`rule_repair_view.py`（书源、章节）、`code_editor_view.py`（书源、规则字段）、
`webdav_view.py`（远端备份包）、`export_view.py`（已缓存书籍）——四条页的选择器在真
界面上点了都没反应。

为什么一直没被发现：测试替身比真事件**多一个字段**。`tests/test_source_rule_editor.py`
里 14 处、`tests/test_tools_chains.py` 里 2 处都是

```python
view._source_dd.on_select(SimpleNamespace(value="https://a/"))
```

`SimpleNamespace(value=…)` 恰好喂饱了 `getattr(e, "value")`，于是界面面 16 条测试全绿。
本轮把 6 处读法改成 `e.control.value`（同仓内一直正确的写法，如
`appearance_view.py:105`、`reader_view.py:950`），并把那 16 处替身换成
`ft.Event(name="select", control=dropdown)`——改完当场红了 22 条，正是替身掩盖的量。

护栏补两头（各自落在自己的射程里）：

- **行为**（`tests/test_views_source_m3.py`）：`test_picking_the_source_by_hand_reloads_chapters`
  与 `test_start_diagnosis_passes_chapter_followers_and_book` 都构造**真** `ft.Event`
  打 `on_select`，断控制器槽拿到的是选中项的键、章节跟着换 —— 上面那两条下拉各一条。
  程序改 `dropdown.value`（列表页带源进来那条路）**不触发** `on_select`，所以它俩
  钉的是不同的路，不能相互替代。
- **静态**（`tests/test_controller_service_surface.py`，与 flet 控件名/枚举/参数同一文件）：
  一条反射 `dataclasses.fields(flet.Event)` 证明 `value` 这个字段本来就不存在，
  一条 AST 扫 `app/views/` 里所有 `on_*=lambda e:` 形参与 `e/ev/evt/event` 具名形参，
  出现 `getattr(x, "value", …)` 或 `x.value` 就报。

## 第六十八轮：深遍挪出这一轮（第六十四轮 §八 的账今天结）

开发者交下的四件事里第 2 件。悬着的问题是：**一条源该在哪一轮被验正文**——
第六十四轮把浅遍和深遍塞在同一轮里跑完，实测每一档都是净亏（深遍占比 5.6% 就已经
−16.1%，最亏 −47.8%），因为那批源浅遍、深遍各付一次钱，而正文段请求数与"一遍全
完整档"完全相等；省的只是"同址两条"那类形状，钱一分没少。本轮按那个结论改形状，
并把"改完之后到底省不省"当场量出来。

### 1. 新形状：一轮只派发一次，贵的阅读链摊到后面几轮

`_run_tiered` 现在是**浅遍扫全书 + 补验这一轮开跑前就欠着的那一片**：

- 补验条数由 `tiered_check.per_round_deep_limit(计划源数) = max(12, 计划源数 × 8%)`
  封顶。8% 这个数是本轮实测出来的（见第 3 节），不是拍的：再高就把快检的时间吃回去，
  再低债还不完。
- 浅遍**当场**排进队列的那些不在这一轮补验，留给后续轮次。于是一条源一轮只被派发一次，
  浅遍那一行和补验那一行不会同时出现——第六十四轮那套轮内机制（`_run_checks` 的
  `counts` 参数、`_merge_by_url` 合并、"只有定论那条才审"的闸门）随之成为死代码，
  本轮一并删掉而不是留着当兼容层，对应的三条旧变异（S2/S3/S6）跟着退场。
- 进度分母仍是本轮计划源数、分子是派发数（两者现在相等），所以进度条的形状没变；
  界面收尾那行照旧是「快检 N 源、补验正文 M 源，待深检 K 源」，K 就是这一轮没吃到的
  那一片。**没有新增任何"深度/模式"控件**。

### 2. 改完之后量到的（`.probe/tiered_deferred_cost.py`，127.0.0.1 假源，A/B 每轮交换）

旧探针每轮都新建服务外壳，队列一轮一清，量不到跨轮形状——这次两臂各留**一个常驻外壳**，
参照单价那一臂也常驻，并各占一个主站路径前缀（/T vs /R）免得上一臂的按主机缓存替下一臂省钱。

|----|-----------|----------|-----|-------------|------------|-------|------|
| 1 | 2347 ms | 2772 ms | 15.3% | 3 次 | 135 次 | 198/2 | 44 |
| 2 | 2557 | 2776 | 7.9% | 48 | 135 | 184/16 | 30 |
| 3 | 2457 | 2850 | 13.8% | 48 | 135 | 184/16 | 30 |
| 4 | 2534 | 2901 | 12.7% | 45 | 135 | 184/16 | 30 |

### 3. 分档把队列的饥饿问题暴露出来了（本轮真正的 bug）

限额切片最初按 `(attempts, ts, 列表序)` 排，而 `add()` 每轮都刷新 `ts`（浅遍每轮都会把
同一批源重新排进来）——于是"欠得久的先"永远读不到真实欠款时长，切片实际按源列表序取前
N 条：**排在后面的那批源每一轮都轮不上，队列成了只进不出的账**。护栏
`test_the_slice_rotates_instead_of_eating_the_same_head` 第一版就是这个形状红的。
修法是入队时另记一个不被刷新的 `queued_at`（原因变了才重置，因为那是新信息），切片按
`(attempts, queued_at, 列表序)` 排。写这条测试时踩到第二个坑：本机 `time.monotonic()`
只有毫秒粒度，同一轮里两次 `check_all()` 落在同一 tick，排序读不出差别——
`DeepQueue` 因此收 `clock` 形参，测试注入假钟（`_Clock`）推进一分钟。

还有一条不对称是本轮定的：浅遍给出明确否定（`unusable`/`blocked`）时**注销**上一轮欠下的
判据③那条债（深遍对已否证过的源只是重付一遍路），但**不注销**静态判据①②那条债——
那两条之所以在开跑前就记账，正因为这类源的浅遍结论本身不可信（搜索主机是模板/JS 算的）。
同理，浅遍的判据③也不许把台账里的原因从 `cross_host` 改写成 `list_usable`（改写会把
它的排队时间一并挪到队尾，公平序跟着失真）。

## 1. 为什么先量"桥调用密度"

004 待修清单 7 说的"把求值也搬进子进程要先解决桥回调跨进程"，卡点从来不是"能不能起
子进程"（第六十三轮的审计进程池已经起过），而是**QuickJS 那一侧的 109 个 `add_callable`
要在子里活着，就得把整条 Python 实现搬过去或做成 RPC**。所以能省多少事的唯一悬念是：
一条阅读脚本实际打到的桥里，有多少**根本不需要父进程**。没量过之前，"阅读多进程"这四个
字既能解释成"再写一套 RPC"也能解释成"只搬一半"，谈不动。

## 2. 静态普查：桥分档 + "这条脚本要不要父进程"

`.probe/reading_bridge_census.py`（四段 A/B/C/D，A/B 是仪器自证）：

* **(A) 桥名录**：AST 从 `legado_js.py` 扫出 **109** 个 `add_callable`，按实现落在哪儿分五档

  DOM 句柄 **17**、再入求值 **6**、网络/UI **12**。
* **(B) 门面表**：不猜——把引擎真正交给 QuickJS 的那 **4 段程序（合计 165 068 字符）**
  用一根临时 `quickjs.Context` 替身受下来（`quickjs` 是在 `_evaluate_locked` 里就地 import
  的，所以要打的是**真模块**），再从里面解出"`java.某个名字` / 某个裸函数 → 会打到哪些桥"。
  124 个门面可见名 + 100 个顶层名里，286 个会打到桥、208 个解出来确实不碰桥。
  自证用门面里**写死**的期望（`md5Encode`/`post`/`getString` 那一族）对表，通过才继续。
* **(C) 真库语料**：917 条源、阅读三段（详情页/目录/正文）里会进 QuickJS 的脚本 **769 段**

  **408/769 = 53.1% 一次父进程回调用不到**。换一种闭包策略（词法作用域 → 过度归因）重算，
  还是 408/769 = 53.1%，结论不跟着仪器换。剩下 361 段里 62.3% 只需父进程回一趟。

静态只能用来决定"要不要搬"，证不了"搬得过去"，所以还有第二步。

## 3. 动态沙箱实测：把那 408 段真放进子里那种 Context 跑一遍

`.probe/reading_sandbox_feasibility.py`：真 quickjs + 真 `LegadoJsRuntime` + 真门面程序，
**只把 71 个非纯桥换成桩**（桩记一笔再返回形状相近的无害值），38 个纯计算桥照挂。
每条脚本最多喂三种输入（HTML / JSON / 纯 URL）取最好的一次。**全程零联网**：非纯桥一律
被桩截住，压根走不到 HTTP。

```
候选 408 段 → 逐条过子进程取回 407 段，进程级出事 1 段；求值累计 14.6 s
  零回调且跑通        253   62.0%
  零回调但没跑通      112   27.5%
  打到回调             42   10.3%
  打穿进程              1    0.2%
```

读数怎么理解：

* **动态确认零回调的 365 段 = 全库阅读三段 769 段的 47.5%**（"没跑通"那 112 段也算零回调：
  它们报错的原因是喂的假 HTML/JSON 内容不对——112 段里只有 8 段是"缺桥"那类报错）。
* **静态判乐观了 42/408 = 10.3%**：这些段静态说"不碰桥"，动态真打到了。写法集中在
  `__dom_parse/__dom_query/__dom_op`（DOM 句柄上的方法调用——句柄是运行时值，门面表按名字
  解不到）和 `__get/__put/__java_get/__cookie_get` 那一族。
  **这一条直接决定了门控的形状：静态判据不能单独当闸门。**
* **引擎自己的引导调用：取回的 407 段里有 406 段的基线都打了 `__get_json('infoMap')`**，
  与规则内容无关（no-op 规则也打）。所以"子里零 RPC"这个说法要改成"每趟固定一次，
  除非把 infoMap 随任务下发"。
* **49/408 段是静态看不见的那一类**：`eval(String(source.bookSourceComment))` 这种
  参数不是字面量的 eval / `new Function`，真代码运行时才拼出来（字面量的 eval 不算——那串
  代码就在正文里，静态看得见）。这一类里动态打到回调 6 段、没跑通 26 段，
  **打穿进程的那 1 段也在里面**。门控必须把它们排除在外，不是"优化"，是因为静态那一步
  对它们**没有定义**。

## 4. 两条仪器教训（都是"探针自己没测到"被当成"被测对象没问题"）

* **记录器必须是进程级的**。`runtime.evaluate` 把活派给引擎那条 `legado-quickjs` 线程，
  桩是在**那条线程**上被调的；第一版把 sink 写成 `threading.local()`，父线程清的是自己
  那一份、子里记的是另一份，于是"零回调 408 段"是一份**读数器压根没接上**的假读数。
  抓出它的就是这次新加的两根对照：一根明知要打到（`__ajax`）、一根明知不该打到
  （纯计算的 `__md5`）。第一根当场报"期望 打到回调，实得 零回调且跑通"。
  以后凡是"计数为 0"的读数，先问那句"明知不是 0 的那根跑了没有"。
* **按 eval 文本分段切不出"引擎的"和"规则的"**。实测一次求值是四段：80 字符的 stringify
  把手、**174 264 字符的"门面 + 这条规则"拼成的一段**、53 字符的 gInt 取值、57 字符的
  收尾 stringify。规则和门面程序在同一段里，所以 `len > 100_000` 那种"这段是门面"的猜法
  把引导调用全记到了规则头上（就是上面那 40/40 的来路）。切不开就**减**：同一条源、同一个
  输入先跑一根 no-op 规则量基线，规则打到的那一档按**次数**相减。

## 5. 顺带量出来的一条现存缺陷（不是沙箱造成的）

## 6. 边界与下一轮的形状（要开发者点头的那件事）

量完之后，"阅读多进程"不再是"要不要写 RPC"，而是这条切线：

  所以它**不会让"点开一章"变快**（那一章要的桥一个都省不掉）；省的是检测轮/换源扫描
  这些**CPU 串行**的批量求值不再全挤在 `_QUICKJS_LOCK` 上，以及阅读页不再排在全库扫描
  后面。这两个好处是不是今天要的东西，得开发者判。
* **工作量**：子里侧的 Context 装配、任务载荷的序列化（`JsContext` 里 `book`/`chapter`/
  `variables` 那几个对象）、墓碑与 `touched` 回传、退回主进程那条重跑路径、

## 1. 下拉在语义树里是一只"没有字的按钮"

（这条不走"我记得 Flet 有 aria 支持"：`flet-0-86-api-surface` 的教训就是控件表面

## 2. 候选书面：预算原来是"本数"，成本却是两种

`chapter_candidates` 原来硬编"书架最近 **3** 本 × 每本 100 章"。毛病不是 3 太小，
是**这一个数同时管着两件成本不同的事**，而且超出的书是静默消失的。先量成本（零联网、
临时目录里的假书架与假目录，`.probe/candidate_book_cost.py` → `.probe/out_candidate_cost.txt`）：

| 书架本数 × 每本章数 | 现 shape（3 本封顶） | 摊派 shape（每本 = 行预算 ÷ 本数） |
| --- | --- | --- |
| 8 × 5000 | 71.6 ms / 3 本 300 行 | 171.9 ms / 8 本 304 行 |
| 16 × 5000 | 71.2 ms / 3 本 300 行 | 351.7 ms / 16 本 304 行 |
| 24 × 5000 | 69.7 ms / 3 本 300 行 | 517.8 ms / 24 本 312 行 |
| 8 × 300 | 6.1 ms / 3 本 300 行 | 17.5 ms / 8 本 304 行 |

读法：**翻目录**是本数 × 每本章数的函数（5000 章一本约 20 ms，跑在 `to_thread`，
不冻界面但候选出现得晚）；**摊候选**只是总行数的函数（整页下发约 0.024 ms/行）。
所以两个预算必须分开：`MAX_CANDIDATE_ROWS=300`（下发）+ `MAX_CANDIDATE_BOOKS=8`
（约 0.17 s 的翻目录），每本摊到 `行预算 ÷ 实际本数`——书多时是"每本露一面、各自少抽
几章"，不再是"第 4 本之后的书没了"。三处细节：

* 没缓存过的书**不占名额**（那一次读是开文件失败，亚毫秒），旧口径本来就是这样，
  新写法必须留住它，否则 10 本空书就把样本挤掉了；
* 抽样步长改成**向上取整**：`len // allowance` 会超额（80 章 / 37 → 步长 2 → 端出 40 章），
  表里 B 臂那 304/312 行就是这么超的——行预算不封顶就白写；

## 3. 写回不发事件：一句道歉字换一条事件

`update_source_rule` 在**冻结基类** `app/services/source_service.py:458` 里，只落盘不发事件；
live 壳 `app/services/sources/source_service.py` 的其它写路径（`save_source`/`delete_source`/
`set_enabled`/`set_group`）每条都发 `SourceChangedEvent`。所以补的是**壳里的覆写**：
`super()` 干完活再 `_publish(SourceChangedEvent(change_type="updated", source_id=...))`，
冻结件零改动。控制器里那句"列表页要刷新才看得到：`update_source_rule` 不发事件"的道歉字
跟着删掉，改成"列表页会自己刷新"。

语义定为 `updated`：`app/core/events.py:131` 的字段注释里 `change_type` 取值就有
`created/updated/deleted/imported`，而三个订阅方（书源列表 / 书架 / 找书）现在一律
**整体重画、不看 change_type**，所以不会误触发别的分支。

接收端也一起钉了（`test_list_controller_takes_the_write_back_event`）：挂在总线上的其实是
界面编组壳 `on_ui`（`app/controllers/base.py:_marshal`），真处理器在它的闭包里——只断
"订阅了"照不出接的是不是刷新那条路，所以断的是闭包里的处理器 == `controller._on_source_changed`。
