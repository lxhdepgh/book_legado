## 第三十六轮：`@js:` 重入会把原生栈打穿——护栏原来借的是 CPython 的递归上限（任务 #69）

### 现场

记忆 `quickjs-native-crash-risk` 记着：2026-09-21 全库差分两次都以 segfault 收场，
栈顶在 `legado_js` 的 `ctx.eval`，当时的判断是"怀疑深层递归把原生栈打穿"，
候选缓解写的是"给每个 Context 设 `set_max_stack_size`（约 1–2MB）"。

本轮先把这句话**测一遍**再动手，因为代码里已经有一段注释（`legado_js.py:653`）
声称默认栈行为是安全的。

### 一、纯 JS 递归确实安全——那条注释没说错

单个 Context、一次 `eval` 内部的递归（`.probe/qjs_stack_probe.py`，默认线程栈）：

| 递归深度 | 结果 |
| --- | --- |
| 400 | ok |
| 800 | **catchable**（QuickJS 自己抛 StackOverflow，Python 侧捕获） |

QuickJS 的栈检查管的是**一次 eval 内部**，这一段没问题。

### 二、但"重入"不在它的管辖范围里

把形状换成 JS→Python 回调→**再 eval 一层**（正是本引擎的重入路径：
`__get_string` / `__css_query` 这些回调里又会求值一条 `@js:`），同一条原生栈、
默认线程栈：

| 重入层数 | 复用同一 Context | 每层新建 Context |
| --- | --- | --- |
| 400 | ok | ok |
| 800 | **CRASH（无输出，进程没了）** | **CRASH（无输出）** |

所以决定"崩 / 不崩"的是**原生栈**，跟用哪个 Context 无关——`set_max_stack_size`
那条候选缓解打的是错的靶子。

### 三、那生产里为什么没崩？——借来的护栏

用**真实** `LegadoJsRuntime` 闭一条自调用链（`.probe/qjs_real_child.py`），
在当前生产配置下：**~165 层**抛 `RecursionError`，被包成 `JsBridgeError` 捕获。
165 这个数字不是任何设计，是 **CPython 默认 `recursionlimit=1000`** 在这条链的
每层 Python 帧数下折算出来的。把它拆掉试（`.probe/qjs_real_parent.py`）：

| recursionlimit | 线程栈 | 退出码 | 判定 |
| --- | --- | --- | --- |
| 1000（生产） | 默认 | 21 | caught |
| 100000 | 默认 | **3221225725** | **STATUS_STACK_OVERFLOW，进程没了** |
| 100000 | 16MB | **3221225725** | **同上，加大栈救不回来** |

两条结论：
1. 生产现在安全，是**借** CPython 的递归上限拦的；谁把递归上限抬高（深层 HTML
   树是最常见的理由），崩溃就还回来。
2. **加大线程栈不是解法**：16MB 一样打穿（本轮只测到"无效"，没有验原因）。

### 四、落地：把边界自己画

`_evaluate_serialized`（所有求值的唯一入口，内联重入 :546 与派发线程 :574 都走它）
加层数上限 `JS_REENTRY_LIMIT = 16`：超了直接抛 `JsBridgeError`，不再建新 Context、
不再进原生栈。取值不是拍的——先量了合法重入到底有多深：用 pytest 插件挂上计数器
（`.probe/depth_plugin.py`）跑引擎/规则/阅读/搜索/找书那一面，**616 次求值里
1 层 613 次、2 层 3 次，最深只有 2 层**。16 层是合法用量的 8 倍，又远低于借来的
那道 165 墙。

第二个坑：这条 `raise` 从 QuickJS 的 C 边界穿出去会被压成通用的
`InternalError: Python call failed`，原因就丢了——和 `_bridge_call` 处理回调异常
是同一件事，所以先写进 `_thread_state.bridge_error`，由外层拼回。改完实测报文的
确带上了 `Bridge: JsBridgeError: JS 规则重入超过 16 层（…）`。

顺带核了两处绕开运行时、直接 `quickjs.Context()` 的地方
（`compat_audit.py:453`、`sources/compat_audit_service.py:140`）：它们只做
"把脚本包成函数体 eval 一遍看能不能编译"，**一个 `add_callable` 都没有**，
桥不回 Python 就闭不成环，不用改。

### 二、落地

三处 `with self._db_lock: self._conn.executemany(...)` 改成
`with self.transaction() as db: db.executemany(...)`。`_db_lock` 是 `RLock`，
`migrate()` 整段持着它，`transaction()` 再进一次同线程无障碍。
`_migrate_appearance` 不动——它最多写一行，包事务只是白加一层。

### 三、语义上变了什么（要说清）

改前一条坏行会让**前 k 行已经落盘、后面没有**，而异常照旧冲出 `migrate()`；
改后整表回滚，旧介质原名保留（`.legacy-bak` 不生成、幂等标记不写），
修好后重跑能从头导。**跨表的"部分失败也继续"不变**（每张表各自一条事务，
互不影响），表内由"逐行半截"变成"全有或全无"。

本轮**没有**动的两件事，写在这里免得下轮误以为已修：

- 写失败仍然冲出 `on_start()` → 启动中断。`migrate()` docstring 里"导入任一介质
  异常都只记录、不阻断启动"这句只对**读**错误成立（`report["missing"]` 那条路）。
- 主库没开 WAL、`synchronous` 仍是默认 FULL（09-28 遗留 10）。等备份路径核完再定。

## 第三十八轮：后台限速那条睡写在**出队之后**——它没让前台少等，只让前台多等（任务 #71）

> 第一批优化的第 1 条。全程离线：`@js:` 纯本地求值 + 127.0.0.1 假源，没有碰任何真实站点。

### 一、这条限速当初为什么加，以及它实际拦住了什么

M1-2.10 那次（`docs/M1网络栈修复记录.md` §2.10）为了治"32 源扫描把**阅读页自己的**
规则堵到等了 33s"，在 `_QuickJsDispatcher` 上加了三样东西：排队超时、执行超时看门狗，
外加 `BACKGROUND_MIN_INTERVAL = 0.05`——"后台批量任务最小间隔，避免饿死前台阅读链路"。

前两条是对的。第三条的位置错了：它写在 `_serve()` **取出任务之后、执行之前**。
所以它实际做的事是——worker 线程把一个后台任务从队列里取走、睡 50ms、再执行。
睡的那 50ms 里，前台任务正躺在**同一个队列**里等这条线程醒来。

- 前台并没有被保护：它照样要等，只是多等一个间隔（原本还要等当前那次求值）。
- "饿死前台"这件事本来就是 `PriorityQueue` 的排序在管：前台优先级 0，只要它在队列里，
  出队的下一个必然是它。真正拦不住的只有**已经在跑的那一次**——QuickJS 无法硬中断，
  那是看门狗的职责。
- 代价却是把唯一的串行资源白白闲置：每次求值单价 9ms，间隔 50ms，吞吐被压到 1/6.6。

### 二、当场实测的对照（改后 → 把 HEAD 版本临时放回文件再测 → 换回并校验 md5）

调度器面（`.probe/qjs_fairness_probe.py`：40 次 10ms 后台风暴，中途插一条前台求值）：

| 指标 | 改前（有 50ms 间隔） | 改后 |
|---|---|---|
| 前台插队等待 | **58 ms** | **6 ms** |
| 40 次后台求值合计 | 2727 ms（68.2 ms/次） | 760 ms（**19.0 ms/次**） |
| 后台求值单价（`.probe/bench_check_attr.py` 微基准，20 次 `@js: 1+1`） | 58.8 ms/次 | **9.0 ms/次**（前台 9.1 ms/次） |

前台和吞吐**一起**变好——这正是"那条睡什么都没保护"的证据。若是真正的公平代价，
删掉它前台必须变差。

检测面（`.probe/bench_check_attr.py`，一条本地假源跑真 `check_sources`，目录 120 章）：

| 段 | 改前 | 改后 |
|---|---|---|
| 单源检测墙钟 | 471 ms | **317 ms** |
| ├ 搜索段 `_engine_search_check` | 84.0 ms | 32.0 ms |
| └ 阅读链路 `_reading_chain_check` | 350.8 ms | 249.9 ms |
| JS 求值 6 次：QuickJS 线程内 | 59 ms | 58 ms |
| JS 求值 6 次：**调用侧合计等待** | 215 ms | **59 ms** |

末两行是本轮最该记住的一对：求值本身一点没变便宜（59 vs 58 ms），
**变化全在"调用方为它多等了 156 ms"**——那 156 ms 里线程在睡、在排队，
而调用它的是那条唯一的服务协程循环。改后两者相等，说明排队开销没了。

事件循环慢回调（>50ms 被同步占住）：两轮都是 0 次——这条假源的 JS 太短，
还够不到 50ms 阈值。多源并发下的"park 引擎循环"是任务 #72 的主体。

## 第三十九轮：取值段把引擎循环钉在 QuickJS 上——先证明 GIL 真的还着，再把整段搬走（任务 #72）

任务单上这条写的是"检测路径改用 `evaluate_async`"。开工后前提就错了：**该 await 的
早就 await 了**。一条源的求值里绝大多数走 `evaluate_async`（不占线程），剩下的不是
"忘了 await"，而是**同步的取值函数**——`_strict_value` / `_field_value` /
`_books_from_nodes` 整条链都是同步的，中间某一层调 `js.evaluate()` 就是
"派给 legado-quickjs 线程 + 原地 `.result()` 等"。你没法把它改成 await：同步函数不能
await。所以本轮真正落地的是另一件事：**把含 JS 的整段取值挪出事件循环线程**。

### 一、动手前先量一件事：跳线程到底有没有意义

把同步等待挪去工作线程，只有在**等的时候循环能干活**的前提下才成立。QuickJS 跑原生
`eval` 期间会不会攥着 GIL 不放？攥着的话挪了也白挪。`.probe/gil_park_probe.py` 四个
形状对照（同一条纯 JS 忙等 200ms 的求值，5ms 心跳测循环被顶开多大间隙）：

| 形状 | 求值耗时 | 心跳最大间隙 | 心跳次数 |
|---|---|---|---|
| B 循环线程上同步 `evaluate` | 209 ms | **204.1 ms** | 7 |
| A `await evaluate_async` | 208 ms | 11.1 ms | 20 |
| D 另起一条线程同步 `evaluate` | 218 ms | 11.1 ms | 20 |
| C 标定：只 `await asyncio.sleep` | 186 ms | 11.0 ms | 18 |

D 是决定性的一行：**同样是同步等待，换一条线程等，循环就完全不受影响**（11.1ms 就是
心跳本身+调度噪声，与标定行 C 同量级）。结论——QuickJS 的原生 eval 期间不攥 GIL，
那 200ms 循环本来就能拿去干活。B/A 的差(193ms)全是被白白钉掉的。

### 二、这笔钉掉的时间在检测里有多大

`.probe/sweep_loop_park.py`：8 条本地假源并发一轮真 `check_sources`，三种源形状各测
多轮取中位。"循环被钉"= 该轮里事件线程被同步 JS 等待占住的总时长。

| 源形状 | 墙钟 前→后 | 循环被钉 前→后 | 心跳最大间隙 前→后 |
|---|---|---|---|
| `@js:` 正文规则（真实形状，只求值不忙等） | 484 → 494 ms | **123 → 0 ms** | **12 → 5 ms** |
| 纯选择器（无 `@js:`，闸门不跳） | 414 → 413 ms | 0 → 0 ms | 4 → 4 ms |

### 三、落地：`_parse_off_loop(gate, parse, *args)`

## 第四十轮：一轮检测共享连接池——量完决定**不做**（任务 #73，实测否决）

任务单上这条写的是"一轮检测共享引擎与连接池，停止每源 new"。量完之后两半都不成立，
所以本轮的产出不是改动，是一条**写在改动点上**的否决记录
（`app/services/check_service.py:415` 上方注释）。同类的先例是任务 #62（JS 共享 scope）。

### 一、为什么第一版探针给的结论是反的

`.probe/engine_reuse_attr.py` 第一版把所有假源都指向 `127.0.0.1:同一个端口`，跑出来
"共享池把 8 条源的拨号从 11 次压到 4 次"。**这是探针自造的假象**：真实书源池里不同源
是不同域名，握手根本没法跨源复用；环回同主机反而造出一个现实中不存在的复用面，还顺带
把 8 条源挤到共享池的 `limit_per_host=5` 上排队（同一条池里**不同主机**的拨号各自加锁，
不会互相挡；同主机才会）。

修法：服务绑 `0.0.0.0`，**每条源用各自的 `127.0.0.N` 环回别名**——拓扑就 and 真实池一致。
另外第二个坑也顺手记下来：预热用的 `ClientSession(connector=共享池)` 默认
`connector_owner=True`，`close()` 会把共享池一起关掉，引擎看到 `closed` 就各自建池，
于是 B 形状量出来永远等于 A。（反空转断言就是为此加的。）

### 二、拓扑摆对之后的对照

三种拓扑 × "每条新拨的 socket 加 0ms / 60ms"（60ms 是把一个 RTT+TLS 折进墙钟的**仿真**，
不是真实互联网测量）。A=现状（每源一条池），B=一轮共享一条池：

| 拓扑（并发 8） | 新连接代价 | A 墙钟 / 拨号 | B 墙钟 / 拨号 |
|---|---|---|---|
| 8 源，每源一台主机 | 0 ms | 433 ms / **16** | 440 ms / **16** |
| 16 源，每源一台主机 | 0 ms | 1475 ms / **32** | 1470 ms / **32** |
| 8 源，每源一台主机 | 60 ms | 823 ms / 16 | 802 ms / 16 |
| 16 源，每源一台主机 | 60 ms | 1539 ms / 32 | 1472 ms / 32 |
| **8 源挤 2 台主机**（同域名多源） | 0 ms | **700 ms / 14** | **746 ms / 8** |
| **8 源挤 2 台主机** | 60 ms | 776 ms / 14 | 792 ms / 12 |

每行都跑了 3 遍取中位，请求数 40 次/8 源、80 次/16 源（拨号能不能复用要对着请求数看）。

读法：
- **真实形状下共享池一次握手都省不下来**——16 次对 16 次、32 对 32，完全相同。前提
  被推翻了：复用要"同主机的连接放回池里时正好别人要连它"，而检测里不同源是不同主机，
  同一条源的首页探测又是**和搜索段并发**发起的（两条池都还没热，各自拨自己的）。
- 同主机的墙钟差（823→802、1539→1472）没有拨号差可以解释，就是噪声，不作为收益。
- **唯一真省下握手的形状反而更慢**：8 源挤 2 台主机时 14 次降到 8 次，墙钟却从
  700ms 顶到 746ms。原因是共享之后 `limit_per_host` 变成**跨源**排队——同一域名上
  4 条源的连接要挤 5 个坑，而各自建池时每条源都有 5 个坑。镜像站/同域名多源恰恰是
  真实书源池里最常见的形状，这条负面是常态化命中的。
- 60ms 那一档同一个形状从 14 次"省"到只剩 12 次：拨号在池里占着 creating 的时间越长，
  越多源等不及自己另拨——**省下来的握手数本身就不稳**。

### 三、"停止每源 new 引擎"这一半

引擎构造/关闭实测：8 源一轮合计构造 4.7 ms、关闭 4.3 ms（16 源 18.4/19.3 ms），
占 433 ms 墙钟的 ~2%。而引擎携带的正是要按源留住的东西——`js_variables`、该源的
cookie 罐、`java.put` 的书/章变量袋（`check_categories` 的注释为此写明"分类页在源内
串行"）。跨源共享一个引擎就得把这些上锁串行，代价远大于那 2%，还会把上一轮 #72 的
`_rule_lock` 从"一条引擎内"扩大成"所有源之间"。

### 四、结论与遗留

- 不做。检查点已写进 `check_service.py:415` 上方，含全部数字与探针路径。
- 探针留在 `.probe/engine_reuse_attr.py`，改检测池相关代码时可直接复跑；它自带的
  反空转行（"注入未生效：引擎仍在各自建池"）是这类 A/B 探针必须的——不然永远量出 A。
- **本轮暴露一条与 #73 无关的事实**：首页探测与搜索段并发发起，所以同一条源也拨了
  2 次握手（16 次 / 8 源）。这是设计使然（探测要独立、不带 cookie），但意味着
  "同一条源内的连接复用"从来没生效过。要不要让探测走引擎的池，需要先想清楚它为什么
  必须独立——登记为遗留，本轮不动。

## 第四十一轮：审计"绕过全局 QuickJS 锁"——那条锁的注释把机制说反了（任务 #74）

待办里这条写的是"把 `compat_audit` / `compat_audit_service` 里裸建的
`quickjs.Context()` 收进 dispatcher 或锁"。收之前先去看被绕过的到底是哪条不变量，
结果发现**注释写错了机制**，于是本轮的产出是"不收 + 把注释换成实测过的 + 给真不变量
补护栏"。

### 一、被绕过的"不变量"是从哪来的

`app/services/engine/legado_js.py` 里 `_QUICKJS_LOCK`（现 :228）上方原本写着：
*"The Windows quickjs extension can access-violate when independent Context objects
are created/evaluated concurrently in different threads."* 全库 grep 只有两处真正绕过
它：`app/services/compat_audit.py:455` 和
`app/services/sources/compat_audit_service.py:145`（两处本轮各加了几行说明注释）。
三件事当场就不对劲：

- 本轮之前 `tests/` 里 grep `_QUICKJS_LOCK` **零命中**——这条从未被钉过的不变量；
- 引入这条注释的提交（重构 `6352f2e`）在开发日志里找不到任何配套实测；
- `compat_audit.audit_source_corpus` **今天没有任何调用方**（app/、tests/ 全库 grep，
  只剩 `old_code/` 里的旧副本）——两处绕过点里有一处根本跑不到。

### 二、四步取证：崩溃按 runtime 算，不按"新建"算

全部离线子进程，python-quickjs 1.19.4 / CPython 3.12.13。

1. **前提查**（`.probe/qjs_gil_held.py`）：`Context.eval` 期间放不放 GIL？放——
   198 ms 的纯 JS 求值期间，旁路 Python 心跳（1ms 节拍）最大间隔 **2.0 ms**。
   所以"两条线程同时待在原生码里"这个前提是真的成立，注释不是想当然。
2. **形状查**（`.probe/qjs_concurrent_context.py`）：审计的生产形状——1 条唯一
   QuickJS 线程在求值真规则，旁路 1 条 / 4 条 `to_thread` 工作线程各自
   `quickjs.Context().eval(...)`。`raw×1`（400+400 次）与 `raw×4`（2000+8000 次）
   各跑 3 遍，**9 遍 0 崩**。
3. **反查真凶**（`.probe/qjs_shared_context_cross_thread.py`）：那到底什么崩？
   两条线程**同时进同一个 Context** → 6/6 崩：
   `Assertion failed: !runtime_data->thread_state, file module.c, line 83`，
   rc=3221226505（0xC0000409 fast-fail，不可捕获）。对照组：每线程自带 Context，
   4×2000 轮 ×3 遍 = 24000 次，0 崩、0 脏值。
4. **补一刀**（`.probe/qjs_context_thread_handover.py`）：同一个 Context **先后**换线程
   （2000 次整体交接 / 2000 轮交替）都活着——所以护栏不能顺手把"换线程"也判死。

结论：quickjs 的线程不安全是**按 runtime** 记账的。python-quickjs 每个 Context 自带
一个 JSRuntime，独立 Context 之间没有共享原生状态，怎么并发都不互相踩；`_QUICKJS_LOCK`
真正守的是 `_shared_js_contexts` 里那批**按 jsLib 缓存复用**的 Context。审计每次新建、
用完就丢，落在安全那一侧。

### 三、"收进去"要花多少钱（`.probe/audit_js_serialize_cost.py`）

600 段真实预编译，同时一条前台线程按 2ms 节拍求值真规则，每形状 3 遍取中位：

| 形状 | 审计自己 | 前台等待（中位 / 最大） |
|---|---|---|
| raw（现状） | **108 ms**（180.6 µs/段） | 9.7 ms / **11.8 ms**（28 次采样） |
| 只加 `_QUICKJS_LOCK` | 158 ms | 18.2 ms / **34.4 ms**（24 次） |
| 收进 dispatcher | 541 ms | 8.4 ms / 9.7 ms（154 次） |
| 收进 dispatcher、按源攒批 | 570 ms | 15.9 ms / 23.1 ms（93 次） |

四种编译形状报出的语法错误条数一致（对照，证明量的是同一段活）。读法：
"只加锁"是**双输**（审计 108→158 ms，前台最大等待从 11.8 顶到 34.4 ms）；
"收进 dispatcher"把审计拖慢 **5.0×** 换来一条本就不需要的保证。raw 那一行前台最大
等待 11.8 ms 与"收进去"的 9.7 ms 同量级——不收紧也不会把阅读页挤出去。

### 四、护栏钉的是哪三件事（`tests/test_check_performance.py::QuickJsRuntimeOverlapTests`）

`_quickjs.Context` 不可子类化（实测 `TypeError: type '_quickjs.Context' is not an
acceptable base type`），所以记账层是转发代理。4 条审计线程 + 2 条引擎求值线程同时跑，
三笔账：

1. **重叠**：任一 runtime 在同一时刻被两条线程进入 → 直接红（且是在进原生码**之前**
   拦下，否则进程一起没了，红都报不出来）；
2. **交接**：runtime 被建它之外的线程用过 → 红。这条不是安全线（上面第 4 步实测先后
   交接安全），是设计线：一次交接正是"把 Context 提到模块级缓存给审计共用"那个错修法
   的第一步；
3. **反空转**：审计必须真的每次新建（`created ≥ 4×15 轮×3 段`），引擎侧必须真的复用
   了缓存 Context（`runtime 数 < 调用数`）——否则第 1、2 条测的是空气。

第一版假红了一次：runtime 的键用了 `id(real)`，而审计一次就造上百个短命 Context，
**id 在回收后被复用**，把两条无关线程拼成"同一个 runtime"。改成构造序号才干净——
这条坑记在 `_runtime_spy` 的注释里。

变异核验：把审计改成"整模块共用一条 Context"（那个错修法），两条路都被抓到——
测试侧先在第 3 笔账红（`created` 只有 2），把重叠窗口撑开（`.probe/mutate_shared_ctx.py`，
生产代码 + 2ms 占用）就是**当场撞断言崩进程**。生产文件已 `git checkout` 复原。

## 第四十二轮：audit_log 落库换写形状——修的不是"没包事务"，是**并进别人的事务**（任务 #75）

待办 #75 原文写的是"落库包进 `transaction()`"。量下来这条**改法选错了**：真正的坏事是
裸 `storage.db.execute()` 会让审计行**静悄悄丢掉**，而"每条自己包一个事务"是四种形状里
第二贵、且不解决丢行的那一格。产出=一次形状纠正 + 两条护栏 + 一条全库同型登记（#78）。

### 一、坏在哪：autocommit 连接上没有"我自己的语句"

`StorageService` 开的是 `isolation_level=None`（autocommit）+ `check_same_thread=False`
的**同一条共享连接**，写路径的原子性全靠 `_db_lock`（`execute()` 持锁、`transaction()`
**从 BEGIN IMMEDIATE 握到 COMMIT**）。`_persist` 当年写的是 `self._storage.db.execute(...)`
——**绕过那把锁**，于是：

- 别的线程正握着事务时，这条 INSERT 不报错、不等待，直接**并进那笔未提交的事务**；
  对方一 ROLLBACK，审计行跟着没了，**而调用方看到的是成功**。
- 私有 `self._lock = threading.Lock()` 给了假安全感：它只排开"另一个审计线程"，
  排不开任何握着 `_db_lock` 干整表镜像的写入方。

### 二、实测（本地临时库、离线，`.probe/audit_log_write_shape.py`，各 3 遍取中位）

1) 丢不丢行——另一条线程开着事务并回滚：

| 写形状 | 回滚后表里 | 审计写等了 |
|---|---|---|
| A 现状：裸 `db.execute` | **0 行**（丢了，且没报错） | 0 ms（根本没等） |
| B `storage.execute`（持 `_db_lock`） | 1 行 | **304 ms**（被挡在事务外面） |

2) 逐条写的代价（8 线程 × 240 条；A 那行的报错与缺行本身就是结论）：

| 形状 | 墙钟中位 | 单条最大 | µs/条 | 表里剩 |
|---|---|---|---|---|
| A 裸 `db.execute` | 503 ms | 42.8 ms | 2096.5 | **610 / 720**（丢 110 行），三遍各抛 `InterfaceError: bad parameter or other API misuse`（每遍只打第一条，真实次数是下界） |
| B `storage.execute` | 705 ms | **91.5 ms** | 2938.4 | 720 |
| C 每条包 `transaction()` | 767 ms | 123.9 ms | 3196.1 | 720 |
| D 一轮攒成一条事务 `executemany` | 4 ms | — | 16.4 | 720 |

读法：
- **C 不是答案**。它比 B 还贵（767 vs 705 ms），因为单条 INSERT 在 autocommit 下
  本来就是一次原子提交，再包一层 BEGIN/COMMIT 只多付一次 fsync；而 B 已经一行不丢。
- **D 便宜 179 倍**（2938.4→16.4 µs/条），但它要的是"一轮攒齐再写"的调用形状，
  而这里三条触发点各自独立到达（导入/编辑保存/检测流水线），本轮没有攒批的现场。
  量到的是"值不值得为它改调用形状"的答案：**还没有**，登记不展开。
- B 的 **91.5 ms / 304 ms 是等锁**，不是写本身。这一格决定了改动必须**两半一起做**：
  只换持锁写、不挪线程，就是"数据对了、界面每次卡 0.1~0.3 秒"。

| 修法 | 整轮墙钟 | 求值次数 | 结论 |

## 第四十四轮：全库裸 `storage.db` 写——修法是**堵住分配口**，不是逐点改写（任务 #78）

待办写的是"11 个模块 28 条语句"。数完之后它是 **12 个模块 54 条**（28 写 + 24 读
+ 1 DDL + 1 条动词拼在变量里），因为盘点脚本自己漏了两处（§五）。产出=一个
`LockedConnection` 收口 + 顺带挖出的两条同族 bug + 14 条护栏（7 格变异全抓到）
+ 一次**实测否决**（不把 40 条 `async def` 里的写挪出界面循环）。

### 一、病灶不是"少写了两个字母"

`StorageService` 只有一条连接：`check_same_thread=False` + `isolation_level=None`
（autocommit），`_db_lock` 是 RLock，`transaction()` 从 BEGIN IMMEDIATE 一直握到
COMMIT。绕开那把锁的语句不是"少等了一会儿"，是**换了一种失败**（本机实测，本地临时库，
坏形状一律经 `StorageService.raw` 复现，`.probe/raw_db_handle_cost.py`）：

| 坏法 | 形状 | 实测（3 遍） | 调用方看到的 |
|---|---|---|---|
| 并进别人未提交的事务 | 书签 INSERT / 设置 UPSERT / 阅读进度 UPSERT，另一线程事务开着 250 ms 后 ROLLBACK | 三种形状都 **0.0~0.1 ms 返回、回滚之后计数 0** | 成功。**数据没了** |
| 多线程互踩同一条连接 | 8 线程 × 240 条 INSERT | 表里只剩 **199~202 行**、抛 **38~41 次** `InterfaceError: bad parameter or other API misuse` | 一部分抛错、一部分静默丢 |
| 替别人提交 | 裸 `db.commit()` 落在别人半成品事务上 | 别人写到一半的批次被当成完整一笔落下去（`rule_engine` cookies 罐就是这条） | 成功。**别人没法回滚了** |

同一条锁的读侧也一起修掉了：SELECT 的**读快照在 `execute()` 里就定了**，行是之后才
materialize（20000 行 execute **0.1~0.2 ms** / fetchall **7.0~15.9 ms**），而 execute
之后再提交的行，这个游标看不见（**20000 行，不是 20001**）→ 锁只要盖住 `execute()` 就
同时挡住"脏读别人未提交的写"，代理不必把 `fetch*` 也包进锁。

### 二、修法二选一，用"使用面"来定

| 路 | 内容 | 问题 |
|---|---|---|
| (B) 逐点改写 | 54 条都改成 `storage.execute(...)` | 挡不住下一个写这类代码的人——裸句柄还在发 |
| (A) 堵住分配口 | `db` 交 `LockedConnection`（每条语句自持锁），裸连接改走 `raw` | 只有在使用面很小时才可行 |

使用面是数出来的（`.probe/attr_inventory_raw_db.py`）：**54 条语句 100 % 只碰
`.execute`**（40 条住在 `async def`、14 条住在 `def`），游标只碰
`fetchone/fetchall/rowcount/lastrowid`，全库没有 `cursor()` / `executescript()` /
`with conn:` / `row_factory`。所以代理只需要放**语句**面：
`execute / executemany / transaction / in_transaction`，其余一律 `AttributeError`
并在报错里指路 `StorageService.raw`（"宁可让新用法在这里撞墙，也不要它绕过锁"）。
(A) 成立，落 (A)。

### 三、代价量过，两条附赠的"顺手优化"都不成立

原以为既然要收口，就该顺带把住在界面循环里的那些写挪去线程池。量完**否决**：

| 要量的 | 实测 | 结论 |
|---|---|---|
| 无争用时锁本身值多少钱 | 同一条 INSERT 裸写 **3190.4~3293.3 µs/条**、走锁 **3039.5~3185.9 µs/条**，三遍差值 **−4.5~−232.9 µs** | **量不出成本**——差值小于 run-to-run 方差，走锁那侧一次都没慢过；分母是逐条 fsync 的 3.2 ms 本身 |

+ `test_handle_identity_is_stable` 钉住（句柄不许退化成每次现造包装——那会把省掉的

### 四、顺带挖出的两条同族 bug

1. **`SearchBookStore._batch`**（09-28 第三十五轮 #68 加的批量落库）在自己的私有锁外面
   对着共享连接 `BEGIN IMMEDIATE`：注入主库时它拿到的是裸连接，于是整批种子骑在

本轮只动一条链：`ReaderEngine._resolved_source_headers`（书源声明头怎么变成请求头）。
改前它在请求路径上每次都要过一次 QuickJS；落地后静态声明的源一次都不过，动态声明照旧。
`app/services/engine/rule_engine.py` **58 行新增 / 11 行删除**——删的那 11 行是零调用方的
死拷贝 `_source_headers`（§四），**求值分支一字未动**，所以"把新分支短路掉"就是精确的
改前行为，这也是下面 A/B 的口径。全部数字来自本轮实测
（127.0.0.1 假源，`.probe/header_map_fastpath.py`；语料口径 `.probe/header_shape_census.py`）。

### 一、凭什么它算大头：不是"贵"，是"每请求一次 × dispatcher 串行"

调用点是三个，全在请求路径上：`rule_engine.py:1292`（每个 HTTP 请求发出前，重试循环里）、
`reading_engine.py:1743`（音视频块补源头）、`reading_engine.py:1753`（受保护图片取字节）。
单源一轮检测（1 搜索 + 1 详情 + 1 目录 + 12 章正文里的 1 章）实测 **5 次**求值、
dispatcher 串行占 **44.0–48.7 ms**（两遍探针里的最小/最大值；无 header 那条源
5 次 / 44.0–45.0 ms）。

贵不贵要看它排在谁后面：这条求值本身只有 ~9 ms，但 dispatcher 是**单线程串行**的
（记忆 [[switch-sweep-is-cpu-serialized]]），它排在队里就把整轮墙钟顶长。16 条静态
header 源、concurrency=8 一轮，A/B 换向跑三轮取中位，整轮**复跑了一遍**：

| 臂 | 第 1 遍三轮墙钟 | 中位 | 第 2 遍三轮墙钟 | 中位 | 求值次数 |
|---|---|---|---|---|---|
| 改前（全走 QuickJS） | 762 / 752 / 773 ms | **762 ms** | 736 / 752 / 746 ms | **746 ms** | 80（getHeaderMap 80） |
| 改后（静态直算） | 455 / 464 / 452 ms | **455 ms** | 436 / 460 / 465 ms | **460 ms** | 0 |

省 307 ms / 285 ms，即 **−40.3% / −38.3%**。换向跑三轮是为了抗本机噪声，同臂三轮互差
不超过 21 ms；两遍之间的差（改前 762 vs 746）比同臂噪声还小。

### 二、为什么能在 Python 侧算完：Legado 那三步本来就是纯数据搬运

`source.getHeaderMap(true)` 在 `legado_js.py` 的 `__resolvedSourceHeaders` 里做三件事：
解析 `source.header` 成对象 → 缺 `User-Agent`（大小写不敏感）就补默认 UA → 叠上
bag 里 `source:loginHeader` 那份登录头。声明里没有脚本时，这三步没有一行是计算，
所以 `_static_header_map`（`rule_engine.py:1148`）照搬形状重写一遍，`_resolved_source_headers`
拿到非 None 就直接返回。

三种情形坚决回落（返回 None 走求值），每条都是"语义不猜"：

1. **动态声明**：`@js:` / `<js>` 打头（正则允许前导空格）——本来就得求值。
2. **值里出现非字符串**：JS 的 `String(true)` 是 `"true"`，Python 的 `str(True)` 是
   `"True"`，`null` 和数字也各有边界。原型阶段就是这么猜错的（见第五节），所以落地版
   宁可回落。语料实测**含非字符串值的 header 0 条**，这条限制当前不花钱。
3. **登录头不可解析成字符串对象**（垃圾串 / 数组 / 值是数字）：同上不猜。

语料口径（`resource/` 917 条快照，直接调落地函数分类，所以报的就是生产会走的分支）：

| header 形状 | 条数 | 占比 |
|---|---|---|
| 无 header | 505 | 55.1% |
| 静态 JSON·值全为字符串 | 338 | 36.9% |
| 动态声明（`@js:`/`<js>`） | 41 | 4.5% |
| 静态但不是 JSON | 32 | 3.5% |
| JSON 但不是对象 | 1 | 0.1% |

→ **落在直算面 876 条（95.5%）/ 回落求值 41 条（4.5%）**。含非字符串值 0 条。

### 三、等价性：84 格逐形状对拍，直算格 0 不等

14 种 header 形状 × 6 种登录头 = 84 格，每格拿"落地版 `_static_header_map` 的答案"对
"把直算短路后真 QuickJS 的答案"：**不等 0 格、不该回落却回落 0 格**。这 84 格原样进了
护栏（`SHAPES` 15 形状 + 登录头叠放/回落两条），所以等价性不是一次性证据。

### 四、落了什么

- `app/services/engine/rule_engine.py`：`_DYNAMIC_HEADER`（L1146）+ `_static_header_map`
  （L1148）+ `_resolved_source_headers` 开头的两行短路（L1203）。求值分支保持原样。
- 顺带删掉同文件里的 `_source_headers`（10 行方法体，连空行算 11 删）：它是
  **5e6e1c1（2026-08-11）** 把 `_resolved_source_headers` 换成 QuickJS 求值时留在原地的
  前朝实现，`git log -S "self._source_headers("` 查得此后 app/ 与 tests/ 零调用方。
  而且它的语义和直算版**不一样**（对所有值 `str()`、不看 `@js:`、不补 UA、不叠登录头 →
  动态声明会被静默解析成空），留着就是"再写一份 headerMap"时的第二个候选答案。同一份
  知识在仓库里存过三处（死的旧实现 / QuickJS 那侧 / 新的直算），收成两处，两处各自点名。
- 顺带把调用面的一个隐患写进护栏而不是写进注释：`rule_engine.py:1296` 会对返回的字典
  `pop("proxy")`，所以直算**每次必须交出一份新字典**——缓存一下就会把一次 pop 传染给
  后面所有请求。M6 就是钉这一格。

### 五、本轮踩的两格计量学坑（都是"改后拿工作树测改前"）

1. **探针第一版的 A/B 在快路径落地之后自己失效了**：它的"现状"臂是
   `_ORIG_RESOLVED = ReaderEngine._resolved_source_headers`，落地后这个函数自己就带快路径，
   于是换向跑出来"改后比改前慢 3.9%"这种荒谬数。改成显式把 `_static_header_map` 短路成
   `lambda: None` 才是 HEAD 的行为。这正是记忆里"改前数字必须从 `git show HEAD` 重算"
   那条的第 N 次命中：**探针也要重新过一遍口径**，不能只重算文档里的数。
2. **原型 ≠ 落地版**：`fast_header_map` 对非字符串值做 `str()` 直替，与 JS 不等价
   （`"True"` vs `"true"`），它测出的"不等 2 格"其实是原型自己的 bug。删原型，对拍改打
   落地函数——顺带这 84 格才从"证明原型可行"变成"钉住生产实现"。

另外记一条：单源那一格不能拿来算比例——"静态 header 改前"两遍量到 420 / 416 ms，而同样
发 5 次求值的"无 header 改前"只有 196–223 ms，因为它是探针里的**第一格**、含引擎冷启动。
所以日志里单源只引用求值次数与 dispatcher 毫秒，墙钟一律用并发那一轮的中位。
