## 第三十六轮：`@js:` 重入会把原生栈打穿——护栏原来借的是 CPython 的递归上限（任务 #69）

### 现场

记忆 `quickjs-native-crash-risk` 记着：2026-09-21 全库差分两次都以 segfault 收场，
栈顶在 `legado_js` 的 `ctx.eval`，当时的判断是"怀疑深层递归把原生栈打穿"，
候选缓解写的是"给每个 Context 设 `set_max_stack_size`（约 1–2MB）"。

本轮先把这句话**测一遍**再动手，因为代码里已经有一段注释（`legado_js.py:653`）
声称默认栈行为是安全的。

### 一、纯 JS 递归确实安全——那条注释没说错

单个 Context、一次 `eval` 内部的递归（`.probe/qjs_stack_probe.py`，默认线程栈）：

| 递归深度 | 结果 |
| --- | --- |
| 400 | ok |
| 800 | **catchable**（QuickJS 自己抛 StackOverflow，Python 侧捕获） |

QuickJS 的栈检查管的是**一次 eval 内部**，这一段没问题。

### 二、但"重入"不在它的管辖范围里

把形状换成 JS→Python 回调→**再 eval 一层**（正是本引擎的重入路径：
`__get_string` / `__css_query` 这些回调里又会求值一条 `@js:`），同一条原生栈、
默认线程栈：

| 重入层数 | 复用同一 Context | 每层新建 Context |
| --- | --- | --- |
| 400 | ok | ok |
| 800 | **CRASH（无输出，进程没了）** | **CRASH（无输出）** |

所以决定"崩 / 不崩"的是**原生栈**，跟用哪个 Context 无关——`set_max_stack_size`
那条候选缓解打的是错的靶子。

### 三、那生产里为什么没崩？——借来的护栏

用**真实** `LegadoJsRuntime` 闭一条自调用链（`.probe/qjs_real_child.py`），
在当前生产配置下：**~165 层**抛 `RecursionError`，被包成 `JsBridgeError` 捕获。
165 这个数字不是任何设计，是 **CPython 默认 `recursionlimit=1000`** 在这条链的
每层 Python 帧数下折算出来的。把它拆掉试（`.probe/qjs_real_parent.py`）：

| recursionlimit | 线程栈 | 退出码 | 判定 |
| --- | --- | --- | --- |
| 1000（生产） | 默认 | 21 | caught |
| 100000 | 默认 | **3221225725** | **STATUS_STACK_OVERFLOW，进程没了** |
| 100000 | 16MB | **3221225725** | **同上，加大栈救不回来** |

两条结论：
1. 生产现在安全，是**借** CPython 的递归上限拦的；谁把递归上限抬高（深层 HTML
   树是最常见的理由），崩溃就还回来。
2. **加大线程栈不是解法**：16MB 一样打穿（本轮只测到"无效"，没有验原因）。

### 四、落地：把边界自己画

`_evaluate_serialized`（所有求值的唯一入口，内联重入 :546 与派发线程 :574 都走它）
加层数上限 `JS_REENTRY_LIMIT = 16`：超了直接抛 `JsBridgeError`，不再建新 Context、
不再进原生栈。取值不是拍的——先量了合法重入到底有多深：用 pytest 插件挂上计数器
（`.probe/depth_plugin.py`）跑引擎/规则/阅读/搜索/找书那一面，**616 次求值里
1 层 613 次、2 层 3 次，最深只有 2 层**。16 层是合法用量的 8 倍，又远低于借来的
那道 165 墙。

第二个坑：这条 `raise` 从 QuickJS 的 C 边界穿出去会被压成通用的
`InternalError: Python call failed`，原因就丢了——和 `_bridge_call` 处理回调异常
是同一件事，所以先写进 `_thread_state.bridge_error`，由外层拼回。改完实测报文的
确带上了 `Bridge: JsBridgeError: JS 规则重入超过 16 层（…）`。

顺带核了两处绕开运行时、直接 `quickjs.Context()` 的地方
（`compat_audit.py:453`、`sources/compat_audit_service.py:140`）：它们只做
"把脚本包成函数体 eval 一遍看能不能编译"，**一个 `add_callable` 都没有**，
桥不回 Python 就闭不成环，不用改。

### 基线与验收

- 新增 `JsReentryGuardTests` 三条：自调用被我们的上限截住（并钉住
  `JS_REENTRY_LIMIT < 165`，把"取值"本身变成被测项）、合法两层重入照常返回、
  拒绝一次之后运行时不被永久毒死。
- 变异核验 4/4 全红：删掉上限本身 / 上限调到 500 / 收尾不恢复 depth /
  不把原因记进 `bridge_error`。
- 全量 `1412 passed + 28 subtests`（92.19s）。
- 探针留在 `.probe/`（`qjs_stack_*`、`qjs_real_*`、`mutate_reentry.py`）。

### 诚实边界

本轮**没有**复现 2026-09-21 那两次全库 segfault——按 `legado-live-scan-av-block`
的约束不联网跑库。本轮做的是：找出一个**能稳定打死进程**的重入形状、证明当前
拦它的是借来的护栏、把护栏换成自己的。原崩溃是否同一条路径，仍待有离线样本时再核。

### 遗留

本轮新开：

- **重入计数是 per-thread 的**：上限拦的是"一条链嵌套多深"，不拦"总共 eval 多少次"。
  一条源在同一个 Context 里循环调 `__get_string` 一百次是 100 次 depth=2，合法。
  真要防的是 CPU/墙钟，那是 `EXECUTION_TIMEOUT` 那条看门狗的职责，它已经在了。
- 上一轮（2026-09-28 遗留）的 9（`StorageService.migrate()` 同型逐行提交）、
  10（主库没开 WAL）本轮未动。

## 第三十七轮：首启 12.2 秒的旧介质导入——同一种逐行提交又捡到一处

### 一、起因与定位

2026-09-28 遗留第 9 条：`SearchBookStore.insert` 修掉之后，同型的"autocommit 连接上
逐行提交"还剩 `StorageService.migrate()` 的三个 `_migrate_*`。主库连接是
`isolation_level=None`（`storage.py:106-107`），裸 `executemany` 就是**每行一个事务、
每行一次 fsync**。老用户首次升级到本版本时，这段是启动里最大的一块。

本机测量（`.probe/bench_migrate.py`，合成旧介质到临时目录，零联网）：

| 段 | 行数 | 改前 | 改后 |
|---|---|---|---|
| `book_sources` | 800 | 2620.5 ms（3.28 ms/行） | 17.1 ms（0.02 ms/行） |
| `bookshelf` | 500 | 1934.1 ms（3.87 ms/行） | 8.9 ms（0.02 ms/行） |
| `search_books` | 2000 | 7693.1 ms（3.85 ms/行） | 18.9 ms（0.01 ms/行） |
| **三段合计** | 3300 | **12247.7 ms** | **44.9 ms** |
| `StorageService.on_start` 墙钟 | — | 12360.7 ms | 152.6 ms |

改后复跑一次是 150.1 ms / 合计 45.8 ms（与上表同一数量级，取第一次跑的数字）。

### 二、落地

三处 `with self._db_lock: self._conn.executemany(...)` 改成
`with self.transaction() as db: db.executemany(...)`。`_db_lock` 是 `RLock`，
`migrate()` 整段持着它，`transaction()` 再进一次同线程无障碍。
`_migrate_appearance` 不动——它最多写一行，包事务只是白加一层。

### 三、语义上变了什么（要说清）

改前一条坏行会让**前 k 行已经落盘、后面没有**，而异常照旧冲出 `migrate()`；
改后整表回滚，旧介质原名保留（`.legacy-bak` 不生成、幂等标记不写），
修好后重跑能从头导。**跨表的"部分失败也继续"不变**（每张表各自一条事务，
互不影响），表内由"逐行半截"变成"全有或全无"。

本轮**没有**动的两件事，写在这里免得下轮误以为已修：

- 写失败仍然冲出 `on_start()` → 启动中断。`migrate()` docstring 里"导入任一介质
  异常都只记录、不阻断启动"这句只对**读**错误成立（`report["missing"]` 那条路）。
- 主库没开 WAL、`synchronous` 仍是默认 FULL（09-28 遗留 10）。等备份路径核完再定。

### 四、基线与验收

写测试前先量了一件事实（`.probe/trace_executemany.py`）：`set_trace_callback` 在
`executemany` 下**逐行触发**——50 行给出 50 次 `INSERT`，而 `BEGIN`/`COMMIT` 各 1 次。
所以护栏钉 BEGIN/COMMIT 次数，不钉时间（计时在别的机器上不可复现）。

- 新增两条（`tests/test_storage_migration.py` §9）：
  - `test_migrate_writes_one_transaction_per_legacy_table`：三类批量介质 →
    `BEGIN`/`COMMIT` 各 3、`ROLLBACK` 0，同时钉住 122 次 INSERT（120 数据行
    + appearance + 幂等标记）与三表各 40 行，防"什么都没写所以没有事务"这种空绿。
  - `test_migrate_batch_failure_rolls_back_the_whole_table`：触发器在批次中间拦一行
    → 表内 0 行、`in_transaction is False`、旧文件未被改名、幂等标记未写。
  - 夹具 `fresh_storage` 用"空 data 启动 → 铺批量介质 → 撤 `m6.legacy_migrated`"
    复现首次启动现场。
- 变异核验 4/4 全红（`.probe/mutate_migrate_batch.py`），每条都有独立断言接住：
  M1 book_sources 退回裸 `executemany` → `assert 2 == 3`；M2 三处全退 → `assert 0 == 3`；
  M3 `transaction()` 失败不回滚 → "坏行之前的源留下了" `assert 1 == 0`；
  M4 写库前先改名 → 旧文件 `exists()` 为假。
- 全量 `1414 passed + 28 subtests`（101.70s）。

### 五、同型扫描的收获

本轮借这次归因把检测链路的第三例翻了出来（`CompatAuditService._persist` 的
`audit_log` INSERT 也在 autocommit 上、且由排在引擎循环上的协程直接调用），

## 第三十八轮：后台限速那条睡写在**出队之后**——它没让前台少等，只让前台多等（任务 #71）

> 第一批优化的第 1 条。全程离线：`@js:` 纯本地求值 + 127.0.0.1 假源，没有碰任何真实站点。

### 一、这条限速当初为什么加，以及它实际拦住了什么

M1-2.10 那次（`docs/M1网络栈修复记录.md` §2.10）为了治"32 源扫描把**阅读页自己的**
规则堵到等了 33s"，在 `_QuickJsDispatcher` 上加了三样东西：排队超时、执行超时看门狗，
外加 `BACKGROUND_MIN_INTERVAL = 0.05`——"后台批量任务最小间隔，避免饿死前台阅读链路"。

前两条是对的。第三条的位置错了：它写在 `_serve()` **取出任务之后、执行之前**。
所以它实际做的事是——worker 线程把一个后台任务从队列里取走、睡 50ms、再执行。
睡的那 50ms 里，前台任务正躺在**同一个队列**里等这条线程醒来。

- 前台并没有被保护：它照样要等，只是多等一个间隔（原本还要等当前那次求值）。
- "饿死前台"这件事本来就是 `PriorityQueue` 的排序在管：前台优先级 0，只要它在队列里，
  出队的下一个必然是它。真正拦不住的只有**已经在跑的那一次**——QuickJS 无法硬中断，
  那是看门狗的职责。
- 代价却是把唯一的串行资源白白闲置：每次求值单价 9ms，间隔 50ms，吞吐被压到 1/6.6。

### 二、当场实测的对照（改后 → 把 HEAD 版本临时放回文件再测 → 换回并校验 md5）

调度器面（`.probe/qjs_fairness_probe.py`：40 次 10ms 后台风暴，中途插一条前台求值）：

| 指标 | 改前（有 50ms 间隔） | 改后 |
|---|---|---|
| 前台插队等待 | **58 ms** | **6 ms** |
| 40 次后台求值合计 | 2727 ms（68.2 ms/次） | 760 ms（**19.0 ms/次**） |
| 后台求值单价（`.probe/bench_check_attr.py` 微基准，20 次 `@js: 1+1`） | 58.8 ms/次 | **9.0 ms/次**（前台 9.1 ms/次） |

前台和吞吐**一起**变好——这正是"那条睡什么都没保护"的证据。若是真正的公平代价，
删掉它前台必须变差。

检测面（`.probe/bench_check_attr.py`，一条本地假源跑真 `check_sources`，目录 120 章）：

| 段 | 改前 | 改后 |
|---|---|---|
| 单源检测墙钟 | 471 ms | **317 ms** |
| ├ 搜索段 `_engine_search_check` | 84.0 ms | 32.0 ms |
| └ 阅读链路 `_reading_chain_check` | 350.8 ms | 249.9 ms |
| JS 求值 6 次：QuickJS 线程内 | 59 ms | 58 ms |
| JS 求值 6 次：**调用侧合计等待** | 215 ms | **59 ms** |

末两行是本轮最该记住的一对：求值本身一点没变便宜（59 vs 58 ms），
**变化全在"调用方为它多等了 156 ms"**——那 156 ms 里线程在睡、在排队，
而调用它的是那条唯一的服务协程循环。改后两者相等，说明排队开销没了。

事件循环慢回调（>50ms 被同步占住）：两轮都是 0 次——这条假源的 JS 太短，
还够不到 50ms 阈值。多源并发下的"park 引擎循环"是任务 #72 的主体。

### 三、落地

`app/services/engine/legado_js.py`：删 `BACKGROUND_MIN_INTERVAL` 常量、
`self._last_background_start` 初始化、`_serve` 里的 sleep 块、`finally` 里那条记账，
共 8 增 11 删。类 docstring 与 §2.10 的措辞跟着改：前台优先级(0) **严格**先于后台(1)。

### 四、基线与验收

新增 `JsDispatcherFairnessTests` 两条，都钉"没发生/顺序"而不是计时（跨机不可复现）：

- `test_a_foreground_job_jumps_the_whole_background_queue`：先用一条占位任务把 worker
  钉住（轮询 `_current_future is placeholder` 用**对象身份**确认它真被取走），
  把 5 条后台 + 1 条**最后到达**的前台全压进队列再放行，断言执行顺序
  `order[0] == "前台"` 且 `order[1:] == 后台0..4`。后半句是防"什么都没跑所以前台第一"
  那种空绿，也钉住同优先级 FIFO。
- `test_background_jobs_are_not_spaced_by_an_interval_sleep`：把 `legado_js.time` 换成
  记录 `sleep` 时长的替身，跑 30 条后台任务，断言 `[s for s in calls if 0 < s <= 0.1]`
  为空（看门狗自己 0.5s 的节拍在区间外）。
- 变异核验 3/3 全红（`.probe/mutate_js_dispatch.py`）：M1 把限速整段插回去 →
  替身抓到 30 个 `0.05`；M2 入队时把优先级写死 0 → `'后台0' != '前台'`；
  M3 写死 1 → 同一条断言从反方向红（防"测试只认 0 这个数"）。
- 全量 `1416 passed + 28 subtests`（93.19s）。
- 两处旧文档口径同步：`docs/M1网络栈修复记录.md` §2.10 标注该限速已删；
  `docs/桌面与安卓实现差异.md` §2.10 里"阅读页规则排在后台批量任务之后"是**错的**
  （PriorityQueue 从来允许它插到队首），改为"能插到队首，但仍要等当前那一次后台求值
  跑完——实测 6ms"。

### 五、诚实边界

- 前台的上界从"间隔 + 一次求值"变成"一次求值"，**不是零等待**：QuickJS 硬中断不了，
  一条正在跑的后台求值必须跑完。短求值下是 6ms，长求值下就是那条源的规则本身多慢——
  治理它的仍是 `EXECUTION_TIMEOUT=30s` 看门狗，本轮没收紧。
- 本轮只动了一条睡。排队超时的丢弃阈值、执行超时阈值、`_source_uses_js` 的闸门判定，
  都留给登记好的 #72–#76。

### 遗留（本轮新开）

- **删掉限速后，"前台被长求值堵住"从被掩盖变成可见**：以前 50ms 间隔顺带把后台摊薄，
  检测风暴里前台偶尔要等一整条后台求值。若真实站点里出现某条源单次 `@js:` 跑数百 ms，
  该现象会直接显形。度量入口已有（`qjs_fairness_probe.py` 换长脚本即可），
  但本轮**没有**真实样本可测，不预判。
