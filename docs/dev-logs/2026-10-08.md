## 1. 令牌中间件先把一类错误从 500 改回 401

`secrets.compare_digest` 对**非 ASCII 字符串**直接抛 `TypeError`。令牌的来源是外部输入，
非 ASCII 就是它的合法形状之一，于是"令牌不对"这件事被写成了"服务炸了"：500 + aiohttp
的错误页，客户端按 JSON 解析就是解析异常。改成比 UTF-8 **字节**（`service.py:506-512`），
"没这个会话"永远回 401 一个 JSON。

护栏在 `tests/test_gateway_inproc.py:195` 那条里：三个 401（无令牌、非 ASCII 令牌、
`Bearer 错令牌`）之后紧跟一句 `called == []`——**没令牌的请求不许打到服务上**，
再放一条合法令牌的正对照（记忆 `zero-counts-need-a-positive-control`：计数为 0 的读数
要一根明知非 0 的对照，否则"仪器没接上"也会读成绿）。这条护栏在 `str` 比对那一版上
是**红**的（收到的是 500 错误页），改成字节比对才绿——所以它的价值是钉住"别退回 `str`"。

## 3. `/ws` 的帧不是按序号排的——一次 `KeyError: 'request_id'` 教的

反向调用（§4）上线后，6 条护栏同时红在 `_answer` 取 `frame["request_id"]`。
原因不是代码错，是**仪器按帧序认帧**：`/ws` 上第一条流是 `ready`，其后**可能**插一条
`snapshot` 和若干合批 `batch`——`ServiceStateChangedEvent` 就在 `COALESCED_EVENTS` 里，
服务一启动就和客户端共用这一条通道，它排在 `request` 前面是完全合法的。

改成按**类型**取帧（`_next_request`：不是 `request` 就只接受 `batch`/`snapshot`，其余当场
断言失败）。这条对 Flutter 侧同样成立，而且是协议面上的一条规矩：**客户端不能按帧序认**，
只能按 `frame["type"]` 认。

## 4. §8 R1 的机制：服务端→客户端的反向请求

方向是反的，所以它不走 `/rpc`：

- 服务端在 `/ws` 上推 `{"type":"request","name":"webview.content","request_id","payload":
  {url, source_url, options}}`；
- 客户端渲染完 `POST /rpc` 的 `engine.webContentReady`（入参 schema 七个字段，
  `additionalProperties: false`），按 `request_id` 解开那条 future。

三条"必须有人放人"的账，一条比一条隐蔽：

1. **没人连就别等**：`_ws_clients` 为空时当场抛 `WebviewUnavailable`，让引擎退回纯 HTTP
   路径，而不是挂满 20s 预算再超时（口径照 `BrowserService.available_fetcher()`）。
2. **最后一个 `/ws` 会话断了**：`_h_ws` 的 `finally` 炸掉所有在途等待。
3. **停服**：`stop_server` 也必须先炸再拆台（`service.py:244-246`，本轮补）。
   runner 一 `cleanup`，客户端的回话就进不来了，留着那条 future 只会让调用方挂到预算走完
   ——"服务已经没了"这件事被写成"渲染超时"，会指错地方。

护栏自己也要验：`.probe/webview_reverse_mutation.py` 摘掉五处防线，五条都被对应护栏看红，
摘完之后同一批测试重跑回绿（证明红是变异造成的，不是环境抖）：

| 变异 | 看见它的护栏 |

| 在途等待不放人（宿主中途断） | `...test_host_dying_mid_flight_releases_the_waiter` |
| 在途等待不放人（停服） | `...test_shutdown_releases_every_waiter` |

### 6.1 对照先跑：正文得真是 JS 造出来的

正文以 base64 递进页面、运行时解码注入，所以纯 HTTP 拿到的 HTML 里**没有**那串标记
（今天读数：原始 HTML **388** 字节，含标记 = `False`）。

这条对照第一版是红的，红得有价值：标记明文写在 `<script>` 的字符串里，服务器直接就把
标记给了——"浏览器渲染出来了"其实是假源自带正文。同一次改写还顺手修了另一个坑：注入的
HTML 里有 `class="…"` 的双引号，直接拼进 JS 字符串字面量会让整段 `<script>` 变成语法错误，
于是浏览器什么也不注入。

### 6.2 慢多少：同一条渲染，两臂交替 5 轮

| 臂 | 5 轮读数（ms） | 中位 |
| --- | --- | --- |
| A 今天进程内渲染 | 684.1, 50.1, 49.1, 50.4, 51.5 | **50.4** |
| B 渲染搬到宿主进程 | 61.9, 49.7, 49.5, 53.0, 49.7 | **49.7** |
| B 里宿主自己报的渲染耗时 | 60, 48, 48, 52, 48 | 48.0 |

**跨进程多出来 −0.7 ms（−1%）**，其中线上那一段 = 49.7 − 48.0 = **1.7 ms**
（一出一进两条 HTTP/WS 帧 + 两次 JSON 往返）。

每轮都是 A 紧跟 B：先跑那臂要背 Chromium 冷启动，A 首轮那 684.1 ms 就是这笔钱，
按顺序跑能把 −1% 虚报成几十个百分点（记忆 `ab-bench-must-interleave`）。中位不受它影响，
所以读数用中位、原始五个数一并打出来。

仪器自己也有闸：宿主报了 10 次渲染（B 臂 5 + 竖切 3 + 晚到正文 1 + JS 桥正对照 1），
与 B 臂发起次数逐一对得上；"B 比 A 快 5 倍"那一条如果触发就说明根本没跨进程——没触发。

### 6.3 通不通：三条真形状 × **两条**臂

| 形状 | A 进程内 | B 跨进程 | 判 |
| --- | --- | --- | --- |
| 11看书｜`urlOption{webView}` | ✔ 27 字 | ✔ 27 字 | 一致 |
| 霹雳书屋｜`webJs`＋webView | ✔ 27 字 | ✔ 27 字 | 一致 |
| 绿色小说｜`class.content` | ✔ 27 字 | ✔ 27 字 | 一致 |

抽出来的是 `'这段正文只有JS跑完才存在的第一段。\n\u3000\u3000第二段收尾。'`——
反向请求出去、宿主渲染回来、**正文规则继续跑完**，端到端整条链在跨进程那一臂上闭合。

这一栏本来只有 B 臂，第一次跑两条形状抛 `ContentEmptyError: chapter content is empty`。
加了 A 臂同测才发现那**不是迁移的锅**：同一条规则在进程内照样抽不出字。判词得读
"B 有没有比 A 差"，不能读"B 有没有成功"——否则会把既有行为记成"通不过就不迁移"。

### 6.4 那一格既有行为单独量：晚到的正文

同一条规则、同一个页，只把正文改成 120 ms 之后才注入：**A 拿到 = False，B 拿到 = False**。
两臂一致 = 迁移没改等待语义。真因是内置浏览器 `page.goto(..., wait_until="domcontentloaded")`
读完就回，不等 `setTimeout`（`headless_browser.py:267`；`webViewDelayTime` 只在有脚本时
的轮询里生效）。这一族和 §5 里那 24 条 `startBrowserAwait` 是同一个待办，**另案**，
不是 R1 的阻塞项。

### 6.5 JS 桥：`_bind_interaction` 那条同步 `.result()` 确实会自锁

`reading_engine.py:541-545` 给 QuickJS 装的桥是**同步阻塞**的
`run_coroutine_threadsafe(...).result()`。三条读数，两两只差一件事——调用它的是哪条线程：

| 调用形状 | 落点 | 读数 |
| --- | --- | --- |
| 真函数（`_bind_interaction` 装的 lambda） | 工作线程（今天的形状） | 56 ms 回，body 411 字，含标记 |
| 同形状，改成走 B 臂反向调用 | 工作线程（正对照） | 55 ms 回，body 411 字，含标记 |
| **同一条**调用 | **网关循环自己** | **deadlock（10.00 s 上限内没回来）** |

正对照是必须的：没有它，第三条只能读成"调用本身坏了"。有了它，结论只能是**互等**——
被冻住的那条循环，正是唯一能收下 `engine.webContentReady` 那条 POST 的循环。

入口在 `legado_js.py:799-813`：`@webjs:` 或求值线程已活动时，`evaluate_async` **原地**跑，
不换线程。今天它落在工作线程上所以不咬人；一旦无头化把 JS 求值请上网关循环（或有人
`await` 之前先在这条循环上同步调那条 lambda），就是死锁。这与记忆
`tts-pyttsx3-com-same-thread` 同族：**跨线程的桥，线程本身就是语义**。

**这条是 G1/G3 的硬约束**：反向调用的等待只能以 `await` 的形式出现在业务协程里，
任何同步 `.result()` 桥必须钉在一条专属线程上（照 tts 那次的修法），不许在网关循环上
原地等任何人回话。

# 第八十轮 收：§8 R3 四条"无 UI 也能启动"的降级路径落地，9 处变异全被抓住

上一轮交的是 G0 + R1（commit `4f09778`）。这轮按同一张 §8 风险表往下走一格：
**R3** 那行的要求写得很具体——"G0 里先给这 4 个加『无 UI 也能启动』的降级路径并测试，
迁移时才有落点"。四个服务是 §7 表里"不进 RPC"那一行：`MediaPlay` / `BossKey` /
`Browser` / `WebPageRenderer`。全程零外网，验证一律打在 `127.0.0.1` 或纯内存替身上。

## 1. 改前普查：四个"能启动"的假象

| 服务 | 无 UI 时今天实际会发生什么 | 现在 |
| --- | --- | --- |
| `MediaPlayService` | `on_start` 缺省塞 `SystemPlayerBackend`，`open()` 走 `os.startfile` — 一个没有窗口的进程**凭空开一个本机播放器** | `HeadlessVideoBackend`：只记账（`media_url`/`state`），`seek` 空转，位置由服务落库 |
| `BossKeyService` | `hide()` 不看 `_apply_visibility` 的回报：拿不到窗口也把 `_hidden` 记成 `True`，快捷键从此失效到重启，还留一只没人摘的托盘图标 | `_apply_visibility` 每条失败分支 `return False`，`hide()` 据此落托盘、记 `error`、拒绝置标志 |

| `WebPageRenderer` | 顶部 `import flet as ft`，只是被懒 import 救着；但 `looks_like_gate`（"渲染完还是不是墙"）住在这个文件里，无头路径想问同一个问题就得把 flet 拖进来 | 谓词搬到 `app/services/block_pages.py`（flet-free），渲染器改成从那里 import |

`verification_fetcher`（验证码）没有降级可言——它要的就是人。无 renderer 时明说
`RuntimeError("验证码需要人工输入：当前进程没有界面，请在有窗口的端打开这本书")`，
不弹窗、不静默返回空串。

## 2. BrowserService 那条链，和它在产品里的落点

`render_webview` 现在按三级走，顺序是有理由的：

1. **静默内核**（`_silent_render`）：chromium 在场就自己渲一次；`looks_like_gate` 判
   回来的**不是墙**才交差 —— 无头进程里大部分 `<useweb>` 根本不需要有人放窗口。
2. **远端宿主**：还是墙 → `self._remote_webview(url, source, options)`，即网关的
   `request_web_content`（上一轮 R1 那条竖切）。`source` 是 Legado `WebviewFetcher`
   的契约第三位，丢不得。
3. **当场拒**：没接宿主就 `WebviewUnavailable` —— 快失败，不占 `WEBVIEW_TIMEOUT`
   等一个永远不会来的回话。

装配根那一跳是新加的：`main._wire_headless_webview(hub, gateway)` 在 `serve()` 里
`hub.register(gateway)` 之后调用，把 `GatewayService.request_web_content` 注进
**注册在册的那一份** `BrowserService`。桌面端对应的是 `_wire_browser_page`（把 flet
page 交给同一个服务）——两条线不共存：有窗口就弹窗，没窗口就推宿主。`serve()` 的
docstring 因此从"差别两处"改成"差别三处"。

# 第八十一轮 收：§8 R2 那一笔——`@webjs:` 的同步桥不再骑在网关循环上

上一轮（R3，commit `0221f20`）交完，§8 里 G0 名下只剩 **R2**：风险表写的是
"原生句柄线程亲和复发……网关是新加的一条并发来源"，而 R1 那一轮已经量出**具体是哪一处**
会咬人（§6.5）：`reading_engine._bind_interaction` 给 QuickJS 装的桥是**同步阻塞**的
`run_coroutine_threadsafe(...).result()`，同一条调用在工作线程 56 ms 回、落在网关循环上
10 s 不回。这一轮就是把那一笔拆掉，并把它钉住。

## 1. 两半，各钉一条

| 落点 | 改法 | 为什么这样切 |
| --- | --- | --- |
| `legado_js.evaluate_async` | `@webjs:` 分支不再**原地**跑，改成 `await asyncio.to_thread(self.evaluate, ...)` | 原地跑等于把脚下这条循环交出去等一次 WebView 渲染；无头装配里这条循环正是唯一能收下 `engine.webContentReady` 那条 POST 的。`@webjs:` 全程不碰 QuickJS（脚本在页面里跑），换线程没有原生亲和问题。另一条分叉（求值线程已活动）留着不动——它本来就在 worker 上 |
| `reading_engine._bridge_from_js`（新 helper） | 进桥先问一句"调用线程正在跑的就是我要等的那条循环吗"，是则**当场抛** `RuntimeError("…互等…")` | 下一轮还会有人从别的入口调这条桥。给一个名字，比一次十分钟的互等便宜；也让护栏有一条不花 60s 的红臂 |

两条是分层的：只改上半，护栏仍然绿（循环自由）；只改下半，端到端那条用例会**真的冻住**
（变异核验里 J2 那一臂跑满 85.95s、两条全红，就是这个形状）。

## 2. 顺带补的一个洞：`@webjs:` 的完成值回不来

量的时候发现反向调用的**答复**里没有 `jsResult` 这一项——`_evaluate_webjs` 读的就是它，
而请求帧早就把脚本递出去了（`options.javaScript`）。也就是说宿主能渲染、能答，但
`@webjs:` 那条规则永远拿不到完成值（"webjs 脚本未返回结果"）。补上：

- `engine.webContentReady` 多一个可选入参 `js_result`（schema 同步；闭合 schema 加可选键
  不破坏老客户端）；
- `web_content_ready(..., js_result=None)` 只在**非 None** 时往回填写 `jsResult` 键——
  空串会被引擎读成"脚本返回了空"，而"宿主压根没跑脚本"与"脚本返回了空"是两件事；
- action 表的 `params` 与 schema 同集合，这条由既有契约护栏盯着（变异 J5 就是删这一项，
  红）。

## 3. 护栏：`tests/test_gateway_inproc.py::JsBridgeThreadAffinityTests`

真引擎（在**引擎循环上**建：`aiohttp.CookieJar()` 要 running loop，生产里它本来就是
`RuleEngineService` 在那条循环上懒建的）+ 真网关 + 真 `/ws` 会话 + 真反向调用，全程零浏览器、
零外访。两条：

1. `@webjs:` 从网关循环上 `await` 出去：请求帧带着脚本 → **等待期间** `engine.status`
   这条 RPC 照样答得出（冻住的话这一发永远进不来）→ 宿主交回 `js_result` → 引擎拿到
   `"正文回来了"`。
2. 从循环上直接调那条桥 → 0.1s 内拿到带"互等"的 `RuntimeError`；**正对照**是同一条桥
   从工作线程进来给得出结果（R1 那轮量的就是那一臂），否则这句"拒"可能只是桥本身坏了。

变异核验 `.probe/r2_mutation_check.py`：**5/5 被抓住**
（J1 原地跑 / J2 拆掉那句问话 / J3 帧里不带 options / J4 不回填 `js_result` / J5 表少一项）。

## 4. 这一轮踩的两条仪器坑（都进记忆了）

- **`write_text` 会把 `"\n"` 翻成 `os.linesep`**：本仓库**逐文件**混用行尾
  （`legado_js.py`、`reading_engine.py`、`main.py` 是 CRLF；`app/gateway/service.py`、
  `methods.py`、`block_pages.py` 是 LF）。变异脚本用 `read_bytes().decode()` 拿到带
  `\r\n` 的文本、再用 `write_text` 写回去，CRLF 文件就变成了 `\r\r\n`——子进程读到的是
  `IndentationError`，而报上来的是一行 `ERROR: found no collectors`，脚本按"退出码非 0"
  判红就会把它误读成"护栏抓住了"。做法：匹配与写回都用文件自己的行尾，还原用原始字节。
- **"非 0 退出码"不是"抓住了"**：第一版判据 `rc != 0` 让三条收集错的变异全被判成红
  （其实是 2/5）。现在的判据是"失败 ≥1 条"，并且**收集/导入错误单列一类、明确不算抓住**，
  报告里带"执行 X 条，失败 Y 条，错误 Z 条"三个数。同一条教训另加一句
  `PYTHONDONTWRITEBYTECODE=1`（旧 `__pycache__` 能把只活几秒的变异整个糊过去），
  R3 那份 runner 也一并补上。

## 1 选走法一，但把"见过客户端"收窄成"成功办完过一次动作"

三条走法里选了第 1 条。判断的依据是把 G0 那条 docstring 读准：它护的是**没跟引擎说过话
的探针**（"纯 curl 试跑不该被一段倒计时打断"），不是"说过话然后消失的客户端"。后者今天
的代价是每次 Flutter 崩溃就永久留一个 python 进程占一个回环端口——这不是设计选择，是漏。

收窄之后的三条规则（`app/services/gateway/service.py`）：

- `/rpc` 进来 `_cancel_idle_timer()`，回完话在 `finally` 里 `_arm_idle_timer()`。
  HTTP 客户端没有"会话断开"这个事件，它的空闲只能读成"最后一次成功动作之后安静了 N 秒"。
- 只有 `ok` 为真的回信封才把 `_clients_seen += 1`（原 `_sessions_seen` 改名）：坏 JSON、
  未知 action、schema 不符的探针不给上倒计时；令牌不对的连处理器都进不来（中间件 401）。
- curl 豁免没有取消，只是搬了家：要一段永不打断的运行用 `--idle-seconds 0`
  （`_arm_idle_timer` 里那条 `<= 0` 判断本来就支持）。

没选第 2 条（RPC 单独一条更长的计时）：留下两个生命周期不同的定时器，将来读日志分不清
是谁杀的，而"N 分钟"这个数现在没有依据。没选第 3 条（租约/心跳）：要加 action、加 Dart
侧定时器，是 G2 的量，而本机单用户引擎没有第二个用途需要服务端知道客户端还活着。

顺手补的一处：`_on_idle_expired` 遇到**在途 job** 改判成"推迟一个窗口再看"。job 动作一发
就回受理凭据、本体还在跑，这时候收摊等于把用户的活半程杀掉且没人记账（进度只从事件流走）。
代价写在注释里：任务本体没有服务端预算（`mode="job"` 不受 `method.timeout` 约束），
所以一个挂死的任务会让这条推迟一直推迟下去——真要收摊走 `engine.shutdown`。

## 2 五臂 + 五条变异，全红

服务面（`tests/test_gateway_inproc.py`，断 `exit_event`）与现场面

| 臂 | 判据 | 变异（`.probe/mut005.py`） |

| `…goes_quiet_lets_the_engine_exit` | 一次成功动作之后没人再来 → 置退出标志 | MUT4 去掉 `finally` 里的 arm → 红 |
| `…keeps_calling_is_not_cut_off` | 正对照：每 0.1s 一发跨 6 发，不许被打断 | MUT1 去掉入口的 cancel → 红 |
| `…never_succeed_never_arm…` | 坏 JSON + 未知 action + 无令牌，`_clients_seen` 仍是 0 | MUT3 失败动作也计数 → 红 |

## 3 一次口径错误：lag 的起点被我记在了 sleep 之后

现场臂第一版跑出 `0.77s`，判词是"比窗口 1.0s 还快 = 不是空闲触发的"——**它咬的是我自己**。
起点记在"最后一发调用之后的那次 `sleep(0.3)`"之后，而窗口是从服务端回完话那一刻就开始走的，
于是 0.3s 的窗口尾巴被算进了"收尾"，读数凭空小了 0.3s。探针第一版更糟：整个窗口都扣，
读出 **−0.22s 的负收尾**（负数才让它现形）。两处改法一样：起点跟着**最后一发调用**走。

要记的不是这条减法，是它的方向：**记错时刻的读数变小，而"更快"永远是好消息**，
所以它不会被人怀疑——是那个负数把它逼出来的。判词里写"不早于窗口"这一条，本来是为了拦
"根本不是空闲触发的退出"，结果第一个被它拦下的是我自己的仪器。

## 4 顺手量出来的一个意外：+5.00s 的收尾抖动，不是这一轮的

`engine.shutdown`），每栏独立启动。第 3 轮里空闲栏 `4.80s`、shutdown 栏 `5.08s`，
夹在中间的 1 发栏正常——两条**不同**收尾路径在同一轮里一起中招，所以它不是空闲专属，
也不是这次改动带来的（`engine.shutdown` 那条路今天一样中招）。

`+5.00s` 这个整数把出处指到了 `app/core/engine_worker.py:228`：

```python
    thread.join(timeout=5.0)
```

第二次跑 24 发一次都没出现。合计 49 发 4 发（≈8%），退出码全 0、端口全放掉——功能没坏，
只是父进程要多等 5 秒。**loop 线程为什么偶发退不出去还没归因**（杀软插手 / loop 上还有
在途任务 / 原生收尾，三个候选一个都没仪器；stderr 的最后一行是 `RuleEngineService 已停止`，
5s 花在这行之后，正是日志照不到的那一段）。不调小 `timeout`：那只是把等待换成"不等了"，
loop 线程照样在跑，症状消失、真因留下，还会让"收尾没走干净"这一类从此静默。
记 `docs/known-issues/006`。

这也是为什么现场臂的上界写在 30s 而不是 3s：把 8% 的收尾抖动判成红，只会让人学会重跑。

## 7 两次全量红是机器的账，不是这次改动的账

带改动跑全量，两次都红，**受害者还不一样**：第一次是
`test_reading_services.py::test_switch_source_scans_concurrently_with_timeout`，
第二次是 `test_reader_continuous_scroll.py` 的两条（一条 failed、一条 setup error）。
两处都跟网关无关，症状却同族：

```
asyncio/proactor_events.py:787: in _make_self_pipe
    self._ssock, self._csock = socket.socketpair()
E   OSError: [WinError 10055] 由于系统缓冲区空间不足或队列已满，不能执行套接字上的操作。
AttributeError: 'ProactorEventLoop' object has no attribute '_ssock'   ← 上一条的次生错误
```

`10055` 是建 loop 时拿不到 socket，`_ssock` 那条 AttributeError 只是自建管道失败之后
清理阶段的次生错误——**别把它读成"某个对象少了个属性"**。

归因没有停在"看起来像环境"。三步：

1. 单跑受害者：两条各 2/2 绿 → 不是它们自己的问题；
2. 数当时的 TIME_WAIT：`1228 → 568 →（45s）→ 277`，而两次全量分别紧跟在归因探针的
   **15 发**与 **39 发**独立引擎启动之后（每发一个监听 socket + 若干短连接）；
3. `git stash -u` 回到 `70ec28f` 跑一次基线：**1923 passed 全绿**；等 TIME_WAIT 退到
   278 之后，带改动再跑一次：**1928 passed, 161 subtests passed in 152.08s**，全绿。

所以压力是探针的启动次数带来的，不是这次改动带来的。要记的是这套件自己的余量：
**一次全量跑完，机器上会留下约 1100 个 TIME_WAIT**（Windows 默认 120s 才退），
紧跟着再跑一遍或紧跟着一轮多进程探针，就会在随机的某个 loop 上撞 10055。
下次遇到"受害者每次都不一样、都是建 loop/建 socket 失败"，先数 TIME_WAIT，再去怀疑代码。
