## 第十四轮：整书缓存的在途任务列表（`list_tasks` / `cancel` 是孤儿方法）

### 现场
`DownloadService.list_tasks()`（`app/services/reading/download_service.py:99`）与
`cancel()`（:88）在 `app/` 里**零调用方**。界面上书架只有一行状态文本
（`整书缓存进度 N%`），于是：两本书并行缓存时说不清是哪本；切页再回来任务就"消失"了
（其实还在跑）；已经入队的任务没有任何取消入口——只能等它跑完或退出程序。

### 设计
- 视图 `BookshelfView`：新增回调槽 `on_cancel_cache`（`bookshelf_view.py:27`）、
  宿主 `_task_host`（:75，插在「最近阅读」与分隔线之间）与渲染接口
  `set_cache_tasks()`（:110）。**一本一行**，每行自带进度条与「取消」，
  列表为空时整块 `visible=False`（不留灰框占位）。
- 控制器 `BookshelfController`：`_cache_rows()`（`bookshelf_controller.py:285`）只取
  `kind == "whole_cache"` 且 `status in ("queued","running")`（:281）的快照，
  书名按 `book_url` 从已加载的书架记录里解析——**服务快照里没有书名**，
  这是跨层契约，视图不该自己猜。
- **冷启动补渲染**：`_load()` 里调一次 `_render_tasks()`（:115）。
  进度只靠事件驱动的话，切页回来就是空白；这条是"服务发了事件 ≠ 界面画出来了"的老坑。
- 取消 `cancel_cache()`（:263）：服务返回 False（任务已结束）时明说"该任务已结束"，
  不假装取消成功。

### 最严重的一类失真：**"进度事件 N 个" 是凭空写的**
旧日志/验收表写着替换规则 12 个、规则修复 11 个、备份导出 4 个进度事件。
当前树里这三条链路**一个进度事件都没有**：
- 替换规则只发 `ReplaceRulesChangedEvent`（`replace_rule_service.py:132/197/210/225`，是"数据变了"不是"进度"）；

- 备份/恢复只发 `BackupFinishedEvent`（`web_dav_service.py` 共 13 处发布点，全部是收尾的成/败一条）。

**但三条里只两条是真缺口，第三条是这次审计自己造的谣**（当日更正，见第十七轮）：
"批量替换"这个动作在项目里不存在。替换规则是 CRUD，真正用它们的地方是阅读链路——
`reading_engine.process_book_content` 每章就地调 `get_global_replace_rules(scope)`
（provider 在 `ReplaceRuleService.on_start` 注入，`replace_rule_service.py:69`）。
逐章替换是纯内存正则、跟着正文一起回来，**没有可以进度的那段路**。
教训与前几轮同型：**"某功能缺进度反馈"也要数调用方**——先确认那个功能是不是一个
会跑 seconds 以上的动作，再登记缺口。

所以真缺口是两条：整库规则修复 / 整库备份上传，几十秒级的任务，界面从点击到出结果

`*ProgressEvent`，视图侧一条进度行。**节流那条当时写错了**：0.5s 合并是给逐条高频事件的，
阶段事件一共十几拍，节流反而把最后几拍推到收尾之后（结果都出来了进度条还在转）——
本轮两条新链都不节流，理由写进 §5.11。

## 第十七轮：自愈链路接出来 + 备份/恢复逐阶段进度
第十五轮登记的两条真缺口本轮补完，另外查出**整条自愈功能是断的**（视图、控制器、服务
三样都在，链路却接不上）。全程离线（本地目录当 WebDAV 远端 + 内存服务替身），未联网。

### 1. 规则修复：`_to_dict` 读的是不存在的字段
`RuleRepairController._to_dict(report)` 按 `report.source_url` / `report.selector` 这类
**顶层属性**取值，而 `services/rule_repair.py`（冻结副本，本轮未动）里这些都在
`report.fix` 下面，`report` 顶层只有 `fix / reason / tried / pages / samples`。
于是：报告卡永远空白，`confirm_fix` 拿到空 `report_id` 永远拒收——用户点「自愈」只会
看到一张什么都没有的卡。这条也是 §5.11 那句"三样都接了，链路仍是断的"的现场（已记进
known-issues 003）。

补的是三处：
- `_to_dict` 改为展平 `report.fix`，`report_id` 由**事件带进来再原样送回**（报告对象自己
  不带 id，它只是 `_reports` 的键）；
- 没有提议的报告（`fix is None`，只有 `reason`）现在渲染成"为什么没提议"的说明卡，
  **不给确认按钮**——以前照样画一个按钮，点下去写回一个空值；
- 服务侧把冻结副本已有的 `on_stage` 钩子接成 `RepairProgressEvent`（诊断要真抓 1-3 页
  样本页，这中间界面以前什么都没有）。

### 2. 阅读器 → 自愈：把入口接出来
以前正文规则坏了以后，用户唯一能到「自愈」页的路是自己去左侧导航找。现在章节加载失败
时阅读器底部亮一条补救条（`reader_view.repair_offer`），点「自动修复该书源」=
**带着那一章**去诊断（`extra_chapters` 取后面 2 个有 url 的章做样本），再跳到
`sources.repair`。本地书与 `LOCAL_BOOK_SOURCE_URL` 不亮条（没有书源规则可修）。
跨组跳转是合法的：阅读器是「阅读」组的整页，自愈是「书源」组的页签，
`nav_actions` 的目的地只要存在于 `NAV_META` 即可（护栏原来错窄地限定在本组，已改）。

### 3. 备份/恢复：`BackupProgressEvent` 逐拍上报
`WebDavService` 在导出（逐成员）→ 校验（逐成员带 done/total）→ 压缩 → 上传（带字节数）
四处发进度；恢复在下载 → 校验包 → 本地留底 → 逐成员落库四处发。视图加进度条 + 阶段行
（`set_progress/clear_progress`），控制器订阅并**不节流**（理由见 §5.11 本轮更正）。
顺带修掉三处真实缺陷：
- `_collect_members(only=…)`：选「词典」以前照样把整张书源表序列化一遍再丢掉，既慢又会在
  进度里报出用户没点过的"正在导出书源"；
- `_on_finished` **没有** `_view is None` 守卫（同族问题第十五轮刚记过一次），切页瞬间的
  在途收尾事件会踩 `None`；
- 结果行有**两支笔**：future 收尾路径和事件路径都写 `_log`，措辞还不一样（`词典：…` 与
  `[dict] …`），最终上屏哪句取决于谁先跑到。本轮定死：本页发起过的动作归 future 路径，
  事件只关进度条；只有本页从没发起过动作（别处触发的备份）时事件才补写结果。

### 1. 新形态：事件发了、也订阅了，界面还是不动
`ExportProgressEvent`（第 22 个事件）+ 视图进度行 + 控制器订阅，三样都齐之后
**这条链仍然是断的**——因为导出通体是同步磁盘/CPU 工作，从头到尾一次 `await` 都没有。
`publish` 只是把处理器**排进**引擎循环（§5.11），引擎循环被导出独占时那些处理器全在排队，
于是表现为"进度条纹丝不动，然后一下子完成"。前四条进度链（下载 / 导入 / RSS / 备份）
都带网络 `await`，循环自然让出，所以从没暴露过这一点；**导出是第一条纯本地重活**。
处置：`_paced` 每章 `await asyncio.sleep(0)`，`write_epub` 这种同步压缩前也先让一拍。
护栏 `test_export_progress_reaches_handlers_while_the_export_runs` 用"publish 即
`create_task`"的同构总线 + 每章睡 50ms 的慢缓存，核的是**读到最后一章时前面的拍已经送达**
——把 `sleep(0)` 拿掉它立刻红。这条已写进 `current-system-design.md` §5.11 正文。

### 2. `cache_counts` 的返回顺序被解反了
`ReadingCache.cache_counts` 返回的是 `(已缓存, 目录可读总数)`（`reading_cache.py:121`），
`list_exportable_books` 却按 `total, cached = …` 解（`book_export_service.py:81`）。
后果：完全没缓存的书被列进导出清单（`if not cached` 实际判的是目录条数），
部分缓存的书在界面上显示成"已缓存 5/2 章"。
**为什么测试没抓到**：护栏 `test_service_lists_only_cached_books` 的替身给的是
`(5, 5)` / `(5, 0)` 这种"两边一样"或"恰好反了也对"的数——**对称数据把顺序错洗白了**。
本轮把替身改成 `(4, 5)`（缓存 4 / 目录 5）并让它必须解对，才钉住。
⇒ 通用教训：**任何成对返回的计数，替身两边不许相等**。

### 3. 进度分母取"已缓存章数"而不是目录条数
未缓存的章压根不会被写，拿目录条数当分母时进度条永远停在 4/6。
读不到计数时报 0，界面走不定长动画，而不是猜一个数。
节拍用 0.2s 合并（几百章不能刷几百条），但**首拍必发**（起点时间戳记 0，
点完立刻有反应）、**末拍 force**（否则条停在半路）。

### 4. 在途标记：迟到的拍不许把条支回来
导出收尾走的是 future 回调，进度走的是异步投递，两者没有先后保证。
所以控制器加了 `_running`：`export()` 置真、`_after` **第一件事**置假，
`_on_progress` 只在真时才动控件。没有这一半的话，症状就是上一轮刚记过的
"结果都出来了进度条还在转"。`_after` 里也补了 `clear_progress()`，
失败路径同样关条、清阶段行、把按钮放回可点态。

## 第二十一轮：视频书接进阅读器（M5 表最后一格 ✗）

起点是 `M5集成验收记录.md` 里唯一还挂着 ✗ 的 1.4：`MediaPlayService` 整条只有服务面，
`app/` 内零调用方；阅读器 `reader_view.py:528-537` 自己 `import flet_video` 建控件，
**每个视频块一个播放器、完全绕过服务**——于是"播放列表 / seek / 记忆位置"三样服务面
能力在界面上没有承接方。本轮把它接成一条链，并第一次用**离线界面探针**验到真控件面。

### 1. 三处实错（都是"照 API 名字写出来必然错"的那类）

- **`Video` 没有 `source` 字段**（0.86）：往控件上写 `control.source = url` 不会下发给
  客户端，换章等于**永远停在第一条视频**。换片只能改 `playlist`，而 `VideoMedia` 是
  `flet_video` 的类型、服务层造不出来（红线：`services/**` 不 import flet）→ 后端构造
  收 `media_factory`，由视图层递。
- **`seek` 的单位是微秒**：`Union[Duration, int]`，而 `Duration` 上线走
  `ExtType(3, in_microseconds)`（`flet/messaging/protocol.py`）。秒→Duration 的换算要
  import flet，所以同样交给视图层 `duration_factory`；**没注入就跳过跳转，不猜单位**——
  猜错的表现是"接着上次的地方放，结果跳到片头几毫秒"，最难查的那种。
- **`stop_playback()` 不能叫 `stop()`**：那会盖掉基类的生命周期 `stop()`，hub 逆序停止
  时这个服务**永远停不掉**（与 `ReadAloudService.stop` 同一坑，见「生命周期方法是保留名」）。
  另外位置必须在叫停**之前**读——播放器 stop 之后多半报 0，那样"接着看"永远回到片头；
  故 `stop_playback(remember_position=True)`，生命周期收尾 `on_stop` 显式走 False。

### 2. schema v7：播放进度不再占用阅读进度

v4 只补了秒级 `play_position`，当时把"播到第几条"存在了 `books.chapter_index` 上——
而 `chapter_index` 同时是**阅读进度**，书架上"读到第几章"于是跟着播放走。v7 新增
`books.play_chapter_index` 单列存播放列表索引，`play_position` 留在原处；有迁移护栏
（`test_core_lifecycle.py:223`）与"落播放库不动阅读进度"的正向断言

## 第二十二轮：视频书连播（遗留 12①）

`ended` 过去没接控件事件——放完一条就停在那，Legado 会接下一条。本轮把播放器自己上报的
两条事件接进同一条派发路径，并第一次查出**护栏自己在"没发生"这类断言上是失效的**。

### 1. 接线

`ftv.Video` 的 `on_complete`/`on_error` → `VideoPlayBar.on_ended`/`on_failed`（新增两槽，
面板共 9 槽）→ `ReaderController.video_ended`/`video_failed`（reader_controller.py:209-211）
→ 服务 `MediaPlayService.mark_ended()`（先把位置清零再发 `ended` 态）→
`_finish_video_entry()` 按列表顺序点下一条。三条闸门都是必要的：

1. **只认"正在放"**：按了停止/收起面板之后客户端还会补发完成事件（缓冲边界、切后台回来），
   照单连播会把用户刚收掉的播放器又点亮。
2. **等状态落库的工夫里换条/切页就放弃**：`self._view is None or index != self._video_index`。
3. **报错不连播**：书源里的视频常常整本都坏（防盗链失效、地址过期），连播就是一路错到底，
   比停在一条上更糟。

另外两处非闸门约束：槽必须**事件到达时**取（`_player_handler("on_ended")`），闭包里写
`callback=self.on_ended` 会把建播放器那一刻的 `None` 钉死，表现是"放完了什么都不发生"；
片尾位置必须清零，否则"接着看"从最后一秒起播。

### 2. 本轮真正的收获：一条**绿的变异**抓出来的护栏缺陷

`.probe/mutate_ended.py` 第一轮 6 条里有 1 条**没红**——「最后一条也绕回第一条」。
用例 `test_the_last_finished_entry_does_not_wrap_around` 写的是：

```python
assert _settled(lambda: media.calls == [("mark_ended",)])
assert [c for c in media.calls if c[0] == "play_chapter"] == []
```

`_settled` 是"谓词一成立就返回"，而 `== [("mark_ended",)]` 在 `mark_ended` 落账那一刻就成立，
绕回去点第一条是**之后**才发生的事——于是这条"没发生"永远看不见，变异照样绿。同一写法在
「报错不触发任何播放动作」那条上也补了窗口。改法与 `test_a_late_completion_after_stop_is_ignored`
一致：先等"该发生的"落了账，再 `time.sleep(0.15)` 收窗口，最后断"没发生的"没出现；
并把用例改成真的最后一条（两条列表停在第 2 条），单条列表那个 rig 压根走不到分支。
新增一条变异「报错也顺手连播下一条」证明这个窗口真在挡东西。

⇒ 与「护栏要钉"没发生"而非"失败了"」同源，补一句：**"没发生"要等过一个窗口再断，
立刻断等于没断；而且"该发生的"和"没发生的"不能写在同一个谓词里等。**

### 3. 界面面**未取证**（诚实记录）

`ended` 是**客户端**产的事件，本轮只验到"服务面 + 装配面 + 护栏"。离线探针
（`WEB_BROWSER` + 回环假 webm）跑过三次都没到"真解码 → 客户端报片尾"那一步，
踩到两个与产品无关的探针装配错，记下来免得下轮再踩：

1. **uvicorn 不能直接挂 aiohttp 的 `web.Application`**：`Application.__call__` 只收 `self`
   （ASGI2 形状），喂给 uvicorn 的 ASGI3 调用就是 `TypeError … takes 1 positional argument
   but 2 were given`，浏览器侧表现为每次取视频都 500。要用 aiohttp 自己的
   `web.AppRunner` + `web.TCPSite`。
2. **独立构造的服务没有总线**：`Service.bus` 由 `hub.register()` 注入，探针里手搓的
   `MediaPlayService` 是 `self.bus is None`，`_publish_state` **静默不发**——所有状态断言
   都停在 `idle`，看着像"接不上"。要么走真装配层，要么自己 `EventBus()` 注进 `MEDIA.bus`。
3. 短片采不到位置变化：假片 2s + 采样窗口 1s 时 `currentTime 0.00 → 0.00` 判不出真解码，
   片长要明显大于采样窗口。

> **第二十四轮已补上这一步**（8/8 取证），并且发现本表 3 处装配错之外还有一处更严重的：
> 当时"看起来过了"的那条判据是**伪 `completed`** 给的绿灯。见第二十四轮 §1。

## 第二十四轮：视频书面取证（遗留 12① / 13 收尾）——上一轮的"通过"是伪事件给的

本轮只做一件事：把第二十二轮欠的那一步（web 面客户端到底报不报 `on_complete`）跑出来。
结论是**报**，但过程里查出三处产品实错，而且第一处直接推翻了上一轮的一条判据。

### 1. 伪事件：一条假的 PASS

探针第一次跑到"等片尾"那一步就过了——位置序列明明还在往上走，`on_ended` 已经落账。
隔离出来单测（`.probe/probe_complete_source.py`，ffmpeg 现制的 6s 真片 + 无头 Chromium）
量到的是：

- `ftv.Video` **构造后约 40 毫秒**（实测 +0.04s）回一发 `on_complete(data=False)`，
  同刻跟着 `on_error('MEDIA_ELEMENT_ERROR: Empty src attribute')`；
- 传 `playlist=[]` 和不传 `playlist` 的两种构造**都报**，跟"有没有给空列表"无关；
- 真片尾是那条 6 秒片放完时的 `data=True`（实测 +6.03s）。

所以上一轮"停止后补发的完成事件不连播"那条 PASS，其实是**起播那一瞬间的伪事件**满足的。
面板原先照单转发 `on_complete` → 真点起来，连播会在起播那一下把整本翻到最后一页。
改在 `VideoPlayBar`（`video_play_bar.py:148-177`）：

- `_completed_handler` 只认 `_as_completed(event.data)`（`True` / `"True"` / `"1"` / `"yes"`，
  插件上线是字符串、单元测递真 `bool`，两种都认）；
- `_error_handler` 丢掉 `Empty src attribute` 那一发（此时用户那本还没开始放，涂红等于凭空
  报错），真坏源的话（`no supported sources` / `FFmpegDemuxer`）照原样递上去。

**取证自己的教训**：`.probe/probe_complete_source.py` 第一版在 A/B 两次构造之间 `EVENTS.clear()`，
把要抓的那两发擦了，于是读出"两种构造都很安静"。事件账本一次都不能清，只打绝对时间线。
这条与「护栏要钉"没发生"」是同一类错误：**观测窗口自己把证据挖掉了，比没测更糟**，
因为它给的是绿灯。

### 2. 另两处 web 面实错

1. **起播竞态**：`playlist=[media]` 之后立刻 `play()`，客户端回
   `The play() request was interrupted by a new load request.` / `The element has no
   supported sources.`，面板停在 error、位置恒为 0。改法是播放意图**随换源同一条消息下发**
   （`_load` 里 `autoplay=True`，`media_play.py:165-176`），`open()` 记 `_intent_with_load`，
   紧随的那发 `play()` **故意不发**（:178-184）；`pause()` 把这一位清掉，暂停之后再点播放
   得真下发。
2. **`stop()` 把播放面弄废**：`.probe/probe_stop_recovery.py` 三种救法——A 停止改用 `pause()`
   → 能放（位置 `[0,1,2,4,4,4,4,4]`）；B `stop()` 后补 `play()` → 位置 `[0]*8`，并回
   `The play() request was interrupted because the media was removed from the document.`；
   C `stop()` 后重建控件 → 能放（但得视图层配合）。web 面控件的 `stop()` 会把 `<video>`
   摘出文档，**这个播放面就此废掉**（之后假源照样被要、位置一动不动）。故
   `FletVideoBackend.stop()` 状态归 `idle`、控件上落的是 `pause()`（:191-205）。
   位置在叫停前已由服务侧 `stop_playback` 读走，重播走 `open()` 换片，实测从片头正常起播。

顺带一条跨源前提（不在本轮改动范围，但解释了 web 面看第三方视频书为什么黑屏）：
flet_web 给页面带 `Cross-Origin-Embedder-Policy: require-corp`，视频地址在另一个端口时
服务端不回 `Cross-Origin-Resource-Policy: cross-origin` 就被浏览器拦成"没有可用源"。
假源自己补这个头才通，真实书源替不了。

### 3. 探针取证的判据换过一次

整套装配里 Playwright 的**页面级和 context 级 `request` 监听一条取片请求都没数到**（NET=0），
而隔离探针里同一个 context 监听是收到的——所以这份账在这里只能当旁证。真正用的判据是
**回环侧记的 UA（`Mozilla/5.0` + `Range: bytes=0-`）+ 位置自己往上走 + 6 秒后真片尾**：
取片的是这个浏览器客户端，不是服务端自己或外部播放器。别把"监听没数到"当成"没请求"。

### 验证（离线）

### 1. 抓出来的实错：「试跑当前规则」在生产里永远是空的

点「试跑当前规则」→ 回显 `示例里没取到值`，但同一份规则（`.title@text`）对同一段正文
在引擎里明明取得到 `远航`/`归途`（当场把 `rule_engine` 拉出来单跑过）。两头错位的原因：

- 控制器 `code_editor_controller.py::_eval_field` 先探 `self._rule_engine` 上的
  `extract_values` / `eval_field` —— **`RuleEngineService` 上没有任何一个**
  （整类方法列表核过：search/explore/book_info/chapters/content/login*/put/get…，
  没有单字段求值）；
- 于是每次都走回落 `rule_engine.select_nodes(sample, kind, "")`。那是搜索管线的**第一步**
  （先按列表规则选容器，再逐容器取字段），传空列表规则就一个容器都选不出来，返回 `[]`，
  接着 `extract_values([], rule, kind)` 对着空节点列表求值 ⇒ **任何规则都只能回"没取到值"**。

24 条单测为什么全绿：替身 `_FakeEngine` 自己定义了 `async def extract_values(...)`，
所以测试跑的是那条"服务上有方法"的分支，**生产永远不走它**；真正的回落分支一次都没被覆盖。
按第二十二轮那条同源的教训（替身比生产面宽 = 绿灯骗人），本轮不只要修，还要把
"替身有没有这个方法"这件事本身钉住。

改法：把单字段求值做成 `RuleEngineService` 真正的公开方法（`extract_values(rule, sample, kind)`，
同步纯函数，**整段正文就是被求值的节点**，不再套 `select_nodes`），控制器只调它、
不再"探方法 + 回落"两头猜。`RuleEngineService` 本来就是"规则求值核心的壳"，这条属于它的本分。

### 3. 探针自身的四个坑（下一条探针别再踩）

- **服务端口不是随叫随到**：`ft.run` 在主线程起，Playwright 线程先起跑就

- **候选节点要挑"标签最短"的那个**：容器节点的 aria-label 会把子节点文字整串拼进来

## 第二十七轮：把"替身比生产面宽"这一类**全库扫一遍**（任务 #55）

第二十六轮那条「试跑当前规则」的根因是**控制器探测了真服务类上根本不存在的成员**，
替身自己定义了那个方法所以单测全绿。本轮不修单点，改成把整类形状扫干净：
`app/controllers/**` 里每一处 `self._<句柄>.<成员>` 和 `getattr(self._<句柄>, "<字面量>")`，
都对照**真服务类**的类面核一遍。

### 1. 扫法与结果：150 条成员引用，1 条假成员

护栏落在 `tests/test_service_surface_probes.py::ServiceSurfaceProbeTests`（不是临时脚本，
是常驻用例）：从 `self._X = self.service(XService)` / `_safe_service(...)` / `require(...)`
三种取用点建"句柄 → 服务类"映射，再逐条核成员是否存在（属性走 `hasattr`，方法额外允许
`inspect.getsource` 里出现 `self.<成员>`，因为老基类有动态挂载）。
**实测核到 150 条引用，命中 0 条假成员**（修完之后）。

扫描器本身两条坑，都是本轮踩过并修进用例的：
- 只走 `ast.Attribute` 会漏掉 `getattr(self._X, "字面量")` 这一整类——而第二十六轮那条
  实错**正是** `getattr` 形状；
- 子进程里 `importlib.import_module("app.*")` 会 `No module named 'app'`，必须把仓库根
  塞进 `sys.path`，否则整个扫描静默返回空表（表现是"一条问题都没有"，最坏的那种假绿）。

元护栏因此跟上：`test_the_scanner_is_actually_looking_at_something` 断
`checked > 120`（本轮实测 150），扫描器一旦瞎掉就红，而不是"没问题"。

### 2. 唯一那条假成员，以及它后半段没人接的链

`update_controller.py` 探的是 `self._svc.current_version` —— **`UpdateService` 上没有这个属性**，
`getattr(..., "")` 静默拿到空串 ⇒ 界面永远停在视图自初始化的「当前版本：未知」。
同一条链的后半段更糟：`main._build_hub()` 注册时**从来没传过本机版本**，
`UpdateService.__init__` 的 `current_version` 默认 `""`，于是
`check_update` 那道"不比当前新就不报"的闸门拿空串比版本，`_version_tuple("")` 退化成 `(0,)`
⇒ **任何远端版本都算"更新"**，闸门形同虚设。

改法（用户定的方向：版本号在代码里定一处）：
- `app/__init__.py` 新增 `APP_VERSION = "1.0.0"`，全应用唯一定义处（PyInstaller 出的 exe
  不带 git 信息，版本必须由代码给）；
- `UpdateService` 加 `current_version` **属性**（真类面变宽，不是控制器再猜），
  默认仍留空串并在注释里钉死"别用 0.0.0"；
- `main._build_hub()` 注册时 `UpdateService(current_version=APP_VERSION)`；
- 控制器**直读属性**、不再 `getattr` 探测（`self._svc.current_version if self._svc is not None else ""`）——
  探测式写法在成员不存在时静默跳过那一行，正是这一类缺陷的载体。

### 3. 一条**误报**：grep 判"假成员"，实面证伪

第一遍手工 grep 把 `SourceService.sources` 也报成假成员。`hasattr(SourceService, "sources")`
