# 第七十四轮 全应用一层背景图：选完就该看到

## 1. 现场与两条裁决

用户那句原话里两件功能是一起提的，第七十三轮做了老板键，背景图留在这轮。开工前定下来的
两件事（都按"推荐"选项走的）：

1. **范围 = 全应用一层**，不是每页一张、也不是只给书架换底。落到形状上就是：读的是
   **同一个偏好**，画的是**同一个根**。
2. **录入 = 文件选择器 + 拷进数据目录**，不是让用户填路径、也不是把图留在原地引用。

第二条不是偏好问题，是"下次开机它还在不在"的问题，见下节。

## 2. 服务面：库里存的必须是那份拷贝

新文件 `app/services/tools/background_service.py`（工具域，零 flet）。

**为什么拷贝**：用户选中的原图可能在移动盘、网盘、或者一个马上会被整理的下载文件夹里。
直接存原路径的话，下次开机它就没了——界面上剩**一块裂图**，而用户已经不知道自己改过什么。
所以归一后拷进 `<data>/backgrounds/<md5-16>.jpg`，键值落的是**那份拷贝**的路径。

配套四件，都是当场能钉住的行为：

- **归一**：长边压到 2560、转 JPEG（质量 85）。一张 6000×4000 的手机照片直接铺满窗口，
  客户端每次重建都要解它；背景层永远罩着一层半透明，85 已经看不出压缩痕迹。**没装 Pillow
  就原样拷贝**——功能不能退化成"用不了"，只是不压。
- **`install()` 是协程**：读原图 + 解码 + 缩放是几百毫秒到几秒的重活，控制器那边就在界面
  循环上，同步方法会直接把窗口冻在那里（本机字体 `add_font_file` 早就是这个惯例）。
- **顺序是硬约束**：先写新图 → 再落键 → 最后删旧图。落键之后界面已经指向新文件，这时删
  旧的才不会闪出一道"背景既没旧的也没新的"的空窗。
- **`current` 认文件不认键**：文件没了就返回空串，因为这一层的替代品是"纯色底"，裂图比
  没背景难看。`_prune` 只删**我们自己目录里**的路径，绝不碰用户自己的文件。

偏好键 `appearance.background.image`（空串 = 没有），存废都发 `SettingsChangedEvent`。

## 3. 外壳那一层：为什么不盖一层固定色的压暗纱

`NavigationHost.render()`（`app/views/navigation.py:346`）：没背景时**直接返回那个布局**
（多包一层 Stack 就是白付一层合成），有背景时
`Stack[Container(expand=True, image=DecorationImage(src, fit=COVER, opacity=0.25)), 布局]`。

关键取舍是**"图半透明压在主题底色上"，不是"图 + 一层黑纱"**：`DecorationImage` 的 opacity
让图跟窗口自己的 scaffold 底色合成，所以浅色面仍是浅底深字、深色面仍是深底浅字，两套主题
都不用认"当前是哪一面"。反过来若在上面盖一层固定颜色的压暗层，就必须知道系统此刻在亮面
还是暗面——而 `theme_mode` 可以是 `SYSTEM`，**Python 侧问不到解析结果**。

`set_background()` 在路径没变时**什么都不做**：这条线会被每次偏好写入打到，重建整棵根树
代价大，而且会把当前视图的在途渲染一起掀掉（第七十三轮那条"show 要幂等"是同一个形状的坑）。
`rebuild()`（宽/窄窗跨阈值重建）走 `render()`，所以缩放重建不会把背景弄丢。

## 4. 装配根订阅：这一跳必须编组回界面循环

红线 §7.5：视图层拿不到服务。**换图的是外观页控制器，画那一层的是导航外壳，两者互相
不认识**，中间这一跳只能由把两边都捏在手里的 `main.py` 搭：

```
main._wire_background(hub)
  ├─ settings.subscribe([BACKGROUND_IMAGE_KEY], on_change)   # 变更
  │     └─ on_change → call_on_ui(apply) → current_host().set_background(...)
  └─ return 首屏路径  → build_app_shell(page, hub, …, background=…)
```

处理器**跑在 EngineHub 守护 loop 上**（`SettingsService.set` 用 `self._engine.submit`
派发键订阅），而 `set_background` 要改控件，所以必须经
`app.core.engine_worker.call_on_ui` 编组回界面循环——§5.2 那条契约，老板键的托盘回调走的
是**同一个口子**。这条不是"写着好看"：探针那一拍把它摘掉（就地 `apply()`）之后护栏立刻红
（§6 变异清单第 16 条）。

返回值是**首屏路径**：外壳创建时就要拿到它，晚一步就得整棵根树重建一次。

## 5. 外观页：背景不走 pending/保存，报成败前自己读回一次

主题三件套是"预览了但没点保存就不落库"；换图**不是**。选完就该看到，落偏好即生效，所以
"恢复默认"也**不动背景**——把用户刚选的图连带清掉，是最容易被当成丢数据的意外。状态行
明说这句话（`已恢复默认外观（保存后生效；背景图不受影响）`）。

控制器 `_install_background` 在 `install()` 返回后**自己读回一次**再比：install 落了键，
但真正铺上去的是装配根那一跳订阅，服务没起来/键没写进去时说"已换上"就是假话。不等时状态
行写 `图拷好了但偏好没落上（期望 …，读到 …）`。取消（`pick_files` 返回空）什么都不写。
选择器没挂上窗口时 `pick_files` 是 None future——点了就是"转圈转到天荒地老"，所以那一拍
当场把话说明白。视图上标签只写**文件名**（`Path(...).name`），不把整条数据目录路径摊给
用户看。

## 7. 桌面像素探针：这一层没有语义节点，只能逐格比图

**为什么不是 WEB_BROWSER 那条路**：背景层是 `Container` 上的一张 `DecorationImage`，
它**既没有 DOM 节点也没有语义节点**——语义树探针能证明"控件在树里"，证不了"屏幕上看得见"。

## 8. 三条诚实条目

**① 探针把自己没接上写成"产品没通"**。第一版探针读数：外壳 `background` 还是 `''`、根还是
`Row`，看起来像"装配根订阅没通"。真因是探针自己绕过了 `build_app_shell`（登记全局宿主句柄
`navigation._APP_HOST` 的那一步就在里面），`current_host()` 一直返回 None，于是那一推推到了
空气上。**产品代码是对的，仪器没接上**——这正是记忆里"计数为 0 的读数要一根明知非 0 的
对照"那一族：正对照（`current_host() 认不认得这个宿主: True`）后来补在起手那一拍，探针注释
里也把这次误判留着了。

**② 一条空断言把变异放过去了**。"状态行不许写整条路径"这条最初写成
`assertNotIn("X:/", 文本)`：测试替身给的是 `X:/a.jpg`，而 `Path("X:/a.jpg").name` 在 Windows
上会被重写成反斜杠，**原样与变异后都不含 "X:/"**，断言永远绿。第一轮变异跑完它是绿的。
第二次修法（扫整页原文、找"数据目录"）在**没变异**时就红了——因为这一页的提示话本来就写着
"存进应用数据目录"。最终写法是**只扫 `_background_label.value` 这一处**，负向词用
"数据目录"/"backgrounds"。教训一句话：**负向断言的作用域必须是那一条控件自己的文本，
不能是整页原文；Windows 上的路径不能拿 "/" 当判据。**

**③ 两处注释差点写成没测过的断言**。我先后写过"实测可能……"和"半途改属性客户端不认"这类
措辞，都是**没量过**的说法。已经改成不宣称读数的写法，只在真量过的地方留数字（同第七十三轮
§8 那一条同族）。

本轮**一行产品代码都没改**（用户的话是"先量后改"）。产物是四份探针与它们的读数：
`.probe/census_portrait_widths75.py`（结构普查）、`.probe/probe_portrait_overflow75.py`
（桌面像素 + 客户端日志，窗宽走 argv：`... 360 780` 再跑一档）、
`.probe/measure_portrait_edges75.py`（拿截图做贴边筛选）、
`.probe/probe_font_page_stall75.py` + `.probe/probe_font_done_callback_deadlock75.py`
+ `.probe/time_font_scan75.py`（第 6 节那条死锁）。

## 1. 三个要回答的问题

"竖屏格式"这件事不能凭感觉改，先要量清楚：

1. **哪些页在窄窗里真的缺东西**——以及"结构普查"（比对 Python 对象上写死的 `width`）
   报出来的那些，能不能直接当真；
2. **有没有机器判据**——溢出这件事，屏幕上长什么样、客户端会不会自己说出来。如果都不说，
   那之后每一轮的竖屏验收就只能人眼，得把这条写死，别让人拿"探针全绿"当"没溢出"；
3. **逐页拍得到吗**——24 个目的地在竖窗里各拍一张，能不能跑完。

## 2. 结构普查：写死的宽度对账

24 个目的地**全部建得起来**（`建成 24，建不起来 0`）。为了让工厂无参也能建，探针自带的
最小服务表按类型**当场无参构造真服务**（不 `on_start`，内存缓存是空的），造不出来的
按"没注册"走视图自己的降级分支——普查要的是"页能不能建、建起来多宽"，不是替身替它把活干了。

| 可用宽 | 报出来的固定宽 offender |
| --- | --- |
| 360 | `reading.reader`：`Container width=760` + 一条不换行 `Row 合计=760`；`sources.repair`：`TextField width=520`；`tools.webdav`：`Dropdown width=380` |
| 420 | 同上，去掉 `tools.webdav` |
| 500 | 同上，去掉 `tools.webdav` |
| 600 | 只剩 `reading.reader` 那两处 |
| **1200（宽窗对照）** | **一条命中都没有** |

最后一行是这根普查的正对照：这些宽度不是本来就写错，是**竖屏才撞**。
`NARROW_WIDTH_THRESHOLD = 720`（`app/views/navigation.py:44`）以下走底部 `NavigationBar`，
内容区可用宽≈窗宽，所以 720 以下全都得重新对账。
普查自己的三条覆盖说明也照抄在这里：树只走常见槽位（清单是**下界**）、没扣 padding/滚动条
（判据偏宽松）、只有构造期写死的 `width` 算数（运行时按 `page.width` 重算的写法扫不到）。

## 3. 窗宽不是客户区宽，溢出在像素上长什么样

`page.window.width = 500` 拍回来 **484×961**，`= 360` 拍回来 **344×741**——差 16px 是窗口
边框。所有竖屏判据要按**截图宽**算，不能按设进去的窗宽算。

两拍对照（同一条不换行 `Row`，两块各 48px 高的色条，`spacing=0`）：

| 档 | 负对照 2×150=300 | 正对照 2×400=800 |
| --- | --- | --- |
| 窗宽 500（可用 484） | 红条右端 159、绿条右端 309（两块都看得见） | 红条右端 **409**、绿条右端 **483 = 最后一列** |
| 窗宽 360（可用 344） | 红条右端 159、绿条右端 309 | 红条右端 **343 = 最后一列**、绿条右端 **−1（整块在屏幕外）** |

也就是：**溢出的像素特征是"顶到最后一列，后面的兄弟整块消失"**，不是"内容画到 800px 处"。
两档四张图里"Flutter 调试溢出条纹那种黄"的采样像素数都是 **0**（release 构建没有条纹，
和上面这个形状是同一件事的两面）。

**客户端会不会自己说出来**：不会。做法是把本进程的 fd 1/2 在 `ft.run` **之前** `dup2`
到文件（`flet_desktop` 起客户端是 `subprocess.Popen(args, env=...)`，不传 stdout，
客户端继承的是**被 spawn 那一刻**的 fd——第一版把 `start_capture()` 写在 `walk()` 里，
日志永远 0 行，那读数是仪器没接上，不是客户端没说）。接上之后：

- 正对照 `subprocess.run([python, "-c", "print('PIPE-OK-75')"])` → **落进来了**（管子通的）；
- 明知溢出那一拍之后：`overflow` / `RenderFlex` / `EXCEPTION` 相关行 **一行都没有**；
- 整场日志总共 **1 行**，就是那根 `PIPE-OK-75`；`flutter:` 前缀 **0 行**。

**结论要写死**：桌面 release 客户端对布局溢出**没有任何机器可读的输出**，竖屏验收拿不到

## 6. 顺手抓到的：进字体页整个界面锁死（必现，不是竞态）

第一版竖屏探针按字母序拍到第 16 页就整条链停死，卡在 `tools.font`；把这一页挪到最后，
前面 23 页全拍上，仍然只有它拍不出来，而 25s 的 `asyncio.wait_for` **不生效**——这本身就是
读数：`wait_for` 靠界面循环还能转，循环转不动说明这段是**同步**压在循环上。
`Get-Process` 六秒内 CPU 累计时间一动不动（0.6875s 不变）= 干等，不是在转。

看门狗线程打出来的主线程栈（`.probe/out_font75_stack.txt`，两次 dump 一模一样）：

```
asyncio/futures.py:401 _call_set_state → concurrent set_result → _invoke_callbacks
  → app/controllers/base.py:246 (on_done.wrapper)
  → app/controllers/tools/font_controller.py:61   user=self._safe(user_future)
  → app/controllers/tools/font_controller.py:66   future.result()
  → concurrent/futures/_base.py:451 → threading.py:355 wait   ← 永久等
```

`FontController.load_fonts` 把 `scan_system_fonts()` 和 `list_user_fonts()` 两条协程都
`ui_call` 到**同一条界面循环**上，然后给第一条挂 done 回调，回调里同步 `.result()` 等第二条。
第一条先派发就先落值，回调必然跑在第二条之前 → **必现死锁**：`app/controllers/base.py:225`
的 docstring 早就写着"等待用 `wrap_future` 而不是 `future.result()`"，这条规矩在字体控制器上
被踩了。离线两臂钉死（`.probe/probe_font_done_callback_deadlock75.py`）：

- **基线臂**（两条派发照旧，回调只读自己那条 future）：心跳 1.5s 里 **47 拍**（间隔 0.02s，
  满拍），回调正常收到值 → harness 没写坏；
- **必现臂**（走真 `FontController.attach`）：12s 主线程没回来，栈顶就是上面那条链。
  设计时本想再留一条"用户字体那条先跑完"的对照臂，实测**不给延迟也照样锁死**，
  所以那条臂没有存在的必要——这条不是时序运气。

影响面：**任何窗宽**进"配置 → 更多工具 → 字体"都会把界面整个冻住，只能杀进程。
同族扫描：全库控制器里在 done 回调上 `.result()` 的写法共 30 处，其余 29 处等的都是
**回调自己那条** future（值已落，不等），跨 future 的只有 `font_controller.py:61` 这一处。

顺带否证一条我自己先写进探针注释的猜测："字体扫描是同步重活压在循环上"。离线单测
（`.probe/time_font_scan75.py`）：`C:\Windows\Fonts` **349 个文件**、解析出族名 **153 条**、
`scan_system_fonts()` 墙钟 **0.08s**、`iterdir` 0.001s、fontTools 打开单个字体 0.1ms。
0.08s 撑不起"整页停摆"，钱不在这条扫描上——写注释前先量，这条又救了一次。

# 第七十六轮 修：字体页那条死锁，和五处窄窗降级

用户的话是"处理A和B"：A = 004 待修清单第 16 条（进字体页整个界面锁死），
B = 第 15 条（四处窄窗布局降级）。两条都改完、都有机器判据，全库 1805 条通过。

## 1. A：两条读取合并成一条协程

`app/controllers/tools/font_controller.py:51` 起：`load_fonts` 只发**一次** `ui_call`，
两条列表在同一条协程里先后 `await`，到齐才 `_render`。没走"回调里改 `ui_await`/
`wrap_future`"那条备选：合并本来就少一次跨线程往返，也不会出现"半张表先落图"的中间态。
两条各兜各的异常，沿用改前 `_safe` 的口径（一次读取失败不该让整页空掉）。

判链拦了我一次：先写成 `await self._read(self._svc.scan_system_fonts(), ...)`，
`tests/test_controller_service_surface.py` 立刻报两条"协程必须 await 或交给 ui_call 派发"
——它只认服务调用的**紧邻父节点**是 `Await` 或派发器，套一层取值助手就不认。落回两处直接
`await` 的 `try/except`（`font_controller.py:72`、`:77`）。这条护栏拦的是我，不是产品代码。

## 2. A 的护栏：心跳断供当判据，以及仪器自己的两个坑

`tests/test_font_page_loop_liveness.py` 三条。判据钉的是**那条循环上有没有一拍断供**，
不是"这次调用返回了"；秒表在另一条线程拿着（`wait_for` 的超时自己就堵在循环上，
第七十五轮量过）。替身服务是 `FontService` 的子类，两次读取各要界面循环跳够拍才回——
"编排还在途"与"循环在跳"被绑成同一件事，判据就不依赖墙钟时长。

- `test_font_page_load_does_not_starve_the_ui_loop`：走真 `attach` 进页，
  `max_gap < 1.0s` 且两条列表都渲染、拍数够两次读取。
- `test_font_page_renders_both_lists_when_it_arrives`：渲染落的是两边的真内容。
- `test_the_instrument_does_read_a_frozen_loop`：对照臂就地重放当年那条写法
  （真 `on_done` 包装、真 `_render`、视图真接着），仪器必须读出 ≈2s 断供。

仪器自己栽过两次，都是本轮当场量出来的：

1. **两臂同速时死锁复现不出来**。第一次落值时第二条已经跑完，回调里 `.result()`
   当场拿到值。改前那一跑，两条正臂只红了一条（`renders_both` 红、`does_not_starve` 绿）
   ——绿灯的那条正是最该红的。→ 加 `USER_BEATS = 30`，让第二次读取慢一拍，
   也就是 004 记下的那条真形状（"第一条先派发就先落值，回调必然跑在第二条之前"）。
2. **`concurrent.futures.Future.add_done_callback` 在登记那一刻 future 已经算完时，
   当场在主线程调用回调**。那一臂冻住的是主线程，界面循环满拍，仪器读数 0.016s
   （20 次重跑撞见 2 次，是时序运气不是设计）。→ 两道闸门：`scan` 闸在登记回调之前
   一直关着（把"登记"钉在第一次读取算完之前），`user` 闸整臂不开（跨 future 等的那条
   永远落不了值）。改完 8 连跑 8/8 全绿。

变异核验：把 `load_fonts` 换回当年那条（两条 `ui_call` + 回调里 `.result()`），
3 次跑 3 次红——`does_not_starve` 必红，`renders_both` 3 次里红 2 次。

## 4. wrap×expand：本轮量到的一条客户端契约

第一版像素探针的截图整块是灰的（196,196,196）。原因不是探针写坏了，是
**`Row(wrap=True)` 里任何子项带 `expand`——连 `expand=False` 都算——release 客户端会把
整条行画成一块灰，并且不再产出后面的兄弟节点**。五臂对照钉死这条
（`.probe/probe_wrap_expand76.py`：`nowrap_plain` / `wrap_plain` / `wrap_expand_false` /
`wrap_expand_true` / `nowrap_expand_true`，只有中间两臂灰）。不换行的 Row + `expand`
是好的，且按 flex 分份——所以 `expand` 那几处改法都落在**不换行**的行上。

全库普查 `.probe/census_wrap_expand_clash76.py`：24 棵目的地树，建成 24、失败 0，
**命中 0 处**。盲区照实记：槽位表只覆盖常见容器（下界），运行时才改 `expand` 的写法扫不出来。
