# 第一百零七轮：打包版两处断线修复（assets 层级 + 数据目录契约）

触发：开发者实跑 dist 双击版截图——图标全方框、书源「共 0 条」、书架空。

## 两处根因（都实跑钉死）

### R1 图标全 tofu = flutter_assets 被拷到 dist 根目录（build_release.py）

Windows runner `main.cpp:20` 是 `flutter::DartProject project(L"data")`，资产只认
`<exe>/data/flutter_assets`。旧脚本 `build_release.py` 拷到 `dist/flutter_assets`（根目录）：

- AOT 在 `data/app.so` → 界面照常起；
- 文字走系统字体 fallback → 中文全正常；
- MaterialIcons 无处加载且无 fallback → **所有图标成方框**。

实跑对照：同一份产物把 `flutter_assets/` 移进 `data/` 后重启，图标全渲染
（截屏 `.probe/test_dist_ui.png`）。Flutter 原生输出目录
（`build/windows/x64/runner/Release/data/flutter_assets`）一直是对的——错只在打包脚本拷贝目标一格。

### R2 书源/书架全空 = Go 引擎默认数据目录没对齐 Python 契约

`register.go` 旧默认 `envOr("LEGADO_BOOKSOURCE_DATA_DIR", "./data")`——打包版双击时
CWD=exe 目录，于是在 dist 旁边新建**空库**。用户真库在
`%LOCALAPPDATA%/LegadoBookSourceCheck/legado.db`（Python `app/services/app_paths.py` 的既有契约）。
实读真库（只读 URI）：`book_sources` **917**、`bookshelf` **8**、`integrity_check` ok。

## 修复

- `build_release.py`：`assets_dst = dist_dir / "data" / "flutter_assets"`；关键文件校验清单
  从 2 项扩到 6 项（`data/app.so`、`data/icudtl.dat`、`data/flutter_assets/FontManifest.json`、
  `data/flutter_assets/fonts/MaterialIcons-Regular.otf` + 原两项 + 引擎 DLL）——这类错以后
  由 `[PASS]` 自己照出来。
- `register.go`：新增 `defaultDataDir()`，镜像 `app_paths.py` 三分支（Windows
  `%LOCALAPPDATA%/LegadoBookSourceCheck`、darwin Application Support、linux XDG）；env 覆盖照旧。
- `.probe/package_smoke.py`：新增第六格「assets 就位（data/flutter_assets/fonts）」。
- 新增 `.probe/win_run_probe.ps1`：起进程 → 等窗 → AttachThreadInput 强制前台（Win11 前台锁
  会让裸 SetForegroundWindow 静默失败，截到的会是别的窗口）→ CopyFromScreen 截屏 → stderr 落盘

# 第一百零九轮：书源页「共 0 条」根因链修复（接线退化同族一锅端）

## 根因链（四个断点，都在同一族「重构后接线退化」）

### R1 四个服务的启动加载从未运行（register.go）

`SourceService`/`ContentSearchService`/`ReplaceService`/`FontService` 的真实
`Start()`（`loadAllSources` / `ensureFTSTable` / `loadAllRules` / `loadAllFonts`）
挂在各自 base 的 onStart 上；但 register.go 注册进 hub 的是只有 base + stopFn
的 `bizSvc` 壳——壳的 base 不跑真身的加载，**书源缓存永远是空的**。
各服务单测直接注入缓存/存储，整条全链路只有种子测试能钉住。

修复：四处注册补 `onStart: func(ctx) { return svc.Start() }` 转发。

### R2 917 → 879：38 条书源被 canReName 类型不匹配丢弃

日志：`json: cannot unmarshal string into Go struct field BookInfoRule.Alias.ruleBookInfo.canReName of type bool`

`bool(str(rules.get("canReName") or "").strip())`（reading_engine.py:1383）。

修复：

  AddRule/UpdateRule/ToggleEnabled 写 updated_at；全局开关走 settings 键；
  ApplyRules 接 is_regex（false 走字面量替换）、scope=title 不参与正文。
- `font_service.go` 重写：模型 Name/Family/Path/Source；加载/新增/删除对齐

  ScanSystem 扩展名集扩到 ttf/otf/ttc/woff/woff2 + 平台目录三分支。

SettingsService 读全走内存缓存，只有 OnStart() 装 DB 全表；grep 零调用方

# 第一百一十一轮：阅读器目录 0 条根因链修复（盘上缓存 + 规则引擎三缺口）

触发：开发者实跑报「功能仍不完善，再排查一下」（截图：阅读器《我的功法无限提升》
「这本书没有目录，没有可读的章」、「目录（共 0 条）」）。

## 根因链（三处引擎断点 + 两类站侧/裁剪面）

### R1 Go 引擎不读 flet 时代落盘的 reader-cache

数据目录里躺着 Python 时代预渲染的 `<数据>/cache/reader-cache/`（catalog.json +
content/*.json，键公式 = sha256(source_url + "\0" + book_url) / sha256(chapter_url)），
Go 的 OpenByURL/TocByURL 全程联网鲜取；真源或改版或设门，鲜取必空——盘上现成的
2279 章就是读不出来。

修复：`core/storage.go` 加 `ReaderCacheDir`（沿用 `LEGADO_BOOKSOURCE_CACHE_DIR`
覆盖契约）；`internal/services/reading_service.go` 移植读盘（目录 catalog + 正文
loadDiskContent，命中回填内存缓存）与写盘（预取正文落盘）；`pkg/ffi/engine.go`
的 chapterRow 八键对齐、chapterWordCount 原文优先。

### R2 ruleparser 缺 Legado getResultLast 语义

`text.下一页@href` 命中的 html/body/a 里只有最后一个 <a> 有 href，旧代码只看
found[0]（html 的 href=""）→ 翻页地址全空。Java 参考（AnalyzeByJSoup.kt:229）：
属性尾段**逐个命中读、跳过缺失/空白、去重**；html/all 分支全部命中 "\n" 相拼、
@html 先摘 script/style。

修复：`pkg/ruleparser/parser.go` 的 `pick` → `pickLast`（+cleanHtml）。

### R3 GetBookInfo 把 `@js:` tocUrl 当选择器

lvsexs 的 ruleBookInfo.tocUrl = `@js:baseUrl.replace(/\/xs\/(\d+)\.html/, '/shu/$1/')`
（详情页 /xs/454135.html 上没有目录，目录在改写出的 /shu/454135/ 页上）。旧代码
把 `@js:` 送 CSS 选择器 → 抽空 → 回落详情页 → 目录 0 条。

修复两处：`internal/engine/rule_engine.go` 加 `fieldRaw` 统一字段口（JS 规则送
jsruntime、其余照走选择器；JS 出错回空——详情字段是"抽不到就回落"的语义）；
`pkg/jsruntime/runtime.go` 的 injectGlobals 补**裸全局 baseUrl**（对齐 Python
bootstrap `var baseUrl = context.base_url or bookSourceUrl`；只注入 java.baseUrl
时脚本炸 "baseUrl is not defined"），releaseVM 同步清理。

Go 写侧发的是新形状的语句（`core/settings.go:97` 三列 `INSERT OR REPLACE`、
`internal/services/source_service.go:352` `ON CONFLICT(url)`），而**读侧一个差异列都不碰**
（书源缓存整份从 `json` 列还原，设置只读 key/value）。所以界面看着全绿、917 条书源照列，
而每一次写都落不回东西——回包还是 `ok:true`。既有 Go 测试全绿是因为它们的库一律由
`NewStorageService` 现场新建，从没跑过"打开一个旧库"这条路。

### 修法（只做加法，一行不删、一表不重建）

`core/storage.go` 在 `ensureSchema` 尾部接两个迁移（`migrateToolsTables` 之后、尾索引之前）：

- `migrateLegacySettingsShape()`：`PRAGMA table_info(settings)` 没有 `updated_at` 才
  `ALTER TABLE settings ADD COLUMN updated_at INTEGER`。这一列没有任何读方，旧行留 NULL。
- `migrateLegacyBookSourceURL()`：`hasUniqueIndexOn("book_sources","url")` 为假时，先数
  重复 url；**有重复就停手**，只 log 一句「有 N 个 url 重复，没有替自动删行；书源写入会继续
  报 ON CONFLICT，请先在书源页删掉重复的那几条」并 return——自动删行是替用户决定丢哪一条，
  而建到一半失败会连带整个引擎起不来。没重复才 `CREATE UNIQUE INDEX idx_book_sources_url`。
- `hasUniqueIndexOn` 走 `PRAGMA index_list` + `PRAGMA index_info`：autoindex 那一行的
  `sql` 是 NULL，读 DDL 字符串会把"新形状已有内联 UNIQUE"误判成没有。

SQLite 语义当场实验过（`.probe` 会话内实测）：旧表上 `ON CONFLICT(url)` 编译期即报错，
补了唯一索引就通；`ALTER TABLE settings ADD COLUMN updated_at` 后三列 upsert 通。

### 顺带挖出的第二条分歧

唯一索引补上之后，`source_save` 换了一条错：`NOT NULL constraint failed: book_sources.group`。
旧表 `"group"` 是 `NOT NULL DEFAULT ''`，而 `models.BookSource.BookSourceGroup` 是 `*string`，
写侧原样递 nil ⇒ 驱动写**显式 NULL**（DEFAULT 只在省略列时生效）。Go 自建那张表这一列可空，
所以这个错只在旧库出现，且原先一直被前面那条编译期 ON CONFLICT 挡着（运行期错误轮不到）。
修法在写侧：`sourceGroupArg(src)` 把 nil 折成 `""`（`Save` 与 `upsertSourceTx` 两处），
理由是这一列没有任何读方，落 `""` 与旧库 917 行的写法一致。
带分组的源单独钉了一条用例，防它退化成"永远写空分组"。
