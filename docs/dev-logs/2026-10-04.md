# 第七十二轮 读屏壳与它包的那只控件必须同进同退

## 1. 现场：全库只有一只壳，芯是藏着的

用户报的这句原文在 **flet 客户端**里（`flet_web/web/main.dart.js` 常量表，与
`SelectionArea.content must be provided and visible`、`Dismissible.content must be visible`、
`Banner.content …` 同一族），意思是：`Semantics` 这个壳要求它的 `content` **既给了、又可见**。

第七十一轮给手填正文页地址那只 `TextField` 外面套了 `ft.Semantics`，而那只框的起手是
藏着的（只在"本地没有可读目录"时才亮出来）。壳没跟着设初值，于是这一页从第一次建树起
就是**壳亮、芯藏**：

```
修前  起手 _manual.visible=False  _manual_sem.visible=True    ← 违反客户端的要求
修后  起手 _manual.visible=False  _manual_sem.visible=False   ← 一起藏，要亮一起亮
```

（这两行是当场构造一只 `RuleRepairView` 打印出来的读数，不是推断。）

`app/views/source/rule_repair_view.py` 只改一处：给 `_manual_sem` 的构造补上 `visible=False`，
并在旁边写清为什么。`set_manual_visible()` 本来就是两条一起写的，所以运行时切换一直是对的，
**错的只有起手那一拍**——这类"只有初值错"的缺陷最省事的上法是把初值也交给同一个写入口，
本轮没那么大动干戈，只在构造处钉住并加护栏。

## 2. 为什么第七十一轮的浏览器探针没抓到

`.probe/probe_repair_manual_a11y.py:197` 在 `main()` 里**先调了** `view.set_manual_visible(True)`
才 `page.update()`。这一句替被测对象做了生产不会做的一步：客户端从来没见过"壳亮着、框藏着"
这一对。探针的三拍读数全绿，第二天用户一进来就红。

这是"探针替被测对象补了一脚"的又一个形状（前一例：把控件树拍平却漏了 `ListTile.title`）。
教训一句话：**起手那一拍必须是原样的**，要验"亮出来之后长什么样"就再跑一拍，别在挂上页之前
替它把状态推好。

## 3. 正对照没响 —— 机制只在桌面上成立，本轮没能离线复现（诚实条目）

新探针 `.probe/probe_repair_mount_no_semantics_error.py`（两条臂，各起一个进程）：

| 臂 | 起手形状 | 页面起没起来 | 控制台里那句 Semantics |
| --- | --- | --- | --- |
| 默认（修后） | 壳藏、芯藏 | ✅ 「开始诊断」在树里，语义节点 11 个 | ✅ 没有 |
| `--broken`（正对照） | 把壳拨回 `visible=True`、芯仍藏 | ✅ 页面照常起来 | ✅ **也没有** |

修后那一臂证明这一页原样起手是好的。但正对照**没响**：web 客户端这一版并没有把这条断言
送到 `console` / `pageerror`，所以"壳亮芯藏 ⇒ 这句报错"的**触发条件我没有在离线面上量到**，
桌面 `FLET_APP` 那条路这一轮没跑（窗口截不了图，见 `docs/dev-logs/2026-09-26.md`
记过的取证套路与 `.probe/` 里那几支探针）。

因此本轮的定性是：**修的是"违反了 flet 客户端自己写明的要求"这一形状**（错误文本 + 全库
唯一一处这种配对 + 修后原样起手页面正常），而不是"复现失败再修好"。要是用户手上有报错现场的
截图/日志（哪一刻出现的：刚进页 / 点「自愈」进来 / 亮出手填框之后），能把这条从"形状对得上"
钉成"机制已量"。

探针自己的另一条坑记在 004：浏览器线程**不能**在 `main()` 里起——`main()` 只有等客户端连上来
才被调用，而客户端要有人导航才会连，于是第一跑死锁、零输出、`timeout` 退 124。

# 第七十三轮 老板键要的是"从桌面上消失"，不是"缩到任务栏角上"

> 需求是两句一起提的：「为项目添加老板键功能和背景图片替换能力」，以及
> 「我打开软件没有在好到对应按键设置的位置。另外阅读页面中也需要可以设置翻页/上下一章的
> 快捷键」。**本轮只做老板键 + 快捷键页**；背景图（用户同一条需求里的另一半）落在下一轮。
> 裁决过的形状：老板键要**最小化到系统托盘，而不是任务栏**；快捷键设置放**设置分组里新加
> 一个「快捷键」页签**；录键方式**按一下就能录**；验收**拆两条**（服务面 / 界面+文档）。

## 1. 取证：flet 三条窗口开关里只有 `visible` 真把任务栏那格摘掉

`.probe/probe_bosskey_window_shape.py`（桌面 `FLET_APP` 真开一只窗，反复藏/显/最小化，
读数一律走 ctypes：`EnumWindows` + `IsWindowVisible` / `IsIconic` / `GetWindowLongW`，
不靠肉眼）。当场读数：

| 动作 | 桌面可见 | `IsIconic` | `WS_VISIBLE` | `TOOLWINDOW`/`APPWINDOW` |
| --- | --- | --- | --- | --- |
| 基线 | True | False | True | False / False |
| `visible=False` | **False** | False | **False** | False / False |
| `visible=True` | True | False | True | False / False |
| `minimized=True` | **True** | True | True | False / False |
| `skip_task_bar=True` | True | False | True | **False / False** |

三条结论：① `visible` 是唯一能让窗口从桌面上消失的开关，且原样回得来；② `minimized`
只是 `IsIconic` 转真，**窗口还在任务栏**，老板键要的那件事（看起来这台机器上没在开小差）
一件都没做成；③ `skip_task_bar` 在这套客户端上**样式位一位没动**，不能拿它当"从任务栏
摘掉"——这条路直接排除，别再试第二次。

顺带量到两条 flet 0.86 的面：`Window.center()` / `to_front()` 是**协程**，裸调用当场就
打 `RuntimeWarning: coroutine ... was never awaited`（那一版日志里有四条），窗口一动没动。

## 2. 托盘：不新增运行期依赖，但两条 API 读法都会骗人

pywin32 已在环境里（`pyttsx3` 在 Windows 就靠它），`win32gui.Shell_NotifyIcon` 可用，
所以托盘这条路不需要引 `pystray` 之类的新依赖。三条实测过的坑：

- **成功返回 `None`**：第一版探针写 `add_ok = bool(Shell_NotifyIcon(NIM_ADD, …))`，
  读出 `add_ok = False`，差点判成"这条路走不通"。改成"没抛异常 + 之后消息环收得到
  自己 `PostMessage` 的那条 `WM_APP+7`"才算挂上（对照臂：`hWnd=0` 的畸形结构**会**报错，
  所以"不报错"这一条不是空判）。
- `NIM_ADD` / `NIF_MESSAGE` 这些常量在 **`win32gui`** 上，不在 `win32con`——按后者的
  名字写，当场 `AttributeError: module 'win32con' has no attribute 'NIM_ADD'`。
- `NOTIFYICONDATA` 唯一实测可用的写法是**六元组** `(hwnd, uID, uFlags, uCallbackMessage,
  hIcon, szTip)`；十元组把尾部的 int 当字符串要（`TypeError`），`NIM_SETVERSION` 在
  pywin32 里签名不对（同样 `TypeError`）。

消息环的停法也量过：直接 join 一条正在 `PumpMessages()` 的线程关不掉，必须从别的线程
`PostMessage(WM_CLOSE)` → `DestroyWindow` → `WM_DESTROY` → `PostQuitMessage` → 线程返回。

## 3. 服务面：图标与窗口之间的顺序是硬约束

`services/tools/boss_key_service.py`：

```
hide()     先 tray.start() 挂图标 → 挂不上就**什么都不做**（并把原因写进 error）
           → 才 window.visible = False
restore()  先 window.visible = True + to_front() → 才 tray.stop() 摘图标
```

为什么这么排：窗口消失而没有任何入口，用户只会以为程序崩了直接强杀，读过的进度全丢——
比功能没做成严重得多。反过来先摘图标，图标比窗口先没，用户同样以为程序消失。
`WinTray` 的图标**只在藏窗期间存在**，恢复那一刻删图标、收线程，进程里不留后台线程。

托盘回调**跑在托盘线程上**，控件只认界面循环（项目硬约束），所以 `_on_tray_activate`
经 `_run_on_ui` 用 `run_coroutine_threadsafe` 编回 `ui_loop()`；没登记界面循环（无头测试）
才就地执行。服务层零 flet：page 由装配根 `set_page_provider(lambda: page)` 注入，
和内置浏览器同一套写法。

## 4. 界面面：八个动作一张表，按一下就能录

「配置 → 快捷键」页签（`settings.shortcuts`，`views/settings/shortcut_view.py` +
`controllers/settings/shortcut_controller.py`）。这轮真正花时间的地方是**键表必须两边共用**：

- 阅读器的键表原先只住在 `reader_controller` 里，界面没有任何地方能改它（用户报的
  就是这句"没找到按键设置的位置"）。要做能录键的页，规范化与显示就得抽到
  `app/core/shortcuts.py`（零 flet 纯函数），两边各写一张表的话，页面显示 `PageDown`、
  比较用 `pagedown`，**用户录进去的键位永远不会命中**。
- 存量分两处：七个阅读动作在 `reader.shortcuts`（字典），老板键在 `bosskey.enabled` /
  `bosskey.shortcut`（两条标量）。界面一张表、落库两处 → `_save()` 分别写，
  任何一处失败都要写在状态行上，不许只记日志。
- 撞键**不拦保存**（Legado 也不拦），但分发是"表内第一个命中"，所以提示语必须说清
  "按下去只有排前面的会动"。
- `chord_of` 在无修饰键时给出的正是 `left` / `pagedown` 这种裸串，所以**历史偏好不用迁移**。
- 录键不开新口子：视图把 `on_key` 槽交给控制器，走的就是导航层已有的
  `current_view().on_key` 分发；只认"正在录的那个动作"，其余按键一律不看。

接线两处都在装配根（红线 §7.5：视图层拿不到服务）——`build_app_shell(page, hub,
shelf_probe=..., key_filter=...)` 是这两条缝，`key_filter` 挂在 `page.on_keyboard_event`
的**最前面**：命中老板键那一拍必须吃掉，既藏窗又翻页是灾难。导航因此涨到
**24 个目的地 = 12 页签 + 12 整页**，服务数从 26 涨到 **27 个业务服务**。

## 5. 桌面真类探针：整链量到最后一寸，剩一腿交给人

`.probe/probe_bosskey_roundtrip73.py`（用**真** `BossKeyService` + **真** `WinTray` +
真窗口；`--human` 才加 12 秒人工点击口，`--keys` 再真按三次组合键）。当场读数
（`.probe/out_bosskey73_keys8.txt`，是修完 §6 那条竞态之后重跑的那一份）：

```
托盘能力 = True
真按 Ctrl+Alt+H：注入 6/6 条；落主键那一刻 OS 键盘状态 ctrl=1 alt=1 shift=0
  → flet 自己造的事件 key='H' ctrl=True alt=True shift=False meta=False → chord='ctrl+alt+h'
  → 真键藏起来等了(秒) = 0.0
handle_key 说这一拍被吃掉 = True      service.error = ''
藏起来等了(秒) = 0.047                藏窗后 桌面可见=False WS_VISIBLE=False
托盘消息窗口 = 131596998
对照臂（发 WM_MOUSEMOVE 后）桌面可见 = False   service.hidden = True   ← 悬停不该回来，挡住了
注入 WM_LBUTTONUP → 回来等了(秒) = 0.062       回窗后 桌面可见=True    service.hidden = False
第二轮：藏 0.063 → 新托盘消息窗口 131662534 → 回来 0.156，上一只托盘线程已退出 = True
真键盘第二次（从托盘回来之后再真按一把）：注入 6/6 → 'H'/ctrl=True/alt=True→'ctrl+alt+h'
  → 桌面可见=False / hidden=True / window.focused=True            ← 不是只能用一次
收尾：托盘消息窗口 0 / 桌面可见 True / 还活着的托盘线程 [] / never-awaited 一类告警 = '没有'
人手点图标 = 未证（没带 --human）
```

**真键盘这一腿之前是空的**：单测里的事件对象全是手拼的 `key="h", ctrl=True`，真客户端
写 `"h"` 还是 `"KeyH"`、修饰键落不落在 `ctrl/alt` 上，一支探针都没量过——而键位表认错
一个拼法，用户看到的就是"录得上、按不动"。现在量到了：`key` 是**大写** `'H'`
（`normalize_key` 折成小写才碰得上 `ctrl+alt+h`），`ctrl/alt` 是真布尔，
组合键在真键盘上按得动，而且**从托盘回来之后还按得动**。

第一版注入把 down×3 + up×3 塞进**同一次** `SendInput`，读回来是"6 条只到 1 个事件、
`ctrl/alt` 全 False"，差点判成"这套客户端根本不写修饰键，默认老板键是死的"。那是仪器自造的：
一批里 Ctrl 的 down 和 up 挨着落地，Dart 读键盘状态时早抬完了。改成**一次一键、中间隔 60ms**，
并把落主键那一刻的 `GetAsyncKeyState` 一起量出来（`ctrl=1 alt=1`）——两边对得上，这条线才算接上。

**两把只按裸键的对照臂（H / Ctrl+F）读数都是"没有事件"，这一条不算证据**：它们那两拍没有
重新抢焦点，而同一条注入路径、带 `_focus_ours()` 的"真键盘第二次"收到了事件。计数为 0 的
读数必须配一根明知非 0 的对照，否则"没收到"分不清是功能断了还是探针没接上。

**没证的那条腿仍然写着**：仪器只能把消息塞进托盘回调，证不了"图标真出现在通知区里、
且点得动"。这一条要么用户自己点一次，要么带 `--human` 跑一支探针，本轮两条都没做，
所以它记在 004 待修清单 12，不写成"已验证"。

探针自己的三条坑（前两条已进 004 探针/工具坑）：
① `os._exit(0)` 只杀 Python 这一侧，它 spawn 的 `flet.exe` 窗口还活着 → 第二跑按标题
`EnumWindows` 量到**两只**同名窗口，延迟全是 `nan`，看着像"这套 API 不可信"，实际是上一轮
的遗骸。修法三条一起：标题带 PID、基线**严格要求只有一只可见窗口**（不满足就宣布仪器没接上）、
收尾先 `await page.window.close()` 再退。
② 收尾那句 `window.close()` 本身在所有读数之后抛 `RuntimeError: Session closed`——
无害，但别把它读成功能失败。
③ 重定向输出不带 `PYTHONIOENCODING=utf-8` 会按 GBK 落盘，中文读数整份乱码（`keys4` 那一份
就是靠 `GetAsyncKeyState` 那几段 ASCII 读出来的）。老坑重踩，写进跑法那行了。

## 6. 连按两下：晚到的 toFront 把刚藏好的窗口又叫回来

`restore()` 里那条 `to_front()` 是**发给客户端的一条独立消息**，客户端把 ShowWindow 做在
**收到之后**。探针把"回窗到再藏"的间隔当变量量（0.3 / 1.6 / 0.3 / **0.0** / **0.0** 五轮，
每轮一条 0.9 秒、50ms 一采的 win32 可见性时间线，`out_bosskey73_keys6.txt`）：

```
隔 0.3s 两轮：0.0亮 0.06藏 0.12藏 …（一路藏到底）
隔 1.6s 一轮：同上
隔 0.0s 两轮：0.0亮 0.05藏 0.11藏 0.16亮 0.22亮 …（一路亮，而 hidden 仍是 True）   2/2 复现
```

也就是**"点完图标立刻再按一次老板键"这一拍会卡住**：窗口亮在桌面上，标志却说藏着，
于是 `handle_key` 之后每一拍都因为 `self._hidden` 直接 return——键盘再按没反应，
只剩托盘图标能回来。间隔 ≥0.3s 一轮都不复现。

**第一版修法没修掉**（记下来，因为它看着最像对的）：在 `to_front()` 的 done 回调里
"以标志为准补一次藏"。带它重跑（`out_bosskey73_keys7.txt`），0 秒那两轮照样 0.23 起一路亮、
0.09 起一路亮——那条协程在**消息发出去**时就算完成了，补的藏排在真 ShowWindow **之前**，
客户端照样把窗口叫亮。谁后落地在 Python 这一侧根本看不见，所以不该赌顺序，而该**不发**：
改成 `_front_later()` 先等 `_FRONT_DELAY = 0.3` 秒（量到那次 ShowWindow 落在发出后
0.09 ~ 0.23 秒），到点时标志还说藏着就**根本不发**这条 toFront。

## 8. 一条差点由我写出来的假话（诚实条目）

写文档时我认定 `0x0205` 是中键抬起、右键抬起应该是 `0x0204`，于是把
`_ACTIVATE_MESSAGES` 改了一版并把注释一起改了。改完觉得不对，当场对 `win32con`：

```
WM_LBUTTONDOWN 0x201  WM_LBUTTONUP 0x202  WM_LBUTTONDBLCLK 0x203
WM_RBUTTONDOWN 0x204  WM_RBUTTONUP 0x205  WM_MBUTTONUP 0x208  WM_MOUSEMOVE 0x200
```

**原写法是对的**，是我记错了——已经改回去，注释只保留当场量到的名字。同一条错误我还写进了
004 待修清单 12（"只在 0x0201/0x0202/0x0203/0x0200 上响应"），一并改掉。
教训一句话：**常量表不凭记忆写，要么当场 `getattr` 打出来，要么别写。**
顺带把这一族真正的边界钉进注释：`0x0200`（悬停）**故意不响应**，因为有对照臂实测
——注入它时窗口确实没回来。
