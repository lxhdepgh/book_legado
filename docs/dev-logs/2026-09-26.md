## 本次完成

### 1. 阅读器目录页不再和正文叠在一起（用户点名）

现象：阅读时点「目录」，章节列表像是"盖在正文上"，两层同时看得见。

根因不是显隐逻辑：`ReaderView` 用 `ft.Stack` 把目录页（`_detail_page`）叠在正文页之上，
而那一页是个**没有底色的 `Column`**——Flutter 里透明覆盖层不会挡住身后任何东西，
于是正文从章节列表背后直接透出来。同视图的左抽屉 `_side_host` 和漫画阅读器的目录层
都规规矩矩设了 `ft.Colors.SURFACE`，只有这一层漏了。

修：`_detail_page` 改成 `ft.Container(bgcolor=ft.Colors.SURFACE, content=Column(...))`。
中途踩了一脚：**0.86 的 `ft.Column` 没有 `bgcolor` 参数**（直接 `TypeError`，
底色只在 `Container` 上有），静态"能不能构造"的冒烟测试当场就把这个错暴露出来了。

### 2. 关闭时的「服务 EngineHub 停止异常」（用户点名，附 traceback）

表层原因：`ServiceHub.shutdown()` 把 `stop_all()` 协程 submit 到 EngineHub 自己的守护
loop 上跑，而 EngineHub 也是注册服务（基础设施 4 个之一），逆序停止轮到它时
`on_stop() → shutdown() → thread.join()` join 的正是当前线程 →
`RuntimeError: cannot join current thread`，被基类 `stop()` 的兜底记成那条 traceback。

修：loop 的收尾（`call_soon_threadsafe(loop.stop)` + `join`）挪到 `ServiceHub.shutdown()`
的 `finally`，由主线程在 `stop_all` 跑完后做；`EngineHub.on_stop()` 不再拆自己的 loop；
`EngineHub.shutdown()` 加"不 join 自己所在线程"的守卫（仪表盘对 EngineHub 那一行点
「停止」走的是同一条路）。`ServiceHub.shutdown()` 另加"已 DISPOSED 直接返回"，
二次调用不再抛穿。

**顺出根因 A：两个服务从来没被停掉过。** 改完 loop 收尾后，退出仍留两行 RUNNING
（`ReadAloudService` / `MediaPlayService`）。查下来是**业务方法盖掉了基类生命周期方法**：
`ReadAloudService.stop()` 是"停止朗读"、`MediaPlayService.stop()/resume()` 是
"停止/继续播放"，把 `Service.stop()/resume()` 整块替换掉了——hub 逆序停止轮到它们时
只停播放、不迁移状态，`stop_all` 的 28/30 次调用里少了这两个；仪表盘上对它们点「恢复」
也只是继续播放，状态机纹丝不动。改名让开保留名：`stop_speaking()` /
`stop_playback()` / `resume_playback()`（后端 `TtsBackend.stop()` 不是 Service 子类，不受限）。
全库 30 个 Service 子类扫过，覆盖生命周期名的只剩零个，并加了静态护栏测试钉住这条。

**顺出根因 B：一解封就死锁。** 这两个服务真被停止之后，退出反而**卡住**：
`faulthandler` 打栈看到引擎循环停在
`read_aloud.py on_stop → comtypes/client/_events.py:107 __del__`。
pyttsx3 在 Windows 上是 COM(SAPI) 对象，最后一个引用在哪个线程被丢掉，
comtypes 的 `__del__` 就在那个线程同步等它自己那条 COM 线程——`self._backends.clear()`
写在 `on_stop` 里，等于把整条 EngineHub loop 冻死（连 `asyncio.wait_for` 的超时回调
都跑不到），`stop_all` 撞到 10s 超时，后面所有服务全停不掉。
修：`on_stop` 把后端字典摘下来交给一次性守护线程去释放，退出不等它（进程随即回收）。
这个死锁此前一直被"方法被盖掉、on_stop 根本没跑"掩盖着。

## 第三轮：章节预取恢复 + 滚动协程下发（同日）

### 1. 章尾不再现取下一章（原 遗留 7）

预取**搬到了服务层**：旧实现把 `_chapter_cache` 挂在 `ReadingView` 上，重构后视图不归
自己管缓存了，放在控制器又会随 detach 一起没。现在每挂出一章，
`ReaderController._run_chapter` 收尾时 `ui_call(self._reading.prefetch_chapters(raw))`
起**一轮**顺序预取（后面 `PREFETCH_CHAPTER_COUNT=10` 章，跳过卷名与空 url 项），
`load_content` 的取用顺序变成**预取副本 > 磁盘缓存（追加路径不读它）> 联网**。

四条不变式（设计 §5.5）：
- **在途合并 + `asyncio.shield`**：`_content_flight` 让"读者真翻到这一章"和后台预取共用
  同一趟请求；等待方被取消（换章/切页）不能把另一趟正在等的请求一起带走。
- **64MB 内存预算**：`_remember_document` 超预算只是这次不留副本，落盘缓存照写，等于
  退回旧行为，绝不会因为预算把内容丢掉。
- **失败即收轮**：预取撞墙直接 `return` 而不是跳过继续——源连不通时后面九次只会连着
  撞墙，还把读者那一章的请求挤到后面排队；真翻到这一章时照常重新请求。
- **作废有四处**（2026-09-27 按调用点复测，原记"三处"漏了重新起轮）：换书
  （`_reset_for_new_book`）/ 关会话（`on_stop`）/ `stop_prefetch()`（阅读器 detach 时调，
  副本留着，回来还能接上）/ `prefetch_chapters()` 自己开头先停旧轮（`reading_service.py`
  :296 / :491 / :529 / :556 四个调用点，定义在 :531）。`_cancel_prefetch` 要能跨 loop 取消
  （控制器在界面循环、任务在 EngineHub 循环），且 loop 已关时静默作废。

### 2. `scroll_to` 协程从没跑起来（用户附 RuntimeWarning）

`ReaderView.restore_scroll` / `scroll_by` 写成 `self._reader_scroll.scroll_to(...)`
就丢——0.86 的 `ScrollableControl.scroll_to` 是**协程**，于是续读定位与翻页滚动纹丝不动，
控制台满是 `coroutine was never awaited`。

修的时候发现**第二层坑**：直接 `page.run_task(coroutine)` 也不行——`Page.run_task`
**只收协程函数**，收到协程对象抛 `TypeError: handler must be a coroutine function`，
症状和没修一样（静默不滚）。现在两个方法把协程交给 `ReaderView._run`，由模块级
`_await_coroutine` 包一层再 `run_task`；`_run` 取不到页面时把协程 `close()`
（`Control.page` 未挂载时抛的是 `RuntimeError`，`getattr(x, "page", None)` 挡不住）。
内嵌音频卡片的播放/暂停按钮顺手统一成同样的下发姿势。

## 第四轮：外观页灰色预览 + 主题切换毫无反应（同日）

### 1. 根因：主题只下发了三件套里的一件

`AppearanceView.apply_preview` 只写 `page.theme`，`theme_mode` 留在 Flet 默认的
`SYSTEM`，`dark_theme` 从来没被赋值过。而 0.86 的 `page.theme` **只在亮面模式下生效**：
深色桌面上客户端用的是 `dark_theme`（=Flet 默认灰），于是换皮肤、切深色、开墨水屏
**一个都不动**，整页停在默认灰——用户侧就是"主题切换没用 + 一片灰"。
旧单体 `ThemeService.apply(page, settings)` 是完整的三件套下发（`theme` + `dark_theme` +
`theme_mode`，墨水屏两面共用一套并强制 LIGHT），重构把服务改成"只给纯数据"时，
这半边落点整个丢了。

补回：视图层新增 `build_theme(palette, eink)` + `apply_page_theme(page, data)`
（`app/views/settings/appearance_view.py`），带 `use_material3 / scaffold_bgcolor /
card_bgcolor / divider_color / visual_density`——少了 `scaffold_bgcolor` 时窗口底色仍由
默认主题给，换皮肤只改到按钮。设计见 §5.7。

### 2. 预览区那一片灰：wrap Row 里塞了 expand 子控件

预览是三块手写 `bgcolor` 的色板 `ft.Container(height=56, expand=True)`，摆在
`ft.Row(wrap=True)` 里——**wrap 与 expand 互斥**（本项目已知 Flet 陷阱，导入页踩过一次），
整行渲染成灰色区域，而且色板只涂三块底色，看不出"控件会怎么变"。
改成旧页那种**真控件样本**（FilledButton / OutlinedButton / Chip / TextField / Divider），
配色全部来自已下发的主题，预览即所见。

### 3. 顺带补的两处断链

- **启动不应用已保存外观**：`page.theme` 只在外观页预览时设过，重启后不进那一页就
  永远是默认灰。`main.py` 新增 `_apply_saved_theme(page, hub)`，在 `build_app_shell`
  之前把服务数据交给视图层下发（装配根桥接，视图仍零 import 服务）。
- **预览失败只写日志**：`AppearanceController.preview()` 的 `except` 只 `logger.warning`，
  等于"点了没反应"。现在同时 `set_status(..., error=True)` 写在状态行上。

  "wrap Row 里不许有 expand 子控件"、控制器 pending→预览不写库/失败上状态行、启动引导）。

## 第五轮：阅读入口落地书架 + 检测跨页续跑（同日）

用户两条，一条是布局取向、一条是"是不是前后端拆分没拆干净"的疑问：

> 1. 阅读进入时，应优先书架，除非书架没有书籍，才进入找书。
> 2. 检测开始后，如果切换到其他页面自动停止了吗？切回来时就没有检测进度了。
>    不是已经拆分了前后端？

### 0. 先回答第 2 条的疑问：检测没被切页停掉

流水线跑在 EngineHub 的专属循环上，切页只是把**渲染**断了：离开「书源」分组时
`BaseController.detach` 退了 `CheckFinishedEvent` 订阅，那期间服务照常逐源发事件，
没人接就永久丢了；回到检测页挂上的是**全新视图**，手上没有任何状态可画，看起来
就像整轮检测白跑。前后端拆分本身是成立的（事件总线 + 引擎循环都没被切页影响），
缺的是"可回放的这一轮"。

### 1. 阅读入口：架上有书先落书架

- `NavigationHost` 新增 `shelf_probe` 注入点（构造参数 + `build_app_shell` 透传），
  `_anchor(group)` 的落地次序改为：**记住的页签 > 书架探测 > 分组第一个页签**。
  只对同时声明了「找书 + 书架」的阅读组生效，其它分组行为不变。
- 探测走 `main._shelf_has_books(hub)` → `SourceService.shelved_books()`（同步读
  `on_start` 已载入的内存缓存，不联网、不查库，所以能在装配首屏的同步路径上用）；
  探测抛错只记一条 warning 并回落找书。视图层仍然零 `app.services.*` import——
  红线没动，探测由装配根（`main.py`）提供。

### 2. 检测跨页续跑：服务留一份本轮快照，控制器 attach 时回放

- `SourceCheckService` 为每轮批量检测维护回放快照
  `_run = {"total","running","cancelled","summary","results":[逐源]}`：
  `_begin_run` / `_end_run` 在引擎循环上开合，`_publish_finished(result, run)`
  在发事件的同一条路上把逐源结果记进 `run["results"]`，
  `check_all` 收尾把 `summary` 写进同一份快照。
- 新增两个协程入口：`run_snapshot()`（当前/最近一轮的快照，**必须是协程**——
  经 EngineProxy 跳回引擎循环读，界面线程直读会拿到流水线改到一半的撕裂进度）、
  `await_run_finished()`（挂在 `_run_done` 事件上等本轮收尾，没有在跑就立即返回）。
- `check_all` 在已有批量在跑时不再派第二遍全量联网，改为接到那一轮的收尾上
  （`await_run_finished` 拿 summary）。`cancel()` 只撤在跑任务，仍绝不碰服务生命周期。
- `CheckController.on_attach` 现在会 `ui_call(self._restore())`：回放快照的逐源结果 +
  进度 + 运行态；若这一轮不是本页签启动的（`running` 仍为真），继续 `await_run_finished`
  等收尾再画结论。切页期间完成的那几源靠快照补回，事件本身不再需要重放。
- **探针抓出来的真 bug（第一轮全绿时没发现）**：attach 排的回放晚于用户点「开始」，
  那一刻 `_restore` 拿旧快照（甚至空快照）一画，`set_running(False, …)` 把刚开始的
  运行态盖了回去——开始按钮又变可点，看着像检测没启动。`_restore` 现在有两道闸：
  本视图已派了本轮（`self._running`）就直接放弃回放；快照"从没检测过"
  （非运行 + 无结果 + 无 summary）也不画，保住初始的「尚未检测」。

## 第七轮：四条"只有服务面"的能力接出界面（本地书 / 网络桥 / RSS / 听书）

用户指令是"持续运行直到功能完善"，范围就定在 遗留 2 与 遗留 10 点名的那四条：能力

### 1. 本地书：重开链路 + 书架导入入口

- **重开必炸在"书源查不到"**：本地书没有规则源，`SourceService.load_source` 返回

  `reading_service.py:66` 的**模块级函数**、:350 处调用，不是 `ReadingService` 的方法）：
  `localsource://` 伪源
  或 `file://` 书地址时造一个只带 `bookSourceUrl` 的合成源对象，reader-cache 的目录/
  正文键（导入时用的正是 `LOCAL_BOOK_SOURCE_URL`）这才命得中。缓存真的丢了
  （`LocalBookCacheMissing`）由 `ReaderController.open_book` 那条 `except` 接住并把话
  说出来——这条一定要接：调用方是 `ui_call` 投递的，没人 await 那个 future，漏出去

- **书架工具栏加「导入本地书籍」**：`LocalBookService` 内已入架，控制器只补刷新与反馈。

### 2. 网络桥：设置页与开关

### 3. RSS：阅读组第三个页签「订阅」

`RssView` 三栏（源 / 文章 / 正文）+ `RssController`。四条判定值得记：

- **刷新进度走事件**：`RssRefreshProgressEvent` 与 `RssRefreshedEvent` 分两个——前者

### 4. 听书：阅读器底部的朗读播放条

`ReadAloudService`（M4）三后端 + 状态事件早就齐了，缺的是整条承接面。新增
`views/reading/read_aloud_bar.py`（播放/停止 + 当前章 + 语速档位 + 连读下一章），挂在正文
与状态栏之间，由 `ReaderController` 编排：

- **粒度是章**：系统 TTS 后端不上报位置（事件 `position` 恒 0），所以没有进度条也不做
  逐句高亮，只说"正在念哪一章"。想再细就得换后端，不是界面能补的。
- **朗读稿在正文挂出来时顺手留一份**：`_run_chapter` 已经把正文切好段了，
  `_spoken_text` 去掉段首缩进的全角空格（不然每段先喘一口）存进单槽缓存；换书
  （`_set_chapters`）一起清。
- **循环里必须自己 flush**：一章能念十几分钟，而 `ui_call` 只在协程收尾 flush 一次，
  不就地补这一下，连读时播放条永远停在第一章。
- **停用换号（`_tts_generation`）而不是取消任务**：再按一次、手动翻章、跳书签/跳搜索
  命中、切页离开四条路径都换号 + 叫停后端，在途循环回到检查点自己收工。
- **状态事件按"当前书 + 当前章"过滤**：连读翻下一章时上一章的 `idle` 可能后到，照单
  渲染会让播放条在两种态之间来回跳。（本条是新增用例第一次跑就抓出来的：
  `int(event.chapter or -1)` 把章号 0 变成 -1，第一章的合法事件反而全被当过期丢了。）
- **有意偏离设计 §1.1**：文档设想"全局覆盖层，切页继续念"。阅读器是整页视图、切页即
  `detach()`，声音继续放着却没地方按停比安静更糟，所以 `on_detach` 叫停。全局形态要
  真做得等播放条挂到 `NavigationHost` 之上，本轮没做。
- 服务缺席（替身装配、精简启动）时整条播放条不出现，走 `_safe_service`。
- **语速档位就在播放条上**：`RATE_PRESETS`（慢 140 / 正常 185 / 快 240 / 很快 300，
  pyttsx3 的词/分钟）→ 选档经 `set_read_aloud_rate` 落 `reader.tts_rate`（与快捷键同类，
  是"进程级读一次"的偏好，不参与重排），朗读时 `_read_aloud_opts` 把档位换成绝对值塞进
  `opts["rate"]`。
- **念的时候标签上写着是谁在念**（`active_backend.name` → 「系统 TTS / edge 语音 /
  书源 HTTP」，只在 `speaking` 态拼上去）：语速**只有系统 TTS 后端吃**，edge / HTTP
  原样忽略，而服务自己会回退（system→edge→http），界面只能问它。不显示后端名，用户
  就是对着一个不吃这参数的后端调语速——"调了没反应"这种静默退化最难查，所以把限制

## 第十轮：目录打开时定位到在读那一章（同日）

遗留 6 的尾巴：第八轮恢复了分批渲染，代价是"打开长目录停在顶部"——读到第 2000 章的
人得自己一路滚过去找自己在读哪。旧实现一次建完 2000 行反而"看得见"，这次要的是
**两边都要**：既不一次建完，也要一进来就在当前章那行。

### 1. 设计：只认 url，行号现算，补一批让一次循环

- `ReaderController.open_directory()`（`app/controllers/reader_controller.py:516`）
  取代原来那个只调 `show_directory(True)` 的裸 lambda：先把目录翻出来，再把**屏幕上
  那一章**的 url 交给视图。分工是刻意的——`_chapter_index` 只有控制器知道，
  而**行号**在过滤/倒序之后会挪，所以跨界的必须是 url（`focus_chapter(url)`）。
  工具栏「目录」按钮和键盘 `F` 都走这一个入口（测试专门让两条走**不同**的章，
  免得"两条都断言同一章"什么都证明不了）。
- `ReaderView.focus_chapter()`（`app/views/reading/reader_view.py:354`）：
  先把 `_directory_current_url` 记下并**重挂**当前已挂出的那一批（高亮挂在行上，
  只存标志不重挂 = 已挂出的那批永远标不出来），再 `_locate_chapter()`。
- `_locate_chapter()` 是这轮的难点：目标行往往还没建。做法是`while 还没建到目标位
  → 补一批 → update() 下发 → await asyncio.sleep(0) 让出循环`。一口气补到第 2000 行
  就是"点开目录卡住"，正是分批要避免的那件事；让出循环之后 UI 每 50 行有一拍可呼吸，
  2000 章的跳转实测不冻结窗口。下发失败（切了页、控件脱离 page）就**当场收手**。

### 2. 探针：三轮，把"能滚"这件事问清楚

这条改动 100% 落在"Flutter 到底怎么渲染"上，单测只能断言参数，不能断言视口真动了
（遗留 7 攒的就是这一笔：第三轮起所有滚动都只有协议层证据，目录这一半第十轮补齐，
内嵌音频那一半仍然只能停在"播放器收到了 media"）。按 `flet-web-probe-ui-verification`
的套路跑了三轮 `WEB_BROWSER` + Playwright 无头 Chromium（`no_cdn` 完全离线，
假目录 1001 行，`.probe/` 用完即删）：

1. **`ListView.scroll_to(scroll_key=...)` 是静默空操作**：服务端返回 OK，客户端
   `pixels` 一动不动。这条推翻了"给每行一个 `scroll_key`、定位时按 key 滚"的原设计
   （`ft.Column` 上 key 是管用的，ListView 不管——分批的 ListView 正是本场景）。
2. **`ListView.item_extent` 客户端不认**（加了等于没加，`on_scroll` 的
   `max_scroll_extent` 仍按实际内容算）。所以"每行高度我知道"这件事只能自己钉死。
3. **`scroll_to(offset=...)` 管用，且不被"行还没建"限制**；`ft.ListTile(height=44)`
   **被尊重**（dense 的自然高度是 40），于是行周期 = 行高 + `ListView.spacing`
   = 44 + 2 = **46**，`第 n 行的 offset = n × 46` 才成立。
   → 结论：`_chapter_row()` 里普通章和卷标题都钉 `height=DIRECTORY_ROW_HEIGHT`，
   章名单行 + `ELLIPSIS`。**让某一行因为章名太长自己撑高，它下面所有行的落点就全偏了**
   （这条是本轮最脆的隐式契约，写进了 `_chapter_row` 的 docstring）。
   实测：滚到第 600 章 → 客户端 `pixels == 600 × 46 = 27600`，截图上第 600 章在顶、
   状态行「已加载 800/1001 章」。
- 两处**探针自己的错**（不是产品 bug，记下来免得下次重踩）：
  ① `WEB_BROWSER` 会顺带拉起用户默认浏览器的那个标签页，它会占住第一个会话并把
  invoke 监听吃掉，表现为一串 `Timeout waiting for invoke method listener`——
  用 `import flet.app as _a; _a.open_in_browser = lambda url: None` 压掉自动开浏览器，
  并在每个会话上 `await page.wait_until_visible()`；
  ② 把 ListView 包在 `Row`/`Container` 里时 `on_scroll` 一次都不回（`pixels=None`），
  量不到东西；改成 `page.add(list_view)` 平铺才有事件。

## 第十一轮：导入的一条源被审了两遍（同日）

遗留 3 的最后一条：`await` 竞态守卫第八轮清完之后，同形状欠账只剩"导入的双重审计"。
这轮把它收掉，顺手把 §3.7 触发点① 的归属在代码里写死。

### 1. 现场：两条链都认为自己负责"导入即审"

- `OnlineImportService._dispatch` 先把 JSON 拆成 dict 列表，逐条
  `CompatAuditService.audit_source`，把缺口汇总成 `ImportResult.warnings`
  （界面红字/黄字要看这一份）；紧接着把**同一份文本**交给
  `SourceService.import_sources_json` 落库——而后者内部**又**逐条
  `await self._audit(item)`，且**返回值整个丢掉**，只有抛异常时才记一条 error。
- 代价不只是几百条源文件白烧一倍 CPU（每次审计都在 `asyncio.to_thread` 里跑，
  含 quickjs 预编译 JS 块）。真正的脏处在 `audit_log`：`audit_source` 每调一次
  **落一行**（干净源也落），于是一次导入每个源两行时间戳几乎相同的记录，
  `list_logs` 回溯"这个源什么时候被审出什么缺口"直接失真——这表就是为审计历史建的。
- 为什么不能简单把 `source_service.py:464`（`if audit:` 一段，464-466；09-27 复核定位）那遍删掉：`import_sources_json` 有
  **三个**调用方，只有一个是门面。`qr_code_controller`（扫码导入）和
  `web_dav_service._apply_members`（云端恢复）是绕过门面直接落库的，那遍审计

## 第十二轮：「从云端恢复」点一下就没了整张表（同日）

### 1. 现场

第六轮记的 遗留 9：备份页点「从云端恢复」，服务侧只校验备份包完整性，校验一过就直接
`import_sources_json(...)`——**整张书源表 + 书架 + 设置被覆盖，没有第二次确认，也没有
任何退路**。结果行里唯一的线索是那个远端路径，而点的人根本看不见包里装的是什么
（旧机器的？上个月传错的？）。导入的「整表替换」尚且有确认框，这条更狠却在裸奔。

### 2. 设计

- **闸放在服务侧，不在界面侧。** `restore(url, token="", confirm=False)` 的默认值是
  保守的那一个：未确认时在**解析客户端之前**就返回，PROPFIND / GET 一个都不发。
  理由：绕过界面的调用方（脚本、网络桥、仪表盘按钮）也得被挡住，界面只负责"问一句"。
  要真跑必须显式 `confirm=True`。
- **界面侧问什么**：模态 `AlertDialog` 列出包名、`self._existing_count()` 条会被覆盖的
  本地书源、"恢复前会自动留一份现状但只保这一次"、以及红色的「此操作不可撤销」。
- **拿不到 page 就拒绝执行**（"界面尚未就绪，本次恢复没有执行"），绝不降级成
  "问不了那就不问了、直接恢复"——那等于把闸的口开在异常分支上。
- **在途守卫**：连点两下「确认恢复」是两次整表覆盖，而第二次的"恢复前留底"抄的是
  第一次**恢复完**的样子，真正的旧数据已经没了。所以第二次直接拒
  （"上一次恢复还在进行，请等它结束"），`_after_restore` 无条件把标志落回。
- **留底只抄包里有的那几样**：`_snapshot_local(set(members))` 与 `_collect_members()`
  的交集。只恢复书源时不为书架留一份空跑的现状。落在
  `<数据根>/restore-safety/<时间戳>/`（**不放 cache**，缓存会被清），同一秒内两次恢复
  用 `_1` / `_2` 后缀避让，不盖掉前一份。
- **保险丝不是关卡**：取现状失败、写盘失败、数据根不可用，一律 warning + 返回 `""`
  继续恢复。留底不能反过来变成"用户点了恢复却什么都没发生"的第三个理由。
  留底路径随 `BackupResult.snapshot` 带回，并拼进结果行。

### 3. 验证

- 服务侧 4 条（`test_tools_backup_export_update_m5.py`）：
  `test_restore_without_confirm_never_downloads`（假客户端记账 + 断言闸门自己的措辞）、

  在途期间第二次确认被拒（`service.delay` + `wait_until` 等标志落回）、

  `test_picking_a_remote_fills_the_restore_path`（选中远端文件现在不再直接恢复）。
- **变异核验，第一条抓出一处假绿**：
  ① 把 `if not confirm:` 短路成 `if False and not confirm:` —— 护栏**第一次照样绿**。
  假客户端 `download` 抛的 `AssertionError` 被服务的 `except` 吞成
  "下载备份包失败: 未确认的恢复不该下载备份包"，于是 `ok=False` 与

## 第十三轮：书源登录——按钮变成了输入框（同日）

### 1. 现场

第十二轮之后跑了一遍"服务方法生产侧零调用方"扫描（`app/services/**` 的公开方法逐个
`grep`），挑出 `LegadoReadingEngine.execute_login_action` **没人调用**。引擎面是好的
（`tests/test_legado_compat.py` 有对 Legado 的 LoginUi 对拍），断的是界面分流。对照
`base_history/legado-3.23.110211/app/src/main/java/io/legado/app/ui/login/`
（`SourceLoginActivity.initView` + `SourceLoginDialog.kt`）读出三处：

1. **`type:"button"` 的行被渲染成输入框**。控制器 `set_fields([...])` 只映射
   `key/label/hint/password` 四个键，于是 `{name:"登 录",type:"button",action:"Login()"}`
   在屏幕上是一个**标着"登 录"的空文本框**，它的 `action` 整行丢弃。靠按钮登录的源
   （扫码 / 过验证码 / 免密跳转）在桌面上永远登不进去。
2. **已存登录值不回填**。引擎 `login_schema` 已经把 `source.getLoginInfoMap()` 的值
   放进 `item["value"]`（Legado 同样 `editText.setText(loginInfo[name])`），控制器不读
   这个键 → 每次打开全空、密码每次重打。
3. **网页登录型源被送进了表单这条路，点「登录」= 删掉自己的登录信息**。
   `loginUi` 为空、`loginUrl` 是网页的源，Legado 的第一分支是开
   `WebViewLoginFragment`；桌面端却弹出一张**没有任何输入框**的框，「登录」按钮
   → `submit_login(source, {})` → 引擎执行 `source.removeLoginInfo()`。
   引擎这条语义本身是**照抄 Legado 的**（它的 `login()` 里
   `loginData.isEmpty() → removeLoginInfo()`），错的是界面把"无表单可填"的源送到了这条
   路上——破坏性动作成了一次误点的副作用。

### 2. 归属与裁决

- **三形态分流放在控制器**（视图保持哑，`LoginDialog` 不 import services）：
  ① 有行 → 表单（输入框回填 `value`，带 `action` 的行渲染**按钮**并绑 `on_action`，
  点它只执行该 action、把当前字段值带进 `result`，不提交整张表单）；
  ② 无行但有 `login_target` → `show_web_login(地址)`：**提交按钮不出现**，
  只给「关闭」和一个红色的、显式的「清除已存登录信息」；
  ③ 两者皆无 → `run_login_action(source)` 直接把源的登录脚本跑一遍，结果写状态行、不弹框。
- **服务侧补两个转发**：`RuleEngineService.login_target(source)`（同步纯函数，不建引擎池，
  界面用它决定铺表单还是报地址）与 `run_login_action(source, action, values)`
  （转 `execute_login_action`）。缺前者时控制器只能猜，缺后者时 ① 的按钮和 ③ 无路可走。
- **为什么 ② 只报地址**：`webview_fetcher` 对登录页只是无头抓一次 HTML，登录态不会回到
  该源引擎的 cookie 罐；JS 桥的 `browser_starter` 钩子在全项目**无人赋值**（同轮扫描出来
  的另一条孤儿）。要做成 Legado 那种"就地登录"得先把内置浏览器会话的 cookie 回流给引擎，
  那是服务侧缺口，新记一条遗留，不在这里假装能用。

    得给表加一列（schema v5）并把 `opts["voice"]` 接上（两个后端都已经读这个键，只差
    界面与表）。Legado 侧同样是一档一引擎，所以先按现状记着，不动 schema。
12. 第十三轮新记：**网页登录型书源还不能"就地登录"**。这类源（`loginUi` 空、
    `loginUrl` 是网页）现在只报出地址，要用户自己去「工具 → 内置浏览器」打开登录。
    缺的不是页面而是**Cookie 回流**：`webview_fetcher` 对登录页只是无头抓一次 HTML，
    登录态回不到该源引擎的 cookie 罐；JS 桥的 `browser_starter` 钩子在全项目**无人赋值**
    （同批孤儿扫描还挑出 `register_interaction_callback` / `open_interactive` 只在测试里
    调用）。要做成 Legado `WebViewLoginFragment` 那种形态，得先把浏览器会话的 cookie
    写回源引擎，再谈把登录页嵌进对话框。
